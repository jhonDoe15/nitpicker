# Nitpicker checks catalog

Every check category in the TypeScript preset, derived from `languages/typescript/preset/quality-checks.mjs`
and the adapters in `languages/typescript/adapters/`. Findings follow
[`findings.schema.json`](findings.schema.json). The `javascript` preset runs the same checks on `.js`, `.mjs`
and `.cjs` files (and on `.ts`, `.mts` and `.cts` files while a project migrates), so this catalog applies to
it unchanged.

How classification works:

- **enforceable**: a finding with `classification: "enforceable"` that is new relative to the base
  snapshot fails the gate (`newEnforceableFindings > 0`).
- **report-only**: `classification: "descriptive"`. Shown in the report (metric changes appear in
  `changedMetrics`) but never fails the gate. Only descriptive findings may carry a `metric`.
- `tool-error`: an analyzer that could not run. Not a check category; it sets
  `overallStatus: "tool-error"`.

Thresholds are the defaults in the preset. Where a value is not a hard-coded limit it says so.
The limits of the custom rules and the languages that enforce them come from
`shared/policy.mjs`; the [Custom rules](#custom-rules) table is generated from it
(`npm run gen:checks`) and a test fails when it is stale.

## ESLint checks

Each runs ESLint with a different config. Every ESLint message becomes an **enforceable** finding
(`rule` is the ESLint rule id). No numeric threshold: any new message fails.

A message is identified by its rule, message and the syntax it points at. A message on a whole
function is identified by the function's signature, not its body. A message inside a named
function whose code was edited keeps matching the base while the function has no more messages of
that rule and kind than on the base (a count ratchet), also on an edited line (an added line paired
with a removed line it resembles, such as `return text.slice(0, 4096)` becoming
`return trimmed.slice(0, 4096)`). A message on a line the change added that resembles no removed
line is new, and so is a message of a strict rule on a touched line outside a named function. Rules that report a
number about a function (`nitpicker/cognitive-complexity`, `complexity`, `max-lines-per-function`,
`max-statements`, `max-params`, `max-depth`) fail an edited function only when that number rises.

| Check                   | Scope                              | Config                                                                         | Status      |
| ----------------------- | ---------------------------------- | ------------------------------------------------------------------------------ | ----------- |
| `eslint-lint`           | source and test globs              | `languages/typescript/preset/defaults/eslint.config.mjs`                       | enforceable |
| `eslint-errors`         | production source (tests excluded) | `languages/typescript/preset/eslint-config/policies/errors.config.mjs`         | enforceable |
| `eslint-logging`        | production source (tests excluded) | `languages/typescript/preset/eslint-config/policies/logging.config.mjs`        | enforceable |
| `eslint-module-effects` | production source (tests excluded) | `languages/typescript/preset/eslint-config/policies/module-effects.config.mjs` | enforceable |

Bounded fan-out: `nitpicker/unbounded-fan-out` (production source, in `eslint-lint`) reports
`Promise.all`, `allSettled`, `any` and `race` over a runtime collection whose element work reaches a
remote or message call with no limiter created outside the worker and no fixed-size chunk. The same
rule runs as `unbounded-fan-out` in the Python preset, `pmd/UnboundedFanOut` in the Java preset and
`kotlin-source/UnboundedFanOut` in the Kotlin preset; each preset's document lists what it recognizes.
Database calls per element are left to the per-item I/O rules, which also keep a bounded or
awaited per-item remote call; a call the fan-out rule reports is not reported twice. A worker pool
started once per slot of a count is bounded, while a count read from a collection's size is not.

## Custom rules

Generated from `shared/policy.mjs`. "enforced" means the language's adapter produces the
rule and it fails the gate; "not enforced" means the check does not exist for that language yet;
"report-only" means the adapter produces the rule when the project opts in and it never fails the gate.

The function limits, the file limits and the CRAP score limit ratchet: editing a function that was
already over a limit on the base fails only when the change raises that metric (lines, statements,
nesting, parameters, or the CRAP score). In the same way a file over its line limit fails only when
it grows, a folder over its file limit only when it gains a file (a moved folder is matched to its
old path), and an edited long line only when it gets longer than the long line it replaced; a long
line with no edited line to stand in for fails. A function the change pushes over a limit, and a new function over
a limit, fail as usual. The failure of a function that got worse names the base value ("grew from 68
to 72 lines"); a touched function that did not get worse is listed in the report as "Touched, still
over limit" and does not fail.

## Timeouts that abandon work

One rule, `timeout-abandons-operation`, in every language that has a timeout construct which stops
waiting without stopping the work.

| Language   | Rule id                                   | Implementation                                                                         | Status      |
| ---------- | ----------------------------------------- | -------------------------------------------------------------------------------------- | ----------- |
| TypeScript | `nitpicker/timeout-abandons-operation`    | `languages/typescript/preset/eslint-plugin/rules/async/timeout-abandons-operation.mjs` | enforceable |
| JavaScript | `nitpicker/timeout-abandons-operation`    | the same ESLint rule                                                                   | enforceable |
| Python     | `python-rules/timeout-abandons-operation` | `languages/python/rules/waits/timeouts.py`                                             | enforceable |
| Java       | `pmd/timeout-abandons-operation`          | `languages/java/gradle/pmd-main-ruleset.xml` (XPath, Gradle and Maven)                 | enforceable |
| Kotlin     | `pmd/timeout-abandons-operation`          | `languages/java/adapters/kotlin/review-rules/main/timeouts/timeouts.mjs`               | enforceable |

TypeScript and JavaScript: `Promise.race` of an operation and a timer that rejects, where the
operation gets no `AbortSignal`, cancelling owner or cleanup in the timeout path (HTTP clients that
`require-http-timeout` recognizes are left to it; a resolving sleep is a hedge, not a timeout).
Python: `asyncio.wait(..., timeout=...)` or `return_when=FIRST_COMPLETED` whose pending tasks are not
cancelled, awaited or handed on (directly or through the awaited collection), and
`asyncio.wait_for(asyncio.shield(task), ...)` with nothing cancelling or awaiting the task afterwards;
`asyncio.wait_for`, `asyncio.timeout`, task groups and Trio and AnyIO scopes cancel and are allowed.
Java: `Future.get(timeout, unit)` whose `TimeoutException` handler neither rethrows nor hands the
future on while the method never calls `cancel(true)` on it, `shutdownNow()` on its executor or
`interrupt()` on its thread (`shutdown()` and `cancel(false)` let it finish), and `get`, `orTimeout`
or `completeOnTimeout` on a `CompletableFuture` that `supplyAsync` or `runAsync` started, which no
cancel interrupts (two PMD rules, one per message, printed under the one id). Kotlin: the same forms,
plus `withTimeout { deferred.await() }` (or `awaitAll`) on a `Deferred` another scope started that the
timeout path does not cancel. The precision limits are in
[TypeScript](../docs/typescript-strict-preset.md), [Python](../docs/python-preset.md),
[Java](../docs/java-preset.md) and [Kotlin](../docs/kotlin-preset.md).
