# Nitpicker checks catalog

Every check category in the TypeScript preset, derived from `languages/typescript/preset/quality-checks.mjs`
and the adapters in `languages/typescript/adapters/`. Findings follow
[`findings.schema.json`](findings.schema.json). The `javascript` preset runs the same checks on `.js`, `.mjs`
and `.cjs` files (and on `.ts`, `.mts` and `.cts` files while a project migrates), so this catalog applies to
it unchanged.

How classification works:

- **enforceable**: a finding with `classification: "enforceable"` that is new relative to the base
  snapshot fails the gate (`newEnforceableFindings > 0`).
- **report-only**: `classification: "descriptive"`. Shown in the report (metric changes appear in
  `changedMetrics`) but never fails the gate. Only descriptive findings may carry a `metric`.
- `tool-error`: an analyzer that could not run. Not a check category; it sets
  `overallStatus: "tool-error"`.

Thresholds are the defaults in the preset. Where a value is not a hard-coded limit it says so.
The limits of the custom rules and the languages that enforce them come from
`shared/policy.mjs`; the [Custom rules](#custom-rules) table is generated from it
(`npm run gen:checks`) and a test fails when it is stale.

## ESLint checks

Each runs ESLint with a different config. Every ESLint message becomes an **enforceable** finding
(`rule` is the ESLint rule id). No numeric threshold: any new message fails.

A message is identified by its rule, message and the syntax it points at. A message on a whole
function is identified by the function's signature, not its body. A message inside a named
function whose code was edited keeps matching the base while the function has no more messages of
that rule and kind than on the base (a count ratchet), also on an edited line (an added line paired
with a removed line it resembles, such as `return text.slice(0, 4096)` becoming
`return trimmed.slice(0, 4096)`). A message on a line the change added that resembles no removed
line is new, and so is a message of a strict rule on a touched line outside a named function. Rules that report a
number about a function (`nitpicker/cognitive-complexity`, `complexity`, `max-lines-per-function`,
`max-statements`, `max-params`, `max-depth`) fail an edited function only when that number rises.

| Check                   | Scope                              | Config                                                                         | Status      |
| ----------------------- | ---------------------------------- | ------------------------------------------------------------------------------ | ----------- |
| `eslint-lint`           | source and test globs              | `languages/typescript/preset/defaults/eslint.config.mjs`                       | enforceable |
| `eslint-errors`         | production source (tests excluded) | `languages/typescript/preset/eslint-config/policies/errors.config.mjs`         | enforceable |
| `eslint-logging`        | production source (tests excluded) | `languages/typescript/preset/eslint-config/policies/logging.config.mjs`        | enforceable |
| `eslint-module-effects` | production source (tests excluded) | `languages/typescript/preset/eslint-config/policies/module-effects.config.mjs` | enforceable |

## Updates across a suspension

A statement reads shared state, suspends, then writes a value derived from the stale read, so
concurrent calls overwrite each other's updates. Each async preset checks it with a rule of its own
analyzer, so the rule id differs per preset and the rule is not part of the generated
[Custom rules](#custom-rules) table, which lists rules nitpicker emits under one id in several
presets. Every finding is enforceable and names a reviewed `exceptions` entry for state that is
already serialized.

| Preset                    | Rule                                      | Implementation                                                                                    |
| ------------------------- | ----------------------------------------- | ------------------------------------------------------------------------------------------------- |
| TypeScript and JavaScript | `nitpicker/require-atomic-updates`        | ESLint's `require-atomic-updates` (`allowProperties: false`), reports narrowed, in `eslint-lint`  |
| Python                    | `python-rules/atomic-update-across-await` | `languages/python/rules/concurrency/atomic_updates.py`                                            |
| Kotlin                    | `pmd/NonAtomicUpdateAcrossSuspension`     | `review-rules/main/suspension/suspended-updates.mjs` over the `kotlin-psi` facts                  |
| Java                      | not covered by this rule                  | nothing suspends inside a Java expression; see `errorprone/NonAtomicVolatileUpdate` in the preset |

What each recognizes:

| Preset                    | `this` / `self` state       | Saved local                                     | Lock recognized                         | Semaphore or limiter recognized               |
| ------------------------- | --------------------------- | ----------------------------------------------- | --------------------------------------- | --------------------------------------------- |
| TypeScript and JavaScript | no (`this` is not followed) | yes                                             | no: a reviewed exception                | no                                            |
| Python                    | yes (`self`, `cls`)         | yes, through derived locals, branches and loops | yes, when built once outside the method | only with one slot, stated as the literal `1` |
| Kotlin                    | yes (bare and `this.`)      | yes, within one function or lambda              | `withLock`, unless the mutex is a local | `withPermit` on a `val` `Semaphore(1)`        |

A lazy initialization written as an operator (`cached ??= await load()`) is reported in TypeScript and
JavaScript; Python and Kotlin have no such operator, and the checked form
(`if cached is None: cached = await load()`) passes in every preset. See
[TypeScript](../docs/typescript-strict-preset.md), [Python](../docs/python-preset.md),
[Kotlin](../docs/kotlin-preset.md#review-rules) and [Java](../docs/java-preset.md#error-prone-and-nullaway)
for what each leaves alone.

## Lock discipline

Two rules check how a class takes its locks. A lock-order inversion is two locks of one class taken
in opposite orders, so two threads that run both nestings can each hold one lock and wait forever for
the other. Inconsistent locking is a field written while a lock is held in one place and with no lock
in another, so the unlocked write races with the locked one. Every finding is enforceable, names both
places, is keyed by the class, the method and the lock pair or the field (no line number) and names a reviewed
`exceptions` entry.

| Preset                    | Lock order                          | Field written with and without a lock         | Implementation                                                                                 |
| ------------------------- | ----------------------------------- | --------------------------------------------- | ---------------------------------------------------------------------------------------------- |
| Java                      | `pmd/LockOrderInversion`            | `pmd/InconsistentFieldLocking`                | XPath rules in `pmd-ruleset.xml`; `messages/locking/lock-evidence.mjs` names both places       |
| Kotlin                    | `pmd/LockOrderInversion`            | `pmd/InconsistentFieldLocking`                | `review-rules/main/locking/` over the `kotlin-psi` locking facts                               |
| Python                    | `python-rules/lock-order-inversion` | `python-rules/inconsistent-attribute-locking` | `languages/python/rules/locking/`                                                              |
| TypeScript and JavaScript | not applicable                      | not applicable                                | one thread runs the code between two `await`s; there is no lock to hold or to take in an order |

What each recognizes:

| Preset | Locks                                                                                                                                    | Not followed                                                                                        |
| ------ | ---------------------------------------------------------------------------------------------------------------------------------------- | --------------------------------------------------------------------------------------------------- |
| Java   | `synchronized` blocks and methods, `lock()` and `lockInterruptibly()` up to `unlock()`, on a field, `this`, `Type.class` or `Type.FIELD` | a lock passed in, held in a local, taken in a called method, or taken with `tryLock`                |
| Kotlin | `synchronized(x) { }`, `@Synchronized`, `withLock` of `ReentrantLock` and `Mutex`, also under an import alias                            | a lock passed in or held in a local, a lambda that may run later, a lock taken in a called function |
| Python | `with` and `async with` on `threading` and `asyncio` locks, `RLock`, `Condition` and a one-slot semaphore built once                     | a lock passed in, an object the analysis cannot identify, a nested function that may run later      |

A write the analysis cannot place (in a constructor or initializer, in a lambda or nested function,
in a method the class calls while it holds a lock, under a `with` it cannot identify; in Python
also in a decorated method or one that calls `acquire()`) is never reported as unlocked. A lock taken
again while the thread already holds it (a reentrant re-acquire) is not an inversion. Java and Kotlin also skip a single write of a `volatile` field and fields of an
atomic or concurrent type.

Bounded fan-out: `nitpicker/unbounded-fan-out` (production source, in `eslint-lint`) reports
`Promise.all`, `allSettled`, `any` and `race` over a runtime collection whose element work reaches a
remote or message call with no limiter created outside the worker and no fixed-size chunk. The same
rule runs as `unbounded-fan-out` in the Python preset, `pmd/UnboundedFanOut` in the Java preset and
`kotlin-source/UnboundedFanOut` in the Kotlin preset; each preset's document lists what it recognizes.
Reactive fan-out has its own rule: `nitpicker/unbounded-reactive-fan-out` (RxJS `mergeMap` without a
concurrency argument over a collection, `forkJoin` and friends over a mapped array),
`pmd/UnboundedReactiveFanOut` and `kotlin-source/UnboundedReactiveFanOut` (Reactor `flatMap` without
a concurrency argument over `Flux.fromIterable`, `Mono.zip`/`Mono.when`/`Flux.zip`/`Flux.merge` over a
list built per element, and Kotlin `flatMapMerge(Int.MAX_VALUE)`). The Python preset has no reactive
rule: RxPY is rare in services, and `asyncio.gather` and task groups are covered by
`unbounded-fan-out`. The Go preset has no fan-out rule yet.
Database calls per element are left to the per-item I/O rules (`io-in-loop` in the Python preset and
`go-rules/io-in-loop` in the Go preset; the other presets' own rules are named in their documents), which also keep a bounded or
awaited per-item remote call; a call the fan-out rule reports is not reported twice. A worker pool
started once per slot of a count is bounded, while a count read from a collection's size is not.

Unbounded thread pools: `pmd/UnboundedThreadPool` in the Java and Kotlin presets reports
`Executors.newCachedThreadPool()` and a `ThreadPoolExecutor` without a maximum size in main
sources. In a Spring project, `pmd/SpringUnreleasedResource` reports a bean field that holds an
executor, event loop, client or other resource the bean built and never releases at shutdown, and
`pmd/SpringStartupCleanup` reports a startup call that can fail after the bean started threads,
outside a `try` that releases them. The TypeScript, JavaScript and Python presets have no
counterpart yet; their thread and timer model differs and the NestJS provider case is tracked
separately.

Objects built on every call: `pmd/ReusableObjectPerCall` in the Java and Kotlin presets,
`nitpicker/reusable-object-per-call` in the TypeScript and JavaScript presets and
`reusable-object-per-call` in the Python preset report an object that is safe to share once built
and costly to build (Jackson mappers, Gson, `JAXBContext`, validator factories, constant-pattern
formatters, `Intl` formatters, Ajv, pydantic `TypeAdapter`, jinja2 `Environment`) made in a
function that runs on every call, in production code. The Go preset has no rule engine of its own
yet.

Child process deadlines: `nitpicker/require-process-timeout` (production source, in `eslint-lint`)
reports production code that waits for a child process to exit without a deadline: a synchronous
`child_process` or `execa` call without a positive `timeout`, and `exec`, `execFile`, an awaited
`execa` or a `spawn` or `fork` whose end is awaited without a `timeout` or an abort `signal`. The
same rule runs as `subprocess-without-timeout` in the Python preset, `pmd/ProcessWaitWithoutTimeout`
in the Java preset and `kotlin-source/ProcessWaitWithoutTimeout` in the Kotlin preset; tests keep
`nitpicker/require-test-process-timeout` (TypeScript) or their runner's own limits.

Time units: `nitpicker/time-unit-mismatch` (production source, in `eslint-lint`) reports time values in
two different units that meet without a conversion: a `+`, `-` or comparison of seconds with milliseconds
(or nanoseconds, microseconds, minutes), a value assigned or passed under a name or parameter of another
unit, and an epoch time cut to 32 bits. Units come from known clock and conversion APIs and from name
suffixes such as `Ms`, `Millis`, `Seconds` and `_seconds`; ratio names (`MS_PER_SECOND`) and flags
(`showSeconds`, `use_ms`) carry no unit, a `format...` call takes its unit rather than returning it,
JWT claims (`exp`, `iat`) count as epoch seconds only on a token, claims or payload object, and an epoch
name needs a unit (`expiresAtEpochSecond`, not `epoch`). The same rule runs as `time-unit-mismatch` in
the Python preset, `pmd/MixedTimeUnits` and `pmd/EpochNarrowedToInt` in the Java preset (Gradle and
Maven; the overlap keeps `pmd/MixedTimeUnits` over Error Prone's `TimeUnitMismatch`) and
`kotlin-source/TimeUnitMismatch` in the Kotlin preset. The Go preset has no own rule engine yet.

Costly collection forms: `nitpicker/no-costly-collection-form` (production source, in `eslint-lint`)
reports three forms with a cheaper equivalent: an array that is appended to and searched with
`includes`, `indexOf` or an identity `some` inside a loop, callback or recursive function (a `Set`); a
`find`, `findIndex` or `some` by one property of the item, in a loop, iteration callback or listener,
over a binding that does not change (a `Map` built once); and a sort that keeps only its first or last
element (one pass). The same forms run as `list-used-as-set`, `linear-lookup-in-loop` and ruff
`FURB192` in the Python preset, `pmd/ListUsedAsSet`, `pmd/LinearLookupInLoop` and `pmd/SortForExtreme`
in the Java preset (main sources, Gradle and Maven) and `kotlin-source/` rules of the same names in the
Kotlin preset. The other presets read `contains` or `in` only, and the Java and Kotlin rules read
loops and iterating lambdas, not recursion or listeners. The Go preset has no counterpart yet.

Streamed rows collected: `nitpicker/no-collected-stream-rows` (production source, in `eslint-lint`)
reports every item of a `for await` loop over a stream, async generator or cursor pushed into one array
that is read only after the loop, so the whole input sits in memory (a batch flushed inside the loop).
The same form runs as `streamed-rows-collected` in the Python preset (`.iterator()`, `yield_per`,
`stream_results=True`, a named or server-side cursor) and as `pmd/StreamedRowsCollected` in the Java
preset (a `Stream` from a Spring Data repository, `getResultStream()`, `queryForStream` or a Hibernate
`stream()`, collected with `toList()`, `collect` or `forEach(list::add)`) and the Kotlin preset (a
`Stream` returned by a repository function, collected in the same chain). A `limit`, an early `break` or
`return`, and a Kotlin `Stream` collected inside `use { }` are left alone. A Kotlin `Flow` is not read:
it is the default return type of a coroutine repository, so `toList()` on it is the usual read of a
small result. The Go preset has no own rule engine yet.

HTTP deadlines: `nitpicker/require-http-timeout` (strict preset, production source) reports an outbound
HTTP call that has no timeout, so a server that accepts the connection and never answers hangs it. The same
rule runs as `http-without-timeout` in the Python preset, `pmd/HttpWithoutTimeout` in the Java preset (main
sources, with or without Spring; the clients Spring builds stay with `pmd/SpringHttpClientTimeouts` and
`pmd/SpringHttpClientPerCall`), `kotlin-source/HttpWithoutTimeout` in the Kotlin preset and
`go-rules/http-without-timeout` in the Go preset; each preset's
document lists the clients it knows.

Configuration reads: the process environment and system properties are read once, in the composition root,
and passed in. The TypeScript presets report `process.env` outside it
(`nitpicker/no-process-access-outside-composition-root`), the Python preset `os.environ` and `os.getenv`
(`process-env-access`). The Java preset reports `System.getenv`, `System.getProperty` of an application key,
`Integer.getInteger`, `Long.getLong` and `Boolean.getBoolean` in main sources outside the file with `main`, a
dependency-injection module or factory (Guice, Dagger, CDI, Micronaut, Quarkus) or a Spring configuration class
as `pmd/ConfigurationReadOutsideCompositionRoot`, with or without Spring; in a Spring project
`pmd/SpringTypedConfiguration` keeps the reads both report. The Kotlin preset reports the same reads as
`kotlin-source/ConfigurationReadOutsideCompositionRoot`, except `System.getenv`, which is detekt's
`ForbiddenMethodCall` there, with the same files allowed.

Query order: `nitpicker/no-unordered-query` (strict preset, production source) reports a query that takes a
page of rows (`limit`, `offset`, `take`, `skip`, a cursor, or SQL `LIMIT`, `OFFSET` or `FETCH`) or builds an
`array_agg`/`json_agg` list with no ORDER BY, so which rows come back can change between runs. It reads Kysely,
Knex, TypeORM and Drizzle builder chains, Prisma, TypeORM and Sequelize option objects and SQL text. The same
rule runs as `unordered-query` in the Python preset (SQLAlchemy, Django querysets, SQL text),
`pmd/UnorderedQuery` in the Java preset (JPQL and SQL text, `setMaxResults`/`setFirstResult`, criteria queries,
unsorted `PageRequest`) and `kotlin-source/UnorderedQuery` in the Kotlin preset. The text analysis is shared:
[`shared/rules/queries/sql-order.mjs`](../shared/rules/queries/sql-order.mjs).

Query arrays: `nitpicker/no-unbounded-query-array` reports a runtime array expanded into an SQL in list or a
multi-row insert with no empty check, size check or chunking: an empty array renders `in ()`, and PostgreSQL
takes at most 65,535 bound parameters. One array parameter (`= any($1::uuid[])`) passes. The same rule runs as
`unbounded-query-array` in the Python preset, `pmd/UnboundedQueryArray` in the Java preset and
`kotlin-source/UnboundedQueryArray` in the Kotlin preset. Go has no counterpart: the Go preset runs the Go
toolchain's own checks and has no rule engine of its own.

Exceptions mapped to a status: `nitpicker/no-unmapped-exception` (TypeScript strict preset, type-aware)
reports a NestJS handler that can throw a project exception class no exception filter in scope maps, so
the client gets a 500. The Python preset runs it as `unmapped-exception` for FastAPI and Starlette routes
and their exception handlers, and the Java and Kotlin presets as `archunit/spring-unmapped-exception` for
Spring MVC and WebFlux controllers, `@ExceptionHandler` and `@ResponseStatus`. Each follows calls four
levels deep and skips code inside a `try` that catches. The JavaScript preset has no type information to
follow calls with, Django, Flask and Go handlers are not checked yet.

Recursive map updates have no TypeScript or JavaScript check: `Map` has no method that runs a
callback while it updates an entry, so a callback cannot change the map in the middle of an update.
The same holds for Python's `dict` (`setdefault` takes a value, and a `defaultdict` factory runs
before the entry is stored and takes no key). The Java and Kotlin presets report it as
`pmd/RecursiveMapUpdate`: a change to a map inside the function passed to its `computeIfAbsent`,
`compute`, `computeIfPresent` or `merge` (Kotlin: also `getOrPut` on a `ConcurrentMap`).

## Custom rules

Generated from `shared/policy.mjs`. "enforced" means the language's adapter produces the
rule and it fails the gate; "not enforced" means the check does not exist for that language yet;
"report-only" means the adapter produces the rule when the project opts in and it never fails the gate.

The function limits, the file limits and the CRAP score limit ratchet: editing a function that was
already over a limit on the base fails only when the change raises that metric (lines, statements,
nesting, parameters, or the CRAP score). In the same way a file over its line limit fails only when
it grows, a folder over its file limit only when it gains a file (a moved folder is matched to its
old path), and an edited long line only when it gets longer than the long line it replaced; a long
line with no edited line to stand in for fails. A function the change pushes over a limit, and a new function over
a limit, fail as usual. The failure of a function that got worse names the base value ("grew from 68
to 72 lines"); a touched function that did not get worse is listed in the report as "Touched, still
over limit" and does not fail.

## Timeouts that abandon work

One rule, `timeout-abandons-operation`, in every language that has a timeout construct which stops
waiting without stopping the work.

| Language   | Rule id                                   | Implementation                                                                         | Status      |
| ---------- | ----------------------------------------- | -------------------------------------------------------------------------------------- | ----------- |
| TypeScript | `nitpicker/timeout-abandons-operation`    | `languages/typescript/preset/eslint-plugin/rules/async/timeout-abandons-operation.mjs` | enforceable |
| JavaScript | `nitpicker/timeout-abandons-operation`    | the same ESLint rule                                                                   | enforceable |
| Python     | `python-rules/timeout-abandons-operation` | `languages/python/rules/waits/timeouts.py`                                             | enforceable |
| Java       | `pmd/timeout-abandons-operation`          | `languages/java/gradle/pmd-main-ruleset.xml` (XPath, Gradle and Maven)                 | enforceable |
| Kotlin     | `pmd/timeout-abandons-operation`          | `languages/java/adapters/kotlin/review-rules/main/timeouts/timeouts.mjs`               | enforceable |

TypeScript and JavaScript: `Promise.race` of an operation and a timer that rejects, where the
operation gets no `AbortSignal`, cancelling owner or cleanup in the timeout path (HTTP clients that
`require-http-timeout` recognizes are left to it; a resolving sleep is a hedge, not a timeout).
Python: `asyncio.wait(..., timeout=...)` or `return_when=FIRST_COMPLETED` whose pending tasks are not
cancelled, awaited or handed on (directly or through the awaited collection), and
`asyncio.wait_for(asyncio.shield(task), ...)` with nothing cancelling or awaiting the task afterwards;
`asyncio.wait_for`, `asyncio.timeout`, task groups and Trio and AnyIO scopes cancel and are allowed.
Java: `Future.get(timeout, unit)` whose `TimeoutException` handler neither rethrows nor hands the
future on while the method never calls `cancel(true)` on it, `shutdownNow()` on its executor or
`interrupt()` on its thread (`shutdown()` and `cancel(false)` let it finish), and `get`, `orTimeout`
or `completeOnTimeout` on a `CompletableFuture` that `supplyAsync` or `runAsync` started, which no
cancel interrupts (two PMD rules, one per message, printed under the one id). Kotlin: the same forms,
plus `withTimeout { deferred.await() }` (or `awaitAll`) on a `Deferred` another scope started that the
timeout path does not cancel. The precision limits are in
[TypeScript](../docs/typescript-strict-preset.md), [Python](../docs/python-preset.md),
[Java](../docs/java-preset.md) and [Kotlin](../docs/kotlin-preset.md).
