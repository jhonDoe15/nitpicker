# Nitpicker checks catalog

Every check category in the TypeScript preset, derived from `languages/typescript/preset/quality-checks.mjs`
and the adapters in `languages/typescript/adapters/`. Findings follow
[`findings.schema.json`](findings.schema.json). The `javascript` preset runs the same checks on `.js`, `.mjs`
and `.cjs` files (and on `.ts`, `.mts` and `.cts` files while a project migrates), so this catalog applies to
it unchanged.

How classification works:

- **enforceable**: a finding with `classification: "enforceable"` that is new relative to the base
  snapshot fails the gate (`newEnforceableFindings > 0`).
- **report-only**: `classification: "descriptive"`. Shown in the report (metric changes appear in
  `changedMetrics`) but never fails the gate. Only descriptive findings may carry a `metric`.
- `tool-error`: an analyzer that could not run. Not a check category; it sets
  `overallStatus: "tool-error"`.

Thresholds are the defaults in the preset. Where a value is not a hard-coded limit it says so.
The limits of the custom rules and the languages that enforce them come from
`shared/policy.mjs`; the [Custom rules](#custom-rules) table is generated from it
(`npm run gen:checks`) and a test fails when it is stale.

## ESLint checks

Each runs ESLint with a different config. Every ESLint message becomes an **enforceable** finding
(`rule` is the ESLint rule id). No numeric threshold: any new message fails.

A message is identified by its rule, message and the syntax it points at. A message on a whole
function is identified by the function's signature, not its body. A message inside a named
function whose code was edited keeps matching the base while the function has no more messages of
that rule and kind than on the base (a count ratchet), also on an edited line (an added line paired
with a removed line it resembles, such as `return text.slice(0, 4096)` becoming
`return trimmed.slice(0, 4096)`). A message on a line the change added that resembles no removed
line is new, and so is a message of a strict rule on a touched line outside a named function. Rules that report a
number about a function (`nitpicker/cognitive-complexity`, `complexity`, `max-lines-per-function`,
`max-statements`, `max-params`, `max-depth`) fail an edited function only when that number rises.

| Check                   | Scope                              | Config                                                                         | Status      |
| ----------------------- | ---------------------------------- | ------------------------------------------------------------------------------ | ----------- |
| `eslint-lint`           | source and test globs              | `languages/typescript/preset/defaults/eslint.config.mjs`                       | enforceable |
| `eslint-errors`         | production source (tests excluded) | `languages/typescript/preset/eslint-config/policies/errors.config.mjs`         | enforceable |
| `eslint-logging`        | production source (tests excluded) | `languages/typescript/preset/eslint-config/policies/logging.config.mjs`        | enforceable |
| `eslint-module-effects` | production source (tests excluded) | `languages/typescript/preset/eslint-config/policies/module-effects.config.mjs` | enforceable |

## Updates across a suspension

A statement reads shared state, suspends, then writes a value derived from the stale read, so
concurrent calls overwrite each other's updates. Each async preset checks it with a rule of its own
analyzer, so the rule id differs per preset and the rule is not part of the generated
[Custom rules](#custom-rules) table, which lists rules nitpicker emits under one id in several
presets. Every finding is enforceable and names a reviewed `exceptions` entry for state that is
already serialized.

| Preset                    | Rule                                      | Implementation                                                                                    |
| ------------------------- | ----------------------------------------- | ------------------------------------------------------------------------------------------------- |
| TypeScript and JavaScript | `nitpicker/require-atomic-updates`        | ESLint's `require-atomic-updates` (`allowProperties: false`), reports narrowed, in `eslint-lint`  |
| Python                    | `python-rules/atomic-update-across-await` | `languages/python/rules/concurrency/atomic_updates.py`                                            |
| Kotlin                    | `pmd/NonAtomicUpdateAcrossSuspension`     | `review-rules/main/suspension/suspended-updates.mjs` over the `kotlin-psi` facts                  |
| Java                      | not covered by this rule                  | nothing suspends inside a Java expression; see `errorprone/NonAtomicVolatileUpdate` in the preset |

What each recognizes:

| Preset                    | `this` / `self` state       | Saved local                                     | Lock recognized                         | Semaphore or limiter recognized               |
| ------------------------- | --------------------------- | ----------------------------------------------- | --------------------------------------- | --------------------------------------------- |
| TypeScript and JavaScript | no (`this` is not followed) | yes                                             | no: a reviewed exception                | no                                            |
| Python                    | yes (`self`, `cls`)         | yes, through derived locals, branches and loops | yes, when built once outside the method | only with one slot, stated as the literal `1` |
| Kotlin                    | yes (bare and `this.`)      | yes, within one function or lambda              | `withLock`, unless the mutex is a local | `withPermit` on a `val` `Semaphore(1)`        |

A lazy initialization written as an operator (`cached ??= await load()`) is reported in TypeScript and
JavaScript; Python and Kotlin have no such operator, and the checked form
(`if cached is None: cached = await load()`) passes in every preset. See
[TypeScript](../docs/typescript-strict-preset.md), [Python](../docs/python-preset.md),
[Kotlin](../docs/kotlin-preset.md#review-rules) and [Java](../docs/java-preset.md#error-prone-and-nullaway)
for what each leaves alone.

## Lock discipline

Two rules check how a class takes its locks. A lock-order inversion is two locks of one class taken
in opposite orders, so two threads that run both nestings can each hold one lock and wait forever for
the other. Inconsistent locking is a field written while a lock is held in one place and with no lock
in another, so the unlocked write races with the locked one. Every finding is enforceable, names both
places, is keyed by the class, the method and the lock pair or the field (no line number) and names a reviewed
`exceptions` entry.

| Preset                    | Lock order                          | Field written with and without a lock         | Implementation                                                                                 |
| ------------------------- | ----------------------------------- | --------------------------------------------- | ---------------------------------------------------------------------------------------------- |
| Java                      | `pmd/LockOrderInversion`            | `pmd/InconsistentFieldLocking`                | XPath rules in `pmd-ruleset.xml`; `messages/locking/lock-evidence.mjs` names both places       |
| Kotlin                    | `pmd/LockOrderInversion`            | `pmd/InconsistentFieldLocking`                | `review-rules/main/locking/` over the `kotlin-psi` locking facts                               |
| Python                    | `python-rules/lock-order-inversion` | `python-rules/inconsistent-attribute-locking` | `languages/python/rules/locking/`                                                              |
| TypeScript and JavaScript | not applicable                      | not applicable                                | one thread runs the code between two `await`s; there is no lock to hold or to take in an order |

What each recognizes:

| Preset | Locks                                                                                                                                    | Not followed                                                                                        |
| ------ | ---------------------------------------------------------------------------------------------------------------------------------------- | --------------------------------------------------------------------------------------------------- |
| Java   | `synchronized` blocks and methods, `lock()` and `lockInterruptibly()` up to `unlock()`, on a field, `this`, `Type.class` or `Type.FIELD` | a lock passed in, held in a local, taken in a called method, or taken with `tryLock`                |
| Kotlin | `synchronized(x) { }`, `@Synchronized`, `withLock` of `ReentrantLock` and `Mutex`, also under an import alias                            | a lock passed in or held in a local, a lambda that may run later, a lock taken in a called function |
| Python | `with` and `async with` on `threading` and `asyncio` locks, `RLock`, `Condition` and a one-slot semaphore built once                     | a lock passed in, an object the analysis cannot identify, a nested function that may run later      |

A write the analysis cannot place (in a constructor or initializer, in a lambda or nested function,
in a method the class calls while it holds a lock, under a `with` it cannot identify; in Python
also in a decorated method or one that calls `acquire()`) is never reported as unlocked. A lock taken
again while the thread already holds it (a reentrant re-acquire) is not an inversion. Java and Kotlin also skip a single write of a `volatile` field and fields of an
atomic or concurrent type.

Bounded fan-out: `nitpicker/unbounded-fan-out` (production source, in `eslint-lint`) reports
`Promise.all` and `allSettled` (`any` and `race` are not reported: bounding them changes what they return) over a runtime collection whose element work reaches a
remote or message call with no limiter created outside the worker and no fixed-size chunk. The same
rule runs as `unbounded-fan-out` in the Python preset, `pmd/UnboundedFanOut` in the Java preset and
`kotlin-source/UnboundedFanOut` in the Kotlin preset; each preset's document lists what it recognizes.
Reactive fan-out has its own rule: `nitpicker/unbounded-reactive-fan-out` (RxJS `mergeMap` without a
concurrency argument over a collection, `forkJoin` and `merge` over a mapped array),
`pmd/UnboundedReactiveFanOut` and `kotlin-source/UnboundedReactiveFanOut` (Reactor `flatMap` without
a concurrency argument over `Flux.fromIterable`, `Mono.zip`/`Mono.when`/`Flux.zip`/`Flux.merge` over a
list built per element, and Kotlin `flatMapMerge(Int.MAX_VALUE)`). The Python preset has no reactive
rule: RxPY is rare in services, and `asyncio.gather` and task groups are covered by
`unbounded-fan-out`. The Go preset has no fan-out rule yet.
Database calls per element are left to the per-item I/O rules (`io-in-loop` in the Python preset and
`go-rules/io-in-loop` in the Go preset; the other presets' own rules are named in their documents), which also keep a bounded or
awaited per-item remote call; a call the fan-out rule reports is not reported twice. A worker pool
started once per slot of a count is bounded, while a count read from a collection's size is not.
In the Python preset `io-in-loop` reports a database call per element also inside `asyncio.gather`, task
groups and callables handed to `start_soon`, `to_thread` or `run_in_executor` (one query per item stays one query per item), while a remote call in those concurrent forms belongs to
`unbounded-fan-out` and a remote call in a sequential loop to `io-in-loop`.

Rows changed in memory: `in-memory-update` in the Python preset reports rows loaded from a Django queryset or a
SQLAlchemy query only to set the same values on each and write them back (`bulk_update`, `commit`), where one `update`
statement does it; models with a `save()` override, signals, `before_update` listeners, `auto_now` fields or a version
column are left alone, and a loop of per-row deletes stays with `io-in-loop`.

Rows read for less: `row-for-one-column` and `row-for-existence` in the Python preset report rows that a Django or
SQLAlchemy query loads whole only to read one known column (`[u.email for u in User.objects.filter(...)]`) or only to test
for existence (`.count() > 0`, `.first() is not None`); `values_list`, `select(User.email)` and `.exists()` are the
allowed forms, and relationships, properties and already narrowed queries stay quiet.

Stale retries: `stale-retry` in the Python preset reports a SQLAlchemy `commit()` or `flush()` that a retry loop, a
`tenacity` or `backoff` decorator or a `Retrying` loop runs again after `StaleDataError` without reading the row again
(`session.get`, `refresh`, a query); the row is read by id inside each attempt.

Python effect rules: `accumulator-copy` (a name rebuilt from a copy of itself in a loop or `functools.reduce`),
`lazy-relation-in-loop` (a Django or SQLAlchemy relationship read once per row of a query that does not fetch it),
`resolver-query-per-parent` (a Strawberry or Graphene field resolver of a type returned as a list that queries per parent; a `DataLoader` is the allowed form),
`cache-write-in-transaction` (a Django or Redis cache write, or a dict filled with a row written in the block, inside
`transaction.atomic()` or `session.begin()`; `transaction.on_commit` is the allowed form),
`remote-call-in-transaction` and `remote-call-under-lock` (a remote call while a database transaction or a lock is
held; a fill-once block under a lock stays allowed), `retry-without-idempotency` (a payment create, message
publish or `INSERT` without a stable key inside a retry scope) and `dual-write-without-outbox` (a database write
and a message publish in one function, without an outbox). They live in
`languages/python/rules/{accumulators,orm,transactions,retries,dual_write}/` and read the effect kinds of
`languages/python/rules/kinds/`; the [Python preset](../docs/python-preset.md) lists what each recognizes.

Python related-write rules: `related-writes-without-transaction` (two writes to different models, or two writes
committed separately, with no `transaction.atomic()` or `session.begin()` around them), `write-outside-transaction`
(a write inside a transaction block through a session or database alias that is not the block's) and
`check-then-write-race` (a read of a model that decides a create of the same model, without a lock, an atomic form
or a transaction). They live in `languages/python/rules/related_writes/`.

Python job rule: `job-item-failure-stops-run` (a loop in a Celery task, an APScheduler job or a Django management
command that does database or remote I/O per item with no `try` around one item, so the first failing item
stops the rest). It lives in `languages/python/rules/jobs/`.

Python soft-delete rule: `soft-delete-filter-missing` (a Django or SQLAlchemy read of a model with a soft-delete or
visibility column that skips the filter or helper at least 80% of the project's reads of that model apply, with at
least five reads counted). It lives in `languages/python/rules/soft_delete/`.

Python deleted-item rule: `deleted-item-filter-missing` (a loop, comprehension or lookup over an annotated collection of
items that carry a deletion flag that skips the guard, helper or narrowed type that at least 80% of the project's
iterations over that item type use, with at least five iterations counted). It lives in
`languages/python/rules/deleted_items/`.

Python route auth rule: `route-without-auth` (a FastAPI route, a Django REST framework view or a Flask route without
the auth requirement, a `Depends(...)`, `permission_classes` or login decorator, that at least 90% of the project's
handlers declare, with at least five handlers counted). It lives in `languages/python/rules/route_auth/`.

Unbounded thread pools: `pmd/UnboundedThreadPool` in the Java and Kotlin presets reports
`Executors.newCachedThreadPool()` and a `ThreadPoolExecutor` without a maximum size in main
sources. In a Spring project, `pmd/SpringUnreleasedResource` reports a bean field that holds an
executor, event loop, client or other resource the bean built and never releases at shutdown, and
`pmd/SpringStartupCleanup` reports a startup call that can fail after the bean started threads,
outside a `try` that releases them. The TypeScript, JavaScript and Python presets have no
counterpart yet; their thread and timer model differs and the NestJS provider case is tracked
separately.

Objects built on every call: `pmd/ReusableObjectPerCall` in the Java and Kotlin presets,
`nitpicker/reusable-object-per-call` in the TypeScript and JavaScript presets and
`reusable-object-per-call` in the Python preset report an object that is safe to share once built
and costly to build (Jackson mappers, Gson, `JAXBContext`, validator factories, constant-pattern
formatters, `Intl` formatters, Ajv, pydantic `TypeAdapter`, jinja2 `Environment`) made in a
function that runs on every call, in production code. The Go preset has no rule engine of its own
yet.

Child process deadlines: `nitpicker/require-process-timeout` (production source, in `eslint-lint`)
reports production code that waits for a child process to exit without a deadline: a synchronous
`child_process` or `execa` call without a positive `timeout`, and `exec`, `execFile`, an awaited
`execa` or a `spawn` or `fork` whose end is awaited without a `timeout` or an abort `signal`. The
same rule runs as `subprocess-without-timeout` in the Python preset, `pmd/ProcessWaitWithoutTimeout`
in the Java preset and `kotlin-source/ProcessWaitWithoutTimeout` in the Kotlin preset; tests keep
`nitpicker/require-test-process-timeout` (TypeScript) or their runner's own limits.

Unbounded waits: `pmd/UnboundedWait` (Java, main sources) reports `get()` or `join()` without a timeout on a
`Future` or `CompletableFuture`, `Thread.join()` and `CountDownLatch.await()`, and
`pmd/ReactorBlockWithoutTimeout` (with `reactor-core` on the compile classpath) reports `block()`,
`blockOptional()`, `blockFirst()` and `blockLast()` without a `Duration`, on Gradle and Maven alike.
`kotlin-source/UnboundedWait` and `kotlin-source/ReactorBlockWithoutTimeout` run the same checks in the
Kotlin preset, and `unbounded-wait` runs them in the Python preset for `concurrent.futures` futures,
`concurrent.futures.wait` and `as_completed`, and `threading.Thread.join()`. The TypeScript and
JavaScript presets have no counterpart, since a promise has no blocking wait.

Blocking helpers in async code: `blocking-helper-in-async` (Python, main sources) reports a call from an `async def`
to a project function that calls `requests`, `httpx`, `urllib.request.urlopen`, `time.sleep`, `os.system` or
`subprocess.run` (up to three calls deep), unless the helper is offloaded with `asyncio.to_thread` or
`run_in_executor`; a blocking call written in the async function itself stays with ruff `ASYNC210` to `ASYNC251`.
The other presets have no helper-aware counterpart.

Time units: `nitpicker/time-unit-mismatch` (production source, in `eslint-lint`) reports time values in
two different units that meet without a conversion: a `+`, `-` or comparison of seconds with milliseconds
(or nanoseconds, microseconds, minutes), a value assigned or passed under a name or parameter of another
unit, and an epoch time cut to 32 bits. Units come from known clock and conversion APIs and from name
suffixes such as `Ms`, `Millis`, `Seconds` and `_seconds`; ratio names (`MS_PER_SECOND`) and flags
(`showSeconds`, `use_ms`) carry no unit, a `format...` call takes its unit rather than returning it,
JWT claims (`exp`, `iat`) count as epoch seconds only on a token, claims or payload object, and an epoch
name needs a unit (`expiresAtEpochSecond`, not `epoch`). The same rule runs as `time-unit-mismatch` in
the Python preset, `pmd/MixedTimeUnits` and `pmd/EpochNarrowedToInt` in the Java preset (Gradle and
Maven; the overlap keeps `pmd/MixedTimeUnits` over Error Prone's `TimeUnitMismatch`) and
`kotlin-source/TimeUnitMismatch` in the Kotlin preset. The Go preset has no own rule engine yet.

Costly collection forms: `nitpicker/no-costly-collection-form` (production source, in `eslint-lint`)
reports three forms with a cheaper equivalent: an array that is appended to and searched with
`includes`, `indexOf` or an identity `some` inside a loop, callback or recursive function (a `Set`); a
`find`, `findIndex` or `some` by one property of the item, in a loop, iteration callback or listener,
over a binding that does not change (a `Map` built once); and a sort that keeps only its first or last
element (one pass). The same forms run as `list-used-as-set`, `linear-lookup-in-loop` and ruff
`FURB192` in the Python preset, `pmd/ListUsedAsSet`, `pmd/LinearLookupInLoop` and `pmd/SortForExtreme`
in the Java preset (main sources, Gradle and Maven) and `kotlin-source/` rules of the same names in the
Kotlin preset. The other presets read `contains` or `in` only, and the Java and Kotlin rules read
loops and iterating lambdas, not recursion or listeners. The Go preset has no counterpart yet.

Streamed rows collected: `nitpicker/no-collected-stream-rows` (production source, in `eslint-lint`)
reports every item of a `for await` loop over a stream, async generator or cursor pushed into one array
that is read only after the loop, so the whole input sits in memory (a batch flushed inside the loop).
The same form runs as `streamed-rows-collected` in the Python preset (`.iterator()`, `yield_per`,
`stream_results=True`, a named or server-side cursor) and as `pmd/StreamedRowsCollected` in the Java
preset (a `Stream` from a Spring Data repository, `getResultStream()`, `queryForStream` or a Hibernate
`stream()`, collected with `toList()`, `collect` or `forEach(list::add)`) and the Kotlin preset (a
`Stream` returned by a repository function, collected in the same chain). A `limit`, an early `break` or
`return`, and a Kotlin `Stream` collected inside `use { }` are left alone. A Kotlin `Flow` is not read:
it is the default return type of a coroutine repository, so `toList()` on it is the usual read of a
small result. The Go preset has no own rule engine yet.

Per-item I/O: `nitpicker/no-io-in-loop` (production source, in `eslint-lint`, type-aware) reports a
database query once per item of a loop or iteration callback (also inside `Promise.all(items.map(...))`, a
`for await` loop or a comparator, where running them concurrently still sends one query per item) and a
remote request once per item of a sequential loop, with the batch or bounded-concurrency form in the message.
A call is classified by the type checker first (the package that declares the receiver's type or the callee),
then through summaries of project helpers (effects proven by a type or an import, named in the finding as a
path), then, where no type is known, by receiver names for a call written in the loop itself; the JavaScript
preset runs the same rule. A call that takes a whole chunk, a paging or polling loop, a retry and a broker
publish are left alone. A remote call inside `Promise.all` is the fan-out rule's, so no call is reported
twice. The same rule runs as `io-in-loop` in the Python preset and `go-rules/io-in-loop` in the Go preset.

Field resolvers: the Go preset reports a gqlgen field resolver of a list parent that queries once per parent without
a dataloader (`go-rules/query-per-parent-resolver`).

Related writes: the Go preset reports two writes on different tables in one function with no transaction
(`go-rules/writes-without-transaction`, `database/sql`, sqlx, pgx and gorm) and a write through the outer
handle inside a function that has an open transaction (`go-rules/write-outside-transaction`).

Scheduled and queue jobs: the Go preset reports a loop in a robfig/cron, gocron, asynq or machinery job that returns,
panics or exits on the first failing database or HTTP call of an item (`go-rules/failing-item-stops-job`).

Accumulator copies: `nitpicker/no-accumulator-concat` (production source, in `eslint-lint`) reports an array
accumulator copied with `concat` on every step of `reduce` or of a loop (`all = all.concat(item.tags)`), where
the work grows with the square of the list; the spread forms are `nitpicker/no-accumulating-spread`'s. It reads
the accumulator's type when the type checker runs, so a string's `concat` is left alone.

Spread arguments: `nitpicker/no-array-spread-arguments` (production source, in `eslint-lint`) reports an array
spread into `push`, `unshift` or `splice` of an array, or into `Math.max`, `Math.min`, `String.fromCharCode` or
`String.fromCodePoint` (`target.push(...items)`, `Math.max(...sizes)`), which throws `RangeError` once the array
reaches about 125,000 items. With the type checker arrays, typed arrays, sets, maps and `any` values are reported
(tuples and strings are not), and `push`, `unshift` and `splice` only on an array; array and string literals and
a function's own rest parameter passed on are allowed.

Null branches that continue: `nitpicker/no-null-branch-fall-through` (production
source, in `eslint-lint`) in the TypeScript and JavaScript presets, and `null-branch-fall-through` (script) in Python. It reports
an `if (x == null)` or `if x is None:` branch without `else` that does something and does not leave (no return, throw, break,
continue, exit or assignment to `x`) when the same block then reads `x` as present (member access, indexing, destructuring,
spread, iteration, or an argument of a call the branch also made). A later guard of `x` ends the search.

Django type plugin: `django-types-missing` (script, Python only) is reported once, on the first model class, when Django is a
dependency and neither `django-stubs` (mypy plugin) nor `django-types` is configured.
Django lookups of one row: `non-unique-lookup` (script, Python only) reports `get`, `aget`, `get_or_create` or `update_or_create` on a model
manager or queryset whose lookup keywords do not cover the primary key, a unique field, a one-to-one field or a unique constraint of the
model, an `|` of `Q` objects given to `get`, and a JSON, array or text field in the lookup of `get_or_create` or `update_or_create`.

Nullable Django values: `nullable-dereference` (script, Python only) reports an attribute, call, subscript, iteration, `len()` or
ordering comparison on a `null=True` model field, a `.first()`/`.last()` result, a `.get(key)` without a default on form or request data,
or a signed-in-only `request.user` attribute, with no `None` test, truthiness test, `or` fallback, `is_authenticated` check or login
decorator before it in the same function.

Lazy relations: `nitpicker/no-lazy-relation-in-loop` (production source, in `eslint-lint`, type-aware)
reports a lazy TypeORM relation awaited once per item of a `find` or `getMany` result in the same function
that does not fetch it (`relations`, `leftJoinAndSelect`), directly or through a project function given the
item. Only proven cases are reported: a collection of unknown origin is not.

Cache writes in transactions: `nitpicker/no-cache-write-in-transaction` (production source, in `eslint-lint`) reports a
Redis, `cache-manager`, `keyv` or `node-cache` write, or a `Map` filled with a row or id written in the same callback,
inside a Prisma `$transaction`, TypeORM `transaction`, Kysely `transaction().execute` or begin/commit scope. The
allowed form is writing the cache after the transaction call returns (or from a TypeORM `afterTransactionCommit`
subscriber); the finding names it.

Remote calls while a resource is held: `nitpicker/no-remote-call-in-transaction` and
`nitpicker/no-remote-call-under-lock` (production source, in `eslint-lint`, type-aware) report a remote call,
direct or through project helpers, inside a transaction that also runs a query (a Prisma `$transaction`
callback, `startTransaction`/`commit` ranges, TypeORM, Sequelize, knex) or while a mutex or distributed lock is
held (`runExclusive`, `async-lock`, Web Locks, redlock). The finding names the call path and the outbox form.
A fill-once block under a lock (`if (!token) token = await refresh()`) is left alone, and an early rollback or
release in a guard clause does not end the scope for the calls after it. Broker publishes belong to the
dual-write rule.

Retried writes: `nitpicker/no-retry-without-idempotency` (production source, in `eslint-lint`, type-aware)
reports a Stripe `create` without an idempotency key, a broker publish without a deduplication id or a plain
SQL `INSERT` inside a retry wrapper (`p-retry`, `async-retry`, `exponential-backoff`, cockatiel) or a
hand-written retry loop, direct or through project helpers.

Dual writes: `nitpicker/no-dual-write` (production source, in `eslint-lint`, type-aware) reports a function
that writes to the database and publishes a broker message at separate calls, since a crash between them
loses or duplicates the message; the outbox table or relay is the allowed form. An outbox relay (publish a
row read from the database, then mark it sent) is not reported.

GraphQL field resolvers: `nitpicker/no-query-per-parent` (production source, in `eslint-lint`, type-aware)
reports a database or remote call made by a NestJS `@ResolveField`, type-graphql `@FieldResolver` or resolver-map
field function (Apollo Server, Mercurius, graphql-yoga) whose parent type is returned as a list somewhere in the
schema: N parents cost N queries. The allowed forms are a DataLoader, a request-scoped cache and data already on
the parent; a parent type that is only returned alone is not reported.

Reactive lookups: `nitpicker/no-lookup-per-element` (production source, in `eslint-lint`, type-aware) reports an
RxJS `mergeMap`, `concatMap`, `switchMap`, `exhaustMap` or `flatMap` over `from(items)` whose function makes a
database or remote call per element, directly or through a helper: fetch the rows in one batched query and join them in
memory. A grouping operator before the lookup (`bufferCount`, `toArray`) and a fixed collection are not reported.

Rows saved back: `nitpicker/no-loaded-rows-saved-back` (production source, in `eslint-lint`, type-aware) reports
query rows (TypeORM, Prisma, Sequelize, MikroORM, Drizzle) loaded only to assign constants to a field of every row
and save them back (`save(rows)`, `bulkCreate`, `flush()`), to `remove(rows)`, or to pass their ids to a delete or an
update; one `update`, `updateMany` or `delete` statement does it without loading anything. Entities with hooks,
subscribers or a version column, and loops that read the row or call functions, are not reported.

Whole rows for one value: `nitpicker/no-whole-rows-for-one-value` (production source, in `eslint-lint`, type-aware
for the column form) reports query rows (TypeORM, Prisma, Sequelize, MikroORM) loaded only to map them to one
declared column, a `count` only compared with zero or one, and a `findOne`/`findFirst` result only used as a
condition: select the column, or ask `exists`/`findFirst` with `select`. A query that already selects, a paged
query and rows used another way are not reported.

Optimistic-lock retries: `nitpicker/no-stale-retry-after-conflict` (production source, in `eslint-lint`) reports a
TypeORM `save` inside a retry that names `OptimisticLockVersionMismatchError` (p-retry, async-retry,
exponential-backoff, cockatiel or a hand-written loop) when it saves an entity loaded before the retried scope, or
one re-read inside it but saved without the change re-applied. Re-read by id and re-apply the change inside the
retried scope.
Related writes: `nitpicker/no-unatomic-writes` (production source, in `eslint-lint`) reports, for projects on
TypeORM, Prisma, Drizzle, Kysely, Knex, Sequelize or MikroORM, a write inside a transaction callback that goes
through a client or repository other than the callback's parameter, and, where the project opens transactions
somewhere, a function that awaits writes to two different tables with no transaction. The finding names the
writes and the allowed forms (one transaction with its manager passed down, an atomic statement).
`nitpicker/no-check-then-write` is the report-only form: a read of a table that decides a write to it with
no transaction, lock or atomic statement.

Job loops: `nitpicker/no-unisolated-job-loop` (production source, in `eslint-lint`, type-aware) reports a `for...of`
loop in a scheduled or queue job (NestJS `@Cron`/`@Interval`/`@Timeout`/`@Process`/`@Processor`, BullMQ
`WorkerHost.process` and `Worker`, Agenda `define`, node-cron `schedule`) whose body awaits a database or remote
call with no `try`/`catch` around it, so one failing item stops the rest. A `try`/`catch` per item, one queued
job per item and `Promise.allSettled` are the allowed forms.

Soft-delete filters: `nitpicker/no-unfiltered-soft-delete-read` (production source, in `eslint-lint`) reports a changed
Kysely, Knex, TypeORM, Drizzle, Prisma, Sequelize or MikroORM read or join of a table whose reads mostly (80%, at
least five reads, measured at the merge base) apply a soft-delete or visibility column or helper and that does not.
The finding names the column and the project's helper; a project with no majority is not reported.

Deleted items in memory: `nitpicker/no-unguarded-deleted-items` (production source, in `eslint-lint`, type-aware) reports
a changed loop or inline array callback over items that carry a deleted or visibility flag (`isDeleted`, `deleted`,
`deletedAt`, `archived`, `hidden`, `isVisible`) when at least 80% of such iterations in the project (at least five) skip
flagged items and this one does not. The finding names the flag and the project's guard form: a helper such as
`getNonDeletedElements` or a narrowed type such as `NonDeleted<T>`.

Route auth: `nitpicker/no-route-without-auth` (production source, in `eslint-lint`) reports a NestJS handler that lacks the
auth decorator shape almost every handler declares (90%, for example `@Authenticated({ permission })`), or, when no
shape has a majority but some handlers use a guard and there is no global guard, a handler with no guard and no public
marker; an Express or Fastify route registered without the auth middleware most routes use is reported the same way.

Generic names: `nitpicker/no-generic-name` (production source, in `eslint-lint`) reports a file,
folder, class, interface, type alias, enum or namespace whose last name word is `utils`, `helpers`,
`manager`, `common`, `misc` or a variant, so code is named for what it does and shared pure logic
goes in a shared folder. The same list runs as `generic-name` in the Python and Go presets, as
`kotlin-source/GenericTypeName`, `GenericFileName` and `GenericPackageName` in the Kotlin preset,
and as `pmd/GenericTypeName` and `pmd/GenericPackageName` in the Java preset (a Java file is named
after its type). A framework role (`CacheManager`, `SessionManager`) and a type that extends a type
with the same last word pass; a domain-term manager takes the exception.

Repeated string literals: `nitpicker/no-repeated-string-literal` (production source, in
`eslint-lint`) reports each use from the third on of a string of five characters or more that
appears three times in a file (a template literal without expressions counts), so the text is named
once as a constant. Import sources, keys, `case` labels, string literal types, JSX attribute and
`className` values, `const` initializers, `typeof` comparisons, decorator arguments, event names,
module mocks, translation keys, discriminant values (the value under a `type`, `kind`, `tag` or
`variant` key, or a text compared with a member of that name), the `error` severity in a lint config
entry and idiomatic texts are not counted. The same
definition runs as `repeated-string-literal` in the Python and Go presets, as
`kotlin-source/RepeatedStringLiteral` in the Kotlin preset and as PMD `AvoidDuplicateLiterals` in
the Java preset.
Dropped log arguments: `nitpicker/no-dropped-log-arguments` (production source, in `eslint-lint`, when the project
depends on pino, bunyan or winston) reports a `trace` to `fatal` call whose literal message has fewer placeholders than
values (pino: the extra values are dropped; winston without `format.splat()`: every value after a message with a
placeholder) and, for pino and bunyan, more placeholders than values. A fields object first (`log.info({ config }, 'x')`),
one value per placeholder and a metadata object are allowed.

Hardcoded secrets and secrets in logs: `nitpicker/no-hardcoded-secret` and `nitpicker/no-secret-in-log`
(production source, not tests or test-support folders, in `eslint-lint`) report a secret-looking string given to a secret-named variable,
field, property, assignment, parameter default or environment-read fallback, a credential-shaped string
anywhere, and a secret-named value passed to a log call or an error message. The same forms run as
`hardcoded-secret`, `credential-shape` and `secret-in-log` in the Python and Go presets, as
`pmd/HardcodedSecret`, `pmd/CredentialLiteral` and `pmd/SecretInLog` in the Java preset (main sources,
Gradle and Maven) and as the `HardcodedSecret`, `CredentialLiteral` and `SecretInLog` source checks in the
Kotlin preset. All presets share one definition of the names and the values
(`shared/naming/secret-words.mjs`). Spring configuration files have their own `literal-secret` check.

Task markers and commented-out code: `todo-without-issue` and `commented-out-code` report a `TODO` or
`FIXME` comment with no issue reference, and a comment that reads as code. The Python preset runs them as
`todo-without-issue` and ruff `ERA001`, the Kotlin preset as detekt `ForbiddenComment` and the `CommentedOutCode`
source check, the Java preset as `pmd/TodoWithoutIssue` and `pmd/CommentedOutCode` (a scan of the source
comments, on `.java` files of Kotlin projects too), and the Go preset as `go-rules/todo-without-issue` and
go-critic `commentedOutCode`. The TypeScript and JavaScript presets ban comments outright.

Boolean flag parameters: `nitpicker/no-boolean-flag-parameter` (strict preset, production source) reports a
`boolean` parameter that an exported function or public member branches on. The same rule runs as
`boolean-flag-parameter` in the Python preset, `pmd/BooleanFlagParameter` in the Java preset (main sources,
Gradle and Maven), the `BooleanFlagParameter` source check in the Kotlin preset and revive `flag-parameter`
in the Go preset. The allowed form is two functions, an options object or an enum.
Cleanup that stops at the first failed release: `nitpicker/no-cleanup-skipped-on-failure` (strict preset,
production source and tests) reports, in a close, dispose, stop or shutdown function, an `afterAll` or
`afterEach` callback and a shutdown-signal callback, an awaited release (`close`, `disconnect`, `destroy`,
`end`, `quit`, `stop`, `unsubscribe`) followed in the same block by another release or a state reset, and
`Promise.all` over releases. The same form runs as `cleanup-skipped-on-failure` in the Python preset (also
the part of a fixture after its `yield`, and `asyncio.gather` over releases without `return_exceptions=True`),
`pmd/CleanupSkippedOnFailure` in the Java preset, `kotlin-source/CleanupSkippedOnFailure` in the Kotlin
preset and `go-rules/cleanup-skipped` in the Go preset (an early `return` after a failed `Close`). A release
inside `try`/`finally`, try-with-resources, `use`, `ExitStack` or `errors.Join` is left alone.

Pending requests left hanging by a close: `nitpicker/settle-pending-on-close` (strict preset, production source)
reports a `Map`, object or array of callbacks, resolve and reject pairs or deferreds in a class or factory with a
close, dispose, stop or shutdown function that never settles it (rejecting or calling each entry, or passing
the collection to a call), since a bare `.clear()` leaves every waiting caller hanging. The same form runs as
`pending-unsettled-on-close` in the Python preset (a dict of futures), `pmd/PendingFuturesNotFailedOnClose` in
the Java preset (a `Map` of `CompletableFuture`, `Future` and the like), `kotlin-source/PendingFuturesNotFailedOnClose`
in the Kotlin preset (also `CompletableDeferred`) and `go-rules/pending-not-closed` in the Go preset (a map of
channels). A close that fails or completes each entry, or hands the collection to a helper that does, is left alone.

Listeners and timers a close never releases: `nitpicker/release-listeners-on-close` (strict preset, production
source outside composition roots) reports, in a class or factory with a close, dispose, stop or shutdown function,
`on`, `addListener` or `addEventListener` on a long-lived emitter (a field, a closure or module variable,
`process`) and a `setInterval` or kept `setTimeout` handle that nothing in the scope removes or clears. `once`,
an `AbortSignal` and a short-lived emitter are left alone. The same form runs as `handle-unreleased-on-close` in
the Python preset (`call_later`, `call_at`, `threading.Timer` and signal handlers), `pmd/TimerNotStoppedOnClose`
in the Java preset and `kotlin-source/TimerNotStoppedOnClose` in the Kotlin preset (a scheduled executor or
`Timer` that close never shuts down) and `go-rules/ticker-not-stopped` in the Go preset (`time.NewTicker`
without `Stop`).

Cached promises that keep a rejection or let a stale attempt win: `nitpicker/no-cached-rejection` (strict preset,
typed production source) reports a promise assigned to a class field or an outliving variable and reused through a
guard (`if (p) return p`, `p ??= start()`, `p ||= start()`) when no catch or rejection callback clears it, and a
clearing that does not check the binding still holds this attempt. Concurrent lazy loads that do not share one in-flight promise are not reported (that needs data flow across calls). A static field cached through the class name is not tracked. The Java and Go forms do not check the identity form. The same form runs as `cached-rejection` in the
Python preset (a task or future on an attribute, and `functools.cache` on an `async def`),
`pmd/CachedFutureKeepsFailure` in the Java preset (a `CompletableFuture` memo field),
`kotlin-source/CachedDeferredKeepsFailure` in the Kotlin preset (a `Deferred` property or `by lazy` that starts an
`async`; the stale-attempt form is not read there) and `go-rules/once-keeps-error` in the Go preset (`sync.Once` and
`sync.OnceValues` around an initialiser that can fail).

Long-lived collections that only grow: `nitpicker/no-add-only-collection` (strict preset, production source) reports a
`Map`, `Set` or array in a class field or in a factory closure (a factory with a close function) that a method or returned function adds to per key and that
nothing in the scope removes from, bounds by `size` or `length`, or hands to a call; startup registries (the
constructor, `init*`, `register*`, literal keys) and `WeakMap` are skipped, and module-level state stays with
`nitpicker/no-module-level-mutable-state` (module bindings are never checked, because a module has no close function; collections that `settle-pending-on-close` owns are skipped). The same form runs as `unbounded-collection` in the Python preset (an
attribute `dict`, `set` or `list` of a class with a close method), `pmd/UnboundedCollectionField` in the Java preset and
`kotlin-source/UnboundedCollectionProperty` in the Kotlin preset (both limited to a singleton bean: a Spring
stereotype or `@Singleton`) and `go-rules/map-only-grows` in the Go preset (a map field of a struct that holds a
mutex).

HTTP deadlines: `nitpicker/require-http-timeout` (strict preset, production source) reports an outbound
HTTP call that has no timeout, so a server that accepts the connection and never answers hangs it. The same
rule runs as `http-without-timeout` in the Python preset, `pmd/HttpWithoutTimeout` in the Java preset (main
sources, with or without Spring; the clients Spring builds stay with `pmd/SpringHttpClientTimeouts` and
`pmd/SpringHttpClientPerCall`), `kotlin-source/HttpWithoutTimeout` in the Kotlin preset and
`go-rules/http-without-timeout` in the Go preset; each preset's
document lists the clients it knows.

Configuration reads: the process environment and system properties are read once, in the composition root,
and passed in. The TypeScript presets report `process.env` outside it
(`nitpicker/no-process-access-outside-composition-root`), the Python preset `os.environ` and `os.getenv`
(`process-env-access`). The Java preset reports `System.getenv`, `System.getProperty` of an application key,
`Integer.getInteger`, `Long.getLong` and `Boolean.getBoolean` in main sources outside the file with `main`, a
dependency-injection module or factory (Guice, Dagger, CDI, Micronaut, Quarkus) or a Spring configuration class
as `pmd/ConfigurationReadOutsideCompositionRoot`, with or without Spring; in a Spring project
`pmd/SpringTypedConfiguration` keeps the reads both report. The Kotlin preset reports the same reads as
`kotlin-source/ConfigurationReadOutsideCompositionRoot`, except `System.getenv`, which is detekt's
`ForbiddenMethodCall` there, with the same files allowed.

Query order: `nitpicker/no-unordered-query` (strict preset, production source) reports a query that takes a
page of rows (`limit`, `offset`, `take`, `skip`, a cursor, or SQL `LIMIT`, `OFFSET` or `FETCH`) or builds an
`array_agg`/`json_agg` list with no ORDER BY, so which rows come back can change between runs. It reads Kysely,
Knex, TypeORM and Drizzle builder chains, Prisma, TypeORM and Sequelize option objects and SQL text. The same
rule runs as `unordered-query` in the Python preset (SQLAlchemy, Django querysets, SQL text),
`pmd/UnorderedQuery` in the Java preset (JPQL and SQL text, `setMaxResults`/`setFirstResult`, criteria queries,
unsorted `PageRequest`) and `kotlin-source/UnorderedQuery` in the Kotlin preset. The text analysis is shared:
[`shared/rules/queries/sql-order.mjs`](../shared/rules/queries/sql-order.mjs).

Query arrays: `nitpicker/no-unbounded-query-array` reports a runtime array expanded into an SQL in list or a
multi-row insert with no empty check, size check or chunking: an empty array renders `in ()`, and PostgreSQL
takes at most 65,535 bound parameters. One array parameter (`= any($1::uuid[])`) passes. The same rule runs as
`unbounded-query-array` in the Python preset, `pmd/UnboundedQueryArray` in the Java preset and
`kotlin-source/UnboundedQueryArray` in the Kotlin preset. Go has no counterpart: the Go preset runs the Go
toolchain's own checks and has no rule engine of its own.

Exceptions mapped to a status: `nitpicker/no-unmapped-exception` (TypeScript strict preset, type-aware)
reports a NestJS handler that can throw a project exception class no exception filter in scope maps, so
the client gets a 500. The Python preset runs it as `unmapped-exception` for FastAPI and Starlette routes
and their exception handlers, and the Java and Kotlin presets as `archunit/spring-unmapped-exception` for
Spring MVC and WebFlux controllers, `@ExceptionHandler` and `@ResponseStatus`. Each follows calls four
levels deep and skips code inside a `try` that catches. The JavaScript preset has no type information to
follow calls with, Django, Flask and Go handlers are not checked yet.

Recursive map updates have no TypeScript or JavaScript check: `Map` has no method that runs a
callback while it updates an entry, so a callback cannot change the map in the middle of an update.
The same holds for Python's `dict` (`setdefault` takes a value, and a `defaultdict` factory runs
before the entry is stored and takes no key). The Java and Kotlin presets report it as
`pmd/RecursiveMapUpdate`: a change to a map inside the function passed to its `computeIfAbsent`,
`compute`, `computeIfPresent` or `merge` (Kotlin: also `getOrPut` on a `ConcurrentMap`).

## Custom rules

Generated from `shared/policy.mjs`. "enforced" means the language's adapter produces the
rule and it fails the gate; "not enforced" means the check does not exist for that language yet;
"report-only" means the adapter produces the rule when the project opts in and it never fails the gate.

The function limits, the file limits and the CRAP score limit ratchet: editing a function that was
already over a limit on the base fails only when the change raises that metric (lines, statements,
nesting, parameters, or the CRAP score). In the same way a file over its line limit fails only when
it grows, a folder over its file limit only when it gains a file (a moved folder is matched to its
old path), and an edited long line only when it gets longer than the long line it replaced; a long
line with no edited line to stand in for fails. A function the change pushes over a limit, and a new function over
a limit, fail as usual. The failure of a function that got worse names the base value ("grew from 68
to 72 lines"); a touched function that did not get worse is listed in the report as "Touched, still
over limit" and does not fail.

## Timeouts that abandon work

One rule, `timeout-abandons-operation`, in every language that has a timeout construct which stops
waiting without stopping the work.

| Language   | Rule id                                   | Implementation                                                                         | Status      |
| ---------- | ----------------------------------------- | -------------------------------------------------------------------------------------- | ----------- |
| TypeScript | `nitpicker/timeout-abandons-operation`    | `languages/typescript/preset/eslint-plugin/rules/async/timeout-abandons-operation.mts` | enforceable |
| JavaScript | `nitpicker/timeout-abandons-operation`    | the same ESLint rule                                                                   | enforceable |
| Python     | `python-rules/timeout-abandons-operation` | `languages/python/rules/waits/timeouts.py`                                             | enforceable |
| Java       | `pmd/timeout-abandons-operation`          | `languages/java/gradle/pmd-main-ruleset.xml` (XPath, Gradle and Maven)                 | enforceable |
| Kotlin     | `pmd/timeout-abandons-operation`          | `languages/java/adapters/kotlin/review-rules/main/timeouts/timeouts.mjs`               | enforceable |

TypeScript and JavaScript: `Promise.race` of an operation and a timer that rejects, where the
operation gets no `AbortSignal`, cancelling owner or cleanup in the timeout path (HTTP clients that
`require-http-timeout` recognizes are left to it; a resolving sleep is a hedge, not a timeout).
Python: `asyncio.wait(..., timeout=...)` or `return_when=FIRST_COMPLETED` whose pending tasks are not
cancelled, awaited or handed on (directly or through the awaited collection), and
`asyncio.wait_for(asyncio.shield(task), ...)` with nothing cancelling or awaiting the task afterwards;
`asyncio.wait_for`, `asyncio.timeout`, task groups and Trio and AnyIO scopes cancel and are allowed.
Java: `Future.get(timeout, unit)` whose `TimeoutException` handler neither rethrows nor hands the
future on while the method never calls `cancel(true)` on it, `shutdownNow()` on its executor or
`interrupt()` on its thread (`shutdown()` and `cancel(false)` let it finish), and `get`, `orTimeout`
or `completeOnTimeout` on a `CompletableFuture` that `supplyAsync` or `runAsync` started, which no
cancel interrupts (two PMD rules, one per message, printed under the one id). Kotlin: the same forms,
plus `withTimeout { deferred.await() }` (or `awaitAll`) on a `Deferred` another scope started that the
timeout path does not cancel. The precision limits are in
[TypeScript](../docs/typescript-strict-preset.md), [Python](../docs/python-preset.md),
[Java](../docs/java-preset.md) and [Kotlin](../docs/kotlin-preset.md).
