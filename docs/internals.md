# Internals

Contributor notes on formats and protocols that code and names cannot carry. Source files stay comment-free (`nitpicker/no-comments`).

## Diff engine (`core/`)

- **Custom analyzers.** A `{name, command, args?}` config entry runs with the analyzed checkout as working directory, so a relative command resolves inside each side. It prints findings JSON on stdout and exits 0; stdout goes through the same parser as built-in analyzers, and a non-zero exit or invalid JSON becomes a tool error.
- **Exit codes.** New violations win over tool errors so CI can tell "violations" from "broken"; `overallStatus` reports tool health first.
- **Tool-error paths.** `runAnalyzers` rewrites tool-error messages (scheduler errors and `tool-error` findings) of a run on a temporary snapshot (`core/diff/snapshot-root/`): a path under the snapshot's project root becomes project-relative, the root itself becomes `base` or `head`. A run on the live project keeps its paths.
- **Analyzer environment.** Analyzers never see where the GitHub Actions job summary lives (`HOST_CI_OUTPUT_VARIABLES`): vitest and Stryker would append their own reports to it, and caught mutants read as test failures.
- **Cache stores.** A store keeps opaque text under a hex key, is synchronous and never throws: `get` returns undefined on any miss or failure, `put` returns whether the value was stored. The local directory is `NITPICKER_CACHE_DIR`, else `node_modules/.cache/nitpicker`. The HTTP store does `GET`/`PUT` of `<baseUrl>/<key>.json` with an optional `Name: value` auth header, and stays off after its first non-miss failure so an unreachable server costs one timeout. Reads try local, then remote (copying a hit locally); writes go to the remote store only with `writeRemote`.
- **HTTP cache worker.** Exit codes: 0 success (GET prints the body), 3 not found, 1 any other failure. The comparison is synchronous, so each request runs in a short-lived `node` child that does the asynchronous fetch: `<GET|PUT> <url> <timeoutMs>`, auth header in `NITPICKER_CACHE_AUTH_HEADER_VALUE` (never argv). S3 answers 403 for a missing key when the caller cannot list the bucket, so 403 counts as not found. The test HTTP server lives in a worker thread for the same reason: the stores block the calling thread.
- **Findings cache key.** Base commit, project, analyzer, tool version, configuration hash, head policy (exclude, layout, exceptions, thresholds) and legacy inventory path. The policy is keyed explicitly because layout and threshold changes rebuild an analyzer without changing its file-based hash. Entries carry their own key, so a misnamed entry is a miss. Only clean reports are stored, and cached analyzers still run when an uncached one depends on them.
- **Publishing a base snapshot.** `cache publish` analyzes HEAD (typically the new tip of `main`) and stores clean reports under the keys later comparisons use when HEAD is their merge base, using HEAD's own policy.
- **Comparison.** Findings split into new, resolved, unchanged and changed-metric. With `touchedCode`, an enforceable finding of a strict rule inside touched lines is new even though the base has it, unless it carries `ratchet.existingCodeOnly` (an ESLint finding inside a named function): then only a line in `inserted` makes it new, and `changed-lines.mjs` leaves out of `inserted` an added line it pairs, by word similarity, with a removed line.
- **Cycle identity.** Dependency cycles are `cycle:a>b>c|...`, starting at the lexicographically smallest rotation. A rename can change that rotation, so renamed cycles are re-rotated before comparing.
- **Report hash.** Zero config keeps the original policy hash input; any override changes it.
- **SARIF output.** One result per new finding; the hashed comparison key is `partialFingerprints["nitpickerIdentity/v1"]`, so consumers match findings across runs when lines move. Tool errors become unsuccessful tool-execution notifications.
- **Base commit of a checkout.** `git.mjs` stages the checkout (untracked, non-ignored files included) in a copy of the index, leaving the user's index, branches and files untouched.
- **Policy links.** Without `transform` the package-owned policy file is linked into the analyzed tree; with one (the layout changed) it is a rewritten copy, still derived from the head policy and never from the analyzed tree.
- **Shared build directory.** `runScheduler` creates one directory per side (`NITPICKER_SHARED_BUILD_DIRECTORY`, inherited by every analyzer process) and removes it when the scheduler exits. `buildOnce(key, build)` runs `build` in the first process to take `<key>.lock`; the others poll for `<key>.result` (or `<key>.failure`, rethrown so a broken build is not repeated). A lock whose owning process is gone (or an empty one left by a crash) is taken over by renaming it aside and re-checking it. A build killed by a signal records nothing, so a waiter builds instead; other failures are recorded. Without the variable, `buildOnce` just builds, so direct runs and tests are unchanged.
- **Temporary files.** Register before creating the file so it is removed on exit or interruption even if the runner's `finally` blocks never run.
- **Presets.** `preset` is explicit; there is no Gradle auto-detection. Injected analyzers win over the preset. Within the Java preset the build tool is detected (`detectJavaBuild`): Maven when the root has a `pom.xml` and no Gradle build file, or both but only `mvnw` and no `gradlew`; Gradle otherwise.

## Shared rules (`shared/`, `spec/`)

Findings follow `spec/findings.schema.json`. Identity (the part of the comparison key beyond rule and path) never contains line numbers, so edits above a finding do not change it.

- **Project conventions** (`shared/conventions/`, `core/conventions/`). A convention is `{ id, label, options, optionLabels, fallback, files, measure(text) }`; `measure` returns the option one file follows, or `undefined`. `detectConventions` takes the files not under `exclude` (the CLI adds the layout's excluded folders, such as `dist`, `build`, `generated` and `target`), samples at most 400 per convention evenly over the sorted paths, counts one vote per file, and picks the plurality; a tie or no votes is `fallback` (`source: 'default'`), a `conventions` pin in the config skips measuring (`source: 'pinned'`). The CLI measures once the config, the analyzer selection and the base ref have been checked, so their errors come first and a run outside git fails as before: a comparison reads the merge-base commit through `git ls-tree -l` (regular blobs up to 512 KiB only, so generated files, symlinks and submodules never vote) and one `git cat-file --batch` by object id (so a branch cannot flip the choice); when every convention is pinned no git command runs, and re-measures on the working tree only the conventions the base had no files for; `--all` measures the working tree and `cache publish` the published commit (which later comparisons use as their merge base, so the keys match). Only choices that differ from the preset default go into the head policy, as `conventions: { id: option }` (omitted when empty, so default-style projects keep their policy and cache keys), also into the base's policy when the base has its own config, so both snapshots and the findings cache key see the same values. Presets list their conventions in `core/conventions/definitions.mjs`; a preset with none leaves the policy as it was. The TypeScript and JavaScript presets measure Prettier options (`languages/typescript/conventions/`) and add the choices to the `nitpicker` Prettier layer for code files, which then always runs through the layered Prettier API path. Short code says nothing about the print width, so a file votes a width only when it is the one value between its longest breakable line and the shortest call, array or assignment Prettier left wrapped (joined, that would have fit any wider limit), or 120 when at least two lines exceed 100. The measures skip comments and template-literal contents, and a file with no evidence casts no vote, so a project keeps the preset default rather than a guess.

## TypeScript preset (`languages/typescript/`)

- **Strict preset assembly.** Flat config replaces rather than merges a rule's options when several entries match a file, so each scope in `eslint-config/strict.mjs` carries its full `no-restricted-syntax` list: the everywhere selectors plus the scope's own. Add a selector to its scope's list, never as a separate entry for a narrower glob. `domain/` has its own loop and forEach selectors, so it takes only the promise-chain selectors from the production set. `strictSyntaxConfig` (`strict.mjs`), `strictAdaptersConfig` (`strict-adapters.mjs`) and `strictTestsConfig` (`strict-tests.mjs`) are standalone configs so the failure-message harness can lint one rule family alone; no tool loads them by path, which is why they are ordinary modules and not `*.config.mjs` files. The typed ones (`strictConfig(parserOptions)`, `strictAdaptersTypedConfig`) need `parserOptions` (e.g. `{ project: './tsconfig.quality.json', tsconfigRootDir }`) and later entries win.
- **React scope.** `eslint.config.mjs` adds `reactScopeConfigFor()` and passes `{ react: true }` to `strictPresetConfig()` only when `isReactProject()` says so: the head policy's `react.enabled` when set, else `react` in the analyzed tree's `dependencies` or `devDependencies` (the head policy carries the decision: `resolveHeadPolicy(config, projectRoot)` fills `react.enabled` and `i18n.enabled` from the head checkout's manifest unless the config sets them, so base and head are linted with the same scope, a pull request that adds React or `react-intl` does not make every existing finding new, and the policy hash and cache key include the decision; a run without a project root, such as `--fix`, falls back to the manifest of the tree being linted, read from `NITPICKER_DIFF_ESLINT_PROJECT_ROOT`). The plugins load through a dynamic import, so a non-React run never pays for them. `react: true` changes one `strict-declarations.mjs` selector: classes extending `Component` or `PureComponent` leave the "classes only for `Error` subclasses" ban and belong to `react-x/no-class-component`. The head policy carries `react` only when the config sets it, which keeps zero-config cache keys unchanged. Unset `react.styling` is inferred from the tree's manifest (`stylingApproachFor`), so it too follows each side. With the scope off, `eslint.config.mjs` drops the exceptions that name a React rule id (`reactRuleIds`) before `applyRuleExceptions`, which still rejects unknown ids. With the scope on, `strict-escape-hatches.mjs` also lets `null` through as the argument and type argument of `useRef` and `createContext`. The custom React rules resolve `useEffect`, `useLayoutEffect` and `useState` through their `react` import bindings (aliases, namespace imports); an identifier with no binding at all is matched by name, so auto-imported hooks still count. `react-rules.mjs` lists every React rule id (strict, like the other scopes' rules); `react-scope.test.mjs` checks it against the config and the accessibility names against the plugin's recommended set. The test rules (`reactTestRuleIds`) are a second entry in `reactSyntaxConfigFor()`, scoped to test files (`layout.testGlobs` plus `__tests__` directories) and independent of the runner: `eslint-plugin-testing-library` (peer range includes ESLint 10) supplies `no-test-id-queries`, `no-node-access` (which also reports `container.querySelector`, so `no-container` is left out to avoid a second message), `prefer-user-event`, `await-async-events`, `await-async-queries` and `await-async-utils`, and `nitpicker/react-test-no-implementation-details` covers what the plugin does not (component instances and state, fiber internals, spies on React hooks). `testingLibraryPlugin` wraps each upstream rule three ways. `withHint()` appends the allowed form. `withoutFixes()` drops `fix` and `suggest` from every report: ESLint 10 calls a fixer at report time, and upstream's `await-async-events` fixer sets `async = true` on the node, which crashed `@typescript-eslint/require-await` and with it the whole analyzer. `inReactTestFilesOnly()` (`react-test-files.mjs`, also used by the custom rule) runs the rule only in a file that imports `@testing-library/*`, `react`, `react-*`, `enzyme` or a relative `test-utils` module, because the plugin's own detection is aggressive without an import and would flag Playwright `getByTestId` or a zustand `setState` in a domain test. The test entry sets `testing-library/utils-module` to `test-utils` so renders re-exported from a project wrapper count as Testing Library renders; other wrapper locations are not detected. `reactScopeConfigFor()` turns `no-test-id-queries` off when the analyzed tree lists `@testing-library/react-native`.
- **i18n scope.** `eslint.config.mjs` adds `i18nScopeConfigFor()` (`eslint-config/i18n/i18n-scope.mjs`) only when `isI18nProject()` says so: the head policy's `i18n.enabled`, filled from the head checkout's manifest like `react.enabled` (see React scope; `react-intl` or `@formatjs/intl` in `dependencies` or `devDependencies`, read by `hasScopePackage()` in `eslint-config/scope-support.mjs`, which also holds `productionScope()` for both scopes). The head policy carries `i18n` (`enabled`, `functionNames`, `componentNames`; the last two become the plugin's `additionalFunctionNames` and `additionalComponentNames` settings). The plugin loads through a dynamic import, so a project without a message library never pays for it. The scope is one config entry for production source minus story files (`*.stories.*`, `*.story.*`, `storyGlobs` in `scope-support.mjs`, which the React scope also uses to turn `react-no-hardcoded-colors` off), independent of the React scope; its rules are syntactic, so they need no type information. `i18n-rules.mjs` is one table, `i18nRules`, of `{ setting, hint, messages?, filters?, ownsParseErrors? }` per enabled rule, plus `i18nOffRules`; `i18n-scope.test.mjs` checks that the two together name every rule of the installed plugin, so a rule a plugin upgrade adds fails the test until it is decided. `i18n-plugin.mjs` builds each rule from the upstream one with `withReportFilter()` (`rule-hints.mjs`, the one wrapper under `withHint()`, `withoutFixes()` and the i18n filters): `i18n-filters.mjs` drops a `no-literal-string-in-jsx` report whose text has no letter after entity decoding (a space, punctuation, a number, `&nbsp;`; the entities are decoded because oxlint hands over the raw JSX text), a `missingValue` report on a `FormattedMessage` whose `values` is not an object literal, a `placeholderAdjacentToWord` report for a message in a script written without spaces, and a `no-invalid-icu` report on a call with a literal `ignoreTag: true`; every rule except `no-invalid-icu` drops its `parseError` reports, because eight rules parse the same message and one syntax error would be reported eight times; and every rule reports at most once per node, because oxlint merges reports of one rule at one location while ESLint keeps both. Hints carry their own leading separator (`. ` or a space, chosen by how the rule's messages end), as the Testing Library hints do, and `messages` replaces the two upstream messages that embed newlines or say "function call or variable" for an empty string. Fixes are dropped: the text is for a person to write, and ESLint 10 runs a fixer at report time. Exceptions that name an i18n rule id (`i18nRuleIds`) are dropped before `applyRuleExceptions` while the scope is off; `validateConfig` rejects one that names a `formatjs/` rule nitpicker does not run. `i18nRuleIds` are strict rules (`strict-rules.mjs`). `eslint-plugin-formatjs` is listed in `ESLINT_PLUGIN_PACKAGES`, so its version is part of the `eslint-lint` analyzer version, and its scope files are in `checks/policy-files.mjs`. `i18n-engines.test.mjs` lints the same sources with ESLint and with oxlint and expects identical findings. The `eslint-config/` folder holds what both scopes share (`scope-support.mjs`, `rule-hints.mjs`); each scope has its own subfolder (`react/`, `i18n/`) because the folder holds at most six source and six test files.
- **Third-party rule messages.** `withHint()` in `rule-hints.mjs` wraps a plugin rule so its messages end with a nitpicker hint (the exception route, or the allowed form), for rules that report by `messageId` and by `message`. The failure-message harness lints with the wrapped rules, so the hint is tested. Custom React rules (`react-no-effect-*`, `react-single-styling-approach`, `react-no-hardcoded-colors`) exist where no ESLint 10 plugin rule names the allowed form: `react-hooks/set-state-in-effect` is a React Compiler rule with a multi-paragraph message and no exception route.
- **Type-aware custom rules.** `nitpicker/exhaustive-union-predicate` sets `meta.docs.requiresTypeChecking`, so the oxlint engine hands it to the residual ESLint pass (`NITPICKER_DIFF_ESLINT_ONLY_RULES`) with every other type-aware rule, and it is registered in the typed entry of `strictTypedConfigFor()` beside the `@typescript-eslint` rules. It returns no listeners when the parser has no program. `nitpicker/no-forwarding-wrapper` is type-aware too: it compares the wrapper's and the callee's single call signature (parameter types and return type by identity, so a named alias or imported type counts and two structurally equal inline object types do not; the optional and rest flags of each parameter must match, and a signature with a type predicate, `asserts` included, on either side never matches) and finds the callee's binding through ESLint's scope analysis. `exhaustive-union-predicate` names the union from the alias of the value's declared type and decides "project or library" from where that alias, or an annotated declaration of the subject, is written, so a local binding that merely holds a library value is not mistaken for a project union. It reports only a chain in a value position (arrow body, `return`, variable initializer, assignment right side, looking through `!`, other logical operators and ternary branches), never a condition.
- **Component stories.** `structure/component-stories.mjs` is a project-level check run by the `structure` analyzer through `structure/project-findings.mjs`, next to the file limits. `syntax/exported-components.mjs` finds the exported real components of a file with the TypeScript parser (functions returning JSX, `memo` and `forwardRef` calls, classes extending `Component`; the parse kind follows the extension, and `.ts` files are not read). One walk of the source roots (`layout.projectCodeFiles`) collects both the components and the story files; story files (`storySuffixes` from `eslint-config/scope-support.mjs`, any code extension) are indexed by package directory and name, and a component file has a story when its stem (the folder for `index.*`) or any exported component name is in its package's index. Storybook presence is read per package, from the nearest `package.json` of the component. Both that and the more-than-half decision come from `liveProjectRoot`, the head checkout the runner is given on both snapshots, so a base run classifies exactly as the head run does: the comparison key includes the classification, so deciding it per side would turn every old finding into a new one when a pull request crosses the half mark. Below the half mark the findings are `descriptive` (listed, never failing); above it they are `enforceable`. Each component of a storyless file is one finding with the identity `component-story-missing:<Component>` (the file stem for an anonymous default export) and the component's line as its location. The rule id is in `RULE_IDS` and `RULES`; `TYPESCRIPT_PROJECT_EXCEPTION_RULES` is derived from the catalog (TypeScript-only structure rules) and `applyRuleExceptions` accepts those ids although no ESLint rule has them. The exception matcher and the copy-paste entry in the message come from `shared/rules/exceptions.mjs`, shared with the file limits. `structure/component-stories-cli.test.mjs` runs the check end to end through the CLI.
- **Prop-shape rules.** `eslint-plugin/rules/react-props/` holds the rules that read a component's props type. `react-components.mjs` finds components syntactically (a PascalCase function or `const` arrow, optionally inside `memo` or `forwardRef`, that returns JSX) and `syntax/component-names.mjs` owns the name test, which the structure analyzer's story check reuses. `nitpicker/no-runtime-exclusive-props-check` resolves the first parameter's destructured names (or `props.x`) and shares its `console` test with `no-production-console` (`consoleMethodOf`). `nitpicker/no-singular-and-plural-prop` expands unions, intersections and same-file aliases into branches (capped at 200) and pairs an optional `tag` with an optional `tags` array of the same type text inside one branch.
- **Type definitions.** `interface` is banned by a `no-restricted-syntax` selector, not `consistent-type-definitions`, because that rule cannot exempt `declare module` and `declare global` augmentations, which can only merge interfaces.
- **Failure messages.** Each case in `failure-messages/test-support/cases.mjs` has a `config`, a `banned` fixture that must fail, and an `allowed` wording (case-insensitive substring) the message must use to name the allowed form. Zod is a documented expectation of the preset, not a dependency.
- **Error wrapping.** Classified wrappers that sanitize external failures list `classificationIndex` and `unclassifiedValue`; only unclassified wrappers must carry the original cause.
- **Exceptions.** Lifted rules and paths come only from `nitpicker.config.json`; inline disables are banned, so this is the one way out.
- **Production policy.** `eslint-config/policy/production-policy.mjs` holds the production-wide rules that are plain ESLint options (`curly`, `no-eval`, `no-param-reassign`, `no-duplicate-imports`, naming convention, magic numbers, `regexp/no-super-linear-backtracking`) and wires the guard rules in `eslint-plugin/rules/guards/`. Naming and magic numbers run as `nitpicker/naming-convention` and `nitpicker/no-magic-numbers`: `eslint-plugin/rules/wrapped/` wraps the typescript-eslint rule and drops reports through `withReportFilter` (a `context` whose `report` is filtered), so the base rule's options and messages stay; a schema constant (also one derived from another schema constant, or from an imported PascalCase binding through a `SCHEMA_DERIVATIONS` method), a component-typed parameter, a number inside a module-level `const` initializer, an HTTP status in the status argument position of a response or error call (`STATUS_POSITIONS`) and a `toFixed` argument are the dropped reports. typescript-eslint marks `naming-convention` as needing type information, which would send it to the residual type-aware ESLint run under oxlint; the policy uses no `types` selector, so the wrapper clears that flag and, when the parser gives no TypeScript services (the oxlint bridge), hands the base rule empty node maps and no program. Route-handler names come from a native naming option instead: `defaults/eslint.config.mjs` passes `routeHandlers` when `usesRouteHandlerFramework` finds one of those frameworks in `package.json`, and `namingConvention` adds an exported-function selector filtered to the HTTP method names that accepts UPPER_CASE. `productionLayoutConfigFor()` holds `nitpicker/no-unknown-main-folder` apart: it reports on line 1 (the file's place, not its code), so it is not in `strictEslintRuleIds` and an edit to a legacy file does not fail; `defaults/eslint.config.mjs` adds it after the strict config, with `react: true` in a React project so the UI folders (`REACT_UI_FOLDERS`) and a feature's `ui/` pass. `strictPresetConfig` puts it first, so the scope entries after it can still replace an option. `no-restricted-properties` and `no-restricted-globals` replace like `no-restricted-syntax`: the `domain/` entry (`domainPurityRules`) comes after the production one and carries the full list. `no-process-access-outside-composition-root` is off for `layout.entryPoints` and config files; `no-module-level-mutable-state` skips `domain/`, which has its own readonly rules.
- **Heuristic guards.** Mutable module state, import-time effects and managed-resource construction match by name (`*Sync` calls, `*Client`/`*Pool` constructors, `create*` factories, `axios.create`), not by type, so a miss is possible and a false hit takes an `exceptions` entry. A try/catch in the composition root is deliberately not flagged. `no-unsafe-path-join` reads containment from the syntax, not from text: a `startsWith` whose prefix ends in a separator (`path-containment.mjs`), or `path.relative(...).startsWith('..')`, in an `if` before the call in an enclosing block whose branch exits, or around the call. `no-self-recursion` folds a callback into the enclosing function unless it goes to a timer or event registration (`DEFERRING_CALLEES`) or to a call that is a bare statement, which is how `emitter.on('change', () => watch())` stays allowed while `await limit(() => crawl(link))` is reported.
- **Boundary rule exceptions.** An `exceptions` entry may name a dependency-cruiser rule of `strictBoundaryRulesFor` (the `domain-*` rules); `exceptions.mjs` leaves those ids out of ESLint handling, and the architecture rules add the globbed `paths` to `from.pathNot`, so the paths are the importing files. `domain-does-not-reach-io-through-shared` uses `reachable: true`, which dependency-cruiser supports with `path` patterns only and reports with one depth-first path; `static-checks-runner.mjs` keeps a violation only when `sharedReachPath` finds a path over runtime (not type-only) edges whose first step is outside every feature and the composition root, and reports that path. A direct I/O import or an import of another domain file is left to the file's own rule. Via steps and targets are printed as dependency-cruiser resolved them, so a monorepo module such as `../libs/shared/clock.ts` appears with its `../`.
- **Unknown through aliases.** `no-unknown-in-domain` walks a same-file, non-generic type alias for any `unknown` (skipping type-parameter declarations and a `cause`/`error` slot) and follows the aliases it references. An alias imported from another file is resolved with the type checker, so the rule is marked `requiresTypeChecking` and runs in the residual type-aware ESLint run under oxlint, next to `no-mutating-method-in-domain` on the same `domain/` files; without parser services it checks same-file aliases only.
- **Analyzer cache keys.** `configured-analyzers.mjs` hashes each analyzer's adapter files and `configurationFiles` with `hashFiles`, which follows their relative imports (`shared/import-closure.mjs`), so a module a listed file imports is hashed without being listed; `POLICY_FILES` and `configurationFiles` only need the files a process loads by path. Each analyzer carries the list as `cacheKeyFiles`, and `configured-analyzers.test.mjs` checks that the import closure of every module its invocation starts (the runner, `--config`) is inside the hashed closure.
- **TypeScript-only compiler flags.** `TYPESCRIPT_ONLY_OPTIONS` (`exactOptionalPropertyTypes`, `noPropertyAccessFromIndexSignature`, `noUncheckedSideEffectImports`) are added to the type-check tsconfig only; the mutation tsconfig keeps `POLICY_COMPILER_OPTIONS`, and JavaScript projects get the three set to false. `typecheck/compiler-hints.mjs` appends the allowed form to their errors (TS4111: bracket access; a message naming `exactOptionalPropertyTypes`: `field?: T | undefined`) in the finding's message only; the identity hashes the compiler's own text, so existing findings keep their identity.
- **`strict-rules.mjs`.** The rule id list is written out because building `strictPresetConfig` loads typescript-eslint; `strict-rules.test.mjs` asserts it matches the real config.
- **Eslint runner.** Findings on comments (no-comments, ts-ignore, inline config) are anchored to the comment text, since the nearest syntax node would be the following code and editing it would change the fingerprint.
- **oxlint engine.** `oxlint/oxlint-plan.mjs` asks ESLint for each file's resolved config and groups files by rules, globals and `settings`; `oxlint-translation.mjs` turns each group into an oxlint override. oxlint reads `settings` only at the top of a config, so groups with different settings go into separate configs, one oxlint run each. `stage/` builds the temp stage and its directive rewrites, `oxlint-diagnostics.mjs` turns oxlint's JSON into ESLint results. Rules map to oxlint's ports, except `PARITY_BRIDGED_RULES` (ports that measured differently) and rules oxlint rejects the options of, which the runner retries as bridged. Bridged rules load from the ESLint plugin through `oxlint-bridge.mjs` under a `js-` alias, since oxlint reserves plugin names like `typescript-eslint`. Type-aware plugin rules oxlint cannot run go to a residual ESLint run limited by `NITPICKER_DIFF_ESLINT_ONLY_RULES`. tsgolint ignores `--tsconfig` and uses the nearest `tsconfig.json`, so oxlint runs in a temp stage of symlinks whose `tsconfig.json` is the lint config (relative `extends` made absolute, `noEmit` on, and `baseUrl` replaced by `paths` rewritten to absolute targets, since tsgolint drops `baseUrl` and rejects `paths` that rely on it). Files under `noInlineConfig` get a stage copy with their directives hidden from oxlint by a U+FEFF before the keyword (same length, so offsets hold; `no-irregular-whitespace` findings at those spots are dropped), plus ESLint's "has no effect" warning. `oxlint-` directives are hidden the same way in every file, since ESLint would not honor them, and `eslint-` directives naming a bridged rule get its `js-` name. Nested `tsconfig.json` files on the way to a linted file are left out of the stage, so every file is checked against the lint config. tsgolint's `tsconfig-error` diagnostics for a missing `types` entry or an option TypeScript 7 dropped are discarded, since typescript-eslint tolerates them; any other config error fails the analyzer. Rule messages are matched against the ESLint rule's message templates to recover its `messageId`, so finding identities match the ESLint engine where the text matches. oxlint spans are UTF-8 bytes and are converted to UTF-16 columns. `eslint/no-unused-vars` stays native with never-matching ignore patterns, because oxlint's defaults differ from ESLint's and bridging it changes scope analysis.
- **Test-code analysis.** `test-code-analysis.mjs` works on one file's syntax tree; calls into other modules are not followed. Per-test visitors report each node once however many tests reach it.
- **Runtime boundaries.** Roles select production modules by `modules` globs (relative to `src/main`) and list `forbiddenDependencies` and `forbiddenCalls` globs; the default declares none. Globstars do not traverse `..`, so relative spellings are resolved before matching.
- **Callback contracts.** Each entry names a `callee`, its `optionsArgument` index, `sourceCallbacks`, `correlatedCallbacks` (`{ name, inputIndex }`), `externalPublicationCallbacks` and `snapshotReadMethods`. Rules contain no consumer or file identities.
- **CRAP roots.** The analyzer expands a directory only when named `src` (or containing `src` folders); other roots are passed as the files inside them.
- **Type check engine.** `typecheck/typescript-program.mjs` returns the pre-emit diagnostics. The `native` engine (`native-diagnostics.mjs`) loads TypeScript 7's `unstable/sync` API from the `typescript-native` npm alias, opens the config as a project and collects config, program, syntactic, global, bind and semantic diagnostics (declaration ones when `declaration` or `composite` is set), the set `getPreEmitDiagnostics` returns. The CLI is not used because it stops after the first stage with errors, so a missing `types` entry would hide every semantic error. Diagnostics are reshaped into TypeScript 6 objects (a `createSourceFile` per file read with `ts.sys.readFile`, so BOMs and UTF-16 are handled as the project engine does, with `path` set for sorting; `messageChain` turned into a `next` chain; program diagnostics located in a `.json` config made file-less, because TypeScript 6 reports option errors without a location) and go through `sortAndDeduplicateDiagnostics`, so messages, symbols, order and identities match the `project` engine. Any config parsing error, a removed-option diagnostic (TS5102, TS5108) or an API that cannot start (no platform binary) makes the run fall back to the project's TypeScript. TypeScript itself is passed in as `ts` from `loadTypeScript`, which refuses a TypeScript 7 install because it has no `lib/typescript.js`. `resolveTool` checks an `npm:` alias against the aliased package's name and version. The analyzer version lists both TypeScript versions. `withoutProjectRoot` makes absolute paths in messages relative to the snapshot root, which differs between base and head and between runs.
- **Dependency cruiser.** The policy TypeScript config is linked into the analyzed root so its include globs resolve against analyzed sources; `typeScriptRoot` defaults to this package and is overridden for fixtures.
- **Reuse checks.** `shared-used-by-one-feature` runs in the `coupling` runner (`coupling/shared-usage.mjs`, `coupling/evaluate-coupling.mjs`: the feature and shared patterns are `architecture/strict-layout.mjs`, and the runner hands the head policy's exceptions in); the other five run in the `structure` runner through `structureProjectFindings()` (`structure/reuse/`); `sibling-copy-edit` (`structure/reuse/rules/sibling-copy-edits.mjs`) also reads the base checkout the head snapshot gets as `baselineRoot`, and reports nothing in the base snapshot or a run without one. It decides which copies were edited by comparing each head file with the base file at its old path: the diff engine writes the renames it already detected (`layout.moves.files`) to a temporary file (`git/patches/moves-file.mjs`) and hands its path to the head run of each quality-area analyzer as `--baseline-moves-file`, the structure runner passes them on as `baselinePaths` (`quality-areas/base-paths.mjs`), and a file whose text equals its base file is never parsed. They read each tree's own `package.json` and `tsconfig.json` (imports resolve through the shared resolver in `modules/module-resolution.mjs`; a workspace package linked into `node_modules` resolves to its source, and `structure/reuse/reuse-paths.mjs` maps a path in the live checkout that a snapshot's `node_modules` links to back into the snapshot, for the structure checks and the coupling graph alike), except that the React scope and the icon package are decided once from the head checkout (`react.enabled`, `react.iconPackage` in the head policy). Their results depend on files the runners import, so `coupling/check-files.mjs` and `structure/check-files.mjs` list the entry modules of each check: the cache key hashes their import closure, and a new module is covered as long as an existing entry imports it. `layout.mjs` holds the generated-file test (`generated/`, `__generated__/`, `*.generated.*`, `*.gen.*`, `*.pb.*`, `*_pb.*`) that source selection, the project code scan and the svg scan share.
- **One import graph per side.** `dependency-architecture`, `coupling`, `test-runtime` and `entry-points` all read `loadDependencyGraph` (`adapters/dependency-graph/project-dependency-graph.mjs`): one dependency-cruiser run over the existing graph roots with the architecture config, shared through the build directory above. Architecture reads `summary.violations`; the others read `modules`. Coupling and entry-points restrict themselves to their own roots (`internalEdges`, `isSourceUnderRoot`, `startsWith(root/)`), so the test roots in the graph do not change their results; test-runtime uses every module, and its roots are the same as before, so its input is unchanged. The key covers project, policy files, roots, exclusion, `--include-only` and the cruiser binary; a request that differs in any of them cruises on its own. Entry points whose source root is not a graph root cruise that root directly.
- **Dependency hooks.** A hook has `language`, `manifests` (the first marks a project; if any differs from the live policy root the snapshot needs its own install instead of a link), `directory`, and `install(projectRoot)`, which installs a regular directory and cleans up and throws on failure.
- **Unused props, options and exports.** `structure` builds one TypeScript program (`unused-api/analyze.mjs`) from the layered policy `tsconfig` that the type check uses (so `extends`, `paths` and project references resolve the same way, parsed with `allowJs`), plus root `*.config.*` files, `scripts/`, and every code file of the other workspace packages, whose names `workspace/entries.mjs` maps through `paths` to the source entry their manifest names (`source`, `types`, `main`, `exports`) or to a source root's `index`, and `name/*` into the source roots. The program sets `types: []` so no `@types` package is parsed, and it is not built at all when a syntax-only pass over the source files finds no component with props and no options parameter. Targets are registered by declaration node (function declarations, `const` functions, the function inside `memo` or `forwardRef`, and `const Y = memo(X)` or `export default memo(X)` aliases); members whose props or options type another declaration also uses (`syntax/shared-types.mjs`) are dropped, as are parameters typed by a type parameter. Then one pass over every file (`references/`) resolves JSX tags, call callees, `createElement`, `jsx` and `cloneElement` calls and `X.defaultProps` assignments through imports, aliases and re-exports with the checker (`getSymbolAtLocation` plus `getAliasedSymbol`) and records, per target, which props or options each reference passes and from which kind of file (production or support: the layout's test files and fixtures, stories, `.storybook` and `test-support`). `cloneElement` props count for every component. An identifier that refers to a target in any other position, and every export of a module loaded by `import()`, `require()` or `import.meta.glob` (a template-literal specifier loads every module under its static prefix) or used as a namespace value, is an escape and ends the judging of that target. Members count only when a declaration lies in an owned file: a production TypeScript file of the project that is not generated. Identity is `<name>.<member>` (`#n` for repeats), so no line number or file moves it. `dead-code` runs knip a second time with the config of `test-only/production-config.mjs`: the normal config with test, `__tests__` and story globs negated in `project`, test entries dropped and the test-runner plugins turned off, so scripts and plugin configs stay entries (knip's `--production` would drop them). The second run's `exports`, `types` and `files` that the normal run does not list are `test-only-export` (`files` under `test-support/` excepted). A package counts as published when its `package.json` has a name, is not `"private": true` and has one of `main`, `exports`, `bin`, `files` or `publishConfig`; `workspace/packages.mjs` finds workspace members from `workspaces` or the `packages:` key of `pnpm-workspace.yaml` (with `!` negations), looking for the workspace root no higher than the repository root. Both runners (`runners/unused-api.mjs`) turn a failure into a tool-error finding, so the analyzer's other findings still report.
- **Public contract usage.** Declaration identity keeps unrelated same-name methods and test-only calls from counting as consumers, so results are stable for a differential gate.

## JavaScript preset (`languages/javascript/`)

The JavaScript preset reuses the TypeScript pipeline; `languages/javascript/preset/` holds only what differs.

- **Preset channel.** `resolveHeadPolicy` copies `preset` into the head policy file only for `javascript`, so the TypeScript policy and its cache key do not change. `readLayout` turns it into `layout.javascript` and the extension lists every runner reads from the layout: `extensions` (`ts`, `mts`, `cts`, `js`, `mjs`, `cjs`; no `jsx` or `tsx`, so a `.jsx` file is neither a source nor a test file), `entryExtensions` (the same, `js` first) and `formatExtensions` (the Prettier patterns). `presetAnalyzers` returns `javascriptAnalyzers()` (same checks, built from the JavaScript layout) and `applyLayout` rebuilds from `resolveLayoutFor(headPolicy)`. `javascript-preset.mjs` is hashed into every analyzer whose config it shapes.
- **Generated configs.** The `tsconfig.quality.json` and `tsconfig.stryker.json` rewrites add `allowJs` and `checkJs` (the first also `noEmit`); with a project `tsconfig.json`, or a `jsconfig.json` when there is none, they extend it. `knip.json` gains `.js/.mjs/.cjs` entries and config files, and `jscpd.json` the `javascript` format next to `typescript`, because jscpd's `typescript` format reads only `.ts` and `.mts`. Stryker's TypeScript checker reports a mutant that fails `checkJs` as a compile error, so JavaScript mutants are killed by types as TypeScript ones are.
- **ESLint dialect.** `eslint-dialect.mjs` rewrites each strict config entry whose rules change: the original entry is kept for `.ts`, `.mts` and `.cts` files and a copy with the dialect rules is added for `.js`, `.mjs` and `.cjs` files (the `files` patterns are intersected with the extension glob, so the entry's own scope is kept). The copy drops the type-syntax rules, `@typescript-eslint/no-require-imports` and the `no-restricted-syntax` selectors that name a `TS*` node, lets the property-assignment selector of `domain/` skip `module.exports` and `exports.x`, passes `jsdocTypes`, `jsdoc` or `commonJsExports` to the four rules that map to JSDoc or CommonJS, and `no-var`, `prefer-const`, `prefer-rest-params` and `prefer-spread` are added (typescript-eslint enables them for TypeScript files only). The mapped rules keep their severity and still accept an exception. The dialect is applied before exceptions.
- **JSDoc parser.** `jsdoc.mjs` accepts one grammar per allowed tag (type in balanced braces, then a name where the tag has one) and reports any other text as prose. A `@type` is a cast only when the comment is directly followed by `(`. `any`, `*`, `null` and the `?T`, `T?` and bare `?` forms are looked for outside string literals and object keys. `unknown` is reported in `@param`, `@property` and `@prop` anywhere, and in the other type tags only inside braces or the parameter list of a function type, which is where the TypeScript rule finds a property or parameter.
- **CRAP on JavaScript.** `@barney-media/crap-typescript-core` selects files by a `.ts`/`.tsx` suffix list it does not let callers change. For a JavaScript project `crap/analyze.mjs` registers `crap-extensions-hook.mjs`, a module-load hook that rewrites that list in the library source before it is imported; the hook throws when the library text differs, so a version bump fails loudly (`crap.test.mjs` also asserts that `.js`, `.mjs`, `.cjs` and `.ts` files are measured). The parser reads JavaScript as TypeScript, which is why `.jsx` is not supported.
- **Constants in `quality-areas-runner.mjs`.** The module-level `invokedPath` block runs the runner on import, so the constants it uses are declared above it. Declared below, they were still in their temporal dead zone when a failing test reached the failure formatter, which crashed the coverage check instead of reporting `tests-failed`.

## Java preset (`languages/java/`)

Gradle runs once and yields findings for all tools.

### Java report directory

`gradle -I languages/java/gradle/nitpicker.init.gradle -Pnitpicker.reportDir=<dir> nitpickerJava`. `collectJavaFindings` makes `<dir>` a fresh temporary directory outside the project and removes it afterwards, so a build script that writes to `build/nitpicker` changes nothing nitpicker reads. When the root build (`gradle.parent == null`) has evaluated its projects, the init script writes `<dir>/modules.json`: `[{ key, path, dir }]`, one entry per project that applies the `java` plugin, in both presets (the Kotlin JVM plugin applies it too), `key` `root` for the root project and `module-<path>` otherwise, the path without its leading `:`, with `_` written `_u` and `:` written `_c` so two paths never share a key, `dir` the project directory relative to Gradle's current directory. Each project writes its reports to `<dir>/<key>/`; without `nitpicker.reportDir` (a manual run, the e2e tests) to `<project>/build/nitpicker/`. Every path in a report and every root in `manifest.json` is relative to Gradle's current directory, so a subproject's paths carry its folder. `readReportModules` (`adapters/gradle-reports/report-modules.mjs`) throws when the list is empty or a listed project has no `manifest.json`; findings are read per project, and a finding with path `.` of any project but the root gets `@<project path>` appended to its identity, so adding a project does not change the root's identities. A project without tests still gets a JaCoCo report: `nitpickerJacocoEmptyData` writes an empty execution data file that `jacocoTestReport` always reads, so its methods are reported as uncovered; a project without main classes may have none. Errors never name the temporary directory. Projects of an `includeBuild` composite build and `buildSrc` are separate builds: the init script's `gradle.parent == null` guard leaves them out, so they are not analyzed. A caller that needs the reports afterwards passes `reportDirectory` to `collectJavaFindings`, which then neither creates nor removes it. File limits, coupling, inline suppressions, Spring configuration and duplicates run once over the merged manifest. Coupling (`builds/project-wide.mjs`, shared with Maven) writes the `jdeps.txt` and `jdeps-classes.txt` of every project that has them into `<dir>/project/`, and reads them in place only when the root project is the only one, so a one-project build keeps its identities. A project's names depend on its folder alone, never on the number of projects: in the merged files a class of a project other than the root, even a lone one, is written `<folder>/<class>` (`<folder>/(root).<class>` in the default package), so its package is `<folder>/<package>`; an edge target is the class of the source's own project when it declares it, else of the one project that does, and an edge whose target several other projects declare is dropped. Each class's file is looked up in its own project's source roots and passed to `readCouplingFindings` as `files`.

- **Report files** (in each project's report directory): `pmd.sarif` (PMD over every source set, SARIF 2.1.0, plus `spring-ruleset.xml` when the compile classpath has `spring-context` or `spring-boot`), `spotbugs.sarif`, `format.txt` (google-java-format `--dry-run`: one file needing a reformat per line), `jacoco.xml`, `checkstyle.xml` (main) and `checkstyle-<source set>.xml` (every other source set), `archunit/*.xml` (JUnit XML of the project's `*ArchTest`/`*ArchitectureTest` classes; `-Pnitpicker.archunit.includes` overrides the patterns), `structure.json` (`StructureMetrics.java`: per method `signature`, `parameterTypes`, `start`, `end`, `lines`, `statements`, `maxControlNesting`, `parameters`, `complexity`, `privateEmptyConstructor`), `pit/mutations.xml` (absent without main classes), `test-results/<task>/TEST-*.xml` (the JUnit XML of every test task in the run except `nitpickerArchunit`, copied by `nitpickerJava`; read for slow tests, and Surefire and Failsafe write the same format), `jdeps.txt` and `jdeps-classes.txt`, `manifest.json` (tool versions, `moduleKey`, `sourceRoots`, `testSourceRoots` = every source set but main, `resourceRoots`, `spring`). With `-Pnitpicker.kotlin=true` also `detekt.sarif`, `ktlint.sarif` or `ktfmt.txt`, `kotlin-metrics.json`, and the `kotlin*` manifest keys. The report directory root also holds `duplicates.json` and `kotlin-duplicates.json`, written by the Node side.
- **Structure metrics.** `StructureMetrics.java` runs as `java StructureMetrics.java <output.json> <projectDir> <sourceRoot>...` in the JDK's single-file source mode (task `nitpickerStructure`, no dependency beyond the JDK that runs Gradle). It parses, never compiles, the main sources with the compiler tree API and writes one object per method and constructor; members of nested, anonymous and local classes are their own entries, lambda bodies count towards the enclosing method. Fields: `lines` (last line - first line + 1, annotations and modifiers included, Javadoc not), `statements` (every statement below the body except blocks), `maxControlNesting` (deepest nesting of `if`, `for`, enhanced `for`, `while`, `do`, `switch` and `catch`; an `else if` stays on the level of the `if` it continues), `parameters`, `complexity` (1 + `if`, `for`, enhanced `for`, `while`, `do`, `catch`, `?:`, `&&`, `||` and each non-default `case`, an arrow case or a case with several constants once; a switch expression or pattern switch whose arrow cases each hold one expression or a `throw` counts once plus once per `when` guard, never more than its cases), `signature` (`Owner.method(parameter types)`, the CRAP identity), `parameterTypes` (without generics or package, arrays and varargs as `Name[]`, a type variable of the method or an enclosing class as its first bound, `Object` without one) and `privateEmptyConstructor`. A syntax error prints `file:line` and the compiler message and exits with status 1, so the task fails instead of dropping methods.
- **Fake Gradle for tests.** `adapters/fixtures/fake-gradle.mjs` stands in for Gradle in tests that run without Java (`NITPICKER_GRADLE`). In the project directory: `GRADLE_FAIL` fails the run with its text; `NO_REPORTS` writes an empty `modules.json`; each line of `violations.txt` is a PMD violation in `src/main/java/demo/A.java`; `jacoco.xml` and `mutations.xml` become those reports; `modules.txt` lists more projects, one directory per line, each with the same reports under its folder and key `module-<directory>`; a project folder's `jdeps.txt` and `jdeps-classes.txt` are copied into its reports. With `-Pnitpicker.kotlin=true`, `detekt.txt` (`rule :: message` or a message for `detekt.style.MagicNumber`), `ktlint.txt` (`rule|message`), `kotlin-format.txt` and `kotlin-metrics.json` feed the Kotlin reports. Reports go to `-Pnitpicker.reportDir`; the arguments are kept in `build/gradle-args.json`.
- **Project settings the init script overrides.** After evaluation it resets the project's JaCoCo filters (`test.jacoco` includes, excludes and class-loader excludes; `jacocoTestReport.classDirectories` back to the main output) and replaces the Checkstyle config of every Checkstyle task. `pitest-junit5-plugin` and a launcher are on PIT's classpath only when the test runtime has `junit-platform-engine`. PMD's `TestClassWithoutTestCases` runs from a generated `pmd-tests.xml` that excludes the main source directories, as the Spring rules run from `pmd-spring-main.xml` that excludes the test ones.
- **Gradle failure text.** `condenseFailure` (`adapters/gradle-wrapper/failure-text.mjs`) drops the JVM's `Picked up JAVA_TOOL_OPTIONS` notices, PIT's `INFO` progress lines, `[ant:checkstyle]` warnings and `SLF4J(W):` no-provider warnings (the Checkstyle tasks also run with `showViolations = false`). When the text is still too long it keeps Gradle's failure block (from `FAILURE:` or `* What went wrong:`, without the `* Try:` hints) whole, every distinct `Caused by:` line before it, and as much of the start as fits, cutting the middle; without a failure block it keeps the start and the end.

### Ingesters

Ingesters turn tool reports into findings:

- **Maven builds.** `detectJavaBuild` (`languages/java/builds/java-build.mjs`) picks the build; `languages/java/maven/` writes the same reports per module in `<module>/target/nitpicker` and `readModuleFindings` (`builds/java-modules.mjs`) prefixes each module's findings. The tool versions on both sides come from the init script's `def pinned = [...]` map, parsed by `readPinnedTools` with a regex, so keep that map one `name: 'version'` pair per entry. The build runs `test`, or `verify` when the effective POM of any module binds maven-failsafe-plugin's `integration-test` goal in an execution that the project does not keep off (`skipITs`/`skipTests` properties, `skip`/`skipITs`/`skipTests` configuration, phase `none`): `runsFailsafe` from `describeModule`, arguments from `lifecycleArgs` in `maven-project.mjs`, which adds `-Djacoco.haltOnFailure=false` and the skip properties of signing, publishing, network and release-check plugins (listed in java-preset.md). Failing Failsafe tests are tool errors like failing Surefire tests, and their reports are copied to `test-results/failsafe/`. Surefire and Failsafe reports and coverage files count as fresh when modified at most 2 s before the build started (file systems with coarse timestamps); our JaCoCo file is `target/nitpicker-jacoco.exec`, which the Failsafe JVM appends to through the same `argLine`, and every fresh file among it and the `destFile`s of the project's `prepare-agent` and `prepare-agent-integration` executions goes to one JaCoCo report. Maven runs at most 15 minutes; a timeout is a `java/maven-failure` that names the limit. The resolved tool classpaths are cached per user in `$XDG_CACHE_HOME/nitpicker` (else `~/.cache/nitpicker`), keyed by a hash of the tool coordinates; base and head run one after the other, so they never resolve at the same time.
- **XML text.** `parseXml` sets `text` on a leaf element (entities decoded, comments dropped, CDATA kept verbatim); an empty leaf has no `text`.

- **Common.** Repeats of one identity within a report get `#n` in report order. The XML parser reads elements and attributes only and throws `TypeError` when malformed.
- **SARIF** (PMD, SpotBugs). Identity is `partialFingerprints` (sorted) when present, else a hash of rule, path and symbol. Absolute `file://` URIs (PMD) and source-root-relative paths (SpotBugs) are made project-relative; results outside the project are skipped. SpotBugs `note`-level results are promoted because the tool already runs at the configured threshold, and its subject comes from message arguments since the text is generic.
- **Checkstyle.** Identity hashes the check `source`, path and message; the line is location only.
- **ArchUnit.** One finding per violated rule and offending class, identified by the fully qualified class; line numbers and violation counts never take part. The path is resolved by `options.resolvePath(className, fileName)`, falling back to the declaring test class. A failed case without violation lines yields one `test-failure`.
- **CRAP.** `crap = ccn^2 * (1 - coverage)^3 + ccn`, with coverage the lower of line ("statement") and branch coverage. `crap-score-limit` when over `options.limit`; `crap-coverage-unknown` when no JaCoCo method matches. Identity is the method signature (`Calc.classify(int, int, String)`, from `structure.json`) plus `#n`. Java's complexity is `complexity` of `structure.json` (`StructureMetrics.java`), and a `privateEmptyConstructor` entry is left out (JaCoCo often omits those, and their complexity of 1 cannot exceed the limit). A JaCoCo method matches a function when file and name agree (`<init>` is the class name) and its first line lies in the function's range, or, for a constructor, when the descriptor's parameter types match `parameterTypes` (aligned at the end, so synthetic leading parameters of inner classes and enums are skipped; `StructureMetrics.java` writes a type variable as the erasure of its first bound, as the descriptor has it). The JaCoCo `<init>` of a class with field initializers starts at the first initializer, before the constructor. A function at 100% coverage gets `crapScoreLimitCovered`, Java's unknown coverage `crapCoverageUnknownJava`. `options.sourceRoots` maps the project-relative paths to JaCoCo's package-relative ones. `ingestCrapFunctions` is the same ingester over already parsed functions; its `selectMethods` option replaces the name-and-range match (the Kotlin preset passes `selectKotlinMethods`).
- **Format check.** One `format` finding per file in the list; identity is the constant `format`.
- **Coverage.** Go coverprofile gives a `statement-coverage` metric per file only (blocks lack function names, and line-based identity is not allowed); `options.modulePath` is stripped from import paths. JaCoCo gives `line-coverage` plus `uncovered-method` (class and method name+descriptor); `options.sourceRoot` is prepended. lcov gives `line-coverage` plus `uncovered-function`.
- **PIT.** Follows `docs/mutation-testing.md`: no score gate, new surviving or uncovered mutants fail, other non-killed statuses are report-only, counts go to `mutation-summary`. A mutant is identified by class, method, mutator and description plus its occurrence `#n` among identical keys (by line, then block index). Mutants with unresolvable sources (generated code) are skipped.
- **Duplicates.** jscpd runs once per build, per existing main source root of the merged manifest, writing `duplicates.json` in the report directory as `{ runs: [{ root, report }] }`. Findings match the TypeScript ones: `duplicate-clone` and `duplicate-clone-size`, identified by file pair, cloned-text hash and occurrence.

## Kotlin preset (`languages/java/`)

The Kotlin preset is the Java preset with `kotlin: true`: same init script, runner and ingesters. User-facing behavior is in `docs/kotlin-preset.md`; the protocol details:

- **Switch.** `gradle -Pnitpicker.kotlin=true` turns the Kotlin tasks on in modules applying `org.jetbrains.kotlin.jvm`; without it the init script is the Java one. The runner takes `--preset kotlin`, `--kotlin-formatter` and `--kotlin-detekt-config` (from `kotlin.formatter` and `kotlin.detektConfig`). Gradle always runs with `--no-configuration-cache` (both presets): the init script registers tasks and reads project state at execution time, which a project's `org.gradle.configuration-cache=true` would fail on.
- **Properties.** `kotlin-tools.mjs` resolves, per snapshot, what the init script needs and passes it as `-Pnitpicker.kotlin.formatter=<ktlint|ktfmt|none>`, `.ktfmtStyle=<kotlinlang|google|meta>`, `.editorconfig=true` (the project has one) and `.detektConfig=<absolute path>`. Without the formatter property the init script runs no format check. The analyzer is named `kotlin`, and its tool-error and `baseline-expansion` findings use that name.
- **Reports.** `detekt.sarif`, `ktlint.sarif` (ktlint's SARIF reporter, relative paths) and `ktfmt.txt` (project-relative Kotlin files, one per line); only the detected formatter's file is read. Skipped Java tools in a Kotlin-only module write empty reports so the Nitpicker side reads one layout. `manifest.json` in this mode: `sourceRoots` are the Java roots only, `kotlinSourceRoots` the Kotlin plugin's source directories (which include `src/main/java`), `kotlin: true`, `kotlinFormatter`. `readKotlinFindings` throws when `kotlin` is absent, so a project without the Kotlin plugin is a tool error and not an empty pass.
- **Java-only class tools.** `analyzedClassDirs` is the output of `compileJava` in this mode (all main class directories otherwise); SpotBugs reads it. SpotBugs gets the rest of the runtime classpath as `-auxclasspath`. PIT reads `mutatedClassDirs` (all main class directories, Java and Kotlin) in both presets, and jdeps reads every main class directory in both modes.
- **Kotlin metrics (KT3).** `languages/java/gradle/KotlinMetrics.java` is run by task `nitpickerKotlinMetrics` as `java -cp <kotlin-compiler-embeddable and its dependencies> KotlinMetrics.java <out> <projectDir> <kotlinSourceRoot>...` and writes `kotlin-metrics.json`: `functions` (one object per unit: `file`, `name`, `start`, `end`, `lines`, `statements`, `maxControlNesting`, `parameters`, `complexity`, `inline`) and `files` (`file`, `package`, `classes`: the JVM names of its top-level classes and file facade). A syntax error exits the program with the file, line and pinned version (the sources compiled, so the compiler is too old). It builds a `KotlinCoreEnvironment` and needs an extension storage registered on the configuration (`FrontendConfigurationKeysKt.setExtensionsStorage`); that is compiler-internal API, so a bump of `kotlinCompiler` in the init script is tested with `npm run test:kotlin`. `kotlin-metrics.mjs` turns `functions` into structure findings (the Java path, `structureFindings`) and into CRAP findings (`ingestCrapFunctions` with `selectKotlinMethods`, which matches a function's JaCoCo methods by first line within its range, skipping `$default`, methods inside a unit of their own and the bridge a `@JvmStatic` function leaves in the outer class; `inline` units get no CRAP score; the JaCoCo file is found by `package/FileName.kt`, not by directory), and `files` into the module map `analyzeJavaCoupling` takes (`moduleOf`, `fileOf`).
- **Kotlin clones.** `runJavaDuplicates(projectRoot, { format: 'kotlin', rootsKey: 'kotlinSourceRoots', reportFile: 'kotlin-duplicates.json' })` after the Java run; the report is read with `readDuplicateFindings` and the same rule and tool name `duplicates`.
- **detekt and ktlint SARIF.** No fingerprints, so the glue sets `nitpicker/subject` from the message text with every whole number replaced by `#` (`\b\d+\b`: a name ending in digits keeps its digits), so a measured value does not change identity, and keeps the SARIF levels (`note` stays descriptive, unlike SpotBugs). Rule ids are kept in detekt's form `detekt.<ruleset>.<Rule>`.
- **Formatter detection** is a text search of the root project's build files (not Gradle API introspection), so it works for plugin ids, version catalogs and Spotless alike. Comments are removed first and a Spotless `kotlinGradle { }` block is cut out (its formatter formats the build scripts, not the Kotlin sources); a string literal that names the other tool still matches. `ktlint` in the build files beats `ktfmt`, and `ktlint_` keys in `.editorconfig` count only when the build files name neither.
- **Source directories** are the Kotlin plugin's main `srcDirs` that exist, are inside the project and are not under the build directory (generated code).
- **detekt config validation** is switched off by a second `--config` file (`languages/java/detekt/detekt-validation.yml`), listed after the project's and Nitpicker's, because the CLI exits with code 3 on rulesets of plugins it does not load.
- **Missing reports.** A build where no project applies the plugin writes an empty `modules.json`; `readReportModules` turns that into an error naming the plugin, and a listed project without reports into one naming the project (both presets).
- **Branch coverage** (`changed-branch-coverage`) reads the source text of every file under `jacocoSourceRoots` (Java roots plus `kotlinSourceRoots`). A `.kt` line is dropped when `isCompilerGeneratedBranchLine` (`kotlin-branches.mjs`) finds a suspension call and nothing that can branch in its code (string literals, comments and type arguments removed); every other line is kept, since the JaCoCo XML has branch counts per line and no instruction detail and a statement that spans lines is reported on the line of its operand. A kept line with a suspension call gets the `arms` hint in its message. Report files are located by `sourceLocator` (`kotlin-reports.mjs`): by directory first, then, for `.kt`, by file name and `package` declaration; the same lookup resolves PIT's `sourceFile`, and a `.kt` file with missed branches that is not found (outside `kotlin`/`kotlinx`) is a descriptive `branch-source-not-found`. The measurement behind it is in `docs/kotlin-preset.md`.
- **Mutation.** `pitFindings` resolves a class's source file under `jacocoSourceRoots` and `reportOnlyKotlinMutants` turns `mutant-*` findings of `.kt` files into `descriptive` ones (the `mutation-summary` counts are unchanged). The Java preset does not call it.
- **One-way rules** (`kotlin-rules.mjs`, `nitpicker-detekt.yml`). `ONE_WAY_RULES` is the list of rules in the yml with the sentence the gate appends when detekt's text does not name the allowed form (`addOneWayHint`, after ingestion, so identity, which is the detekt text, never changes); every rule also gets the exception route. `ForbiddenMethodCall` and the other rules with a `reason` field carry the allowed form in the yml instead. The yml follows the project's config in the `--config` list of the detekt task (only the validation file comes after it), and detekt gives the later file priority per key, so a project's `detekt.yml` cannot override it. Every ruleset and rule in the yml pins `active: true`, `excludes: []` and `includes: []`, and every rule `severity: warning` (the reader classifies SARIF `note` as descriptive, so a project's `severity: info` would otherwise un-gate the rule); `excludes: []` also replaces the default that skips `**/test/**` for `UnsafeCallOnNullableType`, which would skip a production package named `test`. `kotlin-rules.test.mjs` reads the yml and fails when its rules differ from `ONE_WAY_RULES` or one lacks a pin. `UseDataClass` has `allowVars: true` because `DataClassShouldBeImmutable` bans the `var` that `UseDataClass` would otherwise ask to turn into a data class. `runBlocking` is a `ForbiddenMethodCall` entry (type resolution finds the call whatever the import), so it shares the rule id, and the exception, of `run`, `with` and `also`. Lists in the yml replace the project's (detekt does not merge them); reading the project's yml to union them would need a YAML parser and a generated file per snapshot, and is not done.
- **Type resolution classpath.** Detekt 1.23.8 embeds Kotlin 2.0.21 (it resolved a 2.1.0 standard library, not a 2.4.21 one). The stdlib it needs for `run`, `with`, `also` and `!!` is therefore `kotlin-stdlib:2.0.21` (`pinned.detektKotlin`, the version in the detekt jar's `META-INF/compiler.version`), first on the classpath, and every `kotlin-stdlib*` jar of the project is dropped. With the project's 2.4 stdlib the same run reported nothing for those calls and wrongly flagged `?.` on values of an unresolved type. `--jdk-home` is the Gradle JVM's `java.home`; without it JDK types (`StringBuilder`) do not resolve. Bump `detektKotlin` together with `detekt`.
- **Exceptions.** `--exception <rule>:<glob>` (split at the first colon, one per path) reaches `applyJavaPolicy`, which drops findings of that exact rule id under the glob on both snapshots. `validateKotlinOptions` accepts only `ONE_WAY_RULE_IDS` so a typo is an error. Python can reuse the mechanism.
- **Inline suppression.** `kotlin-suppressions.mjs` reads the string literals inside `@Suppress`/`@SuppressWarnings` with any use-site target, after `kotlin-literals.mjs` has masked the source: one pass over comments (nested block comments), strings with `${}` templates, raw strings and character literals, which replaces each string by a numbered placeholder so that a comment opener in a string, or an annotation in a string, does not matter. `isBannedSuppression` bans every token that can target a detekt or ktlint rule: `all` in any letter case, anything starting with `detekt` or `ktlint` followed by `.`, `:` or the end, a detekt ruleset name, and a PascalCase token (every detekt rule id; detekt honors the bare id). Kotlin compiler diagnostics are UPPER_SNAKE or lowercase (`UNCHECKED_CAST`, `unused`) and stay allowed. detekt's `ForbiddenSuppress` cannot do this alone: a suppression of `style` or `all` also hides the `ForbiddenSuppress` finding on the same annotation.
- **Fixture cases.** `test-support/kotlin-rule-cases.mjs` (next to the Kotlin rules) holds, per rule, the banned and the allowed source (`{name}` stands for the file's class name, `Banned` or `Allowed`), the detekt message recorded from the real run, and the wording the final message must contain. The CI test checks the wording against the recorded message; the end-to-end test checks the recorded message against real detekt, so a detekt or yml change that alters a message fails there.

## Python preset (`languages/python/`)

Two analyzers, `python` and `mutation` (which depends on `python`, so it runs after it and is skipped when it had a tool error). One runner process per snapshot and analyzer (`python-runner.mjs --part python|mutation`); the `python` part runs the tools and reads their reports from a temporary directory, the `mutation` part keeps its results in memory. The only things written into the analyzed tree are mutmut's `mutants/` directory and, when the project has no mutmut configuration, a `[tool.mutmut]` table appended to the snapshot's `pyproject.toml` (created if absent). Reports in the temporary directory: `ruff.sarif`, `format.txt`, `coverage.json`, `coveragerc`, `manifest.json` (`formatter`, `formatterDetected`, `sourceRoots`, `testsRan`), `type-check.json` (`checker`, `output`), `python-files.txt` (the `.py` files under the source roots, shared by the file-based steps), `rules.json`, and `structure.json` (`languages/python/metrics/structure_metrics.py`: the limit metrics and the cyclomatic complexity). Each tool step lives in its own module (`python-test-runner.mjs`, `python-types.mjs`, `python-ast-rules.mjs`) and runs through `python-process.mjs`.

- **Environment.** Always that of the live checkout (`liveProjectRoot`), never of the snapshot: lockfiles exist in both, but `.venv` does not exist in a work tree. Detection order: `python.environment`, `uv.lock`, `poetry.lock`, the `uv.lock` of an ancestor whose `pyproject.toml` has `[tool.uv.workspace]`, `.venv`, `PATH`. `uv` runs `uv run --project <live> --no-sync -- <tool>` (no `--project` or no `--no-sync` would create or sync an environment) and only after `<workspace root>/.venv` (or `UV_PROJECT_ENVIRONMENT`) is seen to exist, because `uv run --no-sync` creates an empty `.venv` when there is none. Poetry cannot be used through `poetry run` because `-C` also changes the working directory of the tool, so its environment path is asked once (`poetry -C <live> env info --path`) and used like a virtualenv. A virtualenv launcher resolves a tool in its `bin` and otherwise leaves it to the `PATH` (`bin` first).
- **Snapshot sources.** `PYTHONPATH` starts with the snapshot's import roots (a source root without `__init__.py` imports from itself, a package from its parent), then the inherited value; the tools run with the snapshot as working directory. This is the only thing that makes base tests import base code when the environment has an editable install of head; it is tested for real in the e2e test.
- **Version and cache key.** `resolveVersion` runs `--version` of ruff, black (when it is the formatter) and coverage plus the pytest and mutmut import probes (`importlib.metadata` for mutmut, because `mutmut --version` fails where mutmut cannot guess its source directory) in the live environment, and throws only when the environment itself is unusable (the scheduler reports that as a tool error of each analyzer on each snapshot, with no rule, and does not run it); a missing tool reads `tool@missing` and fails in the runner. `python` has the versions of ruff, black, coverage and the test runner, `mutation` those of mutmut and pytest. The configuration hash covers the analyzer name, the `python` settings, every non-test, non-fixture file under `languages/python/` and the transitive imports of `python-runner.mjs` (followed from the source, so a file the runner starts to import cannot be forgotten).
- **Tool errors.** Each step (`ruff`, format, tests plus `coverage json`) fails independently and all failures are reported, one finding each, rule `<step>-failed` (`tests-failed` is the TypeScript rule), identity the rule, path `.`. When any step failed no other finding of that analyzer is returned. An error without a `rule` property is `python-failed` (`mutation-failed` in the `mutation` part, whose only step is mutmut), with the analyzer as tool.
- **Format output.** `ruff format --check --diff` is parsed by its `--- path` / `+++ path` header pairs, because ruff's summary format differs between versions; black's by its `would reformat` stderr lines. Exit 1 without a parsed path is an error. Black exits 123 and ruff 2 when a file cannot be parsed; that is tolerated only when every `error:` line is a parse error (black words it `cannot format <path>: Cannot parse` or `cannot parse for target version`), because ruff check already reports the file. `exclude` globs go to ruff as `--extend-exclude` and to black as one `--extend-exclude` regex (`^/<glob regex>(/.*)?/?$`, black matches `/<relative path>`, with a trailing `/` for directories).
- **Test runner.** Decided from the project (`python-test-runner.mjs`), never from importability: a silent fall back to `unittest` runs none of a pytest project's tests and exits 5 or 0. `pytest` with a failing import probe is `environment-failed`. One probe prints the pytest version and whether `pytest_cov` and `xdist` are importable; `--no-cov` and `-n0` are added only for installed plugins, since an unknown option is a usage error (exit 4). `-o cache_dir=<report dir>` replaces `-p no:cacheprovider`, which broke `--lf` and `--sw` in `addopts`. `unittest discover -s tests` needs `-t .` when `tests/` is a package, or relative imports in it fail. `manifest.json` `testsRan` is false on exit 5 or `Ran 0 tests`; the reader turns it into the enforceable `python/no-tests-ran` finding, which a comparison reports only when head lost its tests (a per-snapshot analyzer cannot see the other side, so it is a finding and not a tool error).
- **Ruff target version.** `--target-version` is the lowest of `requires-python`, poetry's `python` or `python_requires` (minimum 3.8, also the default); `--config` makes ruff ignore the project's own `requires-python`, so without it version-gated rules such as `B905` flag code that cannot use the fix. Not passed to `ruff format`, which reads the project's config.
- **Coverage.** Run through a nitpicker-owned `coveragerc` (branch on, parallel off, `source` the source roots) with `COVERAGE_FILE` in the report directory; `coverage json --fail-under=0 --ignore-errors`. Ingestion (`coverage-json.mjs`): `line-coverage` from `summary.covered_lines / num_statements` per file, `uncovered-function` for a function (not the module-level `""` entry) with statements and no covered line, identified by its qualified name. A file with no statements has no metric.
- **Structure and CRAP.** Details in `docs/python-preset.md`. The structure step lives in `python-structure.mjs`; it reuses Java's reader (`readStructureFindings`) and passes a Python function-text hash (common indentation removed, not every line trimmed, because indentation is syntax). `python-crap.mjs` reads the same `structure.json` and gives its functions to `ingestPythonCrap` (`ingestCrapRows` of Java underneath). There is no external complexity tool: `structure_metrics.py` computes the cyclomatic complexity from the `ast` module. Definition (McCabe, the decision points of the other presets; unlike TypeScript a lambda counts towards its enclosing function, and the `for` and `if` clauses of a comprehension count): 1 plus one per decision point in the function's own body, where decision points are `if` and `elif`, a conditional expression, `for` and `async for`, `while`, each `except` handler, each `case` of a `match` but a guard-less `case _` (the `default` of a `switch`, which ESLint's `complexity` rule and the Java and Kotlin metrics do not count either), each extra operand of `and` and `or`, and each `for` and `if` clause of a comprehension. `else`, `finally`, loop and `try` `else`, `with` and `assert` add nothing; lambdas and comprehensions belong to the enclosing function; nested functions and the methods of nested classes are entries of their own and add nothing to it. Control nesting treats an `elif` as the same level as its `if`, like `else if` in the TypeScript and Java analyzers; an `else:` block holding an `if` is one level deeper. The entries also carry `definition` (the `def` line) and `bodyStart` (first body line); a function whose body starts on its `def` line is left out of CRAP, because its statements share the line that runs at import. Coverage entries are joined to functions by qualified name (the names coverage.py reports) and line range, not `start_line`, which older coverage.py versions do not report. coverage.py keeps one entry per qualified name, so a function no entry covers (property setter pair, `singledispatch` `_`, conditional definitions) is scored from the file's per-line and per-branch data over its own range, minus nested functions.
- **Changed-branch coverage.** `coverage-branches.mjs` reads the same `coverage.json` (`executed_branches` / `missing_branches` as `[from, to]` arcs, a negative `to` leaving the scope), groups the arcs by `from` line and hands one entry per line to `branchCoverageFindings` (`shared/rules/branch-coverage.mjs`, minimum 95). Its tool name is `coverage-py`, not `coverage` (the TypeScript analyzer's), and `TOUCHED_CODE_RULES` in `shared/policy.mjs` lists `changed-branch-coverage` for `coverage-py`, so an uncovered branch on a changed or added line is new even when the base had it. Identity is `branch-source:<hash of the enclosing def/class chain and the whitespace-normalized line>`, with `#n` counted per path and hash among failing lines; the chain is derived from the indentation of earlier `def` / `class` lines, because the coverage JSON has no scope for a branch. The `coveragerc` also sets `omit` (test files), a fixed `exclude_lines` (`if TYPE_CHECKING:`, the `__main__` guard, `@overload`, `raise NotImplementedError`) and an empty `partial_branches`, so no pragma and nothing in the project's own coverage config applies. coverage.py gives no arcs for `try` / `except` / `finally`, so those are not gated. Java's `jacoco-branches.mjs` numbers identical lines per file, without a scope.
- **Mutation.** `python-mutation.mjs` (the `mutation` part) checks that mutmut is installed and 3.x from the same `importlib.metadata` probe, runs `mutmut run` with `PYTEST_ADDOPTS` extended by `-n0` when the pytest probe saw xdist (mutmut runs pytest itself, and the `-n` of the project's `addopts` makes it fail to collect stats and report every mutant as uncovered), and removes head's `mutants/` afterwards. On Windows it returns a descriptive `mutation-skipped` finding instead of running. pytest exit 5 under mutmut ("failed to collect stats. runner returned 5") yields no mutation findings, since `python/no-tests-ran` covers it; any other "failed to collect stats" adds the `also_copy` line. `python-mutation-data.mjs` reads `mutants/**/*.meta` (`exit_code_by_key`) with the generated and the original source; `languages/python/ingest/mutmut.mjs` splits the generated file into function blocks by indentation (a closing bracket at the `def` indent continues a wrapped signature), diffs `x_f__mutmut_orig` against `x_f__mutmut_N` on tokens, and hands `Survived` and `NoCoverage` (exit 0; 5 and 33) to the shared `mutantFindings`, plus a `mutation-summary` metric per status over all parsed keys. Keys exist but none matches `x…__mutmut_N` is a thrown error naming the supported range (`SUPPORTED_MUTMUT`, the one place the range is written in code). Identity `symbol|original→mutated#n`, `n` counted per status among equal keys in mutant order; the line comes from locating the original block in the real file. Exit 1 with "could not find any test case for any mutant" is accepted and turns the unchecked (`null`) results into 33. The `do_not_mutate` of a generated `[tool.mutmut]` is the test patterns plus each `exclude` glob and `<glob>/*` (mutmut matches with `fnmatch` against the project-relative path, where `*` also crosses `/`). Head's `mutants/` is removed after reading; base's stays so `python-mutation-reuse.mjs` can copy its `.meta` files (only those) into head when the name-status diff from the base commit to head lists nothing but added or modified non-test `.py` files under a source root, and only those of modules outside the changed files' reverse import closure (`import-scan.py`: a Python `ast` script run in the project's environment over head's source roots, edges to every module an `import`, `from … import` or relative import can name, files that do not parse have none; a failed scan reuses nothing).
- **Ruff identity.** The SARIF goes through Java's `prepareSarif` with the message text as the subject, so identity is `fp:nitpicker/subject=<message>`; ruff messages name the symbol, and repeats in one file get `#n`.
- **Type checker choice.** `detectTypeCheckers` scores each checker from the live checkout's hint files: a config (`[tool.mypy]`, `mypy.ini`, a `[mypy]` or `[mypy-...]` section, `[tool.pyright]` or `[ tool.pyright ]`, `pyrightconfig.json`) counts 2 and a declared dependency (a name anywhere on a line, so inline arrays count) 1; the higher score wins, and a tie or no hint at all probes `mypy --version` then `pyright --version` in the environment (`resolveTypeChecker`). basedpyright is not detected. It is read from the live root so both snapshots run the same checker, and it is part of the tool versions in the cache key.
- **mypy run.** `mypy --strict --explicit-package-bases --show-error-codes --no-error-summary --no-pretty --hide-error-context --no-color-output --cache-dir <report dir>/mypy-cache <source roots>` with `MYPYPATH` set to the snapshot's import roots (mypy does not read `PYTHONPATH`); exit 0 or 1 is a result, anything else `types-failed`. `--config-file` is a file generated in the report directory (`mypy-config.mjs`): the project's `[mypy]`, `[tool.mypy]` (pyproject) or `mypy.ini` section reduced to `plugins` (file plugins made absolute), `mypy_path`, `python_version`, `namespace_packages`, `custom_typeshed_dir` and per-module `ignore_missing_imports` and `follow_imports`, plus nitpicker's `exclude` as one regular expression; everything that skips or weakens checking is dropped, so no project setting can turn the gate off. `--python-executable` is the environment's `sys.executable`, because mypy otherwise introspects its own interpreter and misses the project's packages. Lines are matched as `path:line[:col]: error|warning: message  [code]`; notes and the summary are ignored. Identity is the message, `#n` per (file, rule).
- **pyright run.** A generated `pyrightconfig.json` in the report directory (`extends` the project's `pyrightconfig.json` or a `pyproject.toml` with `[tool.pyright]`, `typeCheckingMode: strict`, `enableTypeIgnoreComments: false`, `ignore: []`, `exclude` nitpicker's globs relative to the config (plus pyright's defaults) in place of the project's, `include` the source roots, `extraPaths` the import roots). `include` has to be relative to the config file (pyright ignores absolute entries with a warning); `extends` and `extraPaths` may be absolute. The JSON is read from the first `{` because the pip wrapper can print a notice first; only the first line of a message is the identity.
- **Rules script.** `nitpicker_rules.py` is stdlib-only and compatible with Python 3.8 and later; it takes a file list and a report path, parses with `ast` and finds comments with `tokenize`, and writes `[{rule, path, subject, line}]` sorted by path, line, rule and subject. Files that do not parse or tokenize are skipped. Messages are not in the script: `rule-hints.mjs` owns every message, so they are testable without Python.
- **Hints and exceptions.** `applyRuleHints` appends the allowed form (when the rule has one) and the exception sentence to enforceable findings of `ruff`, `mypy`, `pyright` and `python-rules` by rule id (a prefix for `PTH`); an entry with `exception: false` carries its own advice instead; other findings pass through. Identity is computed before, so a reworded hint never re-baselines; `on line N` and `from line N` are stripped from identity subjects (`withoutLineNumbers`), so moved code keeps its identity. `python.exceptions` filters findings by rule id (exact, or a ruff prefix such as `PTH` for ruff findings) and path glob after hints; the ids are validated when the config loads (`python-rule-ids.mjs`: the ruff selection, the `python-rules` ids, pyright `report*` names, mypy code spelling) and before `exclude` and the legacy inventory; the base snapshot uses the base's config, like every other setting.
- **Shared policy.** `exclude` and the legacy inventory are `configureJavaAnalyzer` / `applyJavaPolicy`, both language-neutral; `applyJavaPolicy` takes `inventoryTool` for the tool of a `baseline-expansion` finding.
- **Duplicates, coupling, import-linter.** More reports in the directory: `duplicates.json` (Java's `runJscpd` output shape; Python passes `together` to run once over all roots, with absolute names made project-relative, and reads it with its own `readDuplicateFindings`, which drops import-only clones; `runJscpd` always passes a nitpicker-owned `jscpd-config.json` so a project's `.jscpd.json` is never read), `imports.json` (`{ modules: [{ file, module, isPackage }], imports: { file: [{ level, module, names }] } }`: the module list comes from `python-sources.mjs`, the statements from `import-scan.py`, which only parses and never resolves) and `import-linter.txt`. Resolving imports to modules, packages and the stability graph is JavaScript (`python-coupling.mjs` into `buildCouplingReport` of `shared/rules/coupling.mjs`), so only the scan needs Python. A file the scan cannot parse is skipped silently. The import-linter text report is parsed in `ingest/import-linter.mjs`; its identity per chain ignores line numbers, and the order import-linter prints chains in is not stable, so tests must not depend on it.
- **Project root.** `resolveProjectRoot` accepts a `nitpicker.config.json` as a project marker beside `package.json`, because a Python project has no `package.json`.
