# Internals

Contributor notes on formats and protocols that code and names cannot carry. Source files stay comment-free (`nitpicker/no-comments`).

## Diff engine (`core/`)

- **Custom analyzers.** A `{name, command, args?}` config entry runs with the analyzed checkout as working directory, so a relative command resolves inside each side. It prints findings JSON on stdout and exits 0; stdout goes through the same parser as built-in analyzers, and a non-zero exit or invalid JSON becomes a tool error.
- **Exit codes.** New violations win over tool errors so CI can tell "violations" from "broken"; `overallStatus` reports tool health first.
- **Tool-error paths.** `runAnalyzers` rewrites tool-error messages (scheduler errors and `tool-error` findings) of a run on a temporary snapshot (`core/diff/snapshot-root/`): a path under the snapshot's project root becomes project-relative, the root itself becomes `base` or `head`. A run on the live project keeps its paths.
- **Analyzer environment.** Analyzers never see where the GitHub Actions job summary lives (`HOST_CI_OUTPUT_VARIABLES`): vitest and Stryker would append their own reports to it, and caught mutants read as test failures.
- **Cache stores.** A store keeps opaque text under a hex key, is synchronous and never throws: `get` returns undefined on any miss or failure, `put` returns whether the value was stored. The local directory is `NITPICKER_CACHE_DIR`, else `node_modules/.cache/nitpicker`. The HTTP store does `GET`/`PUT` of `<baseUrl>/<key>.json` with an optional `Name: value` auth header, and stays off after its first non-miss failure so an unreachable server costs one timeout. Reads try local, then remote (copying a hit locally); writes go to the remote store only with `writeRemote`.
- **HTTP cache worker.** Exit codes: 0 success (GET prints the body), 3 not found, 1 any other failure. The comparison is synchronous, so each request runs in a short-lived `node` child that does the asynchronous fetch: `<GET|PUT> <url> <timeoutMs>`, auth header in `NITPICKER_CACHE_AUTH_HEADER_VALUE` (never argv). S3 answers 403 for a missing key when the caller cannot list the bucket, so 403 counts as not found. The test HTTP server lives in a worker thread for the same reason: the stores block the calling thread.
- **Findings cache key.** Base commit, project, analyzer, tool version, configuration hash, head policy (exclude, layout, exceptions, thresholds) and legacy inventory path. The policy is keyed explicitly because layout and threshold changes rebuild an analyzer without changing its file-based hash. Entries carry their own key, so a misnamed entry is a miss. Only clean reports are stored, and cached analyzers still run when an uncached one depends on them.
- **Publishing a base snapshot.** `cache publish` analyzes HEAD (typically the new tip of `main`) and stores clean reports under the keys later comparisons use when HEAD is their merge base, using HEAD's own policy.
- **Comparison.** Findings split into new, resolved, unchanged and changed-metric. With `touchedCode`, an enforceable finding of a strict rule inside touched lines is new even though the base has it, unless it carries `ratchet.existingCodeOnly` (an ESLint finding inside a named function): then only a line in `inserted` makes it new, and `changed-lines.mjs` leaves out of `inserted` an added line it pairs, by word similarity, with a removed line.
- **Cycle identity.** Dependency cycles are `cycle:a>b>c|...`, starting at the lexicographically smallest rotation. A rename can change that rotation, so renamed cycles are re-rotated before comparing.
- **Report hash.** Zero config keeps the original policy hash input; any override changes it.
- **Base coverage and policy changes.** `createBaseSetupResolver` (`core/command/policy-review/base-setup.mjs`) measures the base once, with its own config passed through `baseConfigCoveringHead(baseConfig, headConfig)` (`core/policy-changes/base-coverage.mjs`): `layout.sourceRoots` and `layout.testRoots` are the union of both sides (an unset side adds the default roots, `testRoots` without `e2e`, because a declared list runs every root it names and the base would execute end-to-end specs); `exclude`, `disable`, `layout.excludedGlobs`, `layout.entryPoints` and each rule's exception paths keep only the entries both sides declare; and each threshold is the lower of the two. A folder the change brings under the gate is then read on both sides, so its existing findings stay unchanged, and neither a widened nor a tightened policy turns old findings new; the facts read from the head checkout come from the head policy (`withHeadCheckoutFacts` in `languages/typescript/preset/head-policy.mjs`: `conventions`, `generatedFiles`, `frameworks`, `react.enabled`, `react.iconPackage`, `react.major`, `react.styling`, `react.autoCleanup`, `i18n.enabled` and, when the base config reads the project Prettier config, `tools.prettier.projectConfigDigest`), as they do for a base analysed with the head config. The base config is read with `readConfigFile` (schema checks only, so a base that `rejectUnreadableSources` or `rejectUndeclaredPreset` would reject is still compared); one that does not load is compared as `{}`. The policy-change lines compare the configs as written. `readPolicyScope` (`core/policy-changes/policy-scope.mjs`) lists both snapshots with `git ls-files --cached --others --exclude-standard` and keeps the code files of the head preset's extensions wherever they are (`code`, `baseCode`), the head files also in the base (`keptCode`, `keptPaths` with their folders), the root sets of each side (`rootSets`), `basePathOf` (a head path mapped back through the run's renames, folders through directory moves), `existsInBase`, `presetRequired` (`presetToDeclare`), for the TypeScript preset every tsconfig of each side with its `checkJs` (`projectTsconfigs` and `checksJavascript` in `languages/typescript/preset/modules/tsconfig-files.mjs`: each `tsconfig.json` outside `node_modules` and the exclusions, plus the configs they reference, followed transitively), `productionReach` and `blobOf` (the git blob id of a head file). `productionReach` is computed once, on first use: one `reachableModules` walk (`module-resolution.mjs`, unlimited depth) from the head layout's source files, the `main`/`bin`/`exports` targets of every tracked `package.json` (`packageEntryFiles`) and the `layout.entryPoints` files, through hidden files, mapping each reached file to the root importer the finding names (`productionReach` in `production-imports.mjs`, specifiers read with `ts.preProcessFile`). Non-layout presets have no reach. The resolver always calls `policyChangeFields(baseConfig, headConfig, scope)`, because code added under an unchanged config can still be hidden. Each part returns `{ loosened, changed }`, a loosening carrying its display `text`, its full `key` and the `files` it names. `coveredPathChanges` (`paths/covered-paths.mjs`) counts an added glob as loosening when it covers a kept code path its base set did not cover: `exclude` and `layout.excludedGlobs` are one set (`keyedExclusions` in `paths/hiding.mjs`, over `layout.hiddenGlobs`), so a respelled glob covering the same files and a glob moved between the two keys (`<glob> moved from exclude to layout.excludedGlobs`) are only listed; exception paths are compared per rule (`exceptionPathsByRule`, the one collector, also used by `base-coverage.mjs`); `layout.entryPoints` over all code paths through `basePathOf`. A base root the head drops is loosening when a code file under it is under no head root of the same kind, and an added test root is loosening when a kept file that was production code in the base becomes test code (`testRootReclassifier`, the one reclassification, also used for hiding). Removed globs are listed as tightenings. `hiddenCodeChanges` (`paths/hidden-code.mjs`) decides per file. `hidingSets` (`paths/hiding.mjs`) builds one set for the exclusions, one per rule's exception paths (`exceptions`, `python.exceptions`) and, with a layout, one for test roots inside source roots; each has `hidesInHead(file)` and `baseHiders(basePath)`, the base globs or root of that set that hid the file's base path. For every code file the change adds (`existsInBase` false) or moves (`basePathOf` differs) that a set hides in the head: no base hider is `where the base config checked it`; base hiders that cover no `baseCode` file is `where the base hid no code` (dormant); otherwise, for the exclusions and test roots only, a file in `productionReach()` is `that production code imports`. An exception under an established glob never fails on imports, because the file is still checked by every other rule. The text lists three files; the key lists all. `tsconfigChanges` (`paths/tsconfig-changes.mjs`) counts a base tsconfig with no head counterpart (`tsconfig removed: <file>`) and `checkJs` turned off in any kept one as loosening, and lists `checkJs` turned on. `listedChanges` (`loosenings.mjs`) adds newly disabled analyzers, thresholds above the base with `THRESHOLD_DEFAULTS` filling missing keys on both sides, and custom analyzers removed or changed (whole entry compared); added analyzers, re-enabled analyzers and lowered thresholds are listed. Every other changed leaf setting is listed as `path: base -> head` (`not set` when absent); `loosensSetting` marks the ones that check less: `preset` by the preset that runs (`typescript` when unset; `javascript` to `typescript` is not loosening, and a first preset is not loosening only when `scope.presetRequired` says the project must declare one), `react.enabled`, `i18n.enabled` and `python.importLinter` turned to `false`, `kotlin.formatter` turned to `none`, any `kotlin.detektConfig` change, and a `tools.<tool>.precedence` that ranks `"project"` higher (for `pmd`, whose layers are unioned, only dropping `"nitpicker"`). Engines, `python.typeChecker`, `python.formatter` and the like stay neutral. `policyLoosenings` is the subset that fails: `buildReport` adds one enforceable `nitpicker-config/policy-loosened` finding per entry (path `nitpicker.config.json`, identity the change) unless the run accepts it; `policyFindings` (`core/diff/reporting/review/policy-findings.mjs`) words it as the change, the allowed form (keep the base's policy and change the code until it passes) and the route for a person reviewing the change. `policyDigest` hashes the sorted loosening keys and, for every file they name, its path and git blob id (`summary.policyDigest`), so an acceptance covers exactly the loosenings and file contents a person saw; `results.mjs` falls back to the loosenings alone when no scope supplied one. `policyAcceptance` (`core/command/policy-review/policy-acceptance.mjs`) honours `--accept-policy-change` only when the CLI is interactive (stdin and stdout are TTYs, `withCliDefaults` in `core/cli.mjs`) and `NITPICKER_ACCEPT_POLICY_CHANGE` only when `CI` is set; an ignored one is written to stderr, and `summary.policyAcceptanceSource` names the route used. `summary.policyChangeAccepted` records an accepted loosening. The evals harness fails a case whose agent used either route or wrote a generator marker (`evals/detectors/policy/policy-shortcuts.mjs`). Only shard 0 (or an unsharded run) adds the findings, and `aggregate` accepts the `nitpicker-config` tool in a shard's entries, so a sharded run counts them once. `summary.json` carries `policyChanges`, `policyLoosenings` and `notices` as arrays of strings, `aggregate` copies them from the first shard (`summaryFields`), and `report.txt` and the console print them under "Policy changed in this change" and "Notices (not failing)". Notices never affect the exit code. `outsideRootsNotices` (`languages/typescript/preset/notices/`) names head-side changed files outside every root when the preset is `typescript`; it skips declaration files, `*.config.*` files, dot folders, built-in and configured exclusions.
- **Config base.** `base` in the config is refused when it is `HEAD` or `@` (`rejectHeadBase`), and when it resolves to the head commit and follows HEAD (`core/diff/git/repository/base-ref.mjs`): a hex SHA, an expression using `HEAD` or `@` (`HEAD~0`, `HEAD^0`, `@{0}`), or a name whose `--symbolic-full-name` is the checked-out branch (`main`, `refs/heads/main` while on `main`). Any other branch that points at the head commit, such as `origin/main` on an up-to-date `main`, is accepted: the head includes uncommitted changes, so that comparison still checks the working tree, and the default remote-branch base relies on it. An explicit `--base HEAD` is accepted for the same reason.
- **SARIF output.** One result per new finding; the hashed comparison key is `partialFingerprints["nitpickerIdentity/v1"]`, so consumers match findings across runs when lines move. Tool errors become unsuccessful tool-execution notifications.
- **Base commit of a checkout.** `git.mjs` stages the checkout (untracked, non-ignored files included) in a copy of the index, leaving the user's index, branches and files untouched. The copy keeps the index's timestamps, so git's racily-clean check still re-reads a same-size edit made in the second the index was written.
- **Policy links.** Without `transform` the package-owned policy file is linked into the analyzed tree; with one (the layout changed) it is a rewritten copy, still derived from the head policy and never from the analyzed tree.
- **Shared build directory.** `runScheduler` creates one directory per side (`NITPICKER_SHARED_BUILD_DIRECTORY`, inherited by every analyzer process) and removes it when the scheduler exits. `buildOnce(key, build)` runs `build` in the first process to take `<key>.lock`; the others poll for `<key>.result` (or `<key>.failure`, rethrown so a broken build is not repeated). A lock whose owning process is gone (or an empty one left by a crash) is taken over by renaming it aside and re-checking it. A build killed by a signal records nothing, so a waiter builds instead; other failures are recorded. Without the variable, `buildOnce` just builds, so direct runs and tests are unchanged.
- **Temporary files.** Register before creating the file so it is removed on exit or interruption even if the runner's `finally` blocks never run.
- **Presets.** `preset` is explicit; there is no auto-detection. `rejectUndeclaredPreset` (`core/configuration/project-checks/preset-detection.mjs`) only refuses a config without `preset` when the source roots have no `.ts`/`.js` family file (best-effort: `ASSET_FOLDERS` such as `resources`, `static`, `public`, `assets`, `webapp`, `wwwroot` and `*.min.js` files are skipped, so a Spring app's bundled scripts do not count) and a Gradle, Maven or Python marker (`pyproject.toml`, `setup.py`, `setup.cfg`, `Pipfile` or `requirements.txt`) is at the project root, so the TypeScript preset never runs on a Java or Python project and ends in tool errors; the message names the preset (Kotlin when `.kt`/`.kts` files outnumber `.java` ones, skipping dot folders, `node_modules`, `build`, `target` and `out`). Injected analyzers win over the preset. Within the Java preset the build tool is detected (`detectJavaBuild`): Maven when the root has a `pom.xml` and no Gradle build file, or both but only `mvnw` and no `gradlew`; Gradle otherwise.

## Shared rules (`shared/`, `spec/`)

Findings follow `spec/findings.schema.json`. Identity (the part of the comparison key beyond rule and path) never contains line numbers, so edits above a finding do not change it.

- **Rule catalog** (`shared/policy.mjs`, `shared/project-rules/size-rules.mjs`). `policy.mjs` is the single source for the custom checks nitpicker adds on top of third-party tools: rule ids, default limits, failure-message templates and the languages that enforce each rule (`RULES`). Every language adapter reads it, and the custom-rules table in `spec/checks.md` is generated from it (`npm run gen:checks`). The size rules (the file limits `file-lines-limit`, `line-length-limit` and `folder-files-limit`, `folder-depth-limit` and the class limits Java, Kotlin and Python enforce), their defaults (`FILE_LIMIT_DEFAULTS`, which `policy.mjs` re-exports), their message templates and the Java line length live in `project-rules/size-rules.mjs`, which `policy.mjs` imports and spreads into `RULE_IDS`, the message tables and `RULES`. `project-rules/size-rules.mjs` imports nothing, and `policy.mjs` imports only from it, `shared/rules`, `shared/unused-api` and `shared/project-rules`, so any entry point can load the catalog. Like everything under `shared/`, neither may import from `core/`, `languages/` or a tool package (`shared/import-direction.test.mjs`).
- **Project conventions** (`shared/conventions/`, `core/conventions/`). A convention is `{ id, label, options, optionLabels, fallback, files, measure(text, file) }`; `measure` returns the option one file follows, or `undefined`. `detectConventions` takes the files not under `exclude` (the CLI adds the layout's excluded folders, such as `dist`, `build`, `generated` and `target`), samples at most 400 per convention evenly over the sorted paths, counts one vote per file, and picks the plurality; a tie or no votes is `fallback` (`source: 'default'`), a `conventions` pin in the config skips measuring (`source: 'pinned'`). The CLI measures once the config, the analyzer selection and the base ref have been checked, so their errors come first and a run outside git fails as before: a comparison reads the merge-base commit through `git ls-tree -l` (regular blobs up to 512 KiB only, so generated files, symlinks and submodules never vote) and one `git cat-file --batch` by object id (so a branch cannot flip the choice); when every convention is pinned no git command runs, and re-measures on the working tree only the conventions the base had no files for; `--all` measures the working tree and `cache publish` the published commit (which later comparisons use as their merge base, so the keys match). Only choices that differ from the preset default go into the head policy, as `conventions: { id: option }` (omitted when empty, so default-style projects keep their policy and cache keys), also into the base's policy when the base has its own config, so both snapshots and the findings cache key see the same values. Presets list their conventions in `core/conventions/definitions.mjs`; a preset with none leaves the policy as it was. The TypeScript and JavaScript presets measure Prettier options (`languages/typescript/conventions/`) and add the choices to the `nitpicker` Prettier layer for code files, which then always runs through the layered Prettier API path. Short code says nothing about the print width, so a file votes a width only when it is the one value between its longest breakable line and the shortest call, array or assignment Prettier left wrapped (joined, that would have fit any wider limit), or 120 when at least two lines exceed 100. The measures skip comments and template-literal contents, and a file with no evidence casts no vote, so a project keeps the preset default rather than a guess. `prettier.jsxQuotes` and `prettier.bracketSameLine` (`conventions/measures/jsx-conventions.mjs`, TypeScript preset only: the javascript layout does not list `.jsx` or `.tsx` as source files, so the scope filter would drop every file) parse `.tsx`/`.jsx` with the TypeScript compiler (`typescript-syntax.mjs`): a quote vote is a `JsxAttribute` with a string initializer holding neither quote character, and a bracket vote compares the end line of the last attribute of a multi-line opening element with the line of its `>` (a self-closing element never votes). `prettier.jsonIndentation` and `prettier.yamlIndentation` (`measures/data-conventions.mjs`, `scope: 'formatted-data'`) are measured from the data files themselves and applied by `prettier-layers.mjs` to files with that extension: `useTabs` and `tabWidth` only, since nothing reliable can be measured for quotes or width in data files. The scope is the `prettierPatterns(layout)` list in `layout.mjs`, the same one the `prettier-format` check uses (so JSON at the root and under source and test roots, YAML under source roots only), minus generated and fixture paths. A `scope` on a definition makes `resolve.mjs` pass an `accepts` filter (`layout`: source and test files; `test-code`: test files plus files under `test-support`, `test-utils`, `testing` or `testkit`; `formatted-data`). A definition with `kind: 'names'` (`typescript.assertionHelpers`, `measures/assertion-helpers.mjs`) votes a list: `measure` returns evidence strings per file, `detectConventions` counts files per string, and `choose(counts)` (default: names counted in at least `minFiles` files) picks the sorted names; a pin is a list of plain identifiers, `sampleLimit` raises the sample size, and the policy carries the list. For assertion helpers a file reports `use:NAME` for the root identifier of the last statement of each `it`/`test` callback (heads: `it`/`test` with `only`, `skip`, `concurrent`, `sequential`, `each`, `for`, `fails`, `todo`, `runIf`, `skipIf`, called, tagged or plain) that contains no `expect`/`assert` call, and `def:NAME` for each function declaration or function-valued constant whose body calls `expect`/`assert`/`expectTypeOf`/`assertType` or throws; a name is followed when it ends tests in at least three files and is defined somewhere in the sample, so `checkIn(guest)` is not an assertion unless the project defines it as one. `defaults/eslint.config.mjs` appends the names to the `assertFunctionNames` of `vitest/expect-expect`. Main has no Jest assertion rule, so there is no second consumer. A hook file name (`use` plus a capital) is exempt from `typescript.fileNames` only when the file exports a function or constant named exactly like the base name, so that definition has `needsText` and the detector reads just those files (an unreadable one is treated as a hook). Two conventions are not Prettier options. `typescript.typeImports` (TypeScript preset only, `languages/typescript/conventions/type-import-style.mjs`) votes `separate` for a file with `import type` statements and `inline` for one with `import { type A }` specifiers (a file with neither, or with the same number of each, casts no vote) and sets the `fixStyle` of `@typescript-eslint/consistent-type-imports` in `defaults/eslint.config.mjs`; that rule accepts both forms and only reports a value import of something used as a type, so the choice only decides which form its fix would write, and the setting reaches the lint engines as ordinary rule options (oxlint plans from the ESLint config). `typescript.fileNames` (`file-name-casing.mjs` in the same folder, both presets) votes from the file path alone, so its definition is `nameOnly` (no file is read, and a file over the 512 KiB read limit still votes; `source.paths({ unreadable: true })` lists those) and `scope: 'layout'` (`resolve.mjs` passes `accepts`, which keeps only files the layout classifies as source or test files). The vote is the casing of the base name before the first dot (`kebab-case`, `camelCase` or `snake_case`); PascalCase names, names that fit every casing (`index`, `404`, `fr-CA`), reserved framework names, Remix route syntax (`[`, `]`, a trailing `_`), names starting with `_`, `+`, `$`, `@`, `(`, `#` or `~`, dot-files, `*.config.*`, names with a lowercase hash segment of 8 or more characters containing a digit, files the layout reports as generated (`isGeneratedPath`: dependency folders and the `generatedFiles` found by generator markers, which the vote skips through the `layout` scope and the rule skips by its own path and sibling listing), `*.graphql.*`, `*.gql.*` and `fixtures/` folders neither vote nor fail. `nitpicker/file-name-casing` (`eslint-plugin/rules/naming/`) takes the project casing as its option from the policy (`kebab-case` unless a convention says otherwise). When the file's folder holds at least three other voting files, their plurality replaces the project casing for that file (a tie keeps it), unless the config pins `typescript.fileNames`: `resolve.mjs` then records the pins as `conventionPins` in the head policy (even a pin equal to the default, which `conventions` omits) and the rule gets `pinned: true`; the rule lists the folder once per run with `readdirSync`, so it needs no extra policy data, and head and base each read their own checkout. It reports once at line 1, so it runs on changed files through the usual differential gate. The Python and Kotlin runners read the choices from the head policy file (`NITPICKER_POLICY`) like the TypeScript adapters.
  - **Applicability and sources** (`core/conventions/definitions.mjs`, `resolve.mjs`). A preset can also give `conventionStyle`, which returns `{ unused, project, note }` for the tools in use: `unused` maps the ids the formatter cannot apply to a reason (they are not measured or printed, and a pin for one is a config error), `project` maps the ids that a listed project tool config sets to `{ choice, from }`, and `note` adds a remark to a printed choice (black accepts both quote styles). A project value replaces a pin and a measurement for its id (`source: 'project'`, printed as "from your ruff config"), and a value outside the options (`tab`, `preserve`) is printed but never reaches the policy. Python: `python-style.mjs` picks ruff or black as the format check does and reads their config through `project-format-config.mjs`. Kotlin: `kotlin-style.mjs` reads the `.editorconfig` keys for `*.kt` (`editorconfig-values.mjs`), the ktfmt style the build names and the `WildcardImport` setting of the detekt config; only the tools whose `tools.<tool>.precedence` lists `"project"` first are read.
  - **Names** (`kind: 'names'`, `minFiles`, `sampleLimit`, `choose`). A convention that collects names instead of choosing an option: `measure(text, file)` returns evidence strings, the counts are per file, and `choose(counts, definition)` (default: every name seen in at least `minFiles` files) returns the followed names, sorted. The choice is an array (`[]` is the fallback, a pin is a list of identifiers) and `describeConventions` prints it as "final call of at least N of M measured files". `java.assertionHelpers` and `kotlin.assertionHelpers` (`measures/assertion-helpers.mjs`, with `languages/java/source/` extracting test methods and function definitions from the masked source) count `use:<name>` (the call that ends an enabled test method without a known assertion, in a `src/test`-style source set, and reads like an assertion: `expect...`, `ensure...`, `must...`, `should...`, `validate...`, `is...`, `has...`, `await...`) and `def:<name>` (a method or function in a test source set or a `test-support`, `test-utils`, `testkit` or `testing` folder whose body calls a known assertion or throws); a name is followed when it is used in at least 3 files and defined at least once, so production helpers such as `validate` or `isEmpty` are never learned. Known assertions are call names that are `assert`, `check` or `verify` followed by a capital or the end (Kotlin also `coVerify`, `expect`, `should`, Kotest infix `should...`, `confirmVerified`, `andExpect`, `forAll`, `fail`); `@Disabled` and `@Ignore` tests are skipped. `java.assertionHelpers` reaches PMD as the project's helpers appended to nitpicker's `extraAssertMethodNames` for `UnitTestShouldIncludeAssert` (`tool-config/pmd-layers.mjs`), on Gradle and Maven alike; `kotlin.assertionHelpers` feeds the Kotlin `test-without-assertion` rule.
  - **Java** (`languages/java/conventions/`): `java.formatter` (`measures/java-layout.mjs`, `formatterProfile`) votes per file only from evidence: tab-indented blocks are `none`, and otherwise the file needs a call the formatter wrapped after `(` (the Kotlin join measure with `wrappedOnly`, so the longest-line fallback of `java.lineLength` never votes for a formatter): two spaces at 100 and four spaces at 100 are `google`, four spaces at 120 `palantir`, 140 columns and two spaces at 120 `none`. The definition sets `minVotes: 3` and `strictMajority: true` (`shared/conventions/detect.mjs`: fewer voting files, or a winner with half of the votes or less, keeps the default `google`, whose indentation `java.indentation` still measures, `tab` included, from block-opening lines outside text blocks and comments; `withoutRawStrings` blanks text blocks). `java.lineLength` accepts any whole number of columns (`COLUMNS` in `shared/conventions/settings.mjs`: `valuePattern` and `unit` on the definition, used by pin validation, `appliedChoices` and the printed label; `kotlin.lineLength`, `python.lineLength` and `prettier.printWidth` carry it too, so a Checkstyle, detekt, `.editorconfig` or ruff width of 110 is followed instead of dropped). `build-style/` holds the project reading: `build-files.mjs` lists the build files of a conventions source (root and module Gradle files, version catalogs, `buildSrc/` and `build-logic/` plugins, every `pom.xml`, at most 200, none under `src/`, `node_modules`, `build`, `target`, `out`, `fixtures` or `testdata`), `build-comments.mjs` removes comments with a string-aware reader (`//` and `/* */` outside quotes for Gradle code, `#` for TOML; A pin or Checkstyle width the formatter contradicts is a config error naming the source when the formatter is pinned or declared, and resolves the formatter to `none` (printed with the reason) when it was only the default or measured. ## Dependency and repository hygiene (`shared/hygiene/`)

`repository-hygiene` is added to every preset's analyzers by `core/configuration/preset-analyzers.mjs` (injected analyzers still replace the whole set). - **Identities.** `file:<path>`, so a file already on the base stays unchanged and only an added one is new.

- **Key blocks.** `git grep -l -I -E` finds the private-key header in any tracked text file.
- **Package rules.** `languages/typescript/adapters/quality-areas/reporting/dead-code.mjs` maps knip's `dependencies` and `devDependencies` to `unused-dependency`, `unlisted` to `unlisted-dependency` and `unresolved` to `unresolved-import`, keyed by package name or specifier. - **oxlint engine.** `oxlint/oxlint-plan.mjs` asks ESLint for each file's resolved config and groups files by rules, globals and `settings`; `oxlint-translation.mjs` turns each group into an oxlint override. - **Test console output.** `test-console` is a quality-area analyzer that depends on `coverage` (like `crap`) and runs no tests; disabling `coverage` turns it off with `crap` (`applyDisable` turns off every transitive dependent of a disabled analyzer, `describeDisableCascade` words the stderr note), so a config written before it existed still applies. `runCoverage` adds `preset/test-console/vitest-reporter.config.mjs` as a second `--reporter` and names its output in `NITPICKER_TEST_CONSOLE_REPORT` (`reports/quality/test-console/report.json` in the snapshot). That file is the whole contract with a test runner: `{ "entries": [{ "file", "test", "messages": ["..."] }] }`, one message per console call, `file` absolute and `test` possibly empty. A Jest or `node:test` reporter only has to write it; the analyzer and the findings do not change. The Vitest reporter is standalone (Node built-ins and `shared/glob.mjs`, loaded by path inside the user's Vitest). It keeps `onUserConsoleLog` entries of type `stderr`, which is where Node's console sends `console.error`, `console.warn`, `console.trace` and a failed `console.assert`. It looks the entity up with `state.getReportedEntityById` (Vitest 4 and 5), skips a log the project's `onConsoleLog` returns `false` for (the call the default reporter makes), and replaces the project root, `os.tmpdir()` and `os.homedir()` (and their real paths) by `<root>`, `<tmp>` and `<home>` so the two snapshots' temporary directories agree. Vitest batches the console calls of one task made in the same microtask into one log, and its `size` is the number of calls: a log is cut into blocks at each unindented line that is not a closing bracket and each block is one message, whether the log holds one call or several (`log.size` is not read), so a call gives the same message alone or batched; a message is the lines of its call that have a letter or digit, without indented `at` and `in` lines (stack frames, component stacks), joined by spaces. `console-messages.mjs` normalizes a message (paths to their last segment, ISO timestamps, `0x` addresses, UUIDs, mixed letter-and-digit tokens of six or more characters, temporary names (`tmp` and six or more of `[a-z0-9_]`, `tmp.` or `tmp-` and six or more letters or digits, and a name under the temporary directory that ends in a separator and six random characters; such a name has no digit to recognize, which is why the temporary directory is part of the rule), every number with its unit, spaces; 300 characters) and `console-findings.mjs` makes one finding per test file and message: identity `console:<hash of the message>`, so the test name, the order and the repeat count are not part of it. A message of three or more words also carries `tokens` (its words), the optional finding field that `compareFindings` uses in `matchSimilarFindings` (`core/diff/comparison/fingerprint.mjs`): a head finding with no exact match counts as present when the base has an unmatched finding with the same tool, rule, path (renames applied) and classification, the same number of tokens and at most one differing token, and that token pair passes `isOpaqueChange` (`core/diff/comparison/similar/opaque-token.mjs`: both tokens, without edge punctuation, are lowercase letters and digits of five or more characters, or carry an `<id>` placeholder, and at least one has a run of four consonants, a vowel ratio under 0.2 or letters mixed with digits; capitalized, camelCase, UPPERCASE and backticked tokens never qualify). Pairs are chosen as a maximum matching (augmenting paths, heads and base findings in identity order), found through an index keyed by the tokens with one position left out and the class of the token left out (random-looking, plain, `<id>` or `<n>`), so only findings that can be paired are ever compared. The search for a longer path stops after two million neighbor visits and keeps the pairs found, which only matters for thousands of messages that differ in one random word. This keeps random values that no pattern can recognize from making unchanged output new without hiding a changed ordinary word. `testConsole.allow` entries (normalized `contains`, optional `paths`) and `exceptions` for `test-console-output` come from the head policy file, so base and head use the same ones. It drops a BOM and skips scripts with a URL query (module mocks). `mapped-nodes.mjs` drops AST nodes with no mapped segment in them (an `if` up to the end of its test, a function up to its body), the `__name(...)` and `obj.x = x` statements loaders add, and an enum function's fallback branch; these are loader helpers that the lookup would otherwise pin to line 1 or past the end. `merge-coverage.mjs` merges child processes and workers by type, line and order on the line, because columns differ by loader. - **Security sink rules.** `eslint-plugin/rules/security/` holds one folder per rule (`sql/no-sql-string-building`, `hash/no-weak-hash`, `tls/no-disabled-tls-verification`, `http/require-http-timeout`, `deserialization/no-unsafe-deserialization`), set by `securityRules` in `eslint-config/policy/security-facts.mjs` (called from `productionGuardRules`) and listed in `strict-rules.mjs`. The rules otherwise read one file at a time, so a helper in another module is caught where its text is built or where its option is written, not where it is called. Shared value resolution is `security-values.mjs`: a `const` chain, a conditional or `??` fallback, a parameter default, a `CONFIG.key` lookup (also through `Object.freeze`), `CONST[key]` with a non-constant key (every value of a `const` object or array), a `for (const x of CONST_LIST)` binding, `toLowerCase()`, and through `member-values.mjs` an `enum` member, a `readonly` class field or `static readonly` field (fixed) and a mutable field or parameter-property default (one possible value). `imported-names.mjs` binds modules: `import`, `require`, `require(x).default`, `import { default as x }`, `import x = require(x)`, `await import(x)`, a namespace alias (`const sandbox = vm`) and aliases of an imported function (`const make = crypto.createHash.bind(crypto)`, `const { createHash: make } = crypto`). In `no-sql-string-building`, `sql-inert.mjs` classifies each interpolated value (constant text, a number shape, an index parameter of an array callback, `+` of inert parts, a template of inert parts, `join` of an inert array and text builders such as `repeat` and `slice`), `sql-arrays.mjs` decides when an array holds only inert text (a literal, `map` or `Array.from` with an inert callback, `fill`, or a local array whose every `push`, `unshift`, `splice` and element write adds inert text; with types a `number[]`), and `sql-sinks.mjs` names the consumer (query call, raw builder method, TypeORM clause on a `createQueryBuilder()` chain, a receiver named like `qb` or typed `*QueryBuilder`); `sql-composition.mjs` applies the SQL-context test per sink. - **Renamed-identifier clones.** The Java preset runs PMD CPD with `--ignore-identifiers --ignore-literals`. PMD is also not shipped: the Java presets resolve it through the project's Gradle or Maven build, and a TypeScript project has no build tool or JVM to resolve `pmd-cli`, `pmd-core`, `pmd-javascript`, `rhino`, `antlr4-runtime` (4.9.3 for PMD 7.7, 4.13.2 for 7.28) and a dozen more jars. ## JavaScript preset (`languages/javascript/`)

The JavaScript preset reuses the TypeScript pipeline; `languages/javascript/preset/` holds only what differs.

- **Preset channel.** `resolveHeadPolicy` copies `preset` into the head policy file only for `javascript`, so the TypeScript policy and its cache key do not change. `readLayout` turns it into `layout.javascript` and the extension lists every runner reads from the layout: `extensions` (`ts`, `mts`, `cts`, `js`, `mjs`, `cjs`; no `jsx` or `tsx`, so a `.jsx` file is neither a source nor a test file), `entryExtensions` (the same, `js` first) and `formatExtensions` (the Prettier patterns). `presetAnalyzers` returns `javascriptAnalyzers()` (same checks, built from the JavaScript layout) and `applyLayout` rebuilds from `resolveLayoutFor(headPolicy)`. `javascript-preset.mjs` is hashed into every analyzer whose config it shapes.
- **Generated configs.** The `tsconfig.quality.json` and `tsconfig.stryker.json` rewrites add `allowJs` and `checkJs` (the first also `noEmit`); with a project `tsconfig.json`, or a `jsconfig.json` when there is none, they extend it. `knip.json` gains `.js/.mjs/.cjs` entries and config files, and `jscpd.json` the `javascript` format next to `typescript`, because jscpd's `typescript` format reads only `.ts` and `.mts`. Stryker's TypeScript checker reports a mutant that fails `checkJs` as a compile error, so JavaScript mutants are killed by types as TypeScript ones are.
- **ESLint dialect.** `eslint-dialect.mjs` rewrites each strict config entry whose rules change: the original entry is kept for `.ts`, `.mts` and `.cts` files and a copy with the dialect rules is added for `.js`, `.mjs` and `.cjs` files (the `files` patterns are intersected with the extension glob, so the entry's own scope is kept). The copy drops the type-syntax rules, `@typescript-eslint/no-require-imports` and the `no-restricted-syntax` selectors that name a `TS*` node, lets the property-assignment selector of `domain/` skip `module.exports` and `exports.x`, passes `jsdocTypes`, `jsdoc` or `commonJsExports` to the four rules that map to JSDoc or CommonJS, and `no-var`, `prefer-const`, `prefer-rest-params` and `prefer-spread` are added (typescript-eslint enables them for TypeScript files only). The mapped rules keep their severity and still accept an exception. The dialect is applied before exceptions.
- **JSDoc parser.** `jsdoc.mjs` accepts one grammar per allowed tag (type in balanced braces, then a name where the tag has one) and reports any other text as prose. A `@type` is a cast only when the comment is directly followed by `(`. `any`, `*`, `null` and the `?T`, `T?` and bare `?` forms are looked for outside string literals and object keys. `unknown` is reported in `@param`, `@property` and `@prop` anywhere, and in the other type tags only inside braces or the parameter list of a function type, which is where the TypeScript rule finds a property or parameter.
- **CRAP is computed here.** `crap/measure.mjs` (`measureCrap`) parses each source file with the TypeScript compiler (`functions/` finds every function-like node, its own complexity without nested functions, its display name and its source), reads the `coverage-final.json` the project's test run writes (`istanbul/`: statement and branch spans, `fnMap` entries, attribution of statements and branches to the innermost function by span) and applies `crap = ccn^2 * (1 - coverage)^3 + ccn` with coverage the lower of statement and branch coverage. `@barney-media/crap-typescript-core` and the module-load hook that widened its `.ts`/`.tsx` suffix list for JavaScript are gone. The identity (`function:<name>:occurrence:<n>:source:<hash>`, ratchet key `function:<name>:occurrence:<n>:crap`) is unchanged, so legacy CRAP findings stay baselined. `crap-equivalence.test.mjs` runs `measureCrap` on a corpus (`crap/fixtures/corpus`: TypeScript constructs, CommonJS, ESM and plain JavaScript, with a coverage file) and compares the whole result to goldens (`expected-ts.json`, `expected-js.json`) that were produced by the library; a differential run against it on thousands of functions gave no difference. Two deliberate differences: `.mts` and `.cts` files are measured (the library skipped them through its `.ts` suffix check), and a coverage entry is matched to a file by its resolved, lower-cased path, without the library's module-root fallback and without grouping the files by their nearest `package.json` (the order of functions within a file, and of files, is the library's for a project with one manifest). Absent values are `undefined`, so the report JSON leaves out the keys the library wrote as `null`; nothing reads them (`normalizeCrap` reads `percent` and `crap` as numbers), and `crap-equivalence.test.mjs` compares the golden with its nulls removed. JavaScript is parsed as TypeScript, which is why `.jsx` is not supported.
- **Constants in `quality-areas-runner.mjs`.** The module-level `invokedPath` block runs the runner on import, so the constants it uses are declared above it. Declared below, they were still in their temporal dead zone when a failing test reached the failure formatter, which crashed the coverage check instead of reporting `tests-failed`.

## Java preset (`languages/java/`)

Gradle runs once and yields findings for all tools.

### Java report directory

`gradle -I languages/java/gradle/nitpicker.init.gradle -Pnitpicker.reportDir=<dir> nitpickerJava`. `collectJavaFindings` makes `<dir>` a fresh temporary directory outside the project and removes it afterwards, so a build script that writes to `build/nitpicker` changes nothing nitpicker reads. File limits, coupling, inline suppressions, Spring configuration and duplicates run once over the merged manifest. - **Project tool configs** (`languages/java/adapters/tool-config/`, with the Checkstyle files in `checkstyle/`). `tools.pmd` and `tools.checkstyle` with `"project"` in `precedence` layer the project's file over nitpicker's instead of replacing it. `toolConfigChoices` returns `{ project, projectWins }` per tool (`projectWins` is false only when `"nitpicker"` is listed before `"project"`); `toolConfigProperties` turns them into `-Pnitpicker.pmd.nitpickerRuleset`, `-Pnitpicker.pmd.projectConfig`, `-Pnitpicker.pmd.testRules`, `-Pnitpicker.checkstyle.projectConfig` and `-Pnitpicker.checkstyle.mergedConfig`. `layerPmdRulesets` (`pmd-layers.mjs`) writes `pmd-nitpicker.xml` (nitpicker's ruleset minus the rules the project names or defines) and `pmd-project.xml` (the project's ruleset, where a rule nitpicker also configures is the overlay of the project's elements on nitpicker's definition, and a whole-category reference becomes single references to the rules nitpicker left out of that category), because PMD keeps the first reference of a rule and applies a ruleset's `exclude-pattern` only to a ruleset loaded on its own; it also clones `UnitTestShouldIncludeAssert` with the measured `java.assertionHelpers` appended to `extraAssertMethodNames`. `layerCheckstyle` (`checkstyle-layers.mjs`) merges modules by name (the `id` only chooses among several nitpicker modules of one name; a project module without an id merges into all of them), keeps the project's `SuppressionFilter`s and drops its inline suppression filters; for Gradle, `runJavaPreset` first runs the `nitpickerCheckstyleConfig` task with `-Pnitpicker.checkstyle.exportConfig` (nitpicker's config, from the pinned Checkstyle jar), merges it in process with `mergeCheckstyleFiles` (`checkstyle-merge.mjs`) and passes the result as `-Pnitpicker.checkstyle.mergedConfig`; the init script sets `configDirectory` to the head checkout's config folder; Maven calls it in `writeCheckstyleSetup`. - **Structure metrics.** `StructureMetrics.java` runs as `java StructureMetrics.java <structure.json> <classes.json> <analysisRoot> <sourceRoot>...` in the JDK's single-file source mode (task `nitpickerStructure`, no dependency beyond the JDK that runs Gradle). It parses, never compiles, the main sources with the compiler tree API and writes one object per method, constructor, static or instance initializer block with a statement (`Owner.<clinit>`, `Owner.<init>`, `initializer: true`), field initializer that branches (`Owner.field`, `initializer: true`) and lambda (`Owner.method.<lambda>`, or `Owner.method.local` / `Owner.field` when it initializes a variable or field, `lambda: true`); members of nested, anonymous and local classes are their own entries, and no unit counts towards the one around it (a lambda's statements, nesting and complexity are its own; `lines` is the physical span). Fields: `lines` (last line - first line + 1, annotations and modifiers included, Javadoc not), `statements` (every statement below the body except blocks), `maxControlNesting` (deepest nesting of `if`, `for`, enhanced `for`, `while`, `do`, `switch` and `catch`; an `else if` stays on the level of the `if` it continues), `parameters`, `complexity` (1 + `if`, `for`, enhanced `for`, `while`, `do`, `catch`, `?:`, `&&`, `||` and each non-default `case`, an arrow case or a case with several constants once; a switch expression or pattern switch whose arrow cases each hold one expression or a `throw` counts once plus once per `when` guard, never more than its cases), `signature` (`Owner.method(parameter types)`, the CRAP identity; the unit name for an initializer or a lambda), `parameterTypes` (without generics or package, arrays and varargs as `Name[]`, a type variable of the method or an enclosing class as its first bound, `Object` without one), `privateEmptyConstructor`, `initializer` and `lambda`. A syntax error prints `file:line` and the compiler message and exits with status 1, so the task fails instead of dropping methods.
- **Fake Gradle for tests.** `adapters/fixtures/fake-gradle.mjs` stands in for Gradle in tests that run without Java (`NITPICKER_GRADLE`). In the project directory: `GRADLE_FAIL` fails the run with its text; `NO_REPORTS` writes an empty `modules.json`; each line of `violations.txt` is a PMD violation in `src/main/java/demo/A.java`; `jacoco.xml` and `mutations.xml` become those reports; `modules.txt` lists more projects, one directory per line, each with the same reports under its folder and key `module-<directory>`; a project folder's `jdeps.txt` and `jdeps-classes.txt` are copied into its reports. With `-Pnitpicker.kotlin=true`, `detekt.txt` (`rule :: message` or a message for `detekt.style.MagicNumber`), `ktlint.txt` (`rule|message`), `kotlin-format.txt` and `kotlin-metrics.json` feed the Kotlin reports. Reports go to `-Pnitpicker.reportDir`; the arguments are kept in `build/gradle-args.json`.
- **Project settings the init script overrides.** After evaluation it resets the project's JaCoCo filters (`test.jacoco` includes, excludes and class-loader excludes; `jacocoTestReport.classDirectories` back to the main output) and replaces the Checkstyle config of every Checkstyle task. `pitest-junit5-plugin` and a launcher are on PIT's classpath only when the test runtime has `junit-platform-engine`, `pitest-testng-plugin` only when it has a `testng` jar. `nitpickerArchunit` takes JUnit 4 for a declared `archunit-junit4`, the JUnit Platform for `archunit-junit5`, and the framework of the project's `test` task with both or neither; it fails when ArchUnit classes exist and none produced a report. PMD's `TestClassWithoutTestCases` runs from a generated `pmd-tests.xml` that excludes the main source directories, as the main-only rules (`pmd-main-ruleset.xml`, and the Spring rules) run from `pmd-main.xml` that excludes the test ones.
- **Gradle failure text.** `condenseFailure` (`adapters/gradle-wrapper/failure-text.mjs`) drops the JVM's `Picked up JAVA_TOOL_OPTIONS` notices, PIT's `INFO` progress lines, `[ant:checkstyle]` warnings and `SLF4J(W):` no-provider warnings (the Checkstyle tasks also run with `showViolations = false`). When the text is still too long it keeps Gradle's failure block (from `FAILURE:` or `* What went wrong:`, without the `* Try:` hints) whole, every distinct `Caused by:` line before it, and as much of the start as fits, cutting the middle; without a failure block it keeps the start and the end.

### Ingesters

Ingesters turn tool reports into findings:

- **Maven builds.** `detectJavaBuild` (`languages/java/builds/java-build.mjs`) picks the build; `languages/java/maven/` writes the same reports per module in `<module>/target/nitpicker` and `readModuleFindings` (`builds/java-modules.mjs`) prefixes each module's findings. The tool versions on both sides come from the init script's `def pinned = [...]` map, parsed by `readPinnedTools` with a regex, so keep that map one `name: 'version'` pair per entry. The build runs `test`, or `verify` when the effective POM of any module binds maven-failsafe-plugin's `integration-test` goal in an execution that the project does not keep off (`skipITs`/`skipTests` properties, `skip`/`skipITs`/`skipTests` configuration, phase `none`): `runsFailsafe` from `describeModule`, arguments from `lifecycleArgs` in `maven-project.mjs`, which adds `-Djacoco.haltOnFailure=false` and the skip properties of signing, publishing, network and release-check plugins (listed in java-preset.md). Failing Failsafe tests are tool errors like failing Surefire tests, and their reports are copied to `test-results/failsafe/`. Surefire and Failsafe reports and coverage files count as fresh when modified at most 2 s before the build started (file systems with coarse timestamps); our JaCoCo file is `target/nitpicker-jacoco.exec`, which the Failsafe JVM appends to through the same `argLine`, and every fresh file among it and the `destFile`s of the project's `prepare-agent` and `prepare-agent-integration` executions goes to one JaCoCo report. Maven runs at most 15 minutes; a timeout is a `java/maven-failure` that names the limit. The resolved tool classpaths are cached per user in `$XDG_CACHE_HOME/nitpicker` (else `~/.cache/nitpicker`), keyed by a hash of the tool coordinates; base and head run one after the other, so they never resolve at the same time.
- **XML text.** `parseXml` sets `text` on a leaf element (entities decoded, comments dropped, CDATA kept verbatim); an empty leaf has no `text`.

- **Common.** Repeats of one identity within a report get `#n` in report order. The XML parser reads elements and attributes only and throws `TypeError` when malformed.
- **SARIF** (PMD, SpotBugs). Identity is `partialFingerprints` (sorted) when present, else a hash of rule, path and symbol. Absolute `file://` URIs (PMD) and source-root-relative paths (SpotBugs) are made project-relative; results outside the project are skipped. SpotBugs `note`-level results are promoted because the tool already runs at the configured threshold, and its subject comes from message arguments since the text is generic.
- **Checkstyle.** Identity hashes the check `source`, path and message; the line is location only.
- **ArchUnit.** One finding per violated rule and offending class, identified by the fully qualified class; line numbers and violation counts never take part. The path is resolved by `options.resolvePath(className, fileName)`, falling back to the declaring test class. A failed case without violation lines yields one `test-failure`.
- **CRAP.** `crap = ccn^2 * (1 - coverage)^3 + ccn`, with coverage the lower of line ("statement") and branch coverage. `crap-score-limit` when over `options.limit`; `crap-coverage-unknown` when no JaCoCo method matches. Identity is the method signature (`Calc.classify(int, int, String)`, from `structure.json`) plus `#n`; for the `<init>`, `<clinit>` and `<lambda>` units `#n` counts only the entries of the same name and source over the limit (`repeatsInSource` in `shared/rules/finding-helpers.mjs`, also used by `structureFindings`). Java's complexity is `complexity` of `structure.json` (`StructureMetrics.java`), and a `privateEmptyConstructor` entry is left out (JaCoCo often omits those, and their complexity of 1 cannot exceed the limit). A JaCoCo method matches a function when file and name agree (`<init>` is the class name) and its first line lies in the function's range, or, for a constructor, when the descriptor's parameter types match `parameterTypes` (aligned at the end, so synthetic leading parameters of inner classes and enums are skipped; `StructureMetrics.java` writes a type variable as the erasure of its first bound, as the descriptor has it). The JaCoCo `<init>` of a class with field initializers starts at the first initializer, before the constructor. A function at 100% coverage gets `crapScoreLimitCovered`, Java's unknown coverage `crapCoverageUnknownJava`. `options.sourceRoots` maps the project-relative paths to JaCoCo's package-relative ones. `ingestCrapFunctions` is the same ingester over already parsed functions; its `selectMethods` option replaces the name-and-range match (the Kotlin preset passes `selectKotlinMethods`).
- **Format check.** One `format` finding per file in the list; identity is the constant `format`. `javaStyle()` turns the `java.formatter` and `java.indentation` conventions into `google`, `aosp`, `palantir` or `none`: the Gradle and Maven runs add `--aosp` to google-java-format for `aosp`, run palantir-java-format (`com.palantir.javaformat.java.Main --palantir`, pinned as `palantirJavaFormat`, a `format-palantir` classpath in the Maven tool project) for `palantir`, and write an empty `format.txt` for `none` (the Maven tool project then resolves no formatter jar: `formatTool` in `maven-tools.mjs` adds `format` or `format-palantir` as an extra tool), and the finding's tool is `google-java-format` or `palantir-java-format`; its message gives the fix command and the `conventions.java.formatter` pin (`JAVA_FORMATTER_TOOLS` in `java-style.mjs`, also used by `layoutFix` in `rule-messages.mjs` for the `layout` Checkstyle findings, which say to fix by hand under `none`). The runner reads the convention from the head policy file (`NITPICKER_POLICY`) when it starts, so it is not in the analyzer's hash, and passes the style as `-Pnitpicker.java.style=aosp` to Gradle (plus `-Pnitpicker.java.indentation` under `none`) and as `javaStyle` to `runFormat` in `maven-lint.mjs`. Checkstyle's layout checks (`Indentation` among them) are suppressed for every formatter style by `checkstyle-suppressions.xml`, which the Maven run's `checkstyleSetup` passes too, so only the formatter reports layout. Under `none` both runs use `checkstyle-suppressions-unformatted.xml` instead, which keeps the whitespace, brace, tab and indentation checks, and add `UnusedImports` to the bundled config (`unformatted-checks.mjs` for Maven, the same edit in `nitpicker.init.gradle`; `Indentation` moves to the measured width, and tab-indented files drop it and `FileTabCharacter`), so unused imports, which Error Prone's off `RemoveUnusedImports` and the formatter no longer cover, are still findings.
- **Class limits.** `StructureMetrics.java` writes `classes.json` in the same parse as `structure.json`: `{ files: { <path>: { package, imports[] } }, classes: [{ file, name, start, kind, methods, fields, extends? }] }`. `name` is `Outer.Inner`, `kind` is `class`, `interface`, `enum`, `record` or `annotation`, `extends` the superclass as written without type arguments. `methods` are declared methods (constructors not), `fields` instance fields and record components. `inheritanceDepths` resolves `extends` by enclosing names, imports, the same package, wildcard imports and the name in full; a superclass it cannot find counts as one level. One finding per class and limit (`class-methods-limit`, `class-fields-limit`, `inheritance-depth-limit`), identity `<metric>:<name>:occurrence:<n>:<value>`, ratchet key the same without the value. `shared/project-rules/size-rules.mjs` holds the size rule ids, defaults, the Java line length and the message templates, and `shared/policy.mjs` merges them into its tables. `StructureMetrics.java` is run as `<structure.json> <classes.json> <analysisRoot> <sourceRoot>...` and writes both reports from one parse, by the Gradle `nitpickerStructure` task and by `runStructure` in `maven-build.mjs` for each Maven module. `readModuleFindings` in `java-reports.mjs` reads `classes.json` per module, for both presets (the Kotlin preset's `.java` files keep the class limits), with `modulePath` so an exception path and the one a message prints are project-relative in a multi-module Maven build. A missing `classes.json` throws, so the run reports a tool error naming the structure step instead of dropping the limits. The folder-depth root package is the common package prefix of the base snapshot's code (`policy.baselineRoot` on a head run, the snapshot itself on a base run), so a branch cannot move it.
- **Folder depth.** `folder-depth-limit` is one finding per folder and kind of file (`folder-depth:<kind>:<depth>`), `ratchet.pathIsFolder` with `ratchet.folderFiles` (the files in the folder, since `value` is the depth) so a moved folder is matched when more than half its files were renamed to one place. Java: levels below the root package, the longest package prefix the base snapshot's code shares (`module-info.java`, `package-info.java` and default-package files do not vote). TypeScript: folders below `features/<feature>/<layer>/` under a source or test root.
- **Coverage.** Go coverprofile gives a `statement-coverage` metric per file only (blocks lack function names, and line-based identity is not allowed); `options.modulePath` is stripped from import paths. JaCoCo gives `line-coverage` plus `uncovered-method` (class and method name+descriptor); `options.sourceRoot` is prepended. lcov gives `line-coverage` plus `uncovered-function`.
- **PIT.** Follows `docs/mutation-testing.md`: no score gate, new surviving or uncovered mutants fail, other non-killed statuses are report-only, counts go to `mutation-summary`. A mutant is identified by class, method, mutator and description plus its occurrence `#n` among identical keys (by line, then block index). Mutants with unresolvable sources (generated code) are skipped.
- **Duplicates.** jscpd runs once per build, per existing main source root of the merged manifest, writing `duplicates.json` in the report directory as `{ runs: [{ root, report }] }`. Findings match the TypeScript ones: `duplicate-clone` and `duplicate-clone-size`, identified by file pair, cloned-text hash and occurrence.

## Kotlin preset (`languages/java/`)

The Kotlin preset is the Java preset with `kotlin: true`: same init script, runner and ingesters. User-facing behavior is in `docs/kotlin-preset.md`; the protocol details:

- **Switch.** `gradle -Pnitpicker.kotlin=true` turns the Kotlin tasks on in modules applying `org.jetbrains.kotlin.jvm`; without it the init script is the Java one. The runner takes `--preset kotlin`, `--kotlin-formatter` and `--kotlin-detekt-config` (from `kotlin.formatter` and `kotlin.detektConfig`). Gradle always runs with `--no-configuration-cache` (both presets): the init script registers tasks and reads project state at execution time, which a project's `org.gradle.configuration-cache=true` would fail on.
- **Properties.** `kotlin-tools.mjs` resolves, per snapshot, what the init script needs and passes it as `-Pnitpicker.kotlin.formatter=<ktlint|ktfmt|none>`, `.ktfmtStyle=<kotlinlang|google|meta>`, `.ktfmtEditorconfig=true` (ktfmt lists the project), `.styleFile=<path of a JSON file>` (written to a temporary folder by `kotlin-run.mjs` and removed after the run; `{ offset, editorconfigs: [{ path, text }], ktlintDefaults, detektConventions }`, generated by `kotlin-style-files.mjs` and `style/editorconfig-mirror.mjs`: the `.editorconfig` files under the policy root and above it up to the repository root, `offset` being the policy root inside the repository, so the init script mirrors the sources at `<offset>/<module>/...`), `.detektLayers=<conventions,project>` and `.detektConfig=<absolute path in the head checkout>`; the project style files are read from the policy root (the head checkout) for both snapshots. Without the formatter property the init script runs no format check. The analyzer is named `kotlin`, and its tool-error and `baseline-expansion` findings use that name.
- **Reports.** `detekt.sarif`, `ktlint.sarif` (ktlint's SARIF reporter, relative paths) and `ktfmt.txt` (project-relative Kotlin files, one per line); only the detected formatter's file is read. Skipped Java tools in a Kotlin-only module write empty reports so the Nitpicker side reads one layout. `manifest.json` in this mode: `sourceRoots` are the Java roots only, `kotlinSourceRoots` the Kotlin plugin's source directories (which include `src/main/java`), `kotlin: true`, `kotlinFormatter`. `readKotlinFindings` throws when `kotlin` is absent, so a project without the Kotlin plugin is a tool error and not an empty pass.
- **Java-only class tools.** `analyzedClassDirs` is the output of `compileJava` in this mode (all main class directories otherwise); SpotBugs reads it. SpotBugs gets the rest of the runtime classpath as `-auxclasspath`. PIT reads `mutatedClassDirs` (all main class directories, Java and Kotlin) in both presets, and jdeps reads every main class directory in both modes.
- **Function units.** Every preset measures the same units, so a limit means the same everywhere: a function, method or constructor with a body, a lambda, arrow function or anonymous function (TypeScript's callbacks, Java and Kotlin lambdas, Python `lambda`), and the code that runs at class initialization (Java static and instance initializer blocks, Kotlin `init` blocks and property initializers that branch). A unit's statements, control nesting and complexity never count towards the unit around it (TypeScript's analyzer stops at nested functions, and so do `StructureMetrics.java`, `KotlinMetrics.java` and `structure_metrics.py`); `lines` is the physical span, so the lines of a nested unit still count towards the one around it, in every language. A lambda is named after the unit that holds it plus `<lambda>`, or after the variable or property it initializes; `repeatsInSource` makes `<init>`, `<clinit>` and `<lambda>` findings number only among the same name and source over the limit. Coverage: JaCoCo's `lambda$...` synthetic methods for Java, the method or the lines of the lambda for Kotlin, the line of the creating statement for Python (coverage.py has nothing finer). TypeScript's CRAP check (`@barney-media/crap-typescript-core`) scores named and assigned functions only and drops the complexity of an anonymous callback from the function around it, a limit of that library.
- **Kotlin metrics (KT3).** `languages/java/gradle/KotlinMetrics.java` is run by task `nitpickerKotlinMetrics` as `java -cp <kotlin-compiler-embeddable and its dependencies> KotlinMetrics.java <out> <projectDir> <kotlinSourceRoot>...` and writes `kotlin-metrics.json`: `functions` (one object per unit: `file`, `name`, `start`, `end`, `lines`, `statements`, `maxControlNesting`, `parameters`, `complexity`, `inline`, `initializer`, `lambda`) and `files` (`file`, `package`, `classes`: the JVM names of its top-level classes and file facade). A syntax error exits the program with the file, line and pinned version (the sources compiled, so the compiler is too old). It builds a `KotlinCoreEnvironment` and needs an extension storage registered on the configuration (`FrontendConfigurationKeysKt.setExtensionsStorage`); that is compiler-internal API, so a bump of `kotlinCompiler` in the init script is tested with `npm run test:kotlin` (it includes `kotlin-metrics.e2e.test.mjs`, which pins the compiler on its own); `.github/workflows/kotlin-e2e.yml` runs the whole `npm run test:kotlin` suite (about 15 minutes) on a push to `main` that changes `languages/java/**`, `core/**`, `shared/**`, `package.json`, `package-lock.json`, `vitest.config.mts` or the workflow, by hand (`workflow_dispatch`), and on a pull request when the `run-ci` label is added. `kotlin-metrics.mjs` turns `functions` into structure findings (the Java path, `structureFindings`) and into CRAP findings (`ingestCrapFunctions` with `selectKotlinMethods`, which matches a function's JaCoCo methods by first line within its range, skipping `$default`, methods inside a unit of their own and the bridge a `@JvmStatic` function leaves in the outer class; `inline` units get no CRAP score; an `initializer` unit (an `init` block, named `Class.<init>` (several blocks of a class share the name; the structure ratchet and the CRAP identity, through `numberedAmongSameSource`, number a finding only among the blocks of that name and source text that are over the same limit, so no other block, under the limit or of other text, and no order of them renames it), or a property initializer that is not a lambda or a call with a lambda but branches or holds braces of its own) runs inside `<init>` or `<clinit>`, whose JaCoCo method starts outside the unit, so `ingestCrapFunctions` joins it through `lineScoped`: the per-line counters of the file's `<sourcefile>` (`ingest/coverage-reports/jacoco-lines.mjs`, one pseudo-method per line) inside its range and outside the units nested in it, through the same `selectKotlinMethods`; the JaCoCo file is found by `package/FileName.kt`, not by directory; a `lambda` unit (a lambda, an anonymous function or a local function, named `Owner.fn.<lambda>` or after the local function or property, `Owner.property` for a property whose initializer or delegate is a call with a lambda) is joined to the JaCoCo method that starts in its range and outside the units nested in it, and, when the compiler inlined it so that no method of its own exists (`run { }`, `map { }`), through `lineFallback` to the per-line counters of its range; the function around an inlined lambda is then scored without the covered and total lines of that lambda, unless that would leave nothing to measure (`languages/java/ingest/units/unit-coverage.mjs`)), and `files` into the module map `analyzeJavaCoupling` takes (`moduleOf`, `fileOf`).
- **Kotlin clones.** `runJavaDuplicates(projectRoot, { format: 'kotlin', rootsKey: 'kotlinSourceRoots', reportFile: 'kotlin-duplicates.json' })` after the Java run; the report is read with `readDuplicateFindings` and the same rule and tool name `duplicates`.
- **detekt and ktlint SARIF.** No fingerprints, so the glue sets `nitpicker/subject` from the message text with every whole number replaced by `#` (`\b\d+\b`: a name ending in digits keeps its digits), so a measured value does not change identity, and keeps the SARIF levels (`note` stays descriptive, unlike SpotBugs). Rule ids are kept in detekt's form `detekt.<ruleset>.<Rule>`.
- **Formatter detection** is a text search of the root project's build files (not Gradle API introspection), so it works for plugin ids, version catalogs and Spotless alike. Comments are removed first and a Spotless `kotlinGradle { }` block is cut out (its formatter formats the build scripts, not the Kotlin sources); a string literal that names the other tool still matches. `ktlint` in the build files beats `ktfmt`, and `ktlint_` keys in `.editorconfig` count only when the build files name neither.
- **Source directories** are the Kotlin plugin's main `srcDirs` that exist, are inside the project and are not under the build directory (generated code). `kotlinFiles` and `kotlinSourceRoots` stay main-only (structure, CRAP, duplicates and coverage read main code); detekt, ktlint and ktfmt read `kotlinLintedDirs` (main plus the `test` source set's directories, `kotlinTestSourceRoots` in the manifest), and the detekt classpath adds the test compile classpath and the `compileTestJava` output (the main classes are dropped from it, because `analyzedClassDirs` carries them). `kotlinLintedRoots` in `kotlin-reports.mjs` gives `readSuppressionFindings` the same roots, so an inline suppression is banned in tests too. Detekt's default config excludes 15 rules from `**/test/**`; the owned rules in `nitpicker-detekt.yml` reset `excludes: []` and so stay on in tests, and `TooGenericExceptionCaught` is owned (ruleset `exceptions`, with the exception names spelled out so that the default does not need the test exclusion) so that the broad-catch ban applies to tests as it does to Java (#224). A legacy test finding is not new because the head's init script runs on both snapshots.
- **detekt config validation** is switched off by a second `--config` file (`languages/java/detekt/detekt-validation.yml`), listed after the project's and Nitpicker's, because the CLI exits with code 3 on rulesets of plugins it does not load.
- **Missing reports.** A build where no project applies the plugin writes an empty `modules.json`; `readReportModules` turns that into an error naming the plugin, and a listed project without reports into one naming the project (both presets).
- **Branch coverage** (`changed-branch-coverage`) reads the source text of every file under `jacocoSourceRoots` (Java roots plus `kotlinSourceRoots`). A `.kt` line is dropped when `isCompilerGeneratedBranchLine` (`kotlin-branches.mjs`) finds a suspension call and nothing that can branch in its code (string literals, comments and type arguments removed); every other line is kept, since the JaCoCo XML has branch counts per line and no instruction detail and a statement that spans lines is reported on the line of its operand. A kept line with a suspension call gets the `arms` hint in its message. Report files are located by `sourceLocator` (`kotlin-reports.mjs`): by directory first, then, for `.kt`, by file name and `package` declaration; the same lookup resolves PIT's `sourceFile`, and a `.kt` file with missed branches that is not found (outside `kotlin`/`kotlinx`) is a descriptive `branch-source-not-found`. The measurement behind it is in `docs/kotlin-preset.md`.
- **Mutation.** `pitFindings` resolves a class's source file under `jacocoSourceRoots` and `reportOnlyKotlinMutants` turns `mutant-*` findings of `.kt` files into `descriptive` ones (the `mutation-summary` counts are unchanged). The Java preset does not call it.
- **One-way rules** (`kotlin-rules.mjs`, `nitpicker-detekt.yml`). `ONE_WAY_RULES` is the list of rules in the yml with the sentence the gate appends when detekt's text does not name the allowed form (`addOneWayHint`, after ingestion, so identity, which is the detekt text, never changes); every rule also gets the exception route. `ForbiddenMethodCall` and the other rules with a `reason` field carry the allowed form in the yml instead. The yml follows the project's config in the `--config` list of the detekt task (only the validation file comes after it), and detekt gives the later file priority per key, so a project's `detekt.yml` cannot override it. Every ruleset and rule in the yml pins `active: true`, `excludes: []` and `includes: []`, and every rule `severity: warning` (the reader classifies SARIF `note` as descriptive, so a project's `severity: info` would otherwise un-gate the rule); `excludes: []` also replaces the default that skips `**/test/**` for `UnsafeCallOnNullableType`, which would skip a production package named `test`. `kotlin-rules.test.mjs` reads the yml and fails when its rules differ from `ONE_WAY_RULES` or one lacks a pin. `UseDataClass` has `allowVars: true` because `DataClassShouldBeImmutable` bans the `var` that `UseDataClass` would otherwise ask to turn into a data class. `runBlocking` is a `ForbiddenMethodCall` entry (type resolution finds the call whatever the import), so it shares the rule id, and the exception, of `run`, `with` and `also`. `ignoreAnnotated: []` is pinned too, next to `excludes: []`, because detekt skips the code of classes carrying a listed annotation for any rule. The one list the yml sets, `ForbiddenMethodCall.methods`, is merged with the project's (detekt replaces a list): `adapters/kotlin/detekt/detekt-lists.mjs` reads the project's detekt file with the `yaml` package (a dependency, loaded lazily with `createRequire`, like `smol-toml`; the parser's alias limit and a parse failure both yield an empty list), keeps the entries that are a method name with an optional balanced parameter list (anything else could crash detekt), appends those the yml does not list and writes the result to `build/nitpicker/detekt-lists.yml`. `kotlin-tools.mjs` passes it as `-Pnitpicker.kotlin.detektLists=<absolute path>`, and the init script puts it in the `--config` list after the project's file and the yml (before the validation file); it carries only the list, so the yml still pins `active`, `severity`, `excludes`, `includes` and `ignoreAnnotated`. The file is written only when the project adds a call. `ForbiddenImport` is not set by the yml, so detekt's own handling of the project's list stands.
- **Type resolution classpath.** Detekt 1.23.8 embeds Kotlin 2.0.21 (it resolved a 2.1.0 standard library, not a 2.4.21 one). The stdlib it needs for `run`, `with`, `also` and `!!` is therefore `kotlin-stdlib:2.0.21` (`pinned.detektKotlin`, the version in the detekt jar's `META-INF/compiler.version`), first on the classpath, and every `kotlin-stdlib*` jar of the project is dropped. With the project's 2.4 stdlib the same run reported nothing for those calls and wrongly flagged `?.` on values of an unresolved type. `--jdk-home` is the installation path of the project's Gradle Java toolchain (`JavaPluginExtension.toolchain`, which `kotlin { jvmToolchain(n) }` also sets) when the project declares one, else the Gradle JVM's `java.home`; without it JDK types (`StringBuilder`) do not resolve. Bump `detektKotlin` together with `detekt`.
- **Exceptions.** `--exception <rule>:<glob>` (split at the first colon, one per path) reaches `applyJavaPolicy`, which drops findings of that exact rule id under the glob on both snapshots. `validateKotlinOptions` accepts only `ONE_WAY_RULE_IDS` so a typo is an error. Python can reuse the mechanism.
- **Inline suppression.** `kotlin-suppressions.mjs` reads the string literals inside `@Suppress`/`@SuppressWarnings` with any use-site target, after `kotlin-literals.mjs` has masked the source: one pass over comments (nested block comments), strings with `${}` templates, raw strings and character literals, which replaces each string by a numbered placeholder so that a comment opener in a string, or an annotation in a string, does not matter. `isBannedSuppression` bans every token that can target a detekt or ktlint rule: `all` in any letter case, anything starting with `detekt` or `ktlint` followed by `.`, `:` or the end, a detekt ruleset name, and a PascalCase token (every detekt rule id; detekt honors the bare id). Kotlin compiler diagnostics are UPPER_SNAKE or lowercase (`UNCHECKED_CAST`, `unused`) and stay allowed. detekt's `ForbiddenSuppress` cannot do this alone: a suppression of `style` or `all` also hides the `ForbiddenSuppress` finding on the same annotation.
- **Fixture cases.** `test-support/kotlin-rule-cases.mjs` (next to the Kotlin rules) holds, per rule, the banned and the allowed source (`{name}` stands for the file's class name, `Banned` or `Allowed`), the detekt message recorded from the real run, and the wording the final message must contain. The CI test checks the wording against the recorded message; the end-to-end test checks the recorded message against real detekt, so a detekt or yml change that alters a message fails there.

Definition (McCabe, the decision points of the other presets; a lambda is an entry of its own like a TypeScript arrow function, and the `for` and `if` clauses of a comprehension count): 1 plus one per decision point in the function's own body, where decision points are `if` and `elif`, a conditional expression, `for` and `async for`, `while`, each `except` handler, each `case` of a `match` but a guard-less `case _` (the `default` of a `switch`, which ESLint's `complexity` rule and the Java and Kotlin metrics do not count either), each extra operand of `and` and `or`, and each `for` and `if` clause of a comprehension. `else`, `finally`, loop and `try` `else`, `with` and `assert` add nothing; comprehensions belong to the enclosing function; lambdas (named after the scope and the name they are assigned to, else `<lambda>`, with `lambda: true` and `statementLine`), nested functions and the methods of nested classes are entries of their own and add nothing to it. A lambda has no coverage.py entry or line of its own, so its coverage is that of the statement that creates it (100 when the statement ran, 0 when it did not). Control nesting treats an `elif` as the same level as its `if`, like `else if` in the TypeScript and Java analyzers; an `else:` block holding an `if` is one level deeper. The entries also carry `definition` (the `def` line) and `bodyStart` (first body line); a function whose body starts on its `def` line is left out of CRAP, because its statements share the line that runs at import. Coverage entries are joined to functions by qualified name (the names coverage.py reports) and line range, not `start_line`, which older coverage.py versions do not report. coverage.py keeps one entry per qualified name, so a function no entry covers (property setter pair, `singledispatch` `_`, conditional definitions) is scored from the file's per-line and per-branch data over its own range, minus nested functions.

it takes a file list, a report path and an options file (`rule-options.json`), parses each file once with `ast`, finds comments with `tokenize`, and works in two phases. `index/project.py` first builds a `Project` over all the files (the names each defines, suffixes, module names and relative imports, one context per file, the test files, a memo, and `locate` for the definition a call refers to), so a rule can follow a call into another file; then every module of `checks/` (comments, declarations, shell, state), `security/` (`sql/`, tls, hashes, timeouts, loading), `discovery/` (test collection, helpers), `environment/`, `errors/` (`errors.py` and `handling.py` for `swallowed-exception` and `blind-suppress`; `logged_errors.py` for `catch-log-without-exception`: a `warning`, `error` or `critical` call in an `except ... as name` body that uses the caught name and neither keeps the traceback nor sits in a handler that re-raises, nested handlers included, through the shared `is_log_owner`, asked by `errors.py` only for a handler it finds handled, so a handler that only logs is reported once, as `swallowed-exception`), `boundary/`, `silent_tests/` (`unasserted.py` for `test-without-assertion` over each test function of a collected test file, fixtures excluded, with `calls.py` for what counts as an assertion and `helpers.py` for the project's assertion helpers, found in a first pass over all files as the names whose `def` in test or support code asserts in its own body and that end the assertion-free tests of at least three test files), `smells/` and `honesty/` runs its `check(context)` (`checks/common.py` holds the shared helpers: import aliases resolved to dotted names, test, domain and boundary path detection, logger call detection; `smells/io_index.py` is the index of input and output functions that `io-in-loop` uses; `security/resolve/` is the value resolution the five security rules share: `scopes.py` resolves a name to what it is bound to (in the function, the enclosing functions, the module or the project module it is imported from, with parameter defaults and loop targets of `enumerate`, `zip` and `.items()`), `classes.py` indexes each class once per project (class-body values, annotations, methods, `self.x` writes in any method, dataclass `field(default_factory=...)`, and subclass overrides of an attribute only for subclasses whose base resolves to that class) and resolves `self.x`, `cls.X`, `type(self).x`, `Class.X` and attributes of an imported project module, `calls.py` gives the effective calls (a `functools.partial` is checked where it is defined unless it is bound to a name that is called, then at each call with the bound arguments merged; also `getattr(x, "name")` and method aliases) and the entries of an options dict (a literal, `dict(...)`, `**options`, and writes in the same scope: `d[k] = v`, `update`, `setdefault`), and `booleans.py` answers whether a value can be `False` or `True` (an `or` can be `False` only through its last operand). Every index is built once per project in its memo, and a check resolves receivers only for the method names it watches, so a file costs one pass per check. `security/sql/` holds `check.py` (the SQL shape: statements including DDL and `MERGE`, clauses in SQL shape), `sinks.py` (query calls by name pattern, aliases, the raw builders and the wrapper index, a project memo of functions and methods that pass a positional or keyword-only parameter straight to a query call), `pieces.py`, `iterables.py` and `shapes.py` (each piece of a built query as text, inert or unsafe, allowlist guards and annotations) and `schema.py` (SQLAlchemy and Django metadata); `security/tls/` and `security/timeouts/` split the switches and client factories from the check, and `security/support.py` decides the test support files.) A security check runs inside a guard: an exception in it becomes one `rules-check-failed` entry naming the check, the file and the error (a `python-rules/rules-check-failed` tool error), and the other checks and files still report; the other checks are not guarded, so a bug there still fails the run loudly as `rules-failed`. It writes `[{rule, path, subject, line}]` sorted by path, line, rule and subject, and beside it `rules-allowances.json` with `supportFiles` (the test support files whose security findings are dropped, ruff's included) and `allowed` (`{rule, path, line}` sites of ruff findings that the script proved to be an allowed form: `S303` on the digest of an HMAC or of RSA-OAEP/`MGF1`, `S506` on `yaml.load` with a loader deriving from `SafeLoader`), which `adapters/analysis/python-ast-rules.mjs` reads (`readAllowances`, empty when the file is missing); a subject repeated in a file is numbered `#n` by the ingester. Files that do not parse or tokenize are skipped, and the modules are imported inside `main` so the script writes no bytecode into the tree (the configuration hash covers every file under `languages/python/`). Messages are not in the script: `rules/hints/` owns every message (`rule-hints.mjs` assembles them), so they are testable without Python. The options file is how a rule reads a project fact that only JavaScript knows: `sourceRoots`, `testRunner`, the whole pytest collection configuration (`pythonFiles`, `pythonClasses`, `pythonFunctions`, `norecursedirs`, `testpaths`, `deselected`, `ignored`, `ignoredGlobs`, `keywords`; read by `pytest/pytest-config.mjs` from `pytest.ini`, `pyproject.toml`, `tox.ini` and `setup.cfg`), `testFiles` (the files pytest collects, which also decide the test-file exemptions of ruff's findings), and `entryFiles` and `entryModules` (`python.entryPoints` and the script entry points of `pyproject.toml` and `setup.cfg`, read by `libraries/entry-modules.mjs`), which make a file a composition root. Why these rules are heuristics and where they stop: a taint rule such as `unsafe-path-join` follows names inside one function only (six assignment steps), `handwritten-boundary-guard` knows the parsers it lists, and `io-in-loop` knows the HTTP, database and repository names it lists plus receivers named like a repository or client; each has fixtures of the correct form that must stay quiet, and a project with an unusual form lifts the rule for its path with `python.exceptions`. Ruff cannot express two allowed forms, so `rules/filters/ruff-allowed-forms.mjs` drops, after ruff runs, `PLR2004` findings for the numbers the TypeScript preset allows and `S602`/`S604`/`S605` findings for a literal command (ruff words them "seems safe"), the ruff findings on the sites the rules script listed in `allowed` (so `weak-hmac` reports HMAC-MD5 once and HMAC-SHA1 is allowed, found from the syntax tree, not the text), and ruff's security findings in the listed `supportFiles` (`rules/filters/test-support.mjs`). The script drops its own security findings in the same files: files under a test root (the pytest `testpaths`, `tests`, `test`), `conftest.py`, and the folder and file names the TypeScript preset's security scope uses, in their Python spelling, when they sit inside a test root or no production module imports them (`security/support.py`, a fixed point over the project's imports).
- **Hints and exceptions.** `applyRuleHints` (both parts) appends the allowed form (when the rule has one) and the one exception sentence, `exceptionSentence`, to enforceable findings not on `.` of `ruff`, the type checkers, `python-rules`, `coverage-py`, `duplicates`, `coupling`, `import-linter`, `dependencies`, `test-runtime` and `mutmut` by rule id (a prefix for `PTH`; `no-import-outside-roots` is routed by its setting instead; `exception-sentences.test.mjs` fails on any other file that writes a route); an entry with `exception: false` carries its own advice instead; `allowed` and `describe` may be functions of `(subject, libraries)`, where `subject` is the script finding's subject (kept on the finding until `withHint` strips it) and `libraries` is `{ logging, validator, validators, pytestStyle }`, read from the project's dependencies and test code by `rules/libraries/` (`detectLibraries`, `pytestStyle`; `DEFAULT_LIBRARIES` when the project shows none), so one rule words its advice for structlog or loguru, pydantic, msgspec, cattrs or marshmallow, and the pytest style the project already uses (`pytestStyleFlags` also hands that style to ruff as `--config` flags; an explicit `flake8-pytest-style` table in the project's ruff configuration wins over the measured one); other findings pass through. Identity is computed before, so a reworded hint never re-baselines; `on line N` and `from line N` are stripped from identity subjects (`withoutLineNumbers`), so moved code keeps its identity. `python.exceptions` filters findings by rule id (exact, or a ruff prefix such as `PTH` for ruff findings) and path glob after hints; the ids are validated when the config loads (`python-rule-ids.mjs`: the ruff selection, the `python-rules` ids, pyright and basedpyright `report*` names, mypy code spelling) and before `exclude` and the legacy inventory; the base snapshot uses the base's config, like every other setting.
- **Shared policy.** `exclude` and the legacy inventory are `configureJavaAnalyzer` / `applyJavaPolicy`, both language-neutral; `applyJavaPolicy` takes `inventoryTool` for the tool of a `baseline-expansion` finding.
- **Duplicates, coupling, import-linter.** More reports in the directory: `duplicates.json` (Java's `runJscpd` output shape; Python passes `together` to run once over all roots, with absolute names made project-relative, and reads it with its own `readDuplicateFindings`, which drops import-only clones; `runJscpd` always passes a nitpicker-owned `jscpd-config.json` so a project's `.jscpd.json` is never read), `imports.json` (`{ modules: [{ file, module, isPackage }], imports: { file: [{ level, module, names, typeOnly }] } }`: the module list comes from `python-sources.mjs`, the statements from `import-scan.py`, which only parses and never resolves) and `import-linter.txt`. Resolving imports to modules, packages and the stability graph is JavaScript (`python-coupling.mjs` into `buildCouplingReport` of `shared/rules/coupling.mjs`), so only the scan needs Python. `typeOnly` is true for a statement under `if TYPE_CHECKING:` (the flag is `TYPE_CHECKING` from `typing` / `typing_extensions`, as `typing.TYPE_CHECKING` or an alias, or the module-level `TYPE_CHECKING = False` idiom; one operand of an `and` counts; other `TYPE_CHECKING` names are plain names) and for the `else` branch of `if not TYPE_CHECKING:`; the `else` of `if TYPE_CHECKING:` is not. `collect` walks the tree with an explicit stack because a recursive walk drops a file with a 1000-branch `elif` chain or a 2500-term sum into `RecursionError`, which `scan` would skip silently. `importEdges` gives each edge `kind: 'runtime'` or `'type-only'`, an edge is type-only only when every statement behind it is, and `buildCouplingReport` computes every metric, package instability included, from all edges, and `computeCoupling` skips an edge of `kind: 'type-only'` only as the candidate dependency of a `stability-direction` violation; TypeScript `import type` edges get the same treatment through the same function (recomputing instability without them would let moving unrelated imports under `TYPE_CHECKING` create a violation elsewhere). import-linter counts them unless the project sets `exclude_type_checking_imports`. A file the scan cannot parse is skipped silently. The import-linter text report is parsed in `ingest/import-linter.mjs`; its identity per chain ignores line numbers, and the order import-linter prints chains in is not stable, so tests must not depend on it.
- **Runner parity.** `test-runs/` holds the JUnit reader, the pytest option pins (`-o addopts=` and a filtered `PYTEST_ADDOPTS`), the test step and the `tests/tests-failed` and `test-runtime/slow-test` findings; pytest runs as `pytest_timings.py <pytest arguments>` (`pytest.main` with one plugin object: a `pytest_fixture_setup` hook wrapper sums the setup time of `scope == "function"` fixtures per item, which includes `setup_method`'s generated fixture and not `setup_class`'s, and adds it to the call report's `duration`, which `-o junit_duration_report=call` writes; `pytest_collection_modifyitems` appends a `nitpicker_marks` user property with the names of `item.iter_markers()`, so a `pytest.param` mark reaches only its case), and unittest runs through `unittest_timings.py <report> discover ...` (a `TextTestRunner` whose result times `startTest` to `stopTest` and writes the same report, with the class's module and qualified name as `classname` and the file and 0-based line of the unwrapped method's code, as pytest's `file` is where the function is defined), so both runners feed one reader. `slow-tests.mjs` takes the collecting file and class from the longest `classname` prefix that is a project file. `python-blocks.mjs` splits a file into logical lines (bracket depth, single and triple-quoted strings, backslash continuations, comment-only lines as blank) and returns each `def` block (decorators, signature, body) with its name, its `owner` (the enclosing class and function names) and its marks (its decorators, every enclosing class's decorators and class-body `pytestmark`, the module `pytestmark`; `withoutParamCalls` drops `param(...)` calls when no recorded marks exist), plus `classHeader` and `mentions` (the logical lines naming a test); the head block is the one at the reported line (a factory's inner function when the name differs), else the one with that name in the collecting class; a test is unchanged when the base file at its path, or else a base test file the head no longer has, has the identical block with the same owner, and, for an inherited or factory-built test, the collecting class's header and the lines naming the test are in the base too; Java's `test-times/inherited-tests.mjs` follows `extends` the same way for a test method its class does not declare; `size/` the folder-depth and class limits over the shared `shared/rules/size/` rules, with the Python defaults and `PYTHON_SIZE_RULES` in `shared/project-rules/size-rules.mjs` (folder depth: each module's package path after the leading namespace folders of its top-level tree, `namespaceDepths`: the index of the tree's shallowest package capped at the folder prefix all the tree's modules share, from the base for trees the base has and from the head otherwise, measured below the common prefix of the base's production modules, as Java's root; test files from `imports.others` are entries of kind `test` whose path drops the source root and the `tests`/`test` folders; class limits: `metrics/class_metrics.py` writes `kind` `protocol` (a `Protocol` base), `interface` (an `ABC`/`ABCMeta` class whose methods are all `@abstractmethod`), `record` (`@dataclass`, attrs decorators, `NamedTuple`, `TypedDict`) or `class`, no fields for the first two, no `@overload` stubs as methods, and `self.x` without entering nested classes; the inheritance walk is memoized per class, counts only resolved project bases and stops at protocol and interface kinds; a base that resolves to the class itself takes the import instead, and when Kahn's queue runs dry with classes left (a cycle and what inherits from it), the first one left is queued with the depth of its parents already measured, which breaks the cycle there and lets the walk go on); `libraries/generated-files.mjs` marks `*_pb2.py`, `*_pb2_grpc.py` (and `.pyi`), a generated-looking path (`generated/`, `_generated/`, `__generated__/`, `*_generated.py`) with `hasGeneratorMarker`, and any file with `hasGeneratorHeader`, which the source listing, the file limits and folder depth leave out (`shared/conventions/generator-marker.mjs`: `hasGeneratorMarker` tests the generic markers on the first five lines, and TypeScript's `markedGeneratedFiles` also gates it on `mayBeGenerated`; `hasGeneratorHeader` matches the exact lines protoc, gRPC Python, datamodel-codegen, OpenAPI Generator, protobuf-es, Thrift and the `Code generated by <tool>. DO NOT EDIT.` convention write against `headerLines`, the leading `#`, `//` and `/* */` comments and one module docstring, so it counts for any file name; `markedGeneratedFiles` reads the first 16 KB of every code file for it, and the evals' `detectGeneratorMarkers` flags either kind written into a file by hand); test files come from the pytest collection configuration (`testFileMatcher` in `python-sources.mjs` over `testFileOptions` and `isTestFile` in `configuration/pytest/collection-options.mjs`), the same as the rules use: `test_*.py`, `*_test.py`, the project's `python_files` except a pattern that matches the probe names `a.py`, `service.py` and `models.py` (then a file under a `testpaths` folder is a test instead), and `DJANGO_TEST_FILES` only when `isDjangoProject` (a Django distribution, `manage.py`, or `DJANGO_SETTINGS_MODULE` in the pytest options), which the coverage `omit`, mutmut's `do_not_mutate` and `nonProductionGlobs` follow too; `imports/` the cycle and outside-roots rules over `imports.json` (which also lists the non-production `others`); `dependencies/` the distribution scan, the dependency findings, the framework allowances and the packages a framework loads for the project (`impliedDistributions`: a detected framework plus a marker in the project's code, such as Django's `ImageField` for `pillow`); `languages/python/libraries/python-dependencies.mjs` the declared-dependency reader, with its parts in `languages/python/libraries/dependencies/`; `mutation/test-run/mutation-scope.mjs` the Python version skip and the failing-module exclusion, `mutation/mutation-markers.mjs` the `mutant-ignored` findings.
