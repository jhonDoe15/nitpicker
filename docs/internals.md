# Internals

Contributor notes on formats and protocols that code and names cannot carry. Source files stay comment-free (`nitpicker/no-comments`).

## Diff engine (`core/`)

- **Custom analyzers.** A `{name, command, args?}` config entry runs with the analyzed checkout as working directory, so a relative command resolves inside each side. It prints findings JSON on stdout and exits 0; stdout goes through the same parser as built-in analyzers, and a non-zero exit or invalid JSON becomes a tool error.
- **Exit codes.** New violations win over tool errors so CI can tell "violations" from "broken"; `overallStatus` reports tool health first.
- **Analyzer environment.** Analyzers never see where the GitHub Actions job summary lives (`HOST_CI_OUTPUT_VARIABLES`): vitest and Stryker would append their own reports to it, and caught mutants read as test failures.
- **Cache stores.** A store keeps opaque text under a hex key, is synchronous and never throws: `get` returns undefined on any miss or failure, `put` returns whether the value was stored. The local directory is `NITPICKER_CACHE_DIR`, else `node_modules/.cache/nitpicker`. The HTTP store does `GET`/`PUT` of `<baseUrl>/<key>.json` with an optional `Name: value` auth header, and stays off after its first non-miss failure so an unreachable server costs one timeout. Reads try local, then remote (copying a hit locally); writes go to the remote store only with `writeRemote`.
- **HTTP cache worker.** Exit codes: 0 success (GET prints the body), 3 not found, 1 any other failure. The comparison is synchronous, so each request runs in a short-lived `node` child that does the asynchronous fetch: `<GET|PUT> <url> <timeoutMs>`, auth header in `NITPICKER_CACHE_AUTH_HEADER_VALUE` (never argv). S3 answers 403 for a missing key when the caller cannot list the bucket, so 403 counts as not found. The test HTTP server lives in a worker thread for the same reason: the stores block the calling thread.
- **Findings cache key.** Base commit, project, analyzer, tool version, configuration hash, head policy (exclude, layout, exceptions, thresholds) and legacy inventory path. The policy is keyed explicitly because layout and threshold changes rebuild an analyzer without changing its file-based hash. Entries carry their own key, so a misnamed entry is a miss. Only clean reports are stored, and cached analyzers still run when an uncached one depends on them.
- **Publishing a base snapshot.** `cache publish` analyzes HEAD (typically the new tip of `main`) and stores clean reports under the keys later comparisons use when HEAD is their merge base, using HEAD's own policy.
- **Comparison.** Findings split into new, resolved, unchanged and changed-metric. With `touchedCode`, an enforceable finding of a strict rule inside touched lines is new even though the base has it.
- **Cycle identity.** Dependency cycles are `cycle:a>b>c|...`, starting at the lexicographically smallest rotation. A rename can change that rotation, so renamed cycles are re-rotated before comparing.
- **Report hash.** Zero config keeps the original policy hash input; any override changes it.
- **SARIF output.** One result per new finding; the hashed comparison key is `partialFingerprints["nitpickerIdentity/v1"]`, so consumers match findings across runs when lines move. Tool errors become unsuccessful tool-execution notifications.
- **Base commit of a checkout.** `git.mjs` stages the checkout (untracked, non-ignored files included) in a copy of the index, leaving the user's index, branches and files untouched.
- **Policy links.** Without `transform` the package-owned policy file is linked into the analyzed tree; with one (the layout changed) it is a rewritten copy, still derived from the head policy and never from the analyzed tree.
- **Temporary files.** Register before creating the file so it is removed on exit or interruption even if the runner's `finally` blocks never run.
- **Presets.** `preset` is explicit; there is no Gradle auto-detection. Injected analyzers win over the preset.

## Shared rules (`shared/`, `spec/`)

Findings follow `spec/findings.schema.json`. Identity (the part of the comparison key beyond rule and path) never contains line numbers, so edits above a finding do not change it.

## TypeScript preset (`languages/typescript/`)

- **Strict preset assembly.** Flat config replaces rather than merges a rule's options when several entries match a file, so each scope in `strict.mjs` carries its full `no-restricted-syntax` list: the everywhere selectors plus the scope's own. Add a selector to its scope's list, never as a separate entry for a narrower glob. `domain/` has its own loop and forEach selectors, so it takes only the promise-chain selectors from the production set. The standalone `strict-*.mjs` configs exist so the failure-message harness can lint one rule family alone; the typed ones need `parserOptions` (e.g. `{ project: './tsconfig.quality.json', tsconfigRootDir }`) and later entries win.
- **React scope.** `eslint.config.mjs` adds `reactScopeConfigFor()` and passes `{ react: true }` to `strictPresetConfig()` only when `isReactProject()` says so: the head policy's `react.enabled` when set, else `react` in the analyzed tree's `dependencies` or `devDependencies` (read from `NITPICKER_DIFF_ESLINT_PROJECT_ROOT`, the tree being linted, so base and head are each judged by their own manifest unless the config pins it). The plugins load through a dynamic import, so a non-React run never pays for them. `react: true` changes one `strict-declarations.mjs` selector: classes extending `Component` or `PureComponent` leave the "classes only for `Error` subclasses" ban and belong to `react-x/no-class-component`. The head policy carries `react` only when the config sets it, which keeps zero-config cache keys unchanged. `react-rules.mjs` lists every React rule id (strict, like the other scopes' rules); `react-scope.test.mjs` checks it against the config and the accessibility names against the plugin's recommended set. The test rules (`reactTestRuleIds`) are a second entry in `reactSyntaxConfigFor()`, scoped to test files (`layout.testGlobs` plus `__tests__` directories) and independent of the runner: `eslint-plugin-testing-library` (peer range includes ESLint 10) supplies `no-test-id-queries`, `no-node-access` (which also reports `container.querySelector`, so `no-container` is left out to avoid a second message), `prefer-user-event` and `await-async-events`, wrapped with `withHint()`; `nitpicker/react-test-no-implementation-details` covers what the plugin does not (component instances and state, fiber internals, spies on React hooks).
- **Third-party rule messages.** `withHint()` in `rule-hints.mjs` wraps a plugin rule so its messages end with a nitpicker hint (the exception route, or the allowed form), for rules that report by `messageId` and by `message`. The failure-message harness lints with the wrapped rules, so the hint is tested. Custom React rules (`react-no-effect-*`, `react-single-styling-approach`) exist where no ESLint 10 plugin rule names the allowed form: `react-hooks/set-state-in-effect` is a React Compiler rule with a multi-paragraph message and no exception route.
- **Failure messages.** Each case in `failure-messages/cases.mjs` has a `config`, a `banned` fixture that must fail, and an `allowed` wording (case-insensitive substring) the message must use to name the allowed form. Zod is a documented expectation of the preset, not a dependency.
- **Error wrapping.** Classified wrappers that sanitize external failures list `classificationIndex` and `unclassifiedValue`; only unclassified wrappers must carry the original cause.
- **Exceptions.** Lifted rules and paths come only from `nitpicker.config.json`; inline disables are banned, so this is the one way out.
- **`strict-rules.mjs`.** The rule id list is written out because building `strictPresetConfig` loads typescript-eslint; `strict-rules.test.mjs` asserts it matches the real config.
- **Eslint runner.** Findings on comments (no-comments, ts-ignore, inline config) are anchored to the comment text, since the nearest syntax node would be the following code and editing it would change the fingerprint.
- **Test-code analysis.** `test-code-analysis.mjs` works on one file's syntax tree; calls into other modules are not followed. Per-test visitors report each node once however many tests reach it.
- **Runtime boundaries.** Roles select production modules by `modules` globs (relative to `src/main`) and list `forbiddenDependencies` and `forbiddenCalls` globs; the default declares none. Globstars do not traverse `..`, so relative spellings are resolved before matching.
- **Callback contracts.** Each entry names a `callee`, its `optionsArgument` index, `sourceCallbacks`, `correlatedCallbacks` (`{ name, inputIndex }`), `externalPublicationCallbacks` and `snapshotReadMethods`. Rules contain no consumer or file identities.
- **CRAP roots.** The analyzer expands a directory only when named `src` (or containing `src` folders); other roots are passed as the files inside them.
- **Dependency cruiser.** The policy TypeScript config is linked into the analyzed root so its include globs resolve against analyzed sources; `typeScriptRoot` defaults to this package and is overridden for fixtures.
- **Dependency hooks.** A hook has `language`, `manifests` (the first marks a project; if any differs from the live policy root the snapshot needs its own install instead of a link), `directory`, and `install(projectRoot)`, which installs a regular directory and cleans up and throws on failure.
- **Public contract usage.** Declaration identity keeps unrelated same-name methods and test-only calls from counting as consumers, so results are stable for a differential gate.

## JavaScript preset (`languages/javascript/`)

The JavaScript preset reuses the TypeScript pipeline; `languages/javascript/preset/` holds only what differs.

- **Preset channel.** `resolveHeadPolicy` copies `preset` into the head policy file only for `javascript`, so the TypeScript policy and its cache key do not change. `readLayout` turns it into `layout.javascript` and `layout.entryExtensions` (`js`, `mjs`, `cjs` instead of `ts`); every runner reads the layout through it. `presetAnalyzers` returns `javascriptAnalyzers` (same checks, built from the JavaScript layout) and `applyLayout` rebuilds from `resolveLayoutFor(headPolicy)`.
- **Generated configs.** The `tsconfig.quality.json` and `tsconfig.stryker.json` rewrites add `allowJs` and `checkJs` (the first also `noEmit`); with a project `tsconfig.json`, or a `jsconfig.json` when there is none, they extend it. `knip.json` gains `.js/.mjs/.cjs` entries and config files, and `jscpd.json` the `javascript` and `jsx` formats, because jscpd's `typescript` format reads only `.ts` and `.mts`. Stryker's TypeScript checker reports a mutant that fails `checkJs` as a compile error, so JavaScript mutants are killed by types as TypeScript ones are.
- **ESLint dialect.** `eslint-dialect.mjs` rewrites the strict config for JavaScript files: it drops the type-syntax rules and the `no-restricted-syntax` selectors that name a `TS*` node, passes `jsdocTypes`, `jsdoc` or `commonJsExports` to the four rules that map to JSDoc or CommonJS, and adds `no-var`, `prefer-const`, `prefer-rest-params` and `prefer-spread` (typescript-eslint enables them for TypeScript files only). The mapped rules keep their severity and still accept an exception. The dialect is applied before exceptions, so an exception for a dropped rule is an error.
- **JSDoc parser.** `jsdoc.mjs` accepts one grammar per allowed tag (type in balanced braces, then a name where the tag has one) and reports any other text as prose. A `@type` is a cast only when the comment is directly followed by `(`. `any` and `null` are looked for outside string literals and object keys.
- **Constants in `quality-areas-runner.mjs`.** The module-level `invokedPath` block runs the runner on import, so the constants it uses are declared above it. Declared below, they were still in their temporal dead zone when a failing test reached the failure formatter, which crashed the coverage check instead of reporting `tests-failed`.

## Java preset (`languages/java/`)

Gradle runs once and yields findings for all tools; reports land in `<projectRoot>/build/nitpicker`. Ingesters turn tool reports into findings:

- **Common.** Repeats of one identity within a report get `#n` in report order. The XML parser reads elements and attributes only and throws `TypeError` when malformed.
- **SARIF** (PMD, SpotBugs). Identity is `partialFingerprints` (sorted) when present, else a hash of rule, path and symbol. Absolute `file://` URIs (PMD) and source-root-relative paths (SpotBugs) are made project-relative; results outside the project are skipped. SpotBugs `note`-level results are promoted because the tool already runs at the configured threshold, and its subject comes from message arguments since the text is generic.
- **Checkstyle.** Identity hashes the check `source`, path and message; the line is location only.
- **ArchUnit.** One finding per violated rule and offending class, identified by the fully qualified class; line numbers and violation counts never take part. The path is resolved by `options.resolvePath(className, fileName)`, falling back to the declaring test class. A failed case without violation lines yields one `test-failure`.
- **CRAP.** `crap = ccn^2 * (1 - coverage)^3 + ccn`, with coverage the lower of line ("statement") and branch coverage. `crap-score-limit` when over `options.limit`; `crap-coverage-unknown` when no JaCoCo method matches. Identity is lizard's long name plus `#n`. A JaCoCo method matches a lizard function when file and name agree (`<init>` is the class name) and its first line lies in the function's range. `options.sourceRoots` maps lizard's project-relative paths to JaCoCo's package-relative ones. Lizard CSV has no header row. `ingestCrapFunctions` is the same ingester over already parsed functions; its `selectMethods` option replaces the name-and-range match (the Kotlin preset passes `selectKotlinMethods`).
- **Format check.** One `format` finding per file in the list; identity is the constant `format`.
- **Coverage.** Go coverprofile gives a `statement-coverage` metric per file only (blocks lack function names, and line-based identity is not allowed); `options.modulePath` is stripped from import paths. JaCoCo gives `line-coverage` plus `uncovered-method` (class and method name+descriptor); `options.sourceRoot` is prepended. lcov gives `line-coverage` plus `uncovered-function`.
- **PIT.** Follows `docs/mutation-testing.md`: no score gate, new surviving or uncovered mutants fail, other non-killed statuses are report-only, counts go to `mutation-summary`. A mutant is identified by class, method, mutator and description plus its occurrence `#n` among identical keys (by line, then block index). Mutants with unresolvable sources (generated code) are skipped.
- **Duplicates.** jscpd runs per existing main source root (from `build/nitpicker/manifest.json`), writing `duplicates.json` as `{ runs: [{ root, report }] }`. Findings match the TypeScript ones: `duplicate-clone` and `duplicate-clone-size`, identified by file pair, cloned-text hash and occurrence.

## Python preset (`languages/python/`)

One runner process per snapshot (`python-runner.mjs`) runs the tools and reads their reports from a temporary directory; the only things written into the analyzed tree are mutmut's `mutants/` directory and, when the project has no mutmut configuration, a `[tool.mutmut]` table appended to the snapshot's `pyproject.toml`. Reports there: `ruff.sarif`, `format.txt`, `coverage.json`, `coveragerc`, `mutation.json`, `manifest.json` (`formatter`, `sourceRoots`), `type-check.json` (`checker`, `output`), `python-files.txt` (the file list a step hands to its script, written by each step just before: ruff's file list for the rules script, the `.py` files under the source roots for the structure script and lizard), `rules.json`, `structure.json` (`languages/python/metrics/structure_metrics.py`) and `lizard.csv`. Each tool step lives in its own module (`python-types.mjs`, `python-ast-rules.mjs`, `python-structure.mjs`, `python-crap.mjs`, `python-mutation.mjs`) and runs through `python-execute.mjs`.

- **Environment.** Always that of the live checkout (`liveProjectRoot`), never of the snapshot: lockfiles exist in both, but `.venv` does not exist in a work tree. Detection order: `python.environment`, `uv.lock`, `poetry.lock`, `.venv`, `PATH`. `uv` runs `uv run --project <live> --no-sync -- <tool>` (no `--project` or no `--no-sync` would create or sync an environment). Poetry cannot be used through `poetry run` because `-C` also changes the working directory of the tool, so its environment path is asked once (`poetry -C <live> env info --path`) and used like a virtualenv. A virtualenv launcher resolves a tool in its `bin` and otherwise leaves it to the `PATH` (`bin` first).
- **Snapshot sources.** `PYTHONPATH` starts with the snapshot's import roots (a source root without `__init__.py` imports from itself, a package from its parent), then the inherited value; the tools run with the snapshot as working directory. This is the only thing that makes base tests import base code when the environment has an editable install of head; it is tested for real in the e2e test.
- **Version and cache key.** `resolveVersion` runs `--version` of ruff, black (when it is the formatter) and coverage plus the pytest and mutmut import probes (`importlib.metadata` for mutmut, because `mutmut --version` fails where mutmut cannot guess its source directory) in the live environment, and throws only when the environment itself is unusable (the scheduler reports that as a tool error of `python` on each snapshot, with no rule, and does not run the analyzer); a missing tool reads `tool@missing` and fails in the runner. The configuration hash covers the `python` settings and every non-test, non-fixture file under `languages/python/` plus the shared files the runner imports.
- **Tool errors.** Each step (`ruff`, format, tests plus `coverage json`, mutation) fails independently and all failures are reported, one finding each, rule `<step>-failed` (`tests-failed` is the TypeScript rule), identity the rule, path `.`. When any step failed no other finding is returned. An error without a `rule` property is `python-failed`.
- **Format output.** `ruff format --check --diff` is parsed by its `--- path` / `+++ path` header pairs, because ruff's summary format differs between versions; black's by its `would reformat` stderr lines. Exit 1 without a parsed path is an error.
- **Coverage.** Run through a nitpicker-owned `coveragerc` (branch on, parallel off, `source` the source roots) with `COVERAGE_FILE` in the report directory; `coverage json --fail-under=0 --ignore-errors`. Ingestion (`coverage-json.mjs`): `line-coverage` from `summary.covered_lines / num_statements` per file, `uncovered-function` for a function (not the module-level `""` entry) with statements and no covered line, identified by its qualified name. A file with no statements has no metric.
- **Structure and CRAP.** Details in `docs/python-preset.md`. The two steps live in `python-structure.mjs` and `python-crap.mjs`; both reuse Java's readers (`readStructureFindings`, `ingestCrapRows`) and pass a Python function-text hash (common indentation removed, not every line trimmed, because indentation is syntax). The structure script and lizard get the same file list from Node because lizard skips content-identical files when it walks a directory. Coverage entries are joined to lizard functions by trailing name and line range, not `start_line`, which older coverage.py versions do not report.
- **Mutation.** `python-mutation.mjs` runs `mutmut run` last (it leaves `mutants/` in the tree, which would otherwise be linted and collected) and only when the tests passed. `python-mutation-data.mjs` reads `mutants/**/*.meta` (`exit_code_by_key`) with the generated and the original source into `mutation.json`; `languages/python/ingest/mutmut.mjs` splits the generated file into function blocks by indentation (a closing bracket at the `def` indent continues a wrapped signature), diffs `x_f__mutmut_orig` against `x_f__mutmut_N` on tokens, and hands `Survived` and `NoCoverage` (exit 0; 5 and 33) to the shared `mutantFindings`. Identity `symbol|original→mutated#n`, `n` counted per status among equal keys in mutant order; the line comes from locating the original block in the real file. Exit 1 with "could not find any test case for any mutant" is accepted and turns the unchecked (`null`) results into 33. Head's `mutants/` is removed after reading; base's stays so `python-mutation-reuse.mjs` can copy its `.meta` files (only those) into head when the name-status diff from the base commit to head lists nothing but added or modified non-test `.py` files under a source root.
- **Ruff identity.** The SARIF goes through Java's `prepareSarif` with the message text as the subject, so identity is `fp:nitpicker/subject=<message>`; ruff messages name the symbol, and repeats in one file get `#n`.
- **Type checker choice.** `detectTypeChecker` scores each checker from the live checkout's hint files: a config (`[tool.mypy]`, `mypy.ini`, a `[mypy]` or `[mypy-...]` section, `[tool.pyright]`, `pyrightconfig.json`) counts 2 and a declared dependency 1; the higher score wins, a tie goes to mypy, no hint at all probes `mypy --version` then `pyright --version` in the environment. It is read from the live root so both snapshots run the same checker, and it is part of the tool versions in the cache key.
- **mypy run.** `mypy --strict --explicit-package-bases --show-error-codes --no-error-summary --no-pretty --hide-error-context --no-color-output --cache-dir <report dir>/mypy-cache <source roots>` with `MYPYPATH` set to the snapshot's import roots (mypy does not read `PYTHONPATH`); exit 0 or 1 is a result, anything else `types-failed`. Lines are matched as `path:line[:col]: error|warning: message  [code]`; notes and the summary are ignored. Identity is the message, `#n` per (file, rule).
- **pyright run.** A generated `pyrightconfig.json` in the report directory (`extends` the project's `pyrightconfig.json` or a `pyproject.toml` with `[tool.pyright]`, `typeCheckingMode: strict`, `enableTypeIgnoreComments: false`, `include` the source roots, `extraPaths` the import roots). `include` has to be relative to the config file (pyright ignores absolute entries with a warning); `extends` and `extraPaths` may be absolute. The JSON is read from the first `{` because the pip wrapper can print a notice first; only the first line of a message is the identity.
- **Rules script.** `nitpicker_rules.py` is stdlib-only and compatible with Python 3.8 and later; it takes a file list and a report path, parses with `ast` and finds comments with `tokenize`, and writes `[{rule, path, subject, line}]` sorted by path, line, rule and subject. Files that do not parse or tokenize are skipped. Messages are not in the script: `rule-hints.mjs` owns every message, so they are testable without Python.
- **Hints and exceptions.** `applyRuleHints` appends the allowed form (and the exception sentence) to findings of `ruff`, `mypy`, `pyright` and `python-rules` by rule id (a prefix for `PTH`); other findings pass through. Identity is computed before, so a reworded hint never re-baselines. `python.exceptions` filters findings by exact rule id and path glob after hints and before `exclude` and the legacy inventory; the base snapshot uses the base's config, like every other setting.
- **Shared policy.** `exclude` and the legacy inventory are `configureJavaAnalyzer` / `applyJavaPolicy`, both language-neutral; `applyJavaPolicy` takes `inventoryTool` for the tool of a `baseline-expansion` finding.
- **Duplicates, coupling, import-linter.** More reports in the directory: `duplicates.json` (Java's `runJscpd` output shape, so `readDuplicateFindings` is shared), `imports.json` (`{ modules: [{ file, module, isPackage }], imports: { file: [{ level, module, names }] } }`: the module list comes from `python-sources.mjs`, the statements from `import-scan.py`, which only parses and never resolves) and `import-linter.txt`. Resolving imports to modules, packages and the stability graph is JavaScript (`python-coupling.mjs` into `buildCouplingReport` of `shared/rules/coupling.mjs`), so only the scan needs Python. A file the scan cannot parse is skipped silently. The import-linter text report is parsed in `ingest/import-linter.mjs`; its identity per chain ignores line numbers, and the order import-linter prints chains in is not stable, so tests must not depend on it.
- **Project root.** `resolveProjectRoot` accepts a `nitpicker.config.json` as a project marker beside `package.json`, because a Python project has no `package.json`.

## Kotlin preset (`languages/java/`)

The Kotlin preset is the Java preset with `kotlin: true`: same init script, runner and ingesters. User-facing behavior is in `docs/kotlin-preset.md`; the protocol details:

- **Switch.** `gradle -Pnitpicker.kotlin=true` (and `-Pnitpicker.kotlin.formatter=<ktlint|ktfmt>` from `kotlin.formatter`) turns the Kotlin tasks on in modules applying `org.jetbrains.kotlin.jvm`; without it the init script is the Java one. The runner takes `--preset kotlin` and `--kotlin-formatter`. The analyzer is named `kotlin`, and its tool-error and `baseline-expansion` findings use that name.
- **Reports.** `detekt.sarif` and `kotlin-format.txt` (project-relative Kotlin files, one per line). Skipped Java tools in a Kotlin-only module write empty reports so the Nitpicker side reads one layout. `manifest.json` in this mode: `sourceRoots` are the Java roots only, `kotlinSourceRoots` the Kotlin plugin's source directories (which include `src/main/java`), `kotlin: true`, `kotlinFormatter`. `readKotlinFindings` throws when `kotlin` is absent, so a project without the Kotlin plugin is a tool error and not an empty pass.
- **Java-only class tools.** `analyzedClassDirs` is the output of `compileJava` in this mode (all main class directories otherwise); SpotBugs reads it. PIT reads `mutatedClassDirs` (all main class directories, Java and Kotlin) in both presets. SpotBugs gets the rest of the runtime classpath as `-auxclasspath`. jdeps reads every main class directory in both modes.
- **Kotlin metrics (KT3).** `languages/java/gradle/KotlinMetrics.java` is run by task `nitpickerKotlinMetrics` as `java -cp <kotlin-compiler-embeddable and its dependencies> KotlinMetrics.java <out> <projectDir> <kotlinSourceRoot>...` and writes `kotlin-metrics.json`: `functions` (one object per unit: `file`, `name`, `start`, `end`, `lines`, `statements`, `maxControlNesting`, `parameters`, `complexity`) and `files` (`file`, `classes`: the JVM names of its top-level classes and file facade). It builds a `KotlinCoreEnvironment` and needs an extension storage registered on the configuration (`FrontendConfigurationKeysKt.setExtensionsStorage`); that is compiler-internal API, so a bump of `kotlinCompiler` in the init script is tested with `npm run test:kotlin`. `kotlin-metrics.mjs` turns `functions` into structure findings (the Java path, `structureFindings`) and into CRAP findings (`ingestCrapFunctions` with `selectKotlinMethods`, which matches a function's JaCoCo methods by first line within its range, skipping `$default` and methods inside a unit of their own), and `files` into the module map `analyzeJavaCoupling` takes (`moduleOf`, `fileOf`).
- **Kotlin clones.** `runJavaDuplicates(projectRoot, { format: 'kotlin', rootsKey: 'kotlinSourceRoots', reportFile: 'kotlin-duplicates.json' })` after the Java run; the report is read with `readDuplicateFindings` and the same rule and tool name `duplicates`.
- **detekt SARIF.** No fingerprints, so the glue sets `nitpicker/subject` from the message text and keeps the SARIF levels (`note` stays descriptive, unlike SpotBugs). Rule ids are kept in detekt's form `detekt.<ruleset>.<Rule>`.
- **Formatter detection** is a text search of the build files at task execution time (not Gradle API introspection), so it works for plugin ids, version catalogs and Spotless alike; the cost is false matches on a comment that names the other tool.
- **Branch coverage** (`changed-branch-coverage`) reads the source text of every file under `jacocoSourceRoots` (Java roots plus `kotlinSourceRoots`). A `.kt` line is dropped when `hasBranchingSyntax` (`kotlin-branches.mjs`) finds nothing in it that can branch; that is the whole generated-branch filter, since the JaCoCo XML has branch counts per line and no instruction detail. The measurement behind it is in `docs/kotlin-preset.md`.
- **Mutation.** `pitFindings` resolves a class's source file under `jacocoSourceRoots` and `reportOnlyKotlinMutants` turns `mutant-*` findings of `.kt` files into `descriptive` ones (the `mutation-summary` counts are unchanged). The Java preset does not call it.
- **One-way rules** (`kotlin-rules.mjs`, `nitpicker-detekt.yml`). `ONE_WAY_RULES` is the list of rules in the yml with the sentence the gate appends when detekt's text does not name the allowed form (`addOneWayHint`, after ingestion, so identity, which is the detekt text, never changes); every rule also gets the exception route. `ForbiddenMethodCall` and the other rules with a `reason` field carry the allowed form in the yml instead. The yml is the last `--config` of the detekt task, and detekt gives the later file priority per key, so a project's `detekt.yml` cannot override it; `excludes: []` on `UnsafeCallOnNullableType` replaces the default that skips `**/test/**` paths, which would also skip a production package named `test`.
- **Type resolution classpath.** Detekt 1.23.8 embeds Kotlin 2.0.21 (it resolved a 2.1.0 standard library, not a 2.4.21 one). The stdlib it needs for `run`, `with`, `also` and `!!` is therefore `kotlin-stdlib:2.0.21` (`pinned.detektKotlin`, the version in the detekt jar's `META-INF/compiler.version`), first on the classpath, and every `kotlin-stdlib*` jar of the project is dropped. With the project's 2.4 stdlib the same run reported nothing for those calls and wrongly flagged `?.` on values of an unresolved type. `--jdk-home` is the Gradle JVM's `java.home`; without it JDK types (`StringBuilder`) do not resolve. Bump `detektKotlin` together with `detekt`.
- **Exceptions.** `--exception <rule>:<glob>` (split at the first colon, one per path) reaches `applyJavaPolicy`, which drops findings of that exact rule id under the glob on both snapshots. `validateKotlinOptions` accepts only `ONE_WAY_RULE_IDS` so a typo is an error. Python can reuse the mechanism.
- **Inline suppression.** `kotlin-suppressions.mjs` reads the string literals inside `@Suppress`/`@file:Suppress`/`@SuppressWarnings` (comments removed) and `isBannedSuppression` matches what detekt's `isSuppressedBy` honors: the rule id with `detekt.`/`detekt:` prefixes and with `detekt.<ruleset>.`/`detekt:<ruleset>:`, the ruleset, and `all` in any letter case; matching is case-sensitive otherwise, as detekt's is. detekt's `ForbiddenSuppress` cannot do this alone: a suppression of `style` or `all` also hides the `ForbiddenSuppress` finding on the same annotation.
- **Fixture cases.** `fixtures/kotlin-rules/cases.mjs` holds, per rule, the banned and the allowed source (`{name}` stands for the file's class name, `Banned` or `Allowed`), the detekt message recorded from the real run, and the wording the final message must contain. The CI test checks the wording against the recorded message; the end-to-end test checks the recorded message against real detekt, so a detekt or yml change that alters a message fails there.
