# Internals

Contributor notes on formats and protocols that code and names cannot carry. Source files stay comment-free (`nitpicker/no-comments`).

## Diff engine (`core/`)

- **Custom analyzers.** A `{name, command, args?}` config entry runs with the analyzed checkout as working directory, so a relative command resolves inside each side. It prints findings JSON on stdout and exits 0; stdout goes through the same parser as built-in analyzers, and a non-zero exit or invalid JSON becomes a tool error.
- **Exit codes.** New violations win over tool errors so CI can tell "violations" from "broken"; `overallStatus` reports tool health first.
- **Gradle failures.** The bounded error shows the Gradle failure block before earlier output. Failed runs also retain unfiltered stdout and stderr in a private `nitpicker-gradle-failure-*` system temporary directory; the error links to `gradle.log`. These logs outlive snapshot/report cleanup until the user or operating system removes them. They contain the project build output, so inspect them before sharing. A log write failure reports why saving failed alongside the original build error.
- **Tool-error paths.** `runAnalyzers` rewrites tool-error messages (scheduler errors and `tool-error` findings) of a run on a temporary snapshot (`core/diff/snapshot-root/`): a path under the snapshot's project root becomes project-relative, the root itself becomes `base` or `head`. A run on the live project keeps its paths.
- **Analyzer environment.** Analyzers never see where the GitHub Actions job summary lives (`HOST_CI_OUTPUT_VARIABLES`): vitest and Stryker would append their own reports to it, and caught mutants read as test failures.
- **Cache stores.** A store keeps opaque text under a hex key, is synchronous and never throws: `get` returns undefined on any miss or failure, `put` returns whether the value was stored. The local directory is `NITPICKER_CACHE_DIR`, else `node_modules/.cache/nitpicker`. The HTTP store does `GET`/`PUT` of `<baseUrl>/<key>.json` with an optional `Name: value` auth header, and stays off after its first non-miss failure so an unreachable server costs one timeout. Reads try local, then remote (copying a hit locally); writes go to the remote store only with `writeRemote`.
- **HTTP cache worker.** Exit codes: 0 success (GET prints the body), 3 not found, 1 any other failure. The comparison is synchronous, so each request runs in a short-lived `node` child that does the asynchronous fetch: `<GET|PUT> <url> <timeoutMs>`, auth header in `NITPICKER_CACHE_AUTH_HEADER_VALUE` (never argv). S3 answers 403 for a missing key when the caller cannot list the bucket, so 403 counts as not found. The test HTTP server lives in a worker thread for the same reason: the stores block the calling thread.
- **Findings cache key.** Base commit, project, analyzer, tool version, configuration hash, head policy (exclude, layout, exceptions, thresholds) and legacy inventory path. The policy is keyed explicitly because layout and threshold changes rebuild an analyzer without changing its file-based hash. Entries carry their own key, so a misnamed entry is a miss. Only clean reports are stored, and cached analyzers still run when an uncached one depends on them.
- **Publishing a base snapshot.** `cache publish` analyzes HEAD (typically the new tip of `main`) and stores clean reports under the keys later comparisons use when HEAD is their merge base, using HEAD's own policy.
- **Comparison.** Findings split into new, resolved, unchanged and changed-metric. With `touchedCode`, an enforceable finding of a strict rule inside touched lines is new even though the base has it, unless it carries `ratchet.existingCodeOnly` (an ESLint finding inside a named function): then only a line in `inserted` makes it new, and `changed-lines.mjs` leaves out of `inserted` an added line it pairs, by word similarity, with a removed line.
- **Cycle identity.** Dependency cycles are `cycle:a>b>c|...`, starting at the lexicographically smallest rotation. A rename can change that rotation, so renamed cycles are re-rotated before comparing.
- **Report hash.** Zero config keeps the original policy hash input; any override changes it.
- **Base coverage and policy changes.** `createBaseSetupResolver` (`core/command/policy-review/base-setup.mjs`) measures the base once, with its own config passed through `baseConfigCoveringHead(baseConfig, headConfig)` (`core/policy-changes/base-coverage.mjs`): `layout.sourceRoots` and `layout.testRoots` are the union of both sides (an unset side adds the default roots, `testRoots` without `e2e`, because a declared list runs every root it names and the base would execute end-to-end specs); `exclude`, `disable`, `layout.excludedGlobs`, `layout.entryPoints` and each rule's exception paths keep only the entries both sides declare; and each threshold is the lower of the two. A folder the change brings under the gate is then read on both sides, so its existing findings stay unchanged, and neither a widened nor a tightened policy turns old findings new; the facts read from the head checkout come from the head policy (`withHeadCheckoutFacts` in `languages/typescript/preset/head-policy.mjs`: `conventions`, `generatedFiles`, `frameworks`, `react.enabled`, `react.iconPackage`, `react.major`, `react.styling`, `react.autoCleanup`, `i18n.enabled`, `layout.colocatedTests` when the head checkout has no test root, for the Java and Kotlin presets `spring` (the build files name `org.springframework`, `javaHeadFacts` in `languages/java/adapters/facts/head-facts.mjs`) and `kotlin` (the effective formatter, `kotlinFormatterOf`), and, when the base config reads the project Prettier config, `tools.prettier.projectConfigDigest`), as they do for a base analysed with the head config. The base config is read with `readConfigFile` (schema checks only, so a base that `rejectUnreadableSources` or `rejectUndeclaredPreset` would reject is still compared); one that does not load is compared as `{}`. The policy-change lines compare the configs as written. `readPolicyScope` (`core/policy-changes/policy-scope.mjs`) lists both snapshots with `git ls-files --cached --others --exclude-standard` and keeps the code files of the head preset's extensions wherever they are (`code`, `baseCode`), the head files also in the base (`keptCode`, `keptPaths` with their folders), the root sets of each side (`rootSets`), `basePathOf` (a head path mapped back through the run's renames, folders through directory moves), `existsInBase`, `presetRequired` (`presetToDeclare`), for the TypeScript preset every tsconfig of each side with its `checkJs` (`projectTsconfigs` and `checksJavascript` in `languages/typescript/preset/modules/tsconfig-files.mjs`: each `tsconfig.json` outside `node_modules` and the exclusions, plus the configs they reference, followed transitively), `productionReach` and `blobOf` (the git blob id of a head file). `productionReach` is computed once, on first use: one `reachableModules` walk (`module-resolution.mjs`, unlimited depth) from the head layout's source files, the `main`/`bin`/`exports` targets of every tracked `package.json` (`packageEntryFiles`) and the `layout.entryPoints` files, through hidden files, mapping each reached file to the root importer the finding names (`productionReach` in `production-imports.mjs`, specifiers read with `ts.preProcessFile`). For Python the same walk is the import scan of the coupling rules (`pythonProductionReach` in `languages/python/adapters/analysis/reach/python-reach.mjs`: `collectImports`, `importEdges`, parent packages of a reached module) from the production modules the head `exclude` does not hide; for Java and Kotlin it is `jvmProductionReach` (`languages/java/builds/reach/source-reach.mjs`) over the `.java` and `.kt` files, from the files under the main source directories that `exclude` does not hide: single-type and wildcard imports, qualified names in the code, and same-package types or Kotlin top-level declarations whose name appears as an identifier, comments and strings removed; a same-package or wildcard name that an explicit import (or its `as` alias) of the same simple name shadows does not count, and a top-level Kotlin `fun`, `val` or `var` without a receiver type counts only where its name is used without a receiver (not after a `.`). It reads sources, not class files, because the review runs before any build and the head classes do not exist yet. Presets without a walk have no reach. The resolver always calls `policyChangeFields(baseConfig, headConfig, scope)`, because code added under an unchanged config can still be hidden. Each part returns `{ loosened, changed }`, a loosening carrying its display `text`, its full `key`, the `files` it names and the guidance `kind` that selects its wording (`entry-point`, `exclusion`, `hidden-exclusion`, `threshold` and the like; the producer sets it next to the text, and `describe-policy-changes.mjs` `looseningKindOfSetting` does for the listed settings). `coveredPathChanges` (`paths/covered-paths.mjs`) counts an added glob as loosening when it covers a kept code path its base set did not cover: `exclude` and `layout.excludedGlobs` are one set (`keyedExclusions` in `paths/hiding.mjs`, over `layout.hiddenGlobs`), so a respelled glob covering the same files and a glob moved between the two keys (`<glob> moved from exclude to layout.excludedGlobs`) are only listed; exception paths are compared per rule (`exceptionPathsByRule`, the one collector, also used by `base-coverage.mjs`); `layout.entryPoints` over all code paths through `basePathOf`. A base root the head drops is loosening when a code file under it is under no head root of the same kind, and an added test root is loosening when a kept file that was production code in the base becomes test code (`testRootReclassifier`, the one reclassification, also used for hiding). Removed globs are listed as tightenings. `hiddenCodeChanges` (`paths/hidden-code.mjs`) decides per file. `hidingSets` (`paths/hiding.mjs`) builds one set for the exclusions, one per rule's exception paths (`exceptions`, `python.exceptions`) and, with a layout, one for test roots inside source roots; each has `hidesInHead(file)` and `baseHiders(basePath)`, the base globs or root of that set that hid the file's base path. For every code file the change adds (`existsInBase` false) or moves (`basePathOf` differs) that a set hides in the head: no base hider is `where the base config checked it`; base hiders that cover no `baseCode` file is `where the base hid no code` (dormant); otherwise, for the exclusions and test roots only, a file in `productionReach()` is `that production code imports`. An exception under an established glob never fails on imports, because the file is still checked by every other rule. The text lists three files; the key lists all. `buildNarrowingChanges` (`build-files/build-narrowing.mjs`) compares the entries `scope.buildSources` holds for each side: `roots` entries (a source set's directories, pytest `testpaths`), `excludes` entries (patterns with a `covers(file, pattern)` check) and `includes` entries (patterns with `inScope(file)` and `admits(file, pattern)`). The readers count only what nitpicker runs. `readGradleSources` (`languages/java/builds/narrowing/gradle-sources.mjs`, statements and block headers from `gradle-script.mjs`) reads `sourceSets` `srcDirs` assignment against `srcDir` addition per language, and `taskFilter` (`gradle-tasks.mjs`) the filters of the `test` task, the main and test compile tasks and the source sets (not `resources`): block form, receiver form (`test.exclude`, `tasks.test.get().enabled`, `tasks.getByName("test")`, `tasks.test.configure`), `withType` for `Test` and the compile types, nested only through `filter`, `options`, `useJUnitPlatform`, `useJUnit`, `useTestNG` and `onlyIf`; other `Test` tasks, dependency and JaCoCo excludes are not read. `readMavenSources` (`maven-sources.mjs`) reads the project and its `activeByDefault` profiles (an active profile may move `sourceDirectory` or `testSourceDirectory`): build-helper and Kotlin plugin directories, surefire excludes, `excludedGroups`, skip flags, `includes`, `groups` and `test`, failsafe excludes and skips only against integration-test names (`*IT`, `IT*`, `*ITCase`), compiler `excludes`, `testExcludes`, `includes` and `testIncludes`, and the `skipITs` and `skipTests` properties against integration tests only and only when a pom binds Failsafe, mirroring `maven-project.mjs`, which then runs `test` instead of `verify` (`maven.test.skip` is not read, and neither property counts against unit tests, because the build passes `-DskipTests=false` and `-Dmaven.test.skip=false`); a pom's filters, `pluginManagement` included, apply to the roots of every module in its folder subtree. `source-patterns.mjs` scopes them: a main filter to the main roots, a test one to the test roots, and surefire includes to the classes surefire runs by default. `readPythonSelection` (`languages/python/adapters/configuration/pytest/test-selection.mjs`) reads `testpaths`, `addopts` `--ignore` and `--ignore-glob`, and `do_not_mutate`, each counted only for the files pytest collects (`isCollectedTestFile`: `python_files` or the defaults, `conftest.py`, the Django names in a Django project); `-k`, `-m` and `--deselect` are not read, because `pytest-pins.mjs` strips them from the run and `uncollected-tests` reports the tests they hide. A `roots` entry loosens when a kept code file the entry's `applies` accepts was inside the base roots and is inside no head roots entry of any build tool that accepts it, so a Maven to Gradle switch on the same roots is quiet; an `excludes` pattern the base lacked loosens when it covers a kept file no base pattern covered, and is only listed otherwise; an `includes` entry loosens when a kept file in its scope was admitted by the base patterns (or the base had none) and is admitted by no head pattern. `generatedMarkingChanges` (`paths/generated-marking.mjs`) counts a kept code file that the head checkout marks as generated and the base did not, with the preset's own test (`isGeneratedJvm`, `isGeneratedPython`, `isMarkedGenerated` from `languages/typescript/preset/layout/generated-files.mjs`), because a marker makes every check skip the file. `toolConfigChanges` (`build-files/tool-config-changes.mjs`, readers in `tool-config-files.mjs`) fingerprints the files of each tool config both sides opted into (the `*.xml` files under `config/pmd/` and `config/checkstyle/`, the Kotlin detekt config and the `.editorconfig` files ktlint or ktfmt read (`kotlinStyleFiles`), the Prettier files with only the `prettier` key of `package.json`) and counts a changed or added file as loosening. `toolConfigText` (`tool-config-text.mjs`) normalizes each file first: XML without comments and layout, JSON parsed, YAML and TOML without comment and blank lines, scripts without whole-line comments, and an `.editorconfig` reduced to its preamble and the sections whose glob matches `.kt` or `.kts` files (ktlint, ktfmt) or the files Prettier formats, so an edit of comments, layout or another language's section is not counted; the project config is read from the head checkout for both sides, so a loosened config would otherwise pass unseen. `tsconfigChanges` (`paths/tsconfig-changes.mjs`) counts a base tsconfig with no head counterpart (`tsconfig removed: <file>`) and `checkJs` turned off in any kept one as loosening, and lists `checkJs` turned on. `featureLayoutChanges` (`feature-layout-changes.mjs`) places every head code file with the base and the head `layout.featureRoots` and `layout.sharedRoots` (the preset's defaults filling an unset key) and, when the head preset runs the feature folder rules, counts the change as loosening if a file leaves the feature or shared folder it was in, moves between the two, or joins a larger feature; otherwise it lists the change. `listedChanges` (`loosenings.mjs`) adds newly disabled analyzers, thresholds above the base with `THRESHOLD_DEFAULTS` filling missing keys on both sides, and custom analyzers removed or changed (whole entry compared); added analyzers, re-enabled analyzers and lowered thresholds are listed. Every other changed leaf setting is listed as `path: base -> head` (`not set` when absent); `looseningKindOfSetting` marks the ones that check less, and names their kind: `preset` by the preset that runs (`typescript` when unset; `javascript` to `typescript` is not loosening, and a first preset is not loosening only when `scope.presetRequired` says the project must declare one), `react.enabled`, `i18n.enabled` and `python.importLinter` turned to `false`, `kotlin.formatter` turned to `none`, any `kotlin.detektConfig` change, and a `tools.<tool>.precedence` that ranks `"project"` higher (for `pmd`, whose layers are unioned, only dropping `"nitpicker"`). Engines, `python.typeChecker`, `python.formatter` and the like stay neutral. `policyLoosenings` is the subset that fails: `buildReport` adds one enforceable `nitpicker-config/policy-loosened` finding per entry (path `nitpicker.config.json`, identity the change) unless the run accepts it; `policyFindings` (`core/diff/reporting/review/policy-findings.mjs`) words it as the change, the guidance of its kind (`POLICY_GUIDANCE` in `policy-guidance.mjs`: one or two sentences on what the change does to the checking and how to undo it, so a setting never says to fix findings where that makes no sense) and the route for a person reviewing the change, and records the kind as `policyKind`. `policyChangeFields` returns the kinds as `policyKinds` (change text to kind), `run-diff.mjs` passes them to `buildReport`, and a finding without a kind gets a generic fallback. `guidance/guidance-coverage.test.mjs` drives one fixture per producer through `policyChangeFields` and fails when a loosening has no kind or no entry in `POLICY_GUIDANCE`, or an entry has no producer fixture. `policyDigest` hashes the sorted loosening keys and, for every file they name, its path and git blob id (`summary.policyDigest`), so an acceptance covers exactly the loosenings and file contents a person saw; `results.mjs` falls back to the loosenings alone when no scope supplied one. `policyAcceptance` (`core/command/policy-review/policy-acceptance.mjs`) honours `--accept-policy-change` only when the CLI is interactive (stdin and stdout are TTYs, `withCliDefaults` in `core/cli.mjs`) and `NITPICKER_ACCEPT_POLICY_CHANGE` only when `CI` is set; an ignored one is written to stderr, and `summary.policyAcceptanceSource` names the route used. `summary.policyChangeAccepted` records an accepted loosening. The evals harness fails a case whose agent used either route or wrote a generator marker (`evals/detectors/policy/policy-shortcuts.mjs`). Only shard 0 (or an unsharded run) adds the findings, and `aggregate` accepts the `nitpicker-config` tool in a shard's entries, so a sharded run counts them once. `summary.json` carries `policyChanges`, `policyLoosenings` and `notices` as arrays of strings, `aggregate` copies them from the first shard (`summaryFields`), and `report.txt` prints them under "Policy changed in this change" and "Notices (not failing)". The console (`consolePolicySummary` in `review/policy-changes.mjs`) takes the unapproved changes from the findings, groups them by `policyKind` (the changes of a kind one per line, then the kind's guidance once), keeps the other changes after them, and ends with `Unapproved policy changes (nitpicker-config/policy-loosened): N`, so an agent can stop on the id, and the acceptance command with the run's digest; the findings themselves are not listed under the code violations, and the headline counts code violations and unapproved policy changes separately (`appendViolationSummary` in `summary.mjs`). Every policy line passes `printable` (`format/text.mjs`: terminal escapes, control characters and format characters such as bidi overrides removed, whitespace collapsed) because a change text can hold an exception `reason`, so a reason cannot add lines or recolor the output. Notices never affect the exit code. `outsideRootsNotices` (`languages/typescript/preset/notices/`) names head-side changed files outside every root when the preset is `typescript`; it skips declaration files, `*.config.*` files, dot folders, built-in and configured exclusions. The Python (`pythonOutsideRootsNotices`, outside `python.sourceRoots`, skipping tests, tool files such as `setup.py`, installed, build and documentation folders, generated files) and Java and Kotlin (`jvmOutsideRootsNotices`, outside `src/<set>/java|kotlin` and the directories the build files declare) notices share the wording of `shared/notices/outside-roots-message.mjs`; `noticeDescriber` picks the describer by preset, and adds `unmatchedLayoutRootNotices` when the head policy sets `layout.featureRoots` or `layout.sharedRoots`.
- **Config base.** `base` in the config is refused when it is `HEAD` or `@` (`rejectHeadBase`), and when it resolves to the head commit and follows HEAD (`core/diff/git/repository/base-ref.mjs`): a hex SHA, an expression using `HEAD` or `@` (`HEAD~0`, `HEAD^0`, `@{0}`), or a name whose `--symbolic-full-name` is the checked-out branch (`main`, `refs/heads/main` while on `main`). Any other branch that points at the head commit, such as `origin/main` on an up-to-date `main`, is accepted: the head includes uncommitted changes, so that comparison still checks the working tree, and the default remote-branch base relies on it. An explicit `--base HEAD` is accepted for the same reason.
- **SARIF output.** One result per new finding; the hashed comparison key is `partialFingerprints["nitpickerIdentity/v1"]`, so consumers match findings across runs when lines move. Tool errors become unsuccessful tool-execution notifications.
- **Base commit of a checkout.** `git.mjs` stages the checkout (untracked, non-ignored files included) in a copy of the index, leaving the user's index, branches and files untouched. The copy keeps the index's timestamps, so git's racily-clean check still re-reads a same-size edit made in the second the index was written.
- **Policy links.** Without `transform` the package-owned policy file is linked into the analyzed tree; with one (the layout changed) it is a rewritten copy, still derived from the head policy and never from the analyzed tree.
- **Shared build directory.** `runScheduler` creates one directory per side (`NITPICKER_SHARED_BUILD_DIRECTORY`, inherited by every analyzer process) and removes it when the scheduler exits. `buildOnce(key, build)` runs `build` in the first process to take `<key>.lock`; the others poll for `<key>.result` (or `<key>.failure`, rethrown so a broken build is not repeated). A lock whose owning process is gone (or an empty one left by a crash) is taken over by renaming it aside and re-checking it. A build killed by a signal records nothing, so a waiter builds instead; other failures are recorded. Without the variable, `buildOnce` just builds, so direct runs and tests are unchanged.
- **Temporary files.** Register before creating the file so it is removed on exit or interruption even if the runner's `finally` blocks never run.
- **Presets.** `preset` is explicit; there is no auto-detection. `rejectUndeclaredPreset` (`core/configuration/project-checks/preset-detection.mjs`) only refuses a config without `preset` when the source roots have no `.ts`/`.js` family file (best-effort: `ASSET_FOLDERS` such as `resources`, `static`, `public`, `assets`, `webapp`, `wwwroot` and `*.min.js` files are skipped, so a Spring app's bundled scripts do not count) and a Gradle, Maven or Python marker (`pyproject.toml`, `setup.py`, `setup.cfg`, `Pipfile` or `requirements.txt`) is at the project root, so the TypeScript preset never runs on a Java or Python project and ends in tool errors; the message names the preset (Kotlin when `.kt`/`.kts` files outnumber `.java` ones, skipping dot folders, `node_modules`, `build`, `target` and `out`). Injected analyzers win over the preset. Within the Java preset the build tool is detected (`detectJavaBuild`): Maven when the root has a `pom.xml` and no Gradle build file, or both but only `mvnw` and no `gradlew`; Gradle otherwise.

## Shared rules (`shared/`, `spec/`)

Findings follow `spec/findings.schema.json`. Identity (the part of the comparison key beyond rule and path) never contains line numbers, so edits above a finding do not change it.

- **Rule catalog** (`shared/policy.mjs`, `shared/project-rules/size-rules.mjs`). `policy.mjs` is the single source for the custom checks nitpicker adds on top of third-party tools: rule ids, default limits and the languages that enforce each rule (`RULES`: per rule, `limit` is the human text of the default threshold and `enforcedBy` says which languages enforce it today). The failure-message templates (`MESSAGES`, `GREW_MESSAGES`, `HELD_MESSAGES`, `EXCEPTION_HINT`, `renderMessage`) live in `shared/messages/messages.mjs`, which `policy.mjs` re-exports. Every language adapter reads it, and the custom-rules table in `spec/checks.md` is generated from it (`npm run gen:checks`). The size rules (the file limits `file-lines-limit`, `line-length-limit` and `folder-files-limit`, `folder-depth-limit` and the class limits Java, Kotlin and Python enforce), their defaults (`FILE_LIMIT_DEFAULTS`, which `policy.mjs` re-exports), their message templates and the Java line length live in `project-rules/size-rules.mjs`, which `policy.mjs` spreads into `RULE_IDS` and `RULES` and `messages.mjs` into the message tables. `project-rules/size-rules.mjs` imports nothing, and `policy.mjs` imports only from `shared/messages`, `shared/rules`, `shared/unused-api` and `shared/project-rules`, so any entry point can load the catalog. Like everything under `shared/`, neither may import from `core/`, `languages/` or a tool package (`shared/import-direction.test.mjs`).
- **Config and head policy** (`shared/config.mjs`, `shared/head-policy.mjs`). `shared/config.mjs` holds the `nitpicker.config.json` rules that do not depend on a language: the file name, the keys every preset honours (the feature folders of `layout` where the language registers the rules that read them), the glob checks and which keys each language's fact rules allow; `core/configuration/validate.mjs` adds the TypeScript-only keys and the preset gate, and `core/configuration/scopes/scope-settings.mjs` validates the `react`, `i18n` and `testConsole` scopes (`testConsole.allow` paths go through the same glob checks). The head policy is the config values that change what analyzers report (`exclude`, `layout`, `exceptions`, `thresholds` and, when set, `react`, `i18n`, `tools` and `testConsole`), written once to a file outside both snapshots so base and head runs see the same policy; its format and reader are language-neutral, and the TypeScript preset adds its layout defaults in `languages/typescript/preset/head-policy.mjs`.
- **Globs** (`shared/paths/glob.mjs`). `globMatcher(glob)` is what nitpicker itself matches paths with (`exceptions`, `exclude`, `layout` folder roots, `testConsole.allow`): it compiles `**`, `*`, `?` and `{a,b}` into a small automaton and builds its deterministic states lazily per character, so a test is linear in the path length however many `**` the glob has (the regular expression it replaced backtracked for seconds on ten `**/` segments over a 30-folder path). `globToRegExpSource(glob)` gives the same language as a regular expression source for the tools that take one (dependency-cruiser, mypy, Python tool excludes). The config check rejects a glob that can never match (a leading `./`, a trailing `/`, a `(?i)`-style flag, an unclosed `{`) in the `exceptions` of nitpicker's own rules, the `layout` folder roots and `testConsole.allow`; ESLint rule exceptions are left to ESLint, whose globs take character classes.
- **Project conventions** (`shared/conventions/`, `core/conventions/`). A convention is `{ id, label, options, optionLabels, fallback, files, measure(text, file) }`; `measure` returns the option one file follows, or `undefined`. `detectConventions` takes the files not under `exclude` (the CLI adds the layout's excluded folders, such as `dist`, `build`, `generated` and `target`), samples at most 400 per convention evenly over the sorted paths, counts one vote per file, and picks the plurality; a tie or no votes is `fallback` (`source: 'default'`), a `conventions` pin in the config skips measuring (`source: 'pinned'`). The CLI measures once the config, the analyzer selection and the base ref have been checked, so their errors come first and a run outside git fails as before: a comparison reads the merge-base commit through `git ls-tree -l` (regular blobs up to 512 KiB only, so generated files, symlinks and submodules never vote) and one `git cat-file --batch` by object id (so a branch cannot flip the choice); when every convention is pinned no git command runs, and re-measures on the working tree only the conventions the base had no files for; `--all` measures the working tree and `cache publish` the published commit (which later comparisons use as their merge base, so the keys match). Only choices that differ from the preset default go into the head policy, as `conventions: { id: option }` (omitted when empty, so default-style projects keep their policy and cache keys), also into the base's policy when the base has its own config, so both snapshots and the findings cache key see the same values. Presets list their conventions in `core/conventions/definitions.mjs`; a preset with none leaves the policy as it was. The TypeScript and JavaScript presets measure Prettier options (`languages/typescript/conventions/`) and add the choices to the `nitpicker` Prettier layer for code files, which then always runs through the layered Prettier API path. Short code says nothing about the print width, so a file votes a width only when it is the one value between its longest breakable line and the shortest call, array or assignment Prettier left wrapped (joined, that would have fit any wider limit), or 120 when at least two lines exceed 100. The measures skip comments and template-literal contents, and a file with no evidence casts no vote, so a project keeps the preset default rather than a guess. `prettier.jsxQuotes` and `prettier.bracketSameLine` (`conventions/measures/jsx-conventions.mjs`, TypeScript preset only: the javascript layout does not list `.jsx` or `.tsx` as source files, so the scope filter would drop every file) parse `.tsx`/`.jsx` with the TypeScript compiler (`typescript-syntax.mjs`): a quote vote is a `JsxAttribute` with a string initializer holding neither quote character, and a bracket vote compares the end line of the last attribute of a multi-line opening element with the line of its `>` (a self-closing element never votes). `prettier.jsonIndentation` and `prettier.yamlIndentation` (`measures/data-conventions.mjs`, `scope: 'formatted-data'`) are measured from the data files themselves and applied by `prettier-layers.mjs` to files with that extension: `useTabs` and `tabWidth` only, since nothing reliable can be measured for quotes or width in data files. The scope is the `prettierPatterns(layout)` list in `layout.mjs`, the same one the `prettier-format` check uses (so JSON at the root and under source and test roots, YAML under source roots only), minus generated and fixture paths. A `scope` on a definition makes `resolve.mjs` pass an `accepts` filter (`layout`: source and test files; `test-code`: test files plus files under `test-support`, `test-utils`, `testing` or `testkit`; `formatted-data`). A definition with `kind: 'names'` (`typescript.assertionHelpers`, `measures/assertion-helpers.mjs`) votes a list: `measure` returns evidence strings per file, `detectConventions` counts files per string, and `choose(counts)` (default: names counted in at least `minFiles` files) picks the sorted names; a pin is a list of plain identifiers, `sampleLimit` raises the sample size, and the policy carries the list. For assertion helpers a file reports `use:NAME` for the root identifier of the last statement of each `it`/`test` callback (heads: `it`/`test` with `only`, `skip`, `concurrent`, `sequential`, `each`, `for`, `fails`, `todo`, `runIf`, `skipIf`, called, tagged or plain) that contains no `expect`/`assert` call, and `def:NAME` for each function declaration or function-valued constant whose body calls `expect`/`assert`/`expectTypeOf`/`assertType` or throws; a name is followed when it ends tests in at least three files and is defined somewhere in the sample, so `checkIn(guest)` is not an assertion unless the project defines it as one. `defaults/eslint.config.mjs` appends the names to the `assertFunctionNames` of `vitest/expect-expect`. Main has no Jest assertion rule, so there is no second consumer. A hook file name (`use` plus a capital) is exempt from `typescript.fileNames` only when the file exports a function or constant named exactly like the base name, so that definition has `needsText` and the detector reads just those files (an unreadable one is treated as a hook). Two conventions are not Prettier options. `typescript.typeImports` (TypeScript preset only, `languages/typescript/conventions/type-import-style.mjs`) votes `separate` for a file with `import type` statements and `inline` for one with `import { type A }` specifiers (a file with neither, or with the same number of each, casts no vote) and sets the `fixStyle` of `@typescript-eslint/consistent-type-imports` in `defaults/eslint.config.mjs`; that rule accepts both forms and only reports a value import of something used as a type, so the choice only decides which form its fix would write, and the setting reaches the lint engines as ordinary rule options (oxlint plans from the ESLint config). `typescript.fileNames` (`file-name-casing.mjs` in the same folder, both presets) votes from the file path alone, so its definition is `nameOnly` (no file is read, and a file over the 512 KiB read limit still votes; `source.paths({ unreadable: true })` lists those) and `scope: 'layout'` (`resolve.mjs` passes `accepts`, which keeps only files the layout classifies as source or test files). The vote is the casing of the base name before the first dot (`kebab-case`, `camelCase` or `snake_case`); PascalCase names, names that fit every casing (`index`, `404`, `fr-CA`), reserved framework names, Remix route syntax (`[`, `]`, a trailing `_`), names starting with `_`, `+`, `$`, `@`, `(`, `#` or `~`, dot-files, `*.config.*`, names with a lowercase hash segment of 8 or more characters containing a digit, files the layout reports as generated (`isGeneratedPath`: dependency folders and the `generatedFiles` found by generator markers, which the vote skips through the `layout` scope and the rule skips by its own path and sibling listing), `*.graphql.*`, `*.gql.*` and `fixtures/` folders neither vote nor fail. `nitpicker/file-name-casing` (`eslint-plugin/rules/naming/`) takes the project casing as its option from the policy (`kebab-case` unless a convention says otherwise). When the file's folder holds at least three other voting files, their plurality replaces the project casing for that file (a tie keeps it), unless the config pins `typescript.fileNames`: `resolve.mjs` then records the pins as `conventionPins` in the head policy (even a pin equal to the default, which `conventions` omits) and the rule gets `pinned: true`; the rule lists the folder once per run with `readdirSync`, so it needs no extra policy data, and head and base each read their own checkout. It reports once at line 1, so it runs on changed files through the usual differential gate. The Python and Kotlin runners read the choices from the head policy file (`NITPICKER_POLICY`) like the TypeScript adapters.
  - **Applicability and sources** (`core/conventions/definitions.mjs`, `resolve.mjs`). A preset can also give `conventionStyle`, which returns `{ unused, project, note }` for the tools in use: `unused` maps the ids the formatter cannot apply to a reason (they are not measured or printed, and a pin for one is a config error), `project` maps the ids that a listed project tool config sets to `{ choice, from }`, and `note` adds a remark to a printed choice (black accepts both quote styles). A project value replaces a pin and a measurement for its id (`source: 'project'`, printed as "from your ruff config"), and a value outside the options (`tab`, `preserve`) is printed but never reaches the policy. Python: `python-style.mjs` picks ruff or black as the format check does and reads their config through `project-format-config.mjs`. Kotlin: `kotlin-style.mjs` reads the `.editorconfig` keys for `*.kt` (`editorconfig-values.mjs`), the ktfmt style the build names and the `WildcardImport` setting of the detekt config; only the tools whose `tools.<tool>.precedence` lists `"project"` first are read.
  - **Names** (`kind: 'names'`, `minFiles`, `sampleLimit`, `choose`). A convention that collects names instead of choosing an option: `measure(text, file)` returns evidence strings, the counts are per file, and `choose(counts, definition)` (default: every name seen in at least `minFiles` files) returns the followed names, sorted. The choice is an array (`[]` is the fallback, a pin is a list of identifiers) and `describeConventions` prints it as "final call of at least N of M measured files". `java.assertionHelpers` and `kotlin.assertionHelpers` (`measures/assertion-helpers.mjs`, with `languages/java/source/` extracting test methods and function definitions from the masked source) count `use:<name>` (the call that ends an enabled test method without a known assertion, in a `src/test`-style source set, and reads like an assertion: `expect...`, `ensure...`, `must...`, `should...`, `validate...`, `is...`, `has...`, `await...`) and `def:<name>` (a method or function in a test source set or a `test-support`, `test-utils`, `testkit` or `testing` folder whose body calls a known assertion or throws); a name is followed when it is used in at least 3 files and defined at least once, so production helpers such as `validate` or `isEmpty` are never learned. Known assertions are call names that are `assert`, `check` or `verify` followed by a capital or the end (Kotlin also `coVerify`, `expect`, `should`, Kotest infix `should...`, `confirmVerified`, `andExpect`, `forAll`, `fail`); `@Disabled` and `@Ignore` tests are skipped. `java.assertionHelpers` reaches PMD as the project's helpers appended to nitpicker's `extraAssertMethodNames` for `UnitTestShouldIncludeAssert` (`tool-config/pmd-layers.mjs`), on Gradle and Maven alike; `kotlin.assertionHelpers` feeds the Kotlin `test-without-assertion` rule.
  - **Java** (`languages/java/conventions/`): `java.formatter` (`measures/java-layout.mjs`, `formatterProfile`) votes per file only from evidence: tab-indented blocks are `none`, and otherwise the file needs a call the formatter wrapped after `(` (the Kotlin join measure with `wrappedOnly`, so the longest-line fallback of `java.lineLength` never votes for a formatter): two spaces at 100 and four spaces at 100 are `google`, four spaces at 120 `palantir`, 140 columns and two spaces at 120 `none`. The definition sets `minVotes: 3` and `strictMajority: true` (`shared/conventions/detect.mjs`: fewer voting files, or a winner with half of the votes or less, keeps the default `google`, whose indentation `java.indentation` still measures, `tab` included, from block-opening lines outside text blocks and comments; `withoutRawStrings` blanks text blocks). `java.lineLength` accepts any whole number of columns (`COLUMNS` in `shared/conventions/settings.mjs`: `valuePattern` and `unit` on the definition, used by pin validation, `appliedChoices` and the printed label; `kotlin.lineLength`, `python.lineLength` and `prettier.printWidth` carry it too, so a Checkstyle, detekt, `.editorconfig` or ruff width of 110 is followed instead of dropped). `build-style/` holds the project reading: `build-files.mjs` lists the build files of a conventions source (root and module Gradle files, version catalogs, `buildSrc/` and `build-logic/` plugins, every `pom.xml`, at most 200, none under `src/`, `node_modules`, `build`, `target`, `out`, `fixtures` or `testdata`), `build-comments.mjs` removes comments with a string-aware reader (`//` and `/* */` outside quotes for Gradle code, `#` for TOML; poms go through `parseXml`), `java-formatter-detection.mjs` returns `{ formatter, aosp }` from Spotless (`googleJavaFormat().aosp()`, `palantirJavaFormat().style("GOOGLE")`, `eclipse()` and `prettier()` in a `java` block as `none`), the palantir plugin, `fmt-maven-plugin` and the artifacts (most common declaration wins, a tie declares nothing), and `checkstyle-width.mjs` the `max` of a `LineLength` module (80 when it has none) with `parseXml`. `java-project-style.mjs` is the preset's `conventionStyle`: `project` maps `java.lineLength` to the Checkstyle `max` when `tools.checkstyle.precedence` lists `"project"`, and `derive(detected)` (a hook of `conventionStyle` that `resolve.mjs` applies after `project`) returns the formatter from the build file when it is not pinned and the choices the formatter fixes (`google` 100 columns, plus 2 or 4 spaces when it was declared, `palantir` 4 spaces and 120). A pin or Checkstyle width the formatter contradicts is a config error naming the source when the formatter is pinned or declared, and resolves the formatter to `none` (printed with the reason) when it was only the default or measured. The styles get a `source` (`{ paths, readMany }`) from `resolve.mjs`: the merge base when it holds Java sources (else the working tree), filtered by the policy's `exclude`, so a pull request cannot loosen its own limits by adding a formatter or editing the Checkstyle config; `kotlinStyle` and `pythonStyle` read the opted-in project configs (detekt, ktlint and ktfmt settings, `.editorconfig`, `ruff.toml`, `pyproject.toml` and the files they `extend`) from the same merge base through a config root, and only when a tool lists `"project"`: `lazyConfigRoot` (`core/conventions/style-snapshot.mjs`) writes the known config names of the project, its parent folders and the `extend` chains it follows, plus `kotlin.detektConfig`, into a temporary directory (made from the absolute temporary path) with an empty `.git` marker, so the tools' upward config search stops there. It copies shallowest files first, fails when more than 1000 style files match, leaves out names the system cannot hold (too long, `:`, reserved) with a printed note, and removes the directory when the conventions are resolved or when copying fails. Symbolic links are read through their target inside the project folder, in the merge base and in the working tree alike (`core/conventions/sources.mjs`). The formatter itself is detected from the same source without copying anything (`kotlinFilesFromSource`, `detectFormatterFromSource`), and a convention is unused only when neither the base nor the head formatter uses it, so a pull request that adds a formatter can keep its pin. A choice read from a config is marked `followsConfig`, so it reaches the policy even when it equals the preset default, and the format runs enforce it over a different value in the head config (Python flags, a ktlint section appended to every mirrored `.editorconfig`, a detekt `enforced` layer written to its own file). A width outside 10 to 999 is ignored with a printed note, as are `LineLength` modules with severity `ignore` and detekt rules with `active: false`. The TypeScript preset has no project-config convention, and `prettier.printWidth` drives no limit rule, so it has nothing to read from the base. For the kotlin preset the Java and Kotlin styles are merged in `definitions.mjs`. `javaLineLength(conventions)` feeds `javaLineLengthFindings`.
  - **Kotlin** (`languages/java/conventions/`): `kotlin.indentation` reuses the Java block-step measure and has no preset default, because ktfmt's is 2 and ktlint's is 4, so a choice always reaches the tools: ktfmt style `meta` or `kotlinlang`, ktlint `indent_size`; `kotlin.trailingCommas` compares wrapped call and declaration lists that end with a comma with those that do not (ktfmt always adds them, so only ktlint is affected); `kotlin.lineLength` (`measures/kotlin-line-length.mjs`, 100, 120 or 140, no preset default) is the `python.lineLength` rule for Kotlin: the longest breakable line against the shortest join of a wrapped `(...)` list, else lines past 100 or 120; ktlint gets `max_line_length` in its defaults file, ktfmt `--max-width` (`-Pnitpicker.kotlin.ktfmtMaxWidth`), detekt a `MaxLineLength` convention layer, and with no formatter it is unused; `kotlin.wildcardImports` marks a file `wildcard` when it has any wildcard import except the `java.util.*` and Android synthetics that detekt and ktlint allow anyway. `java.wildcardImports` (`measures/java-imports.mjs`; any star import except a static one in a test source set marks a file `wildcard`) and `java.testStaticImports` (static star imports, measured over the `src/*test*` source sets) are applied after the tools ran: `withoutFollowedImports` (`adapters/imports/`) drops `checkstyle/AvoidStarImport` and `errorprone/WildcardImport` findings before the overlap step, the latter only on `import static` lines of test files, so Gradle, Maven and the Kotlin preset's Java files behave alike; the detector passes the file path to `measure(text, file)`. `java.indentation` (Java sources, google-java-format 2 or `--aosp` 4) has the preset default 2, `kotlin.indentation` has none; both use the same measure. The ktlint and ktfmt runs happen in a mirror of the Kotlin sources (`nitpickerKotlinStyleWorkspace`) with a generated root `.editorconfig`, so project `.editorconfig` files stay out unless the tool lists the project; ktlint gets the conventions as `--editorconfig` defaults, detekt as a layer below the project's config (`nitpickerDetektLayers`).

## Dependency and repository hygiene (`shared/hygiene/`)

`repository-hygiene` is added to every preset's analyzers by `core/configuration/preset-analyzers.mjs` (injected analyzers still replace the whole set). It runs `core/cli.mjs hygiene --check repository-hygiene --project-root <root>` (the CLI entry hands the arguments to `runHygieneCli` in `runner.mjs`, so the runner needs no entry point of its own; the rule ids and the catalog rows live in `shared/project-rules/hygiene-rules.mjs`, which `shared/policy.mjs` imports), lists files with `git ls-files -z` and reads the head policy file for `exclude` and `exceptions`: an excepted finding is dropped inside the runner, by rule id and project-relative path.

- **Identities.** `file:<path>`, so a file already on the base stays unchanged and only an added one is new.
- **Sizes.** `git ls-files -s` and `git cat-file --batch-check` size the committed blob of each regular file, so an LFS pointer is small and a symlink or submodule is not sized.
- **Configuration hash.** The runner's relative-import closure (`shared/import-closure.mjs`); the TypeScript analyzers hash the import closure of their adapter files, which reaches the dependency ESLint rule and `quality-areas/reporting/dead-code.mjs`.
- **Key blocks.** `git grep -l -I -E` finds the private-key header in any tracked text file.
- **Package rules.** `languages/typescript/adapters/quality-areas/reporting/dead-code.mjs` maps knip's `dependencies` and `devDependencies` to `unused-dependency`, `unlisted` to `unlisted-dependency` and `unresolved` to `unresolved-import`, keyed by package name or specifier. Their exceptions come from the head policy file like the rules above; an entry with `packages` lifts only findings whose package name or specifier it lists. `knip.json` lists `ignoreDependencies` for the packages nitpicker itself needs. `nitpicker/no-dev-dependency-in-production` (in `eslint-lint`) reads the nearest `package.json` and flags value imports of a package that is only in `devDependencies`.

## Change history (`shared/history/`)

`change-history` is an analyzer of its own that reuses the hygiene plumbing: it runs `core/cli.mjs history --check change-history --project-root <root> [--history-ref <sha>]` (`runHistoryCli` in `shared/history/runner.mjs`, which shares `runCheckCli` and the argument parser of `shared/hygiene/cli.mjs`, reads the head policy file and drops excepted findings by rule id and module path like the hygiene runner). `createHistoryAnalyzers` (`shared/history/analyzers.mjs`) builds it with `createCheckAnalyzer`, whose configuration hash is the import closure of `history/runner.mjs`, so the hygiene hash does not move when history code changes. Its `resolveConfigurationHash(policyRoot)` adds `cloneDepth` (`full` or `shallow` from `git rev-parse --is-shallow-repository` in the head snapshot, or the unavailable reason when git cannot tell) to that hash, so a base result cached by a shallow run (always unavailable, so empty) is never reused by a full-history run on the same merge base. The git calls share the `git` wrapper of `shared/hygiene/tracked-files.mjs`, which pipes stderr so a failure carries git's own message. `core/configuration/preset-analyzers.mjs` adds it to any preset's analyzers only when `config.history.coChange` is `true` (injected analyzers still replace the whole set; `disable` names it like any analyzer, and `"disable": ["change-history"]` without the opt-in is an unknown-analyzer error). The check lists the files of the history ref (`committedFiles`, `git ls-tree -r` at the ref) only once the history is available, so a project that is not in a repository is "unavailable", not a tool error. The rule id `co-change`, its catalog row, the defaults and the limits (`CO_CHANGE_DEFAULTS`, `CO_CHANGE_LIMITS`) are in `shared/project-rules/hygiene-rules.mjs`; `enforcedBy` is `'reported'` for every language, which `shared/checks-catalog.mjs` prints as `report-only`.

- **Config.** `history` is `{ coChange, commits, minSupport, minConfidence, maxCommitFiles }`, validated by `core/configuration/scopes/history-settings.mjs` (a setting without `coChange` is an error; with `coChange: false` it is validated and kept, so `false` is a clean off switch; `maxCommitFiles` is at most `CO_CHANGE_LIMITS.maxCommitFiles` = 100). It is a head-policy key (`shared/head-policy.mjs`), so it is part of the cache key. It is not a loosening in `core/policy-changes/`: turning it on or off, or moving a threshold, is listed as a plain policy change, because the findings never fail. The base is measured with the head's `history` (`baseConfigCoveringHead`, as for `duplicates`), otherwise a base without the key would report no pairs and every pair would be new. `layout.featureRoots` is accepted by every preset when `coChange` is on (`validateFactRuleSettings`, `validateLayout`).
- **History.** `evidence/git-history.mjs` runs `git log -n <commits> --no-merges -M --name-status -z --relative --format=%x01%H --end-of-options <ref> -- .` in the project root (so a project below the repository root sees only its own paths) after `git rev-parse --is-shallow-repository` and an empty-repository probe (`git rev-list -n 1 --all`). It returns `{ available: false, reason }` for `shallow`, `not-a-repository`, `too-few` (fewer than `CO_CHANGE_LIMITS.minHistory` = 20 commits, 0 in an empty repository), `git-missing` (the spawn failed with `ENOENT`) and `unreadable` (with the first line of git's stderr as `detail`), never an exception. `<ref>` is `HEAD` unless `--history-ref` names one. Both sides of a comparison read the same window: the base worktree is checked out at the merge base, and `createInvocation` of the head run adds `--history-ref` with `git rev-parse HEAD` of `baselineRoot` (the base worktree), so the head reads the merge base's window too; commits the change adds, the synthetic commit of a dirty tree and a window that would shift by those commits never reach either side. Modules are resolved against the files of the ref, not the head's tracked files.
- **Evidence.** `evidence/evidence.mjs` walks commits newest first. Every rename entry maps its old path to the current path of the new one, so older commits count for the file where it lives now (also for commits that are skipped). A commit counts when it has at most `maxCommitFiles` entries (all files, tests and documents included) and edits (`M`, `T`, or a rename that is not `R100`) at least one production file; its modules are the modules of its edited production files only, so added files, pure renames and edits to tests and documents are no evidence, and a pair needs edits in both modules. Modules get integer ids and a pair key is `first * 2^21 + second`; pairs are counted only between modules with at least `minSupport` commits, which keeps the pair map small; the cost per commit is quadratic in its modules, bounded by the 100-file cap. `confidence` is `support / min(commits(a), commits(b))`; a pair is reported at `support >= minSupport` and `confidence >= minConfidence`, unless one module is the parent folder of the other. Sample size is the number of counting commits.
- **Modules.** `evidence/production-files.mjs` keeps a file of the ref that has a code extension (ts, tsx, mts, cts, js, jsx, mjs, cjs, py, java, kt, kts), is not a declaration file (`.d.ts`, `.d.mts`, `.d.cts`), a build or tool file (`*.gradle`, `*.gradle.kts`, `*.config.*`, `.*rc.js`, `setup.py`, `conftest.py`), a test (`layout.testRoots`, a test name, a test folder at any depth, a test source set under `src/`, or a root `fixtures/` or `testing/`; under `src/main/` only the name counts), generated (output folders such as `build/` and `out/` at any depth, generated names, `generatedFiles` of the head policy, a generator header or `@Generated` annotation via `shared/conventions/generator-marker.mjs`; a file missing from the working tree is not treated as generated) and is not under `exclude`. Its module is `featureRoles` (`shared/rules/features/feature-roles.mjs`, the function `shared-used-by-one-feature` uses, with no shared roots) feature folder, else the folder holding it; files in the project root have no module.
- **Findings.** `tool` `change-history`, `rule` `co-change`, `path` the smaller module (plain string order), `identity` `<a>|<b>`, `classification` `descriptive`, `exceptionPaths` both modules with and without a trailing `/` (stripped by the runner after the `exceptions` check, so an entry for either module lifts it). The message has three parts: the evidence (support, sample size, confidence over the less-changed module's commits, up to `CO_CHANGE_EXAMPLES` short commit ids), one remedy sentence that says co-change is correlation, and the exception route with a `<module>/**` glob. The longer reading (which way out fits, why nitpicker does not read imports at this layer) is in `docs/usage.md#change-history`.
- **Notices.** `core/command/policy-review/notices.mjs` composes the language notices with `coChangeNotices` (`history/co-change/notices.mjs`) when `history.coChange` is on and the analyzer is not disabled. `runQualityDiff` calls `describeNotices(changedFiles, { mergeBaseSha, touchedPaths })`: `touchedPaths` (`readTouchedPaths` in `core/diff/git/patches/project-moves.mjs`) holds every path of the base-to-head name-status diff, both sides of a rename, deletions and additions included, scoped to the project, and `coChangeNotices` reads the history at `mergeBaseSha` and resolves those paths against the merge base's files, so a deleted or renamed partner counts as touched. A changed module gets one notice for the partners no touched path belongs to and with which it shares at least `minConfidence` of its own commits (`support / commits(changed module)`, printed as a percentage), at most three partners by support and at most three modules by support, then a count of the rest; pairs lifted by `exceptions` are left out. Unavailable evidence is one notice with the reason (`unavailableNotice`); `historyAvailabilityNotes` writes it to stderr for `--all` runs, which have no notices.

## Facts schema (`shared/rules/facts/`)

The reuse, doc-comment, test-only-export and console rules are written once, over neutral facts. A language only produces the facts; `sharedFactFindings` turns them into findings. Lines are 1-based, a field marked optional may be left out, and unknown fields are ignored, so a producer can add its own. Every path is project-relative with `/` separators, with no leading `./`, no `.` or `..` segment, no empty segment and no trailing `/` (`app/orders/service.py`, never `./app/orders/service.py` or `app/orders/`); `validateFacts` rejects any other form.

A facts bundle is one JSON object. Each list is optional in the schema, but a rule needs the lists it reads (see the table below): when the bundle lacks one, `sharedFactFindings` throws instead of skipping the rule, so a registered rule without a producer is a tool error rather than a silent pass.

```json
{
  "modules": [
    { "file": "app/orders/service.py", "role": "production", "entry": false },
    { "file": "app/billing/invoice.py", "role": "production" }
  ],
  "packages": [{ "root": "libs/money", "published": true }],
  "definitions": [
    {
      "file": "app/orders/service.py",
      "name": "total",
      "kind": "function",
      "line": 12,
      "exported": true,
      "tokens": ["def", "total", "(", "items", ")", ":", "return", "sum", "(", "items", ")"]
    }
  ],
  "imports": [
    {
      "from": "app/billing/invoice.py",
      "to": "app/orders/service.py",
      "names": [{ "name": "total", "alias": "order_total" }],
      "reexport": false,
      "typeOnly": false
    }
  ],
  "docComments": [
    { "file": "app/orders/service.py", "line": 11, "name": "total", "lines": ["Sum of the items."] }
  ],
  "console": [
    {
      "file": "tests/test_service.py",
      "test": "test_total",
      "messages": ["WARNING: rate limit is 0"]
    }
  ]
}
```

- **`modules`**: every file the producer read. `role` is `production` or `test` (a test file, or a helper only tests load, such as a `test-support/` module or `conftest.py`). `entry` (optional, default false) marks a file loaded by path rather than imported: a script, a `__main__` module, a class the build or container starts. `generated` (optional, default false) marks generated code that stays in the facts so imports of it resolve: the feature folder rules leave out every edge from or to it and never report it. `initializer` (optional, default false) marks a package initializer such as a Python `__init__.py`, which `shared-used-by-one-feature` never reports. When `modules` is present, every `imports[].from`, `imports[].to`, `definitions[].file` and `docComments[].file` must be one of its files, and every `console[].file` one of its files, a folder that holds one, or `""`; a dangling one is an error, so list the file or leave the entry out (an import of a file outside the analysed sources, such as a generated or excluded module, is left out).
- **`packages`**: `root` is the folder of a unit that is versioned and depended on by itself (an npm workspace package, a Gradle or Maven module, a Python distribution; `""` is the project root). A file belongs to the longest root that contains it. `published` says whether other projects install it (npm without `private`, `maven-publish`/`java-library` or a deployed Maven module, a `pyproject.toml` with `[project]` and a build backend and no `Private :: Do Not Upload` classifier). A published package's own tests count as callers, so `test-only-export` does not judge it. The package is also the unit `duplicate-definition`, `exported-name-collision` and `sibling-copy-edit` compare within. A single-package project passes `[]`.
- **`definitions`**: module-level declarations. `kind` is one of `function`, `class`, `const`, `type`, `interface`, `enum`. Map each language's declarations onto them:

  | Declaration                                                             | `kind`      |
  | ----------------------------------------------------------------------- | ----------- |
  | Java `record`, Kotlin `object` and `data class`, Python `class`         | `class`     |
  | Java `@interface`, Kotlin `typealias`, Python `Protocol` and type alias | `type`      |
  | Java or Kotlin `interface`                                              | `interface` |
  | Java static method, Kotlin top-level `fun`, Python `def`                | `function`  |
  | Java `static final`, Kotlin `const val`, Python `UPPER = literal`       | `const`     |
  | Java and Kotlin `enum class`, Python `Enum` subclass                    | `enum`      |

  `exported` says whether another module can import it (TypeScript `export`; Python a public name or one in `__all__`; Java and Kotlin `public`, `protected` or `internal`). `tokens` are the declaration's token texts in order, with comments and layout dropped and each string literal one token; two copies are compared by these tokens. A language whose blocks are set by indentation (Python) keeps them as `INDENT` and `DEDENT` tokens, so two bodies that differ only in nesting differ in tokens. A declaration with no tokens is never a copy. Emit the declarations of every module; those of a `test` module are ignored. Optional fields:
  - `qualifier` (default: `name`): the declaration's identity when its name is not unique in its file, such as `Money.of(int)` for one of several overloads or same-named methods of different classes. Findings, the base copy `sibling-copy-edit` compares with and the definitions an import resolves to are keyed by it; copies are still grouped by `name`.
  - `lines` (default 1): the declaration's line count. `duplicate-definition` leaves a declaration of 5+ lines and 50+ tokens to the duplicates check.
  - `size` (default: the number of tokens): the token count the duplicates check would see, for the 50-token cut-off.
  - `literal` (default false): a `const` whose value is built only from literals; only those `const`s are compared.
  - `usedLocally` (default false): the module itself reads the name outside its declaration. A name that is neither used locally nor imported by a production module is not compared (the dead-code check owns it).
  - `exportNames` (default `[name]` when `exported`): the names other modules import it by, for example `default` or an alias.
  - `key` (default: `text`): the identity two same-named copies must share to be duplicates; a producer that resolves free names adds them, so `return helper()` over two different `helper`s is not a copy.
  - `text` (default: the tokens joined by spaces): compared with the base copy to tell an edited declaration from an untouched one.
  - `entry` (default false): a framework entry (a route handler, a default export a framework loads); `sibling-copy-edit` skips it.
  - `package` (default: from `packages`): overrides the package the declaration is compared within.

- **`imports`**: one per resolved dependency edge between two project files: an import statement, and also an implicit reference the language resolves without one, such as a class in the same Java or Kotlin package (the parent `__init__.py` files a Python import runs are not edges). Edges to other packages or installed libraries are left out. `names` holds `{ name, alias? }` pairs: `name` is the name in the target, `alias` the local name when it differs. `*` is the whole module: a namespace import, `import pkg.mod`, a dynamic import, a star re-export, a Java wildcard `import com.acme.money.*` or Kotlin `import com.acme.money.*`, a Python `from mod import *`. A wildcard over a package becomes one edge per file of the package the importer uses, each with `[{ "name": "*" }]`, or, when the producer resolves which names it uses, one edge per file with those names. An empty list only loads the module. `reexport` (default false) marks a statement that makes the names part of the importer's own exports (`export { a } from`, `export *`, a Python `__init__.py` import of a public name, and a name its `__all__` lists, which the scan reports as an `exported` statement). A `reexport` edge with the whole-module name `*` from a feature's public file to a file of the same feature makes that file public: a Python `from . import models` or `__all__ = ["models"]` in the feature `__init__.py`. `typeOnly` (default false) marks an edge that exists only for the type checker (TypeScript `import type`, a Python import under `if TYPE_CHECKING:`): it still couples the importer to the target, so the boundary rules count it, but it does not run, so `feature-cycle` leaves it out. A target imported both ways is two edges, one of them `typeOnly`. An edge's role is the role of its `from` module: an import from a `test` module is a test use, so it never keeps a name alive for `test-only-export`, `duplicate-definition` or `shared-used-by-one-feature`.
- **`docComments`**: one per doc comment on a declaration. `name` is the declaration's name and `qualifier` (optional, as for definitions) tells two same-named ones in one file apart; `lines` are the description lines: the text before the first block tag (`@param`, `@return` in JSDoc, Javadoc and KDoc; `:param x:`, `Args:`/`Returns:` sections or a numpy section underline in docstrings), with comment markers stripped and blank lines dropped. The long check counts only prose: `codeExampleState()` in `shared/rules/doc-comments/doc-comments.mjs` skips fenced blocks (` ``` ` or `~~~` lines and what lies between; the last fence of an odd count is never closed, so it and what follows count as prose, and `descriptionLines()` still cuts at a block tag after it) and an `@example` tag with its body up to the next block tag (tag lines never count), for every language, so a producer may pass those lines through; bullets and other prose count.
- **`console`**: what tests printed, one entry per test, or per file or module when the runner only knows that. `file` is the test file; a runner that only knows the module, such as a Gradle or Maven module's test task output, gives the module folder (`""` for the root module) and `test: ""`. `test` is the test name (`""` when unknown), `messages` the printed lines that count: stderr lines, `console.error`/`console.warn` output, and stdout lines whose log level is `WARN` or `ERROR`. Normalization (paths, numbers, ids, ANSI colors) is done by the evaluator. `testConsole.allow[].paths` and the `test-console-output` exception paths match this `file` (`.` for a root module); a module folder is matched as it is, so lift a whole module with its folder (`billing`), not `billing/**`.

**Registering a rule.** `FACT_RULE_LANGUAGES` in `shared/project-rules/fact-rules.mjs` is the single source for which language enforces each fact rule: per language the value is `true`, `'partial'` or `false`. It fills the rule's columns of the checks table (the catalog in `shared/policy.mjs` gives no `enforcedBy` for these rules), decides which rules `sharedFactFindings` runs for a language, lets every preset name a rule a non-TypeScript language registers in `exceptions`, and widens that preset's config: `FACT_RULE_SETTINGS` names the config keys each rule reads (`testConsole` for `test-console-output`, `layout.sharedRoots` and `layout.featureRoots` for `shared-used-by-one-feature` and the three feature boundary rules), and a preset accepts those keys only once its language registers the rule. A language that enforces a rule with a tool rule of its own instead (TypeScript and JavaScript enforce the feature boundary rules with dependency-cruiser) has the value `OWN_TOOL`: the checks table shows it as enforced, but the rule is not registered, so `sharedFactFindings` never runs it there and its settings do not widen that preset's config. A rule that is not a fact rule but reads the same keys (`contract-infrastructure-type`, run by ArchUnit on the JVM and by the Python rules script) lists its languages and keys in `OWN_RULE_SETTINGS`, and `factRuleSettings(language)` returns the union of both. A runner calls `sharedFactFindings(facts, { language, analyzerName, policy, baseline, rules, siblingCopiesAcrossPackages })` from `shared/rules/facts/evaluate.mjs` and adds the findings it returns to its own; the TypeScript structure runner does the same for its three reuse rules (`structure/reuse/reuse-findings.mjs`). A runner with cycle rules of its own calls `featureFactAnalysis(facts, options)` instead, with the same options: it validates and evaluates the same way and returns `{ findings, explainedCycles, featureOf }`, where `explainedCycles` lists each feature cycle that produced at least one finding (an exception that lifts all of them leaves the cycle out) as `{ features, edges }`, the feature folders and every `{ from, to }` file edge inside it, and `featureOf(file)` gives a file's feature folder or `undefined`:

- `policy` is the head policy (`readHeadPolicyFile()` from `shared/head-policy.mjs`, which every analyzer process can read). Its `exceptions`, `testConsole.allow` and `layout.sharedRoots`/`layout.featureRoots` apply. A policy of the wrong shape (including a `testConsole` or `layout` that is not an object) is a `TypeError` that names the field, and so is an `analyzerName` that is not a non-empty string.
- `baseline` is `{ facts, movesFile }` on the head run of a change: the bundle the producer emits for the base checkout (`--baseline-root`; only `definitions` are read) and a JSON file of `[basePath, headPath]` renames, which only the TypeScript quality-area runners receive today, as `--baseline-moves-file`; the Java, Kotlin and Python runners take neither until a rule they register reads the base. A runner that reads the base lazily passes `{ readFile }` instead: a function from a head file to `{ unchanged, definitions }`, as the TypeScript structure runner does. Without a baseline `sibling-copy-edit` reports nothing. Any other baseline value is a `TypeError`, and a bad baseline bundle fails like the head facts with `baseline` in front of the message.
- `rules` (optional) narrows the run to some registered rules, for a runner that produces some lists in one place and the rest in another (console output from test reports, definitions from source). A rule the language does not register, an empty list and a language that registers no rule at all are errors, never an empty result.
- `siblingCopiesAcrossPackages` (default false) lets `sibling-copy-edit` compare copies in different packages, such as the same class in two Gradle or Maven modules.
- `publicFace` (required by the three feature boundary rules) says which files of a feature other code may import: `PUBLIC_FACES.python` or `PUBLIC_FACES.jvm` from `shared/rules/features/feature-roles.mjs`, or any `{ isPublic(name), describe(directory) }`. `isPublic` gets the file name of a file directly in the feature folder (a file in a sub-folder is always internal), and `describe` the text a message uses for the face. Without it those rules throw.
- `validateFacts` (`shared/rules/facts/schema.mjs`) checks the shapes, paths and module references (when `modules` is given, every import end, definition and doc comment names a listed file, and every console entry a listed file, a folder holding one, or the root) first and names the first bad field; `readFactsFile(file)` reads a producer's JSON output and validates it.

| Rule                         | Lists it reads                                                  |
| ---------------------------- | --------------------------------------------------------------- |
| `duplicate-definition`       | `modules`, `packages`, `definitions`, `imports`                 |
| `exported-name-collision`    | `modules`, `packages`, `definitions`, `imports`                 |
| `sibling-copy-edit`          | `modules`, `packages`, `definitions` (head; base `definitions`) |
| `shared-used-by-one-feature` | `modules`, `imports`                                            |
| `feature-internal-import`    | `modules`, `imports`                                            |
| `shared-imports-feature`     | `modules`, `imports`                                            |
| `feature-cycle`              | `modules`, `imports`                                            |
| `test-only-export`           | `modules`, `packages`, `definitions`, `imports`                 |
| `doc-comment-content`        | `docComments`                                                   |
| `test-console-output`        | `console`                                                       |

**Feature layout.** `shared-used-by-one-feature` and the feature boundary rules need to know which folders are shared and which are features. `layout.sharedRoots` and `layout.featureRoots` are folder globs (a Java or Kotlin package is its source folder, such as `**/com/acme/shared`). A file under a shared root is shared; a file under `<feature root>/<name>/` belongs to feature `<name>`, so a new folder there is a feature with no configuration. When feature roots nest, the innermost one that holds the file decides its feature. A shared folder that is itself the folder under a feature root (`features/shared/`) is shared; one inside a feature folder (`features/billing/shared/`) is part of that feature while the shared roots are the defaults, and shared when `layout.sharedRoots` is configured (`featureLayout` sets `sharedInsideFeatures`). Everything else is `other` (a composition root, an entry module, a module directly in a feature root). `featureRoles` (`shared/rules/features/feature-roles.mjs`) gives each file `{ kind, directory, name }`; `featureRoleContract(layout, publicFace)` adds to a feature file whether it `isPublic` and the `face` text; the rules are `feature-boundaries.mjs` and `feature-cycles.mjs` beside it. The TypeScript default is `<source root>/main/shared` and `<source root>/main/features` (`typescriptFeatureLayout` in `languages/typescript/preset/coupling/feature-layout.mjs`, whose folder names `architecture/strict-layout.mjs` shares with the import boundary rules, which do not follow the config keys); the other presets default to `**/shared` and `**/features`. Without a feature folder the rules find nothing. A configured glob that matches no folder is a notice (`unmatchedLayoutRootNotices` in `shared/notices/layout-roots-notice.mjs`, added by `noticeDescriber`), and a change of either key is compared per file by `featureLayoutChanges` (`core/policy-changes/features/feature-layout-changes.mjs`).

- **`feature-internal-import`**: a production edge from a file outside feature F (another feature or an `other` file; shared files are left to the next rule) to a file of F that is not on its public face. One finding per importer and target file, identity `feature-internal:<target>`. Type-only edges count. A name re-exported by F's public `__init__.py` is imported from that file, so it is allowed; a submodule (`from features.billing import _rates`) is an edge to the submodule's file, allowed only when F's public face re-exports that file whole.
- **`shared-imports-feature`**: a production edge from a shared file to any feature file. One finding per importer and feature, identity `<feature folder>|shared-imports-feature`, listing the imported files.
- **`feature-cycle`**: the strongly connected components (`shared/graph/strongly-connected.mjs`, which the Python package and module cycle rules use too) of the feature graph whose edges are the production edges that are not `typeOnly` between files of two different features. Edges through shared or `other` modules do not join features: a cycle through a shared module needs a shared-to-feature edge, which `shared-imports-feature` already reports, and module cycles through other code stay with the language's own cycle rules. One finding per importer and target feature whose edge lies inside a component, identity `<target feature folder>|feature-cycle`. `featureFactAnalysis` returns the components that produced a finding with their edges, so a runner can drop its own cycle findings with the same root cause.
- **Identities** carry no line and no importer (the finding's path is the importer, which the comparison remaps through renames), and a folder in front of `|` is remapped through the detected folder moves (`remapRootPrefix`), so moving a file inside a feature or moving a feature folder keeps the finding.

## TypeScript preset (`languages/typescript/`)

- **Strict preset assembly.** Flat config replaces rather than merges a rule's options when several entries match a file, so each scope in `eslint-config/strict.mjs` carries its full `no-restricted-syntax` list: the everywhere selectors plus the scope's own. Add a selector to its scope's list, never as a separate entry for a narrower glob. `domain/` has its own loop and forEach selectors, so it drops those from the production set. Default exports, `null` and promise chains are not in these lists: `nitpicker/no-default-export`, `nitpicker/no-null` and `nitpicker/no-promise-chain` (`eslint-plugin/rules/syntax/syntax-bans.mjs`) take the same `{ selector, message }` options as `no-restricted-syntax`, are set once on the source entry (domain/ and adapters/ inherit them, the config-file entry turns the default-export and promise-chain ones off) and in the test entry (promise chains), so an exception for one lifts only that ban. The JavaScript dialect strips TypeScript-only selectors from `nitpicker/no-null` as it does from `no-restricted-syntax`. `strictSyntaxConfig` (`strict.mjs`), `strictAdaptersConfig` (`strict-adapters.mjs`) and `strictTestsConfig` (`strict-tests.mjs`) are standalone configs so the failure-message harness can lint one rule family alone; no tool loads them by path, which is why they are ordinary modules and not `*.config.mjs` files. The typed ones (`strictConfig(parserOptions)`, `strictAdaptersTypedConfig`) need `parserOptions` (e.g. `{ project: './tsconfig.quality.json', tsconfigRootDir }`) and later entries win.
- **Immutability check.** `functional/prefer-immutable-types` is-immutable-type caches a verdict per recursion identity, and for a type that recurses through its own arguments (`readonly (readonly T[])[]`) the checker hands out one identity for every depth, so the verdict depended on which file was linted first. `type-identity/functional-plugin.mjs` wraps the rule so that, past 12 nested type arguments, instantiations share one identity and each shallower instantiation keeps its own (`recursion-identity.mjs` replaces the checker's internal `getRecursionIdentity` once per checker, and leaves a checker without that method alone; the replacement is shared by every typed rule on that program, which only changes how deep instantiations are told apart). Every config uses that one plugin object, because flat config rejects two objects under one plugin name.
- **Scripts in a TypeScript project.** `javascript-in-typescript-project` (`structure/sources/javascript-files.mjs`, run by `typescriptStructureProjectFindings`) reports every `.js`, `.mjs`, `.cjs` and `.jsx` file (`SCRIPT_EXTENSION`, derived from `codeExtensionNames`) of `layout.projectCodeFiles` that no exception for the rule covers and that is not a test input (`layout.isTestFixture`: under `fixtures/` or `__fixtures__/` in a test location), when the head checkout (`liveProjectRoot`) is a TypeScript project, that is it has a `tsconfig.json` outside `node_modules` and the exclusions (`projectTsconfigs`, which also follows `references`), and the preset is not `javascript`. `layout.entryPoints` do not lift it. The message names the `.ts` or `.tsx` file to write instead. The identity is the rule id, so the file path alone tells base and head apart and only an added file is new. The type-aware lint rules run on scripts as on TypeScript. The rule's id, message and catalog entry live in `shared/project-rules/source-rules.mjs` with `component-story-missing`, spread into `shared/policy.mjs`.
- **Built-in excludes.** `layout.mjs` anchors `dist`, `build`, `generated`, `coverage`, `reports` and `target` to the project root and `node_modules` to any depth (`EXCLUDED_PATH_PATTERN`, the one regular expression dependency-cruiser, the structure analyzer and the spawned-entry scan share). The JSON tool configs (`tsconfig.quality.json`, `tsconfig.stryker.json`, `jscpd.json`, `knip.json`) and `vitest.quality.config.ts` write the same folders, and `layout.test.mjs` keeps them equal to `builtInExcludedGlobs`. A `layout.excludedGlobs` entry that is not built in hides its files like `exclude` (`isExcluded`, `excludePattern`). Generated code is decided by content, not name: `markedGeneratedFiles` (`layout/generated-files.mjs`) keeps the tracked code files that `mayBeGenerated` (a `*.gen.*`, `*.generated.*`, `*.pb.*` or `*_pb.*` name, a `__generated__/` folder, or a root output folder) and whose first five lines match `GENERATOR_MARKER` (`@generated`, `DO NOT EDIT`, `<auto-generated`, `auto-generated`, `This file was generated`). `withProjectFacts` puts the list in the head policy as `generatedFiles`; `isGeneratedPath` (and so `isSourceFile`, `projectCodeFiles` and the reuse walk) and the outside-roots rule's `generatedFilePattern` read it, so an unmarked file is checked like any other. The default roots are `sourceRoots` and `testRoots` of `layout.mjs`, which the project checks, the base coverage and the tool configs import, and folder walks go through `filesUnder` (`shared/filesystem.mjs`). `*.d.ts` is not excluded: ESLint lints it and TypeScript reads its declarations (the analysis tsconfig sets `skipLibCheck`, so errors inside `.d.ts` files, the project's own included, are not reported; checking them would also check every package's types), and `runtimeExcludedGlobs` adds it for the tools that instrument code (Stryker, CRAP, coverage).
- **Lint errors that are not findings.** ESLint 9 reports `/* eslint-env */` as a fatal message and its runner used to throw on it; `withoutFatalDirectives` (`adapters/hints/eslint-hints.mjs`) drops that message in the three ESLint analyzers and the regular lint rules report the comment as one finding.
- **React scope.** `eslint.config.mjs` adds `reactScopeConfigFor()` and passes `{ react: true }` to `strictPresetConfig()` only when `isReactProject()` says so: the head policy's `react.enabled` when set, else `react` in the analyzed tree's `dependencies` or `devDependencies` (the head policy carries the decision: `resolveHeadPolicy(config, projectRoot)` fills `react.enabled` and `i18n.enabled` from the head checkout's manifest unless the config sets them, so base and head are linted with the same scope, a pull request that adds React or `react-intl` does not make every existing finding new, and the policy hash and cache key include the decision; a run without a project root, such as `--fix`, falls back to the manifest of the tree being linted, read from `NITPICKER_DIFF_ESLINT_PROJECT_ROOT`). The plugins load through a dynamic import, so a non-React run never pays for them. `react: true` changes one `strict-declarations.mjs` selector: classes extending `Component` or `PureComponent` leave the "classes only for `Error` subclasses" ban and belong to `react-x/no-class-component`. The head policy carries `react` only when the config sets it, which keeps zero-config cache keys unchanged. Unset `react.styling` is resolved once from the head checkout into the head policy (`stylingApproachFor()` in `eslint-config/react/react-styling.mjs`, called from `detectedScopes()`): `usedStylingApproach()` counts the layout's source files (at most 3000) that import a stylesheet or pass `className`, import a CSS-in-JS library (`cssInJsSource` in `layout.mjs`), call `StyleSheet.create` or write an inline `style` object, and takes the largest count (ties in that order); with none, `dependencyStylingApproach()` reads the manifest (`css-in-js`, `style-sheet` for `react-native` or `expo`, else `class-names`). Base and head are linted with the head's approach and the policy hash includes it. `react.autoCleanup` is resolved the same way (`testsCleanUpAutomatically()` in `scope-support.mjs`: true without a Vitest dependency, else true only when the project's Vitest config sets `globals: true`); the test entry turns `testing-library/no-manual-cleanup` off when it is false. The production and test entries carry `globals.browser` unless the tree lists `react-native` or `expo`, so a JavaScript React project knows `document`; `browserGlobalEntries()` adds `no-restricted-globals` with `restrictedBrowserGlobals` (the standard confusing-browser-globals list, each naming `window.<name>`) for the same files, as the last entry of `reactScopeConfigFor()` and ignoring the `domain/` globs, whose own `no-restricted-globals` list would otherwise be replaced. `isReactProject()` returns false for the JavaScript preset (`layout.javascript`) whatever the manifest or `react.enabled` says, and `validateConfig` rejects the `react` key with that preset, so there is no config route to switch the scope on or off there. With the scope off, `eslint.config.mjs` drops the exceptions that name a React rule id (`reactRuleIds`) before `applyRuleExceptions`, which still rejects unknown ids. With the scope on, `strict-escape-hatches.mjs` also lets `null` through as the argument and type argument of `useRef` and `createContext`. The custom React rules resolve `useEffect`, `useLayoutEffect` and `useState` through their `react` import bindings (aliases, namespace imports); an identifier with no binding at all is matched by name, so auto-imported hooks still count. `react-rules.mjs` lists every React rule id (strict, like the other scopes' rules); `react-scope.test.mjs` checks it against the config and the accessibility names against the plugin's recommended set. The test rules (`reactTestRuleIds`) are a second entry in `reactSyntaxConfigFor()`, scoped to test files (`layout.testGlobs` plus `__tests__` directories) and independent of the runner: `eslint-plugin-testing-library` (peer range includes ESLint 10) supplies `no-test-id-queries`, `no-node-access` (which also reports `container.querySelector`, so `no-container` is left out to avoid a second message), `prefer-user-event`, `prefer-screen-queries` (in the plugin's own React config; reports queries destructured from a `render` result), `await-async-events`, `await-async-queries`, `await-async-utils`, `prefer-user-event-setup`, `prefer-presence-queries`, `no-unnecessary-act`, `no-debugging-utils` and `no-manual-cleanup`, and `nitpicker/react-test-no-implementation-details` covers what the plugin does not (component instances and state, fiber internals, spies on React hooks; a spy target counts as React when it is `React`, `react`, a binding of the `react` package (default, `{ default as R }`, namespace, `import = require`, `require`, `await import('react')`, `vi.importActual('react')`, `jest.requireActual('react')`, wherever in the file it is declared) or an alias of one (`const R = React`, `.default`), or a direct load of `react`, resolved by `reactBindingNames()` and `isReactExpression()` in `react-test-files.mjs`; the hook name may carry `as 'useState'`). Upstream `prefer-user-event-setup` recognises a direct call only through the default `userEvent` import once `utils-module` is set, so `withNamedUserEventImport()` reports `userEvent.click(...)` (any method but `setup`) in a file whose only import of `@testing-library/user-event` is the named `{ userEvent }` (or an alias of it). `testingLibraryPlugin` wraps each upstream rule three ways. `withHint()` appends the allowed form. `withoutFixes()` drops `fix` and `suggest` from every report: ESLint 10 calls a fixer at report time, and upstream's `await-async-events` fixer sets `async = true` on the node, which crashed `@typescript-eslint/require-await` and with it the whole analyzer. `inReactTestFilesOnly()` (`eslint-plugin/rules/react-tests/react-test-files.mjs`, also used by the custom rule) runs the rule only in a `.tsx`/`.jsx` file that is not a browser end-to-end test (`isBrowserEndToEndTest()` in `analysis/test-code-analysis.mjs`: an `@playwright/*` or `cypress` import, or a path under the repo-root `e2e/` test root), a file that imports `@testing-library/*`, `react`, `react-*`, `enzyme` or a relative `test-utils` module, or a file that mocks `react` or `react-dom` with `vi.mock`/`jest.mock` (`mockedModuleSource()` in `analysis/test-code-analysis.mjs`, the one mock parser the testing rules share), because the plugin's own detection is aggressive without an import and would flag Playwright `getByTestId` or a zustand `setState` in a domain test. - **Test console output.** `test-console` is a quality-area analyzer that depends on `coverage` (like `crap`), runs no tests and takes the version of the project's test runner for its cache key, as `coverage` does; disabling `coverage` turns it off with `crap` (`applyDisable` turns off every transitive dependent of a disabled analyzer, `describeDisableCascade` words the stderr note), so a config written before it existed still applies. The test run adapters start the capture through `startTestConsole` (`adapters/test-runners/test-console-run.mjs`), which names the report in `NITPICKER_TEST_CONSOLE_REPORT` (`reports/quality/test-console/report.json` in the snapshot), the project root in `NITPICKER_TEST_CONSOLE_ROOT` and, for the runners whose test processes cannot write one file, a lines file in `NITPICKER_TEST_CONSOLE_LINES`; the capture is off in a `rerun` (the retiming of slow tests), so a partial run never replaces the report. That report is the whole contract with a test runner: `{ "entries": [{ "file", "test", "messages": ["..."] }] }`, one message per console call, `file` absolute (or empty for a Vitest log with no task) and `test` possibly empty. Each runner has one producer loaded by path inside the user's process, and they share `console-report.mjs` (normalization to messages, placeholders, the report writer, a block's group indent removed first so a call inside `console.group` reads like one outside it, whichever runner indented it). The ESM producers are `*.config.mjs` files in `preset/test-console/` (what the lint policy lets read `process.env` and default-export), and each only passes `process.env` (and, for Jest, the working directory; for Mocha, `process.argv[1]`) to a function of a sibling module that holds the logic and is tested directly. A producer does not normalize: it hands over the split messages, and the shared `testConsoleFindings` (`shared/rules/console/`, the `test-console-output` fact rule that `FACT_RULE_LANGUAGES` registers for TypeScript and JavaScript alike) normalizes them with `normalizeConsoleMessage` and applies `testConsole.allow` through `consoleAllowMatcher`, so no runner has its own copy. Vitest: `vitest-reporter.config.mjs`, a second `--reporter` of the coverage run. Jest: `runners/jest-reporter.config.mjs` (logic in `jest-reporter.mjs`), passed as `--reporters=default --reporters=<path>` with `--silent=false --verbose=false`, because only `BufferedConsole` keeps `testResult.console` (a `silent` project gets a `NullConsole` and a `verbose` one, or a run of one file, which Jest makes verbose, a `CustomConsole` that prints at once; only reporters see the buffer: Jest drops it from the aggregated results, so a `testResultsProcessor` gets none). It keeps the `error`, `warn` and `assert` types (`console.trace` is an `error` entry) per test file and rewrites Jest's `AssertionError [ERR_ASSERTION]: <first argument>` as Node's `Assertion failed: ...` (Jest drops the other arguments); Jest gives no timing for those entries, so there is no test name. After a file's tests Jest freezes its console: a later call prints "Cannot log after tests are done" and sets `process.exitCode = 1`, which fails a run in band (one file, or `-i`). With the forced `BufferedConsole` that also happens to a `silent` or `verbose` project (`CustomConsole` prints errors and warnings through `_logError`, which the freeze does not replace), so `runJest` treats an exit of 1 as a pass when Jest's report passed everything (`success`, no failed test or suite, no runtime error, no snapshot `failure`, not interrupted), standard error holds that text, and `--showConfig` shows `silent` or `verbose` (`shownConfig`, global or any project) or the run had one test file; a buffered multi-file run in band still fails, as it does without nitpicker. The late call is not recorded, as with Vitest, whose worker ends with the file. `node:test`: the coverage preload `v8-coverage/loaded-sources.cjs`, which the coverage run passes with `--require` and in `NODE_OPTIONS`, so every process of the run loads it, including those a test spawns. It records only in a test file process the runner started: the runner process (no `NODE_TEST_CONTEXT`, `--test` in `execArgv`) writes its pid to `NITPICKER_TEST_CONSOLE_RUNNER` when that variable is empty (`startTestConsole` sets it to `''` for the run, so an inner `node --test` that a test starts with `NODE_TEST_CONTEXT` removed inherits the outer pid, claims nothing, and its files do not record), and a process records when `NODE_TEST_CONTEXT` starts with `child`, `argv[1]` is set and its parent is that pid; a process a test starts has the test file process as its parent, so it never loads `node:test` and keeps its own output and exit code. There it takes the file from `argv[1]` and registers root hooks that keep the stack of running test names (`fullName`): `beforeEach` pushes the name, and `afterEach` (which runs before the project's root `afterEach` hooks) adds a `t.after` hook that pops it, which node:test runs after every `afterEach` hook and after the test's own `t.after` hooks, so those keep the test name. Its root `after` hook, which runs first, adds one more root `after` hook through its context (`context.after`), which node:test appends and runs last because it rereads the hook list; that one stops recording one `setImmediate` later, so the project's root `after` hooks count, async ones too, and a timer that fires later does not. A context without `after` stops at once. With `--experimental-test-isolation=none` the runner process runs the tests and nothing records (root hooks the preload registers there never run for the files' tests, so the file of a call is unknown). The preload has to be a CommonJS file with no ESM in it: `--import` loads the main file through the ESM loader and skips `require.extensions` hooks such as `ts-node/register`, and a `require` of an ESM file breaks `mock.module` (`resolveSync() is not implemented`) and `tsx`; it exports `recordConsole`, `LINES_VARIABLE` and `MAX_CONTENT_LENGTH` for the ESM modules, so the variable name and the 4000-character cut exist once. Mocha: `runners/mocha-capture.config.mjs` (logic in `mocha-capture.mjs`), passed as `--require`, a root hook plugin whose `mochaHooks` function adds no hooks: it resolves the running Mocha from `process.argv[1]` (the Mocha CLI or its parallel worker script), wraps `Mocha.prototype.loadFiles`/`loadFilesAsync` to listen to the root suite's `pre-require`/`post-require` (the loading file) and hook-added events (the file of a root-level hook), and `Runner.prototype.run` to listen to `hook`, `test` and `end`. Each of those sets the current place (a `beforeEach`/`afterEach` hook takes its test, a `before`/`after` hook its suite's file and title, a test its `file` and its `titlePath()` joined as `suite > test`) and enters it into an `AsyncLocalStorage`, so a timer or promise keeps the place where it started; a call whose origin is another spec file (a timer from a finished file) is not recorded. A call whose origin has no file (work that a root hook from a `--require` file or `mochaGlobalSetup` started, such as a server) takes the current place, so a request handler that logs during a test belongs to that test, as with Vitest; a call made in such a root hook itself, after `end` or with no file at all (Mocha's own warnings in the main process) is not recorded. The place lives in the process, never in `process.env`, so a process a test spawns inherits nothing and, since Mocha's `--require` is not a Node option, does not load it. It works in `--parallel` workers too, which load the `--require` modules themselves. Both wrap only `console.error` and `console.warn`: Node's `console.trace` and `console.assert` print through `this.error` and `this.warn`, so each call is recorded once with Node's own `Trace: ` and `Assertion failed: ` text. The wrapper formats the call as Node would (`util.format`), cuts it to 4000 characters and appends one raw JSON line `{ file, test, content }` to the lines file, with `openSync`/`fstatSync`/`writeSync` taken from `fs` and the file opened when the preload loads, so a test that replaces `fs.writeFileSync` (`mock.method`, sinon) never sees the write. mock-fs replaces the fs binding and numbers its own descriptors from 3, so the writer first checks that `fstatSync` of its descriptor gives the device and inode the file had when it was opened; when it does not (or fails) the line waits and is retried on the next call, so a line never lands in a mocked file. At `exit`, lines still waiting (a mock left active) are appended by a `node -e` child started with `spawnSync`, whose `fs` is not mocked. Nothing the wrapper does throws into the console call. It then calls the original, so a project that stubs the method later also hides the call from the check, as with a silenced Vitest log. The parent normalizes: `startTestConsole(...).finish()` skips a line that is not JSON with a string `content` (a process killed mid-write), runs each line through `consoleEntry` (placeholders for the project root, temporary and home directories, then the splitting into messages) and writes the report right after the run, an empty one if nothing was printed. The Vitest reporter keeps `onUserConsoleLog` entries of type `stderr`, which is where Node's console sends `console.error`, `console.warn`, `console.trace` and a failed `console.assert`. It looks the entity up with `state.getReportedEntityById` (Vitest 4 and 5), skips a log the project's `onConsoleLog` returns `false` for (the call the default reporter makes), and replaces the project root, `os.tmpdir()` and `os.homedir()` (and their real paths) by `<root>`, `<tmp>` and `<home>` so the two snapshots' temporary directories agree. Vitest batches the console calls of one task made in the same microtask into one log, and its `size` is the number of calls: a log is cut into blocks at each unindented line that is not a closing bracket and each block is one message, whether the log holds one call or several (`log.size` is not read), so a call gives the same message alone or batched; the same splitting applies to every runner, and a message is the lines of its call that have a letter or digit, without indented `at` and `in` lines (stack frames, component stacks), joined by spaces. `console-messages.mjs` (in `shared/rules/console/`, so every preset's console findings use it) normalizes a message (terminal colors written as the escape character, as `?` (Gradle) or as `&#27;`/`&amp;#27;` (Surefire); control characters and lone surrogates, whether raw, written as an entity or replaced by `?` between two letters or digits, are dropped so a Gradle and a Maven report agree; the thread name of a Spring Boot or Logback line as `[<thread>]`; paths to their last segment, ISO timestamps, `java.util.logging` clock lines (`Oct 17, 2026 3:04:05 AM`) and clock times, ISO-8601 durations (`PT1M12.345S`) and compound ones (`1h2m3s`) as `<duration>`, the random part of Mockito (`$MockitoMock$`) and ByteBuddy class names and the number of `$$SpringCGLIB$$0`-style proxies, a trailing counter on a word of three or more lowercase letters (`conn6`), `0x` addresses, UUIDs, mixed letter-and-digit tokens of six or more characters, temporary names (`tmp` and six or more of `[a-z0-9_]`, `tmp.` or `tmp-` and six or more letters or digits, and a name under the temporary directory that ends in a separator and six random characters; such a name has no digit to recognize, which is why the temporary directory is part of the rule), every number with its unit, spaces; 300 characters) and `console-findings.mjs` makes one finding per test file and message: identity `console:<hash of the message>`, so the test name, the order and the repeat count are not part of it. A message of three or more words also carries `tokens` (its words), the optional finding field that `compareFindings` uses in `matchSimilarFindings` (`core/diff/comparison/fingerprint.mjs`): a head finding with no exact match counts as present when the base has an unmatched finding with the same tool, rule, path (renames applied) and classification, the same number of tokens and at most one differing token, and that token pair passes `isOpaqueChange` (`core/diff/comparison/similar/opaque-token.mjs`: both tokens, without edge punctuation, are lowercase letters and digits of five or more characters, or carry an `<id>` placeholder, and at least one has a run of four consonants, a vowel ratio under 0.2 or letters mixed with digits; capitalized, camelCase, UPPERCASE and backticked tokens never qualify). Pairs are chosen as a maximum matching (augmenting paths, heads and base findings in identity order), found through an index keyed by the tokens with one position left out and the class of the token left out (random-looking, plain, `<id>` or `<n>`), so only findings that can be paired are ever compared. The search for a longer path stops after two million neighbor visits and keeps the pairs found, which only matters for thousands of messages that differ in one random word. This keeps random values that no pattern can recognize from making unchanged output new without hiding a changed ordinary word. `testConsole.allow` entries (normalized `contains`, optional `paths`) and `exceptions` for `test-console-output` come from the head policy file, so base and head use the same ones. Without a report the runner returns a `test-console-report-missing` tool error; when the tests fail `coverage` fails first and the scheduler skips this analyzer.
- **Type check engine.** `typecheck/typescript-program.mjs` returns the pre-emit diagnostics. The `native` engine (`native-diagnostics.mjs`) loads TypeScript 7's `unstable/sync` API from the `typescript-native` npm alias, opens the config as a project and collects config, program, syntactic, global, bind and semantic diagnostics (declaration ones when `declaration` or `composite` is set), the set `getPreEmitDiagnostics` returns. The CLI is not used because it stops after the first stage with errors, so a missing `types` entry would hide every semantic error. Diagnostics are reshaped into TypeScript 6 objects (a `createSourceFile` per file read with `ts.sys.readFile`, so BOMs and UTF-16 are handled as the project engine does, with `path` set for sorting; `messageChain` turned into a `next` chain; program diagnostics located in a `.json` config made file-less, because TypeScript 6 reports option errors without a location) and go through `sortAndDeduplicateDiagnostics`, so messages, symbols, order and identities match the `project` engine. - **Reuse checks.** `shared-used-by-one-feature` runs in the `coupling` runner (`coupling/shared-usage.mjs`, `coupling/evaluate-coupling.mjs`: the feature and shared patterns are `architecture/strict-layout.mjs`, and the runner hands the head policy's exceptions in); the other five run in the `structure` runner through `structureProjectFindings()` (`structure/reuse/`): `structure/reuse/reuse-findings.mjs` turns the parsed files into facts (`definition-facts.mjs`) and hands `duplicate-definition`, `exported-name-collision` and `sibling-copy-edit` to `sharedFactFindings` (see [Facts schema](#facts-schema-sharedrulesfacts)), and runs the two React rules itself; `sibling-copy-edit` also reads the base checkout the head snapshot gets as `baselineRoot`, and reports nothing in the base snapshot or a run without one. - **Dependency hooks.** A hook has `language`, `manifests` (the first marks a project; if any differs from the live policy root, compared byte for byte, the snapshot needs its own install instead of a link), `directory`, `dependencyRoot(projectRoot)` and `install(projectRoot)`, which installs a regular directory and cleans up and throws on failure. The one hook (`dependency-hooks.mjs`) serves TypeScript and JavaScript and is package-manager aware (`dependency-graph/package-managers/`). `managerRoot()` (`detect.mjs`) is the nearest folder from the project up to the repository root (the first folder with a `.git`; without one the project folder alone) that holds a lockfile, and is where `node_modules` lives, where the install runs and where `manifests` are compared (a different relative position of that folder on the two sides counts as a difference). `manifests` lists `package.json`, every lockfile, `pnpm-workspace.yaml`, `.npmrc`, `.yarnrc`, `.yarnrc.yml` and `bunfig.toml`. `detectPackageManager()` reads the `packageManager` field of the root `package.json` (parsed; the text of a malformed file is matched instead; a known name wins), then the first lockfile in the order pnpm, yarn, bun, npm, else npm, and gives Yarn a `major`: the field's, else the `__metadata` version of `yarn.lock` (4 and below is Yarn 2), else the `yarn lockfile v1` header (1), else `.yarnrc.yml` (Yarn 3+). `installInvocation()` (`commands.mjs`) holds the frozen command per manager and Yarn major (Yarn 2 `--skip-builds`, 3 and later `--mode=skip-build`, which also stops the root workspace's scripts), runs it through `env` with `COREPACK_ENABLE_AUTO_PIN=0` (a Corepack shim must not write `packageManager` into the base) and, for Yarn, `YARN_IGNORE_PATH=1`, because a module outside the composition root may not read `process.env` to merge variables; pnpm gets `--ignore-pnpmfile`. These keep repository code from running during the install; Yarn plugins cannot be neutralized, so `install.mjs` refuses a Yarn 2+ base whose `.yarnrc.yml` has `plugins`. - **Unused props, options and exports.**
  - Program: `structure` builds one TypeScript program (`unused-api/analyze.mjs`) from the layered policy `tsconfig` that the type check uses (so `extends`, `paths` and project references resolve the same way, parsed with `allowJs`), plus root `*.config.*` files, `scripts/`, and every code file of the other workspace packages, whose names `workspace/entries.mjs` maps through `paths` to the source entry their manifest names (`source`, `types`, `main`, `exports`) or to a source root's `index`, and `name/*` into the source roots. The program sets `types: []` so no `@types` package is parsed, and it is not built at all when a syntax-only pass over the source files finds no component with props and no options parameter.
  - Targets: registered by declaration node (function declarations, `const` functions, the function inside `memo` or `forwardRef`, and `const Y = memo(X)` or `export default memo(X)` aliases); members whose props or options type another declaration also uses (`syntax/shared-types.mjs`) are dropped, as are parameters typed by a type parameter.
  - References: one pass over every file (`references/`) resolves JSX tags, call callees, `createElement`, `jsx` and `cloneElement` calls and `X.defaultProps` assignments through imports, aliases and re-exports with the checker (`getSymbolAtLocation` plus `getAliasedSymbol`) and records, per target, which props or options each reference passes and from which kind of file (production or support: the layout's test files and fixtures, stories, `.storybook` and `test-support`). `cloneElement` props count for every component. An identifier that refers to a target in any other position, and every export of a module loaded by `import()`, `require()` or `import.meta.glob` (a template-literal specifier loads every module under its static prefix) or used as a namespace value, is an escape and ends the judging of that target. A re-export statement is not a reference. Members count only when a declaration lies in an owned file: a production TypeScript file of the project that is not generated. Identity is `<name>.<member>` (`#n` for repeats), so no line number or file moves it.
  - Test-only exports: `dead-code` runs knip a second time with the config of `test-only/production-config.mjs`: the normal config with test, `__tests__` and story globs negated in `project`, test entries dropped and the test-runner plugins turned off, so scripts and plugin configs stay entries (knip's `--production` would drop them). The second run's `exports`, `types` and `files` that the normal run does not list are `test-only-export` (`files` under `test-support/` excepted).
  - Re-exports: knip counts a re-export from an entry as a use. `test-only/reexported-exports.mjs` reads the re-exports of the entry files (knip's `entry` globs, `layout.entryPoints` and the files the manifests name, found with the same skip rules as the walk of the whole project: no dot, excluded or linked directory, no declaration file) from the syntax (`syntax/module-facts.mjs`, specifiers resolved with `modules/module-resolution.mjs`; `test-only/reexport-graph.mjs` follows named, renamed, `export *` and `export * as` re-exports, imports that are only exported again and `export const y = x` aliases of an import that the file does not read, together with the further aliases of it (`export default y`, `export { y as z }`, `export const w = y`), through any number of files, to the declarations; a namespace that production reads as a whole value uses every member, and one read as `ns.member` only that member). Only when a test reads such a declaration does it run knip a third time, the second config with `includeEntryExports`. A declaration is `test-only-export` when that run lists it as unused (or, for an import that is only exported again, which hides it from knip, when no production file, script or tool config references it), when the entry's own export is listed too (knip leaves out what a framework plugin consumes, such as a Next route, and never lists the name of an `export * as`, which therefore counts as unconsumed), when it is in the same package as the entry and inside the project, and when it is not on the public surface of a published package or of a `layout.entryPoints` file. A declaration that nothing imports, tests included, is not reported. A finding that knip does not list has the line of its declaration. Limits: code that reads an import without being reachable (an unused local alias, a function nobody calls) still counts as a use, as it does for knip; an entry that spreads a namespace (`{ ...feat }`, `export default feat`) uses it, and a host that loads an entry without importing it has to be listed in `layout.entryPoints`.
  - Published packages: a package counts as published when its `package.json` has a name, is not `"private": true` and has one of `main`, `exports`, `bin`, `files` or `publishConfig`; `workspace/packages.mjs` finds workspace members from `workspaces` or the `packages:` key of `pnpm-workspace.yaml` (with `!` negations), looking for the workspace root no higher than the repository root.
  - Failures: both runners (`runners/unused-api.mjs`) turn a failure into a tool-error finding, so the analyzer's other findings still report.

- **Coverage run output.** The coverage run uses the `dot` reporter and the `json` reporter (`--outputFile.json=<file>`): the JSON file has no unhandled errors, and a timeout appears in it only as `Error: STACK_TRACE_ERROR`, so the runner reads the `Unhandled Rejection` / `Uncaught Exception` / `Unhandled Error` sections of stderr (header lines of `⎯`, the originating file in `This error originated in "<file>" test file`) and takes the timeout duration from the assertion.
- **Test runners.** `preset/test-runner/` picks the runner (`detect-runner.mjs`) and parses its command from the test script (`script-command.mjs`); `adapters/test-runners/` runs it and turns its output into one report shape, the Jest/Vitest JSON (`numTotalTests`, `testResults[].assertionResults[]`), which `quality-areas/reporting/test-report.mjs` reads for every runner. Long options are matched without dashes and case (`--outputFile` is `--output-file`); short ones exactly, because Mocha's `-R` (reporter) and `-r` (require) differ only in case. The coverage and mutation analyzer versions name the runner and its version, so switching runners changes the cache key. `node:test` and Mocha coverage: `NODE_V8_COVERAGE` plus `v8-coverage/loaded-sources.cjs`, preloaded with `--require` and passed on through `NODE_OPTIONS` (Mocha starts a child process for Node options, which inherits the environment but not the parent's arguments). `--import` would make Node load the main entry through the ESM loader and skip `require.extensions` hooks such as `ts-node/register`. The preload keeps an inspector session and records the source V8 compiled for each project script when it is parsed, skipping copies equal to the file; the `node --test` parent has no inspector, so there it only sets `NODE_OPTIONS`. Hook-based capture was tried first: a `module.register` load hook sees the code only when it is registered after the loader, and `module.registerHooks` crashed Node 22 on CommonJS loaded from ESM. `executed-script.mjs` picks the recorded copy whose length matches V8's script range and maps it back through its source map; for files no loader rewrote that type stripping rejects (enums, namespaces, parameter properties), it uses Node's transform mode with a source map. It drops a BOM and skips scripts with a URL query (module mocks). `mapped-nodes.mjs` drops AST nodes with no mapped segment in them (an `if` up to the end of its test, a function up to its body), the `__name(...)` and `obj.x = x` statements loaders add, and an enum function's fallback branch; these are loader helpers that the lookup would otherwise pin to line 1 or past the end. `merge-coverage.mjs` merges child processes and workers by type, line and order on the line, because columns differ by loader. With that, tsx, ts-node and Node's type stripping give the same functions and branches per line; a `ts-node` target below ES2022 is raised through `TS_NODE_COMPILER_OPTIONS`, keeping `useDefineForClassFields`. Mocha adds the `spec` of `.mocharc` and `package.json` to the files on its command line and only drops repeated strings, so a test file nitpicker passes that a `spec` glob also matches is collected twice; a serial run requires it once, but `--parallel` hands each copy to a worker, and two workers load and run it twice. The Mocha adapter therefore always passes `mocha/mocha-files.config.mjs` with `--require`, a root hook plugin with no hooks that wraps `Mocha.prototype.run` to keep each file once in first-seen order (the console capture resolves Mocha with its `loadMochaClass`). Jest's `--runTestsByPath` reads the script's own arguments as paths too and keeps repeats, so a rerun leaves out a file the script already names. Vitest gets no files outside a rerun, where they only filter its `include`, and `node:test` resolves the script's patterns itself and passes one set of paths, so neither runs a file twice.
- **Slow tests (TypeScript).** `adapters/slow-tests/slow-tests.mjs` reads the `duration` (ms) of each `assertionResults[]` entry of the report `runCoverage` already has, so every runner is covered by the one report shape and `slow-test` is reported by the `coverage` analyzer (`tool` must be the analyzer name). `test-calls.mjs` parses the test file with the TypeScript compiler and turns each `it`/`test`/`specify` call into a key (the `describe`, `suite` and `context` titles plus its own, joined by spaces, as a regular expression where `.each` placeholders and non-literal title parts are `.*`) and the call text with whitespace collapsed; a reported full name is matched against those keys, preferring keys with no dynamic title. The head policy's `thresholds` and `exceptions` are read with `readHeadPolicy()`, so they are already part of the cache key. `exclude` is `layout.isExcluded`. Only `passed` assertions count (`report-runs.mjs`). The findings carry `tool: 'test-runtime'`, which the analyzer lists in `reportedTools` (`quality-areas/analyzer.mjs`, `preset/checks/test-execution.mjs`) so `process.mjs` accepts it. A run over the smaller budget is timed again by `rerun-timings.mjs`: `runProjectTests` gets `options.rerun = { files, namePattern }`, and each runner adapter then runs just those files, selected by an anchored name pattern (Vitest and Jest `--testNamePattern`, `node --test-name-pattern`, Mocha `--grep`), with one worker and `uncoveredRun` (no coverage instrumentation, no coverage output). `runCoverage` awaits `readSlowTestFindings`, so the rerun happens inside the coverage analyzer. Changes to the seam files: `test-run.mjs` gains `testTimeoutMs()` (the 10 s `TEST_TIMEOUT_MS` plus the larger slow-test budget, used by the four adapters instead of `TEST_TIMEOUT_MS`), `workerCount()` and `uncoveredRun()`; `vitest.mjs`, `jest.mjs`, `node-test.mjs` and `mocha.mjs` use them and honor `options.rerun`; `quality-areas/runners/tests.mjs` awaits the findings. Integration tests are decided in `integration-tests.mjs` from the layout's test roots, as for Java: a folder name counts only below a test root.

- **Security sink rules.** `eslint-plugin/rules/security/` holds one folder per rule (`sql/no-sql-string-building`, `hash/no-weak-hash`, `tls/no-disabled-tls-verification`, `http/require-http-timeout`, `deserialization/no-unsafe-deserialization`), set by `securityRules` in `eslint-config/policy/security-facts.mjs` (called from `productionGuardRules`) and listed in `strict-rules.mjs`. A later block of `productionPolicyConfigFor` turns the five off in test support files: the reuse rules' non-production folders (`structure/reuse/reuse-paths.mjs`: `__mocks__`, `__fixtures__`, `fixtures`, `stories`) and story globs, plus `test-support`, `.storybook`, `mocks` and `setupTests`-style files; the other production guard rules keep their scope. `securityFactsFor` reads project facts once per ESLint run from the analyzed root (like `routeHandlers`): a browser framework in `package.json` (`react`, `preact`, `vue`, `svelte`, `solid-js`, `@angular/core`) turns the `fetch` check off, the first tagged-template SQL library (`@prisma/client`, `drizzle-orm`, `kysely`, `postgres`, `slonik`, `@databases/pg`, `sql-template-strings`) is named first in the SQL message, the installed js-yaml major (`node_modules/js-yaml/package.json`, else the declared range) turns on the js-yaml 3 `load` check, node-fetch below 3 (or unknown) lets `timeout` count, and `git grep --no-index --exclude-standard` over the project (skipping `node_modules`) finds production files that set `<axios import>.defaults.timeout` to a non-zero value or call undici `setGlobalDispatcher` with a `headersTimeout`/`bodyTimeout`/`connectTimeout`; those pass `projectDefaults: ['axios' | 'fetch']`, which covers the axios default instance and global or undici `fetch` in every module. The rules otherwise read one file at a time, so a helper in another module is caught where its text is built or where its option is written, not where it is called. Shared value resolution is `security-values.mjs`: a `const` chain, a conditional or `??` fallback, a parameter default, a `CONFIG.key` lookup (also through `Object.freeze`), `CONST[key]` with a non-constant key (every value of a `const` object or array), a `for (const x of CONST_LIST)` binding, `toLowerCase()`, and through `member-values.mjs` an `enum` member, a `readonly` class field or `static readonly` field (fixed) and a mutable field or parameter-property default (one possible value). `imported-names.mjs` binds modules: `import`, `require`, `require(x).default`, `import { default as x }`, `import x = require(x)`, `await import(x)`, a namespace alias (`const sandbox = vm`) and aliases of an imported function (`const make = crypto.createHash.bind(crypto)`, `const { createHash: make } = crypto`). In `no-sql-string-building`, `sql-inert.mjs` classifies each interpolated value (constant text, a number shape, an index parameter of an array callback, `+` of inert parts, a template of inert parts, `join` of an inert array and text builders such as `repeat` and `slice`), `sql-arrays.mjs` decides when an array holds only inert text (a literal, `map` or `Array.from` with an inert callback, `fill`, or a local array whose every `push`, `unshift`, `splice` and element write adds inert text; with types a `number[]`), and `sql-sinks.mjs` names the consumer (query call, raw builder method, TypeORM clause on a `createQueryBuilder()` chain, a receiver named like `qb` or typed `*QueryBuilder`); `sql-composition.mjs` applies the SQL-context test per sink. With type information (`parserOptions.project`), `no-sql-string-building` also accepts a `number`, `boolean` or union of plain string literals in an interpolation, and `require-http-timeout` tells a URL argument from an options argument, a `Request` from a URL and a callback from options; without it both fall back to the syntactic reading (a callback is a function, a name like `resolve`, `cb` or `onResponse`, or an identifier after an options object). The rules do not read other modules, so a project helper that wraps `fetch` or `createHash` is judged where it calls them.
- **Renamed-identifier clones.** No preset runs PMD CPD (the Maven build passes `-Dcpd.skip=true` and the Gradle init script has no CPD task), and CPD could not cover the other languages anyway: PMD 7.7.0, 7.16.0 and 7.28.0 accept `--ignore-identifiers --ignore-literals` for `typescript` and `ecmascript` and neither lexer applies them (`TypeScriptCpdLexer` is ANTLR, `EcmascriptCpdLexer` a Rhino token stream, both emit every token image as written), and the `pmd-kotlin` (`KotlinCpdLexer`, ANTLR, whose filter only skips `package`, `import` and new lines) and `pmd-python` (`PythonCpdLexer`, JavaCC) lexers do not read the flags at all. A TypeScript or Python project also has no JVM or build tool to resolve PMD and its jars. So TypeScript, JavaScript, Python, Kotlin and Java (on Gradle and Maven: `runJavaDuplicates` passes the `.java` files by default, `runKotlinDuplicates` the `.kt` and `.kts` files, and `readJavaFindings` passes the project or Maven module root so the renamed report is read) run jscpd a second time over a normalized copy, all through `shared/renamed-clones/`. `withNormalizedTree` writes the listed source files to a `renamed-*` directory under the caller's report folder (the report root for Java, Kotlin and Python, `reports/quality/duplicates` for TypeScript), registered through the `temporaryPaths` the caller passes (`trackTemporaryPath` and `untrackTemporaryPath` from `core/tooling/temporary-files.mjs`, since the shared layer imports nothing outside it) so an interrupted run removes it too, under the same project-relative paths (generated files, by `@generated`, `DO NOT EDIT` and the generator headers of `generator-marker.mjs`, are left out) with every name, string, number and comment rewritten to a fixed token and every line break kept, so jscpd's line numbers are the original ones. `normalize/typescript.mjs` uses the TypeScript compiler's syntax tree (the project's own `typescript` peer, passed in, since `shared/` imports no tool package): imports and re-exports, `interface`, `type` and `enum` declarations, field declarations without logic and literal-only objects and arrays are blanked, and JSX markup (tags, attributes, text, and `{name}` or `{a.b}` expression holders) is blanked too, so two components that only share markup structure have no tokens in common while handlers, conditions and `.map` calls inside the markup stay. `normalize/scanned.mjs` does the same for Python, Kotlin and Java from a small scanner (`scanner.mjs`: comments, strings with templates, text blocks and raw forms, numbers, names): import and `package` lines, `__all__` and literal-only lists, dicts, tuples, `listOf` or `mapOf` calls, Java `List.of`, `Map.of`, `Arrays.asList` calls and `= { ... }` array initializers, and Kotlin `when (x) { ... }` bodies made only of data are blanked; a qualified name (`Status.NEW`, the counterpart of a TypeScript property access) and Kotlin's `->` count as data, as TypeScript counts names and property accesses. The run uses 100 tokens and 5 lines (`RENAMED_SETTINGS`), the Java CPD threshold; jscpd's 50-token run stays for exact copies. A renamed clone is reported as `duplicates/duplicate-clone` with an identity starting `renamed:` that hashes its token shape (so editing a name or literal in a legacy copy keeps it), the message of every `duplicate-clone` (so it names `exclude` as the way to lift it, and `clonePartnerPath` reads the pair from the identity without the prefix), and it keeps the descriptive `duplicate-clone-size` lines and tokens of the plain clone it replaces; a plain jscpd clone that covers the same two ranges is dropped (`withoutRenamedCopies`), as are clones that overlap their own copy, clones made only of declarations (`boilerplate.mjs`, matched on the original lines: fields, accessors, Python enum members `NAME = value`, Kotlin constructor parameters with a type whose default calls a function, Java fields, constructors and getters) and clones that only repeat one or two statements (`repetition.mjs`: the normalized fragment, spaces removed, holds a run of at least three copies of one unit of at most 120 characters and the rest of the fragment, with one unit kept, is under half of it), which is what DTO mappers, enum `when`/`switch` tables, argument lists and `if` ladders that differ only in names and literals look like once names are one token. TypeScript runs the second jscpd with its config in the copy, a relative `--config` path and `path: ['.']`, so names come out project-relative: with an absolute config path jscpd matches each ignore glob (`reports/**`) against any folder of the absolute path, which would drop every file of a copy that lives under `reports/`. The TypeScript `duplicates` check has a two-minute timeout for the two runs. Both runs pass their config by a name relative to the scanned folder and keep names relative (`absolute: false`; the plain run scans `.` with a `pattern` naming the layout roots), because jscpd matches its ignore globs against the names it reports: with absolute names a checkout under a folder called `build`, `dist`, `reports`, `target`, `generated` or `coverage` lost every file. TypeScript also drops a renamed clone between two test files that defines no named function, as for plain clones, and points two test files at a helper or a table-driven test.

## JavaScript preset (`languages/javascript/`)

The JavaScript preset reuses the TypeScript pipeline; `languages/javascript/preset/` holds only what differs.

- **Preset channel.** `resolveHeadPolicy` copies `preset` into the head policy file only for `javascript`, so the TypeScript policy and its cache key do not change. `readLayout` turns it into `layout.javascript` and the extension lists every runner reads from the layout: `extensions` (`ts`, `mts`, `cts`, `js`, `mjs`, `cjs`; no `jsx` or `tsx`, so a `.jsx` file is neither a source nor a test file), `entryExtensions` (the same, `js` first) and `formatExtensions` (the Prettier patterns). `presetAnalyzers` returns `javascriptAnalyzers()` (same checks, built from the JavaScript layout) and `applyLayout` rebuilds from `resolveLayoutFor(headPolicy)`. `javascript-preset.mjs` is hashed into every analyzer whose config it shapes.
- **Generated configs.** The `tsconfig.quality.json` and `tsconfig.stryker.json` rewrites add `allowJs` and `checkJs` (the first also `noEmit`); with a project `tsconfig.json`, or a `jsconfig.json` when there is none, they extend it. `knip.json` gains `.js/.mjs/.cjs` entries and config files, and `jscpd.json` the `javascript` format next to `typescript`, because jscpd's `typescript` format reads only `.ts` and `.mts`. Stryker's TypeScript checker reports a mutant that fails `checkJs` as a compile error, so JavaScript mutants are killed by types as TypeScript ones are.
- **ESLint dialect.** `eslint-dialect.mjs` rewrites each strict config entry whose rules change: the original entry is kept for `.ts`, `.mts` and `.cts` files and a copy with the dialect rules is added for `.js`, `.mjs` and `.cjs` files (the `files` patterns are intersected with the extension glob, so the entry's own scope is kept). The copy drops the type-syntax rules, `@typescript-eslint/no-require-imports` and the `no-restricted-syntax` selectors that name a `TS*` node, lets the property-assignment selector of `domain/` skip `module.exports` and `exports.x`, passes `jsdocTypes`, `jsdoc` or `commonJsExports` to the four rules that map to JSDoc or CommonJS, and `no-var`, `prefer-const`, `prefer-rest-params` and `prefer-spread` are added (typescript-eslint enables them for TypeScript files only). The mapped rules keep their severity and still accept an exception. The dialect is applied before exceptions.
- **JSDoc parser.** `jsdoc.mjs` accepts one grammar per allowed tag (type in balanced braces, then a name where the tag has one) and reports any other text as prose. A `@type` is a cast only when the comment is directly followed by `(`. `any`, `*`, `null` and the `?T`, `T?` and bare `?` forms are looked for outside string literals and object keys. `unknown` is reported in `@param`, `@property` and `@prop` anywhere, and in the other type tags only inside braces or the parameter list of a function type, which is where the TypeScript rule finds a property or parameter.
- **CRAP is computed here.** `crap/measure.mjs` (`measureCrap`) parses each source file with the TypeScript compiler (`functions/` finds every function-like node, its own complexity without nested functions, its display name and its source), reads the `coverage-final.json` the project's test run writes (`istanbul/`: statement and branch spans, `fnMap` entries, attribution of statements and branches to the innermost function by span) and applies `crap = ccn^2 * (1 - coverage)^3 + ccn` with coverage the lower of statement and branch coverage. `@barney-media/crap-typescript-core` and the module-load hook that widened its `.ts`/`.tsx` suffix list for JavaScript are gone. The identity (`function:<name>:occurrence:<n>:source:<hash>`, ratchet key `function:<name>:occurrence:<n>:crap`) is unchanged, so legacy CRAP findings stay baselined. `crap-equivalence.test.mjs` runs `measureCrap` on a corpus (`crap/fixtures/corpus`: TypeScript constructs, CommonJS, ESM and plain JavaScript, with a coverage file) and compares the whole result to goldens (`expected-ts.json`, `expected-js.json`) that were produced by the library; a differential run against it on thousands of functions gave no difference. Two deliberate differences: `.mts` and `.cts` files are measured (the library skipped them through its `.ts` suffix check), and a coverage entry is matched to a file by its resolved, lower-cased path, without the library's module-root fallback and without grouping the files by their nearest `package.json` (the order of functions within a file, and of files, is the library's for a project with one manifest). Absent values are `undefined`, so the report JSON leaves out the keys the library wrote as `null`; nothing reads them (`normalizeCrap` reads `percent` and `crap` as numbers), and `crap-equivalence.test.mjs` compares the golden with its nulls removed. JavaScript is parsed as TypeScript, which is why `.jsx` is not supported.
- **Constants in `quality-areas-runner.mjs`.** The module-level `invokedPath` block runs the runner on import, so the constants it uses are declared above it. Declared below, they were still in their temporal dead zone when a failing test reached the failure formatter, which crashed the coverage check instead of reporting `tests-failed`.

### Java report directory

`gradle -I languages/java/gradle/nitpicker.init.gradle -Pnitpicker.reportDir=<dir> nitpickerJava`. `collectJavaFindings` makes `<dir>` a fresh temporary directory outside the project and removes it afterwards, so a build script that writes to `build/nitpicker` changes nothing nitpicker reads. - **Structure metrics.** `StructureMetrics.java` runs as `java StructureMetrics.java <structure.json> <classes.json> <analysisRoot> <sourceRoot>...` in the JDK's single-file source mode (task `nitpickerStructure`, no dependency beyond the JDK that runs Gradle). Fields: `lines` (last line - first line + 1, annotations and modifiers included, Javadoc not), `statements` (every statement below the body except blocks), `maxControlNesting` (deepest nesting of `if`, `for`, enhanced `for`, `while`, `do`, `switch` and `catch`; an `else if` stays on the level of the `if` it continues), `parameters`, `complexity` (1 + `if`, `for`, enhanced `for`, `while`, `do`, `catch`, `?:`, `&&`, `||` and each non-default `case`, an arrow case or a case with several constants once; a switch expression or pattern switch whose arrow cases each hold one expression or a `throw` counts once plus once per `when` guard, never more than its cases), `signature` (`Owner.method(parameter types)`, the CRAP identity; the unit name for an initializer or a lambda), `parameterTypes` (without generics or package, arrays and varargs as `Name[]`, a type variable of the method or an enclosing class as its first bound, `Object` without one), `privateEmptyConstructor`, `initializer` and `lambda`. A syntax error prints `file:line` and the compiler message and exits with status 1, so the task fails instead of dropping methods.
- **Fake Gradle for tests.** `adapters/fixtures/fake-gradle.mjs` stands in for Gradle in tests that run without Java (`NITPICKER_GRADLE`). In the project directory: `GRADLE_FAIL` fails the run with its text; `NO_REPORTS` writes an empty `modules.json`; each line of `violations.txt` is a PMD violation in `src/main/java/demo/A.java`; `jacoco.xml` and `mutations.xml` become those reports; `modules.txt` lists more projects, one directory per line, each with the same reports under its folder and key `module-<directory>`; a project folder's `jdeps.txt` and `jdeps-classes.txt` are copied into its reports. With `-Pnitpicker.kotlin=true`, `detekt.txt` (`rule :: message` or a message for `detekt.style.MagicNumber`), `ktlint.txt` (`rule|message`), `kotlin-format.txt` and `kotlin-metrics.json` feed the Kotlin reports. Reports go to `-Pnitpicker.reportDir`; the arguments are kept in `build/gradle-args.json`. Tests call it in process: `runGradle` (`adapters/gradle-wrapper/gradle-process.mjs`) takes the function that starts its supervisor as a `spawn` option (`spawnSync` by default), and `spawnFakeGradle` in `adapters/test-support/in-process-gradle.mjs` answers the supervisor call for the fake's path with `runFakeGradle` (`adapters/test-support/fake-gradle/`; the fixture is the program around it).
- **Fake Maven for tests.** `core/command/java/test-support/` holds `fake-maven.mjs` and `fake-jdk.mjs`, two pure functions, `runFakeMaven({ args, cwd })` and `runFakeJdk({ tool, args, cwd })`, which `spawnFakeMaven` in `in-process-maven.mjs` answers in process. The Maven preset takes an injected `spawn` (`runMavenPreset`, `runMaven`, `runJava`, `writeJdepsReports` and the direct `jar` and `java -version` calls; `spawnSync` by default), `runTasksWithFakeMaven` in `java-cli-harness.mjs` passes the fake, `NITPICKER_MAVEN` is the path of `fake-maven.mjs`, a program name of `java`, `jdeps` or `jar` is the fake JDK wherever it is found (a non-fake command goes to the real `spawnSync`), and `useMavenFixtures` points `XDG_CACHE_HOME` at an empty directory, so no process starts and the real Maven preset (effective POM, build, tool resolution, every tool outside Maven) runs without Java tools or network. The fake Maven copies `pom.xml` as the effective POM, writes one `classpath.txt` per tool of the tools project, and for the build creates `target/classes` and `target/test-classes` (with a class per source file when `MAIN_CLASSES` exists) and the dependency list, copies `test-results/test/*.xml` to `target/surefire-reports/` with a JaCoCo execution file; `MAVEN_FAIL` makes the build fail with `[ERROR] <its text>`. The fake JDK writes the reports the Gradle fake writes (`violations.txt` as PMD violations, `jacoco.xml`, `mutations.xml`, `jdeps/jdeps.txt` and `jdeps/jdeps-test.txt` as the `jdeps` output, empty SpotBugs, Checkstyle, structure and Error Prone reports). `java-cli.test.mjs` and `java-cli-legacy-inventory.test.mjs` run every case against both fakes.
- **Project settings the init script overrides.** After evaluation it resets the JaCoCo filters of every `Test` task (`jacoco` includes, excludes and class-loader excludes; `jacocoTestReport.classDirectories` back to the main output) and replaces the Checkstyle config of every Checkstyle task. `pitest-junit5-plugin` and a launcher are on PIT's classpath only when the test runtime has `junit-platform-engine`, `pitest-testng-plugin` only when it has a `testng` jar. `nitpickerArchunit` takes JUnit 4 for a declared `archunit-junit4`, the JUnit Platform for `archunit-junit5`, and the framework of the project's `test` task with both or neither; it fails when ArchUnit classes exist and none produced a report. PMD's `TestClassWithoutTestCases` runs from a generated `pmd-tests.xml` that excludes the main source directories, as the main-only rules (`pmd-main-ruleset.xml`, and the Spring rules) run from `pmd-main.xml` that excludes the test ones.
- **Gradle failure text.** `condenseFailure` (`adapters/gradle-wrapper/diagnostics/failure-text.mjs`) drops the JVM's `Picked up JAVA_TOOL_OPTIONS` notices, PIT's `INFO` progress lines, `[ant:checkstyle]` warnings and `SLF4J(W):` no-provider warnings (the Checkstyle tasks also run with `showViolations = false`). When the text is still too long it keeps Gradle's failure block (from `FAILURE:` or `* What went wrong:`, without the `* Try:` hints) whole, every distinct `Caused by:` line before it, and as much of the start as fits, cutting the middle; without a failure block it keeps the start and the end.

### Ingesters

Ingesters turn tool reports into findings:

- **Maven builds.** `detectJavaBuild` (`languages/java/builds/java-build.mjs`) picks the build; `languages/java/maven/` writes the same reports per module in `<module>/target/nitpicker` and `readModuleFindings` (`builds/java-modules.mjs`) prefixes each module's findings. The tool versions on both sides come from the init script's `def pinned = [...]` map, parsed by `readPinnedTools` with a regex, so keep that map one `name: 'version'` pair per entry. The build runs `test`, or `verify` when the effective POM of any module binds maven-failsafe-plugin's `integration-test` goal in an execution that the project does not keep off (`skipITs`/`skipTests` properties, `skip`/`skipITs`/`skipTests` configuration, phase `none`): `runsFailsafe` from `describeModule`, arguments from `lifecycleArgs` in `maven-project.mjs`, which adds `-Djacoco.haltOnFailure=false` and the skip properties of signing, publishing, network and release-check plugins (listed in java-preset.md). Failing Failsafe tests are tool errors like failing Surefire tests, and their reports are copied to `test-results/failsafe/`. Surefire and Failsafe reports and coverage files count as fresh when modified at most 2 s before the build started (file systems with coarse timestamps); our JaCoCo file is `target/nitpicker-jacoco.exec`, which the Failsafe JVM appends to through the same `argLine`, and every fresh file among it and the `destFile`s of the project's `prepare-agent` and `prepare-agent-integration` executions goes to one JaCoCo report. Maven runs at most 15 minutes; a timeout is a `java/maven-failure` that names the limit. The resolved tool classpaths are cached per user in `$XDG_CACHE_HOME/nitpicker` (else `~/.cache/nitpicker`), keyed by a hash of the tool coordinates; base and head run one after the other, so they never resolve at the same time.
- **XML text.** `parseXml` sets `text` on a leaf element (entities decoded, comments dropped, CDATA kept verbatim); an empty leaf has no `text`.

- **Common.** Repeats of one identity within a report get `#n` in report order. The XML parser reads elements and attributes only and throws `TypeError` when malformed.
- **SARIF** (PMD, SpotBugs). Identity is `partialFingerprints` (sorted) when present, else a hash of rule, path and symbol. Absolute `file://` URIs (PMD) and source-root-relative paths (SpotBugs) are made project-relative; results outside the project are skipped. SpotBugs `note`-level results are promoted because the tool already runs at the configured threshold, and its subject comes from message arguments since the text is generic.
- **Checkstyle.** Identity hashes the check `source`, path and message; the line is location only.
- **ArchUnit.** One finding per violated rule and offending class, identified by the fully qualified class; line numbers and violation counts never take part. The path is resolved by `options.resolvePath(className, fileName)`, falling back to the declaring test class. A failed case without violation lines yields one `test-failure`.
- **Spring architecture rules.** `languages/java/gradle/archunit/` holds `ArchRules.java` and helpers (in the default package, in subfolders too: every `.java` file under it is compiled, sorted by path), compiled by the `nitpickerSpringArch` task with `javac` from the JDK that runs Gradle against the pinned ArchUnit jar into `<Gradle user home>/caches/nitpicker/spring-arch/<sha256 of the rule sources, the ArchUnit version and the JDK vendor and version>` (compiled into a uniquely named sibling, then moved there atomically; a concurrent run that loses the race drops its copy), then run as `java @run.args [-Dnitpicker.spring.roles=<file>] ArchRules <output.json> <main-class-dirs> <unit-test-class-dirs> [<other-test-class-dirs>]` (class directories joined by the path separator; the unit ones are the `test` source set's, the other ones every other test source set's, and Maven passes its one test output directory as the unit one and no other; the argument file carries the classpath: ArchUnit, the compiled rules, both compile classpaths and the class directories) in `build/nitpicker/spring-arch/`. The task runs only when `runsArchRules()`: `usesSpring()`, a `jmolecules-ddd-*.jar` on the main compile classpath, or `-Pnitpicker.featureFolders=true`, which the Gradle stages pass when the head checkout has a `.java` or `.kt` file of a main source set (`src/main/java`, `src/main/kotlin`) directly in a feature folder (`featureFolders` head fact from `languages/java/adapters/facts/head-facts.mjs`, in `HEAD_CHECKOUT_FACTS` so the base runs the same rules; Maven: `runsArchRules` in `languages/java/maven/spring/arch-rules-gate.mjs`, the same jar test, or the policy's `featureFolders`). Output `spring-arch.json`: `{ "root": "<root package or null>", "violations": [{ "rule", "className", "fileName", "detail" }] }`, sorted and deduplicated by rule, class and detail. `className` is the outermost class's binary name, `fileName` its compiled-from source file (empty when unknown), `detail` the dependency's class name, `<method>:<entity>` for `spring-controller-entity`, `<scope>:<injected type>` for `spring-scope-capture` on a component and `<method>:<scope>:<injected type>` on a `@Bean` method (the scope is the alphabetically first of the matching beans), `<aggregate root>:<entity>` for `ddd-foreign-entity`, the layer package for `spring-layout`, `<face>|<kind>|<method>:<type>` for `contract-infrastructure-type` (face `service`, `controller`, `feature` or `package`, kind `persistence` or `transport`, method `Nested.method` for a nested class, type its binary name), or empty. A `package` entry is a public class outside the classes directly in a feature package of the Spring root (or any class when there is no Spring root); `spring-arch/contract-types.mjs` keeps it only when its source file, made project-relative with the module path, is on a feature's public face (`featureFaceMatcher(layout)`), and the `spring-*` entries are read only when the manifest says `spring: true`. The reader drops a `spring-feature-boundary` entry when a layering rule (`spring-controller-repository`, `spring-controller-controller`, `spring-repository-service`, `spring-service-web`) has the same class and detail and no exception lifts that layering finding (`isExcepted`, which `java-reports.mjs` builds from the config's exceptions with the module path), so an excepted layering finding never hides the boundary finding. The roles file (`nitpicker.spring.roles`, written from the config's `spring.roles` by `spring-arch/spring-roles.mjs` into the analysis directory and passed as `-Pnitpicker.spring.roles=<file>` on Gradle or straight to the JVM on Maven) has one `<role>=<binary name>` line per mapping; `Roles.java` gives a class a role when it is meta-annotated with, or (being another type) assignable to, a mapped name, on top of the stereotypes. `spring-arch/spring-arch.mjs` (`readSpringArchFindings`) turns each entry into an enforceable `archunit` finding: symbol the simple class name, identity that name (empty detail) or `<name>|<short detail>`, where the short detail drops the package of each `:`-separated part (`all:Customer`, `pricing:request:Basket`, `HttpServletRequest`) so a package move matched as a rename keeps the identity, with `#n` for repeats counted per resolved file, path from `resolvePath(className, fileName)` (an unresolvable class is skipped, an unknown rule or a missing file throws), message from a per-rule template that leads with the allowed form plus `exceptionHint` (`shared/rules/exceptions.mjs`). `ArchRules` runs the layout, layering, lifetime and test rules only when `org.springframework.context.ApplicationContext` loads from its classpath (the project's compile classpaths), so a jMolecules-only module gets the aggregate rules alone; it runs `contract-infrastructure-type` (`contracts/Contracts.java`) in every case. `ddd/DddModel.java` builds the membership (roots, typed entities with their owner from the generic binding, `@Entity` classes owned by the roots that reach them, value objects; abstract classes and interfaces included) and `ddd/HeldTypes.java` walks a class's own fields and those of superclasses that are not members themselves, resolving type variables through the subclass's bindings; roots compare by assignability, so a subtype or an interface root counts as the same aggregate. `ArchRules` reports every context-starting class of the unit test directories under `spring-test-placement`, and the reader drops those that `isIntegrationTest` (`adapters/test-times/integration-tests.mjs`, also used by the slow-test budget) accepts by name or package, so the two checks share one definition of an integration test. The init script writes `springArch: true` to `manifest.json` whenever the task runs (`runsArchRules()`), and `java-reports.mjs` reads the report only when the manifest says so; the Maven build writes `springArch: <spring, jmolecules-ddd or featureFolders>` per module too (`springFacts`, `withDeclaredSpring` and `withFeatureFolders` in `spring/arch-rules-gate.mjs`, which also resolve ArchUnit for a build whose `pom.xml` declares Spring or whose policy says `featureFolders`; `runSpringArch` takes the result as `archRules`), and `languages/java/maven/spring/maven-spring-arch.mjs` compiles the same rule sources with the JDK's `javac` against the ArchUnit jar (resolved with the other Maven tools only when some module runs the rules) into `$XDG_CACHE_HOME/nitpicker/spring-arch/<same hash>` (else `~/.cache/nitpicker/spring-arch/<hash>`, a separate cache from Gradle's), and runs `ArchRules` with `<module>/target/nitpicker/spring-arch.json` as output.
- **CRAP.** `crap = ccn^2 * (1 - coverage)^3 + ccn`, with coverage the lower of line ("statement") and branch coverage. `crap-score-limit` when over `options.limit`; `crap-coverage-unknown` when no JaCoCo method matches. Identity is the method signature (`Calc.classify(int, int, String)`, from `structure.json`) plus `#n`; for the `<init>`, `<clinit>` and `<lambda>` units `#n` counts only the entries of the same name and source over the limit (`repeatsInSource` in `shared/rules/finding-helpers.mjs`, also used by `structureFindings`). Java's complexity is `complexity` of `structure.json` (`StructureMetrics.java`), and a `privateEmptyConstructor` entry is left out (JaCoCo often omits those, and their complexity of 1 cannot exceed the limit). A JaCoCo method matches a function when file and name agree (`<init>` is the class name) and its first line lies in the function's range, or, for a constructor, when the descriptor's parameter types match `parameterTypes` (aligned at the end, so synthetic leading parameters of inner classes and enums are skipped; `StructureMetrics.java` writes a type variable as the erasure of its first bound, as the descriptor has it). The JaCoCo `<init>` of a class with field initializers starts at the first initializer, before the constructor. A function at 100% coverage gets `crapScoreLimitCovered`, Java's unknown coverage `crapCoverageUnknownJava`. `options.sourceRoots` maps the project-relative paths to JaCoCo's package-relative ones. `ingestCrapFunctions` is the same ingester over already parsed functions; its `selectMethods` option replaces the name-and-range match (the Kotlin preset passes `selectKotlinMethods`).
- **Format check.** One `format` finding per file in the list; identity is the constant `format`. `javaStyle()` turns the `java.formatter` and `java.indentation` conventions into `google`, `aosp`, `palantir` or `none`: the Gradle and Maven runs add `--aosp` to google-java-format for `aosp`, run palantir-java-format (`com.palantir.javaformat.java.Main --palantir`, pinned as `palantirJavaFormat`, a `format-palantir` classpath in the Maven tool project) for `palantir`, and write an empty `format.txt` for `none` (the Maven tool project then resolves no formatter jar: `formatTool` in `maven-tools.mjs` adds `format` or `format-palantir` as an extra tool), and the finding's tool is `google-java-format` or `palantir-java-format`; its message gives the fix command and the `conventions.java.formatter` pin (`JAVA_FORMATTER_TOOLS` in `java-style.mjs`, also used by `layoutFix` in `rule-messages.mjs` for the `layout` Checkstyle findings, which say to fix by hand under `none`). The runner reads the convention from the head policy file (`NITPICKER_POLICY`) when it starts, so it is not in the analyzer's hash, and passes the style as `-Pnitpicker.java.style=aosp` to Gradle (plus `-Pnitpicker.java.indentation` under `none`) and as `javaStyle` to `runFormat` in `maven-lint.mjs`. Checkstyle's layout checks (`Indentation` among them) are suppressed for every formatter style by `checkstyle-suppressions.xml`, which the Maven run's `checkstyleSetup` passes too, so only the formatter reports layout. Under `none` both runs use `checkstyle-suppressions-unformatted.xml` instead, which keeps the whitespace, brace, tab and indentation checks, and add `UnusedImports` to the bundled config (`unformatted-checks.mjs` for Maven, the same edit in `nitpicker.init.gradle`; `Indentation` moves to the measured width, and tab-indented files drop it and `FileTabCharacter`), so unused imports, which Error Prone's off `RemoveUnusedImports` and the formatter no longer cover, are still findings.
- **Class limits.** `StructureMetrics.java` writes `classes.json` in the same parse as `structure.json`: `{ files: { <path>: { package, imports[] } }, classes: [{ file, name, start, kind, methods, fields, extends? }] }`. `name` is `Outer.Inner`, `kind` is `class`, `interface`, `enum`, `record` or `annotation`, `extends` the superclass as written without type arguments. `methods` are declared methods (constructors not), `fields` instance fields and record components. `inheritanceDepths` resolves `extends` by enclosing names, imports, the same package, wildcard imports and the name in full; a superclass it cannot find counts as one level. One finding per class and limit (`class-methods-limit`, `class-fields-limit`, `inheritance-depth-limit`), identity `<metric>:<name>:occurrence:<n>:<value>`, ratchet key the same without the value. `shared/project-rules/size-rules.mjs` holds the size rule ids, defaults, the Java line length and the message templates, and `shared/policy.mjs` merges them into its tables. `StructureMetrics.java` is run as `<structure.json> <classes.json> <analysisRoot> <sourceRoot>...` and writes both reports from one parse, by the Gradle `nitpickerStructure` task and by `runStructure` in `maven-build.mjs` for each Maven module. `readModuleFindings` in `java-reports.mjs` reads `classes.json` per module, for both presets (the Kotlin preset's `.java` files keep the class limits), with `modulePath` so an exception path and the one a message prints are project-relative in a multi-module Maven build. A missing `classes.json` throws, so the run reports a tool error naming the structure step instead of dropping the limits. The folder-depth root package is the common package prefix of the base snapshot's code (`policy.baselineRoot` on a head run, the snapshot itself on a base run), so a branch cannot move it.
- **Folder depth.** `folder-depth-limit` is one finding per folder and kind of file (`folder-depth:<kind>:<depth>`), `ratchet.pathIsFolder` with `ratchet.folderFiles` (the files in the folder, since `value` is the depth) so a moved folder is matched when more than half its files were renamed to one place. Java: levels below the root package, the longest package prefix the base snapshot's code shares (`module-info.java`, `package-info.java` and default-package files do not vote). TypeScript: folders below `features/<feature>/<layer>/` under a source or test root.
- **Coverage.** Go coverprofile gives a `statement-coverage` metric per file only (blocks lack function names, and line-based identity is not allowed); `options.modulePath` is stripped from import paths. JaCoCo gives `line-coverage` plus `uncovered-method` (class and method name+descriptor); `options.sourceRoot` is prepended. lcov gives `line-coverage` plus `uncovered-function`.
- **PIT.** Follows `docs/mutation-testing.md`: no score gate, new surviving or uncovered mutants fail, other non-killed statuses are report-only, counts go to `mutation-summary`. A mutant is identified by simple class name, method with its descriptor, mutator and description plus its occurrence `#n` among identical keys in the same source file (by line, then block index), so a same-named class in another package has its own count; package names are dropped from the class, the descriptor's `L...;` types and the description's `a/b/C` names, so a package move matched as a git rename keeps the identity. Mutants with unresolvable sources (generated code) are skipped.
- **Duplicates.** jscpd runs once per build, per existing main source root of the merged manifest, writing `duplicates.json` in the report directory as `{ runs: [{ root, report }] }`. Findings match the TypeScript ones: `duplicate-clone` and `duplicate-clone-size`, identified by file pair, cloned-text hash and occurrence.

## Kotlin preset (`languages/java/`)

The Kotlin preset is the Java preset with `kotlin: true`: same init script, runner and ingesters. User-facing behavior is in `docs/kotlin-preset.md`; the protocol details:

- **Switch.** `gradle -Pnitpicker.kotlin=true` turns the Kotlin tasks on in modules applying `org.jetbrains.kotlin.jvm`; without it the init script is the Java one. The runner takes `--preset kotlin`, `--kotlin-formatter` and `--kotlin-detekt-config` (from `kotlin.formatter` and `kotlin.detektConfig`). Gradle always runs with `--no-configuration-cache` (both presets): the init script registers tasks and reads project state at execution time, which a project's `org.gradle.configuration-cache=true` would fail on.
- **Properties.** `kotlin-tools.mjs` resolves, per snapshot, what the init script needs and passes it as `-Pnitpicker.kotlin.formatter=<ktlint|ktfmt|none>`, `.ktfmtStyle=<kotlinlang|google|meta>`, `.ktfmtEditorconfig=true` (ktfmt lists the project), `.styleFile=<path of a JSON file>` (written to a temporary folder by `kotlin-run.mjs` and removed after the run; `{ offset, editorconfigs: [{ path, text }], ktlintDefaults, detektConventions }`, generated by `kotlin-style-files.mjs` and `style/editorconfig-mirror.mjs`: the `.editorconfig` files under the policy root and above it up to the repository root, `offset` being the policy root inside the repository, so the init script mirrors the sources at `<offset>/<module>/...`), `.detektLayers=<conventions,project>` and `.detektConfig=<absolute path in the head checkout>`; the project style files are read from the policy root (the head checkout) for both snapshots. Without the formatter property the init script runs no format check. The analyzer is named `kotlin`, and its tool-error and `baseline-expansion` findings use that name.
- **Reports.** `detekt.sarif`, `ktlint.sarif` (ktlint's SARIF reporter, relative paths) and `ktfmt.txt` (project-relative Kotlin files, one per line); only the detected formatter's file is read. Skipped Java tools in a Kotlin-only module write empty reports so the Nitpicker side reads one layout. `manifest.json` in this mode: `sourceRoots` are the Java roots only, `kotlinSourceRoots` the Kotlin plugin's source directories (which include `src/main/java`), `kotlin: true`, `kotlinFormatter`. `readKotlinFindings` throws when `kotlin` is absent, so a project without the Kotlin plugin is a tool error and not an empty pass.
- **Java-only class tools.** `analyzedClassDirs` is the output of `compileJava` in this mode (all main class directories otherwise); SpotBugs reads it. SpotBugs gets the rest of the runtime classpath as `-auxclasspath`. PIT reads `mutatedClassDirs` (all main class directories, Java and Kotlin) in both presets, and jdeps reads every main class directory in both modes.
- **Function units.** Every preset measures the same units, so a limit means the same everywhere: a function, method or constructor with a body, a lambda, arrow function or anonymous function (TypeScript's callbacks, Java and Kotlin lambdas, Python `lambda`), and the code that runs at class initialization (Java static and instance initializer blocks, Kotlin `init` blocks and property initializers that branch). A unit's statements, control nesting and complexity never count towards the unit around it (TypeScript's analyzer stops at nested functions, and so do `StructureMetrics.java`, `kotlin-psi` and `structure_metrics.py`); `lines` is the physical span, so the lines of a nested unit still count towards the one around it, in every language. A lambda is named after the unit that holds it plus `<lambda>`, or after the variable or property it initializes; `repeatsInSource` makes `<init>`, `<clinit>` and `<lambda>` findings number only among the same name and source over the limit. Coverage: JaCoCo's `lambda$...` synthetic methods for Java, the method or the lines of the lambda for Kotlin, the line of the creating statement for Python (coverage.py has nothing finer). TypeScript's CRAP check (`@barney-media/crap-typescript-core`) scores named and assigned functions only and drops the complexity of an anonymous callback from the function around it, a limit of that library.
- **Kotlin metrics (KT3).** `languages/java/gradle/kotlin-psi/` is compiled with the `javac` of the JVM that runs Gradle (`kotlinPsiClasses` in the init script: once per build into `<root project build>/tmp/nitpickerKotlinPsi/<key>`, the key a hash of the program sources, the pinned compiler, its classpath and the Gradle JVM version, so a later build reuses it; a lock keeps modules that run in parallel to one compile, and a new key deletes the directories of keys this build did not use; a Gradle JVM without `javac` fails the task with a message to run on a JDK) and run by task `nitpickerKotlinPsi` as `java -cp <kotlin-compiler-embeddable and its dependencies>:<classes> nitpicker.kotlinpsi.KotlinPsi <metrics.json> <facts.json> <projectDir> <root>...` (a root prefixed `test:` is a test root; the metrics cover the other roots only). The program runs on a thread with a 512 MB stack, so deeply nested expressions are read; it parses each file once and feeds `metrics/` (the units below) and `facts/` (next entry) from the same tree. It writes `kotlin-metrics.json`: `functions` (one object per unit: `file`, `name`, `start`, `end`, `lines`, `statements`, `maxControlNesting`, `parameters`, `complexity`, `inline`, `initializer`, `lambda`), `files` (`file`, `package`, `classes`: the JVM names of its top-level classes and file facade; `imports`: the imported names, `.*` for a star import) and `types` (`metrics/Types.java`: one object per named class, interface, object and companion object, local and anonymous ones left out: `file`, `name` with its enclosing classes joined by `.`, `start`, `kind`, `methods` (member functions), `fields` (constructor `val`/`var` parameters and properties with a backing field), and `extends`, the written name of the supertype with a constructor call). `kotlin-class-limits.mjs` resolves `extends` in the project like the Java class limits (enclosing classes, single imports, same package, star imports, the name itself; an unresolved name ends the chain and counts one level) and hands the classes to the shared `classLimitFindings` (`shared/rules/size/class-limits.mjs`, as Java and Python do), so a `data class` gets the components message of a Java record, the findings of one file are ordered largest first for a stable ratchet, and an exception is matched on the module path. A syntax error exits the program with the file, line and pinned version (the sources compiled, so the compiler is too old). It builds a `KotlinCoreEnvironment` and needs an extension storage registered on the configuration (`FrontendConfigurationKeysKt.setExtensionsStorage`); that is compiler-internal API, so a bump of `kotlinCompiler` in the init script is tested with `npm run test:kotlin` (it includes `kotlin-metrics.e2e.test.mjs`, which pins the compiler on its own); Declarations gain `annotationEntries` (with the annotation `type`; secondary constructors too), `superClass`, `constructorAnnotations`, a parameter's `defaultValue`, a function's `expressionBody`, `returns` (the parameter or name an expression body is) and, for an expression body that is a call, `typeArgumentList`, a property's `initializer` callee, `literal` and `computed` (a getter with a body and no backing field). Every message starts with a verb that names the allowed form; `adapters/spring/test-support/allowed-form.mjs` lists those verbs and the Kotlin and Java ruleset tests check each message against it. - **Duplicates in every language.** `core/tooling/jscpd/` holds what the languages share: `run-jscpd.mjs` (`runJscpd`, `jscpdVersion`), `jscpd-clones.mjs` (report to neutral clones), `skipped-folders.mjs` (the per-language default lists and `duplicates.skippedFolders` replacing them; TypeScript and JavaScript also rewrite `jscpd.json` through `layoutJscpdConfig`) and `import-only.mjs`. jscpd reports whole lines, so the last line of a fragment is where the clone ends, often the line that starts the next declaration; `importsOnly(fragment, format)` treats the clone as imports only when every line is an `import`/`package` line (a leading partial name or the tail of a multi-line import are accepted; TypeScript and JavaScript also take `export ... from` re-exports; Python also takes `__all__` lists and needs at least one real import line, so a table of numbers or `import os; run()` is code). The last line is forgiven only when it starts a declaration (`class`, `def`, `fun`, `function`, `export`, an annotation or decorator, a comment and the like in that language); any other last line counts, so imports plus one real statement are reported. The duplicate scan of the base snapshot always uses the head's `duplicates` setting (`baseConfigCoveringHead` in `core/policy-changes/base-coverage.mjs`), so widening the scan never turns a legacy clone into a new one. The TypeScript `normalizeDuplicates`, the Java/Kotlin `readDuplicateFindings` and the Python one all drop such clones. - **Kotlin clones.** `runJavaDuplicates(projectRoot, { format: 'kotlin', rootsKey: 'kotlinSourceRoots', reportFile: 'kotlin-duplicates.json', renamedExtensions: ['.kt', '.kts'] })` after the Java run, writing `kotlin-duplicates.json` and, from the normalized copy of the `.kt` and `.kts` files, `renamed-kotlin-duplicates.json`; both are read with `readDuplicateFindings` (given the project root) and the same rule and tool name `duplicates`.
- **detekt and ktlint SARIF.** No fingerprints, so the glue sets `nitpicker/subject` from the message text with every whole number replaced by `#` (`\b\d+\b`: a name ending in digits keeps its digits), so a measured value does not change identity, and keeps the SARIF levels (`note` stays descriptive, unlike SpotBugs). Rule ids are kept in detekt's form `detekt.<ruleset>.<Rule>`.
- **Formatter detection** is a text search of the root project's build files (not Gradle API introspection), so it works for plugin ids, version catalogs and Spotless alike. Comments are removed first and a Spotless `kotlinGradle { }` block is cut out (its formatter formats the build scripts, not the Kotlin sources); a string literal that names the other tool still matches. `ktlint` in the build files beats `ktfmt`, and `ktlint_` keys in `.editorconfig` count only when the build files name neither.
- **Source directories** are the Kotlin plugin's main `srcDirs` that exist, are inside the project and are not under the build directory (generated code). `kotlinFiles` and `kotlinSourceRoots` stay main-only (structure, CRAP, duplicates and coverage read main code); detekt, ktlint and ktfmt read `kotlinLintedDirs` (main plus the `test` source set's directories, `kotlinTestSourceRoots` in the manifest), and the detekt classpath adds the test compile classpath and the `compileTestJava` output (the main classes are dropped from it, because `analyzedClassDirs` carries them). `readSuppressionFindings` reads the same roots, so an inline suppression is banned in tests too, except a compiler-warning token (`UNCHECKED_CAST`, `DEPRECATION`, ...), which is banned on `kotlinSourceRoots` only, because the kotlinc lint compiles main sources only. Detekt's default config excludes 15 rules from `**/test/**`; the owned rules in `nitpicker-detekt.yml` reset `excludes: []` and so stay on in tests, and `TooGenericExceptionCaught` is owned (ruleset `exceptions`, with the exception names spelled out so that the default does not need the test exclusion) so that the broad-catch ban applies to tests as it does to Java (#224). A legacy test finding is not new because the head's init script runs on both snapshots.
- **detekt config validation** is switched off by a second `--config` file (`languages/java/detekt/detekt-validation.yml`), listed after the project's and Nitpicker's, because the CLI exits with code 3 on rulesets of plugins it does not load.
- **Missing reports.** A build where no project applies the plugin writes an empty `modules.json`; `readReportModules` turns that into an error naming the plugin, and a listed project without reports into one naming the project (both presets).
- **Branch coverage** (`changed-branch-coverage`) reads the source text of every file under `jacocoSourceRoots` (Java roots plus `kotlinSourceRoots`). A `.kt` line is dropped when `isCompilerGeneratedBranchLine` (`kotlin-branches.mjs`) finds a suspension call and nothing that can branch in its code (string literals, comments and type arguments removed); every other line is kept, since the JaCoCo XML has branch counts per line and no instruction detail and a statement that spans lines is reported on the line of its operand. A kept line with a suspension call gets the `arms` hint in its message. Report files are located by `sourceLocator` (`kotlin-reports.mjs`): by directory first, then, for `.kt`, by file name and `package` declaration; the same lookup resolves PIT's `sourceFile`, and a `.kt` file with missed branches that is not found (outside `kotlin`/`kotlinx`) is a descriptive `branch-source-not-found`. - **Mutation.** `pitFindings` resolves a class's source file under `jacocoSourceRoots` and `reportOnlyKotlinMutants` turns `mutant-*` findings of `.kt` files into `descriptive` ones (the `mutation-summary` counts are unchanged). The Java preset does not call it.
- **One-way rules** (`kotlin-rules.mjs`, `nitpicker-detekt.yml`). `ONE_WAY_RULES` is the list of rules in the yml with the sentence the gate appends when detekt's text does not name the allowed form (`withAllowedForm`, after ingestion, so identity, which is the detekt text, never changes). `kotlin-messages.mjs` then ends every enforceable Kotlin finding (detekt, `kotlin-source`, `kotlinc`) with `exceptionHint` for the rule as the finding prints it (`kotlin-source/<Rule>` and `kotlinc/<rule>` carry the tool, detekt ids already name it), unless the message already names `nitpicker.config.json`; `validateKotlinOptions` accepts exactly the rules that function routes to. A rule with `mainOnly` in `ONE_WAY_RULES` keeps detekt's test globs in `excludes` (`StringLiteralDuplication`: repeated literals are the norm in test data). `ForbiddenMethodCall` and the other rules with a `reason` field carry the allowed form in the yml instead. The yml follows the project's config in the `--config` list of the detekt task (only the validation file comes after it), and detekt gives the later file priority per key, so a project's `detekt.yml` cannot override it. Every ruleset and rule in the yml pins `active: true`, `excludes: []` and `includes: []`, and every rule `severity: warning` (the reader classifies SARIF `note` as descriptive, so a project's `severity: info` would otherwise un-gate the rule); `excludes: []` also replaces the default that skips `**/test/**` for `UnsafeCallOnNullableType`, which would skip a production package named `test`. `kotlin-rules.test.mjs` reads the yml and fails when its rules differ from `ONE_WAY_RULES` or one lacks a pin. `UseDataClass` has `allowVars: true` because `DataClassShouldBeImmutable` bans the `var` that `UseDataClass` would otherwise ask to turn into a data class. `runBlocking` is a `ForbiddenMethodCall` entry (type resolution finds the call whatever the import), so it shares the rule id, and the exception, of `run`, `with` and `also`. `ignoreAnnotated: []` is pinned too, next to `excludes: []`, because detekt skips the code of classes carrying a listed annotation for any rule. The lists the yml sets (`MERGED_LISTS`: `ForbiddenMethodCall.methods`, `ForbiddenImport.imports`, `ForbiddenComment.comments`, `UseDataClass.excludeAnnotatedClasses`) are merged with the project's (detekt replaces a list): `adapters/kotlin/detekt/detekt-lists.mjs` reads the project's detekt file with the `yaml` package (a dependency, loaded lazily with `createRequire`, like `smol-toml`; the parser's alias limit and a parse failure both yield an empty list), keeps the entries that are a method name with an optional balanced parameter list (anything else could crash detekt), appends those the yml does not list and writes the result to `build/nitpicker/detekt-lists.yml`. `kotlin-tools.mjs` passes it as `-Pnitpicker.kotlin.detektLists=<absolute path>`, and the init script puts it in the `--config` list after the project's file and the yml (before the validation file); it carries only the list, so the yml still pins `active`, `severity`, `excludes`, `includes` and `ignoreAnnotated`. The file is written only when the project adds an entry, and holds only the lists it adds to. `ForbiddenComment.comments` values are regular expressions detekt matches with `containsMatchIn`; the preset's one flags a marker at the start of a comment line or before `:`/`(`, and `allowedPatterns` (one expression, not merged) skips a comment that names an issue (`#123`, `PROJ-123` but not `SHA-256`, or a link) right after the marker.
- **Type resolution classpath.** Detekt 1.23.8 embeds Kotlin 2.0.21 (it resolved a 2.1.0 standard library, not a 2.4.21 one). The stdlib it needs for `run`, `with`, `also` and `!!` is therefore `kotlin-stdlib:2.0.21` (`pinned.detektKotlin`, the version in the detekt jar's `META-INF/compiler.version`), first on the classpath, and every `kotlin-stdlib*` jar of the project is dropped. With the project's 2.4 stdlib the same run reported nothing for those calls and wrongly flagged `?.` on values of an unresolved type. `--jdk-home` is the installation path of the project's Gradle Java toolchain (`JavaPluginExtension.toolchain`, which `kotlin { jvmToolchain(n) }` also sets) when the project declares one, else the Gradle JVM's `java.home`; without it JDK types (`StringBuilder`) do not resolve. Bump `detektKotlin` together with `detekt`.
- **Exceptions.** `--exception <rule>:<glob>` (split at the first colon, one per path) reaches `applyFindingPolicy` (`shared/findings/finding-policy.mjs`), which drops findings whose rule, or `tool/rule`, is that id under the glob on both snapshots. `validateKotlinOptions` accepts any `detekt.<ruleset>.<Rule>`, `KOTLIN_LISTED_RULES` and the shared ones, so a typo is an error. Python can reuse the mechanism.
- **Inline suppression.** `kotlin-suppressions.mjs` reads the string literals inside `@Suppress`/`@SuppressWarnings` with any use-site target, after `kotlin-literals.mjs` has masked the source: one pass over comments (nested block comments), strings with `${}` templates, raw strings and character literals, which replaces each string by a numbered placeholder so that a comment opener in a string, or an annotation in a string, does not matter. `isBannedSuppression` bans every token that can target a detekt or ktlint rule: `all` in any letter case, anything starting with `detekt` or `ktlint` followed by `.`, `:` or the end, a detekt ruleset name, and a PascalCase token (every detekt rule id; detekt honors the bare id). The compiler warnings the kotlinc lint reports (`COMPILER_WARNINGS`: `DEPRECATION`, `TYPEALIAS_EXPANSION_DEPRECATION`, `UNCHECKED_CAST`, `USELESS_CAST`) are banned too, and their message routes to the `kotlinc/<rule>` exception; other compiler diagnostics are UPPER_SNAKE or lowercase (`UNUSED_PARAMETER`, `unused`) and stay allowed. detekt's `ForbiddenSuppress` cannot do this alone: a suppression of `style` or `all` also hides the `ForbiddenSuppress` finding on the same annotation.
- **Source checks** (`adapters/kotlin/scan/`). `kotlin-source.mjs` scans a file once into `code` (the same length as the source, comments and string bodies blanked, newlines kept, so offsets and lines stay), `literals` (start, body, `template` when it holds `$name` or `${...}`, `raw`) and `comments` (`line`, `block`, `doc`); nested block comments and templates with braces are followed. Each rule in `scan/rules/` takes the scanned file and returns `{ rule, offset, subject? }`; `kotlin-scan.mjs` turns them into findings (tool `kotlin-source`, identity `<rule>:<hash of subject or normalized line>` numbered per file) and runs the test-class rule on `kotlinTestSourceRoots` only. `log-calls.mjs` gives the log, catch and secret rules the log calls of `languages/java/source/loggers.mjs`, the one notion of a log call (receivers declared from a logger factory or named like a logger, every SLF4J, Log4j, JUL, kotlin-logging and Android level, the call's arguments and its lambda message), with offsets, plus `print`/`println` where a rule asks for the console. `loops.mjs` holds the loop bodies (`for`, `while`, `do` and the iterating lambdas), the retry test (`isRetry`, a `try` that leaves its loop with `return` or `break`, shared by `CatchOnlyLogsOrReturnsDefault` and `IoCallInLoop`) and the paging test of `IoCallInLoop`, Python's `io-in-loop` in Kotlin: a `while` or `do` whose condition, an `if (...) break`/`return` in it or a `?: break` reads a name assigned, over two passes, from an input or output call in the body. `catches.mjs` also exports `swallowedCatchBlocks`, the catches `CatchOnlyLogsOrReturnsDefault` reports; `readCatchLogFindings` passes them to `catchLogViolations` as `reportedElsewhere` for the files of `kotlinSourceRoots`, so a catch that only logs is reported once, as in Python. `framework-allowances.mjs` drops the detekt findings frameworks require (the environment read in a composition root, the spread into `runApplication` with `manifest.spring`), and the forbidden-API `ForbiddenMethodCall`/`ForbiddenImport` entries of the yml (every value but the scope functions, `runBlocking`, `print` and `println`) on `kotlinTestSourceRoots`, and so the one-way rules marked `mainOnly` (`StringLiteralDuplication`), by the test roots instead of a path glob, so a `test` package in main sources is still checked. Each rule also gets a context, `{ declarations }`: `security/sql-values.mjs` collects the enum names and the declared property types of every main file of the module before the rules run, and resolves a template or concatenation piece to inert or runtime from the file's own declarations and that context. `security/` holds the sinks (`sql.mjs`, `crypto.mjs`, `clients.mjs`); a reported entry may carry its own `message` (HMAC-MD5 under `WeakHash`). The patterns that match a bare name (`TlsVerificationOff`'s insecure types, `UnsafeDeserialization`'s `JsonTypeInfo.Id.CLASS`) skip an import line (`inImport` in `kotlin-source.mjs`); the others need a call. A one-line `const val` initializer ends at the brace or `;` that closes it, so `companion object { private const val table = "users" }` reads as a literal. `isConstantExpression` (a literal, a number, a CONSTANT_CASE name or a `const val` with a literal) is what `LogStringConcatenation` treats as a compile-time constant. The SQL text patterns (`STRONG_STATEMENT`, `LOOSE_STATEMENT`, `FRAGMENT_BEFORE_VALUE`) live in `shared/rules/security/sql-text.mjs`, shared with the TypeScript rule.
- **kotlinc lint** (`gradle/kotlin/kotlin-lint.gradle`, applied by the init script inside the Kotlin block after it sets `project.ext.nitpickerKotlinFiles` and `nitpickerKotlinJdkHome`). `nitpickerKotlinLint` runs `K2JVMCompiler` from the pinned `nitpickerKotlinCompiler` configuration with an argument file (every argument quoted), into the task's temporary directory, and writes `kotlinc.json`. The project's options come from `compileKotlin.compilerOptions` and its `pluginClasspath`/`pluginOptions`, each read in a `try`, so a Kotlin Gradle plugin without them still runs the lint, without them. `kotlin-compiler.mjs` keeps the `warning: [NAME]` lines whose name is in `COMPILER_WARNINGS` and whose file is under a Kotlin source root; a non-zero exit is one descriptive `kotlinc/lint-not-run`, since kotlinc reports no warnings once the compile has an error.
- **Fixture cases.** `test-support/kotlin-rule-cases.mjs` (next to the Kotlin rules) holds, per rule, the banned and the allowed source (`{name}` stands for the file's class name, `Banned` or `Allowed`), the detekt message recorded from the real run, and the wording the final message must contain. The CI test checks the wording against the recorded message; the end-to-end test checks the recorded message against real detekt, so a detekt or yml change that alters a message fails there.

## Python preset (`languages/python/`)

Two analyzers, `python` and `mutation` (which depends on `python`, so it runs after it and is skipped when it had a tool error, except a tool error of the tools in its `toleratedDependencyErrors`: `tests`, `dependencies`, `test-runtime`; the scheduler option is generic and validated like `reportedTools`). Each tool step lives in its own module (`python-test-runner.mjs`, `python-types.mjs`, `python-ast-rules.mjs`) and runs through `python-process.mjs`.

- **Environment.** That of the live checkout (`liveProjectRoot`) for the head, and for a snapshot whose dependency files equal the head's: lockfiles exist in both, but `.venv` does not exist in a work tree. `openSnapshotEnvironment` (`python-environment.mjs`, called by `createToolContext`) first asks `baseEnvironment` (`environments/base/base-environment.mjs`) for a snapshot of another root: `dependenciesDiffer` (`dependency-files.mjs`) compares `uv.lock`, `poetry.lock`, `pdm.lock`, `Pipfile`, `Pipfile.lock`, `requirements*.txt`, `constraints*.txt`, `requirements/*.txt` and the dependency tables of `pyproject.toml` (parsed with `smol-toml`; unparseable text is compared as it is), and on a difference the plan of `installers.mjs` runs in the snapshot through `execute` (`python-process.mjs`): `uv sync --frozen --no-install-project --no-install-workspace`, `poetry install --no-root --no-interaction`, `pdm sync --no-self` or `pipenv sync --dev` (each with its in-project virtualenv variable set, so the environment is `<snapshot>/.venv`), or `python3 -m venv` plus `pip install --prefer-binary -r` of a copy that `safeRequirements` (`requirements.mjs`) wrote to a temporary folder with editable, local and `file:` entries and includes outside the snapshot dropped. A `Pipfile.lock` with editable or path packages is refused, because `pipenv` has no flag to skip them. When the tool leaves no environment (a project without packages), `python3 -m venv` makes an empty one. The settings `path`, `hatch`, `conda`, a directory and an absolute path never rebuild. A missing tool raises `missingToolError` (`install-hints.mjs`, one install command per tool, also used by the head launchers). Head detection order: `python.environment`, `uv.lock`, `poetry.lock`, the `uv.lock` of an ancestor whose `pyproject.toml` has `[tool.uv.workspace]`, `Pipfile`/`Pipfile.lock` (`pipenv --venv`), `[tool.hatch.envs...]` or `hatch.toml` (`hatch env find`), `environment.yml`/`environment.yaml` (conda: its `prefix:`, else the environment `conda env list --json` lists under the file's `name:`), `.venv`, `PATH`; the code for the three managers is in `adapters/execution/environments/` (`managed.mjs` detects and asks the manager, `launchers.mjs` builds the conda launcher, `environment-error.mjs` holds the shared error), and a detected manager whose command is not installed falls through to the next row (a setting that names it errors). Nothing in that folder reads `process.env`, because the self-gate bans new environment reads outside a composition root: the conda launcher runs a tool by its path in the environment and sets `CONDA_PREFIX`, and the manager commands inherit the environment. `uv` runs `uv run --project <live> --no-sync -- <tool>` (no `--project` or no `--no-sync` would create or sync an environment) and only after `<workspace root>/.venv` (or `UV_PROJECT_ENVIRONMENT`) is seen to exist, because `uv run --no-sync` creates an empty `.venv` when there is none. Poetry cannot be used through `poetry run` because `-C` also changes the working directory of the tool, so its environment path is asked once (`poetry -C <live> env info --path`) and used like a virtualenv. A virtualenv launcher resolves a tool in its `bin` and otherwise leaves it to the `PATH` (`bin` first).
- **Snapshot sources.** `PYTHONPATH` starts with the snapshot's import roots (a source root without `__init__.py` imports from itself, a package from its parent), then the inherited value; the tools run with the snapshot as working directory. This is the only thing that makes base tests import base code when the environment has an editable install of head; it is tested for real in the e2e test.
- **Version and cache key.** `resolveVersion` runs `--version` of ruff, black (when it is the formatter) and coverage plus the pytest and mutmut import probes (`importlib.metadata` for mutmut, because `mutmut --version` fails where mutmut cannot guess its source directory) in the live environment, and throws only when the environment itself is unusable (the scheduler reports that as a tool error of each analyzer on each snapshot, with no rule, and does not run it); a missing tool reads `tool@missing` and fails in the runner. Each probe is remembered per memo (`context.probes`, created on first use), keyed by the launched command, its arguments, the working directory and the context environment. `createPythonAnalyzers` hands one memo to its `python` and `mutation` analyzers, so base and head resolve once and a type checker choice is not probed twice (`createPythonAnalyzer` and `createMutationAnalyzer` alone each keep their own); every snapshot context of a runner has its own memo. A tool that appears in the environment changes the launched command and is probed again, but a package installed behind an unchanged command (`pytest-django` in the same virtualenv) is not seen until a new process, and `process.env` is not part of the key. `python` has the versions of ruff, black, coverage and the test runner, `mutation` those of mutmut, pytest and pytest-django (`pytest-django@installed|missing`, since `-o django_find_project=false` depends on it). The configuration hash covers the analyzer name, the `python` settings, every non-test, non-fixture file under `languages/python/`, the transitive imports of `python-runner.mjs` (followed from the source, so a file the runner starts to import cannot be forgotten) and, through `styleFiles`, the project config files that can now apply: `pythonConfigFiles` (`pyrightconfig.json`, `pyproject.toml`, `mypy.ini`, `setup.cfg`, `.mypy.ini`, `tox.ini` and the `extends` chain) for `python`, and `mutationConfigFiles` (`pyproject.toml`, `setup.cfg`) for `mutation`, read from `policyRoot ?? projectRoot`.
- **Tool errors.** Each step (`ruff`, format, tests plus `coverage json`) fails independently and all failures are reported, one finding each, rule `<step>-failed` (`tests-failed` is the TypeScript rule), identity the rule, path `.`. When any step failed no other finding of that analyzer is returned. An error without a `rule` property is `python-failed` (`mutation-failed` in the `mutation` part, whose only step is mutmut), with the analyzer as tool.
- **Format output.** `ruff format --check --diff` is parsed by its `--- path` / `+++ path` header pairs, because ruff's summary format differs between versions; black's by its `would reformat` stderr lines. Exit 1 without a parsed path is an error. Black exits 123 and ruff 2 when a file cannot be parsed; that is tolerated only when every `error:` line is a parse error (black words it `cannot format <path>: Cannot parse` or `cannot parse for target version`), because ruff check already reports the file. `exclude` globs go to ruff as `--extend-exclude` and to black as one `--extend-exclude` regex (`^/<glob regex>(/.*)?/?$`, black matches `/<relative path>`, with a trailing `/` for directories).
- **Test runner.** Decided from the project (`python-test-runner.mjs`), never from importability: a silent fall back to `unittest` runs none of a pytest project's tests and exits 5 or 0. `pytest` with a failing import probe is `environment-failed`. One probe prints the pytest version and whether `pytest_cov`, `xdist`, `pytest_rerunfailures` and `pytest_django` are importable; `--no-cov` and `-n0` are added only for installed plugins, since an unknown option is a usage error (exit 4). `-o cache_dir=<report dir>` replaces `-p no:cacheprovider`, which broke `--lf` and `--sw` in `addopts`. `unittest discover -s tests` needs `-t .` when `tests/` is a package, or relative imports in it fail. Detection (`python-test-runner.mjs`, with the `manage.py` lookup in `python-django.mjs`: the project root, then its direct subdirectories, and the tests run from that directory; mutation is skipped (`django-subdirectory`) for a subdirectory, because mutmut's module names, which it derives from the path below the root, would not match the ones the tests import) checks an explicit pytest configuration or dependency first, then Django (`manage.py`), then nose2, then pytest-style test files, so a nose2 or Django project with `def test_` functions is not run by pytest. Django runs `manage.py test --noinput`, which sets the project's own `DJANGO_SETTINGS_MODULE`; `unittest discover` would import the tests without settings and fail them all. For mutation, mutmut's pytest gets `-o python_files=test*.py` when the runner is not pytest, and `-o django_find_project=false` whenever pytest-django is installed: otherwise pytest-django finds the real `manage.py` above `mutants/` and puts the unmutated project first on `sys.path`, so every mutant is reported as `NoCoverage`. The project's coverage `[run]` `concurrency`, `patch`, `plugins` and `omit` and its `[report]` `omit` are carried into the generated rcfile (`python-coverage-config.mjs`, read with `parseIni` of `mypy-config.mjs`, which like configparser keeps a continuation across blank and comment lines), with relative `omit` patterns and `source` made absolute; per-process data files are combined before `coverage json`. `manifest.json` `testsRan` is false on exit 5 or `Ran 0 tests`; the reader turns it into the enforceable `python/no-tests-ran` finding, which a comparison reports only when head lost its tests (a per-snapshot analyzer cannot see the other side, so it is a finding and not a tool error).
- **Slow tests.** `languages/python/adapters/test-runs/`. The test command writes the JUnit report (`pytest_timings.py` or `unittest_timings.py`, see `python-test-runner.mjs`). `slowCandidates` in `slow-tests.mjs` reads it (passed cases only), classifies and change-checks each test over the smaller budget (a file or test that cannot be read becomes a descriptive `slow-test-not-timed` notice, not a thrown error), and is shared by two callers. The `retimeSlowTests` step (`slow-retime.mjs`, after `test` in `runPythonTools`; `testSeconds` is on the tool context) runs the candidates once more through `execute` with `python <test command>` (no `coverage run`), the JUnit path swapped for `rerun-junit.xml` and a node id (pytest) or `-k <dotted id>` (unittest) per test. `readSlowTestFindings` (called from `python-reports.mjs` with `testsRan` from the manifest) reads the same candidates, replaces a time with the one in `rerun-junit.xml` when that run passed it, and builds the findings with `slowTestFindings` of `shared/rules/slow-tests/`, so the message, budgets and exception hint are those of Java and TypeScript. A missing JUnit report after a run that ran tests is a notice. The findings carry `tool: 'test-runtime'`, which `python-analyzer.mjs` lists in `reportedTools`.
- **Ruff target version.** `--target-version` is the lowest of `requires-python`, poetry's `python` or `python_requires` (minimum 3.8, also the default); `--config` makes ruff ignore the project's own `requires-python`, so without it version-gated rules such as `B905` flag code that cannot use the fix. Not passed to `ruff format`, which reads the project's config.
- **Coverage.** Run through a nitpicker-owned `coveragerc` (branch on, parallel off, `source` the source roots) with `COVERAGE_FILE` in the report directory; `coverage json --fail-under=0 --ignore-errors`. Ingestion (`coverage-json.mjs`): `line-coverage` from `summary.covered_lines / num_statements` per file, `uncovered-function` for a function (not the module-level `""` entry) with statements and no covered line, identified by its qualified name. A file with no statements has no metric.
- **Structure and CRAP.** Details in `docs/python-preset.md`. The structure step lives in `python-structure.mjs`; it reuses the shared reader (`readStructureFindings` in `shared/ingest/structure-report.mjs`) and passes a Python function-text hash (common indentation removed, not every line trimmed, because indentation is syntax). `python-crap.mjs` reads the same `structure.json` and gives its functions to `ingestPythonCrap` (`ingestCrapRows` in `shared/ingest/lizard-crap.mjs` underneath). There is no external complexity tool: `structure_metrics.py` computes the cyclomatic complexity from the `ast` module. Definition (McCabe, the decision points of the other presets; a lambda is an entry of its own like a TypeScript arrow function, and the `for` and `if` clauses of a comprehension count): 1 plus one per decision point in the function's own body, where decision points are `if` and `elif`, a conditional expression, `for` and `async for`, `while`, each `except` handler, each `case` of a `match` but a guard-less `case _` (the `default` of a `switch`, which ESLint's `complexity` rule and the Java and Kotlin metrics do not count either), each extra operand of `and` and `or`, and each `for` and `if` clause of a comprehension. `else`, `finally`, loop and `try` `else`, `with` and `assert` add nothing; comprehensions belong to the enclosing function; lambdas (named after the scope and the name they are assigned to, else `<lambda>`, with `lambda: true` and `statementLine`), nested functions and the methods of nested classes are entries of their own and add nothing to it. A lambda has no coverage.py entry or line of its own, so its coverage is that of the statement that creates it (100 when the statement ran, 0 when it did not). Control nesting treats an `elif` as the same level as its `if`, like `else if` in the TypeScript and Java analyzers; an `else:` block holding an `if` is one level deeper. The entries also carry `definition` (the `def` line) and `bodyStart` (first body line); a function whose body starts on its `def` line is left out of CRAP, because its statements share the line that runs at import. Coverage entries are joined to functions by qualified name (the names coverage.py reports) and line range, not `start_line`, which older coverage.py versions do not report. coverage.py keeps one entry per qualified name, so a function no entry covers (property setter pair, `singledispatch` `_`, conditional definitions) is scored from the file's per-line and per-branch data over its own range, minus nested functions.
- **Changed-branch coverage.** `coverage-branches.mjs` reads the same `coverage.json` (`executed_branches` / `missing_branches` as `[from, to]` arcs, a negative `to` leaving the scope), groups the arcs by `from` line and hands one entry per line to `branchCoverageFindings` (`shared/rules/branch-coverage.mjs`, minimum 95). Its tool name is `coverage-py`, not `coverage` (the TypeScript analyzer's), and `TOUCHED_CODE_RULES` in `shared/policy.mjs` lists `changed-branch-coverage` for `coverage-py`, so an uncovered branch on a changed or added line is new even when the base had it. Identity is `branch-source:<hash of the enclosing def/class chain and the whitespace-normalized line>`, with `#n` counted per path and hash among failing lines; the chain is derived from the indentation of earlier `def` / `class` lines, because the coverage JSON has no scope for a branch. The `coveragerc` also sets `omit` (test files), a fixed `exclude_lines` (`if TYPE_CHECKING:`, the `__main__` guard, `@overload`, `raise NotImplementedError`) and an empty `partial_branches`, so no pragma and nothing in the project's own coverage config applies. coverage.py gives no arcs for `try` / `except` / `finally`, so those are not gated. Java's `jacoco-branches.mjs` numbers identical lines per file, without a scope.
- **Mutation.** `python-mutation.mjs` (the `mutation` part) checks that mutmut is installed and 3.x from the same `importlib.metadata` probe, runs `mutmut run` with `PYTEST_ADDOPTS` extended by `-n0` when the pytest probe saw xdist (mutmut runs pytest itself, and the `-n` of the project's `addopts` makes it fail to collect stats and report every mutant as uncovered), and removes head's `mutants/` afterwards. On Windows it returns a descriptive `mutation-skipped` finding instead of running. pytest exit 5 under mutmut ("failed to collect stats. runner returned 5") yields no mutation findings, since `python/no-tests-ran` covers it; any other "failed to collect stats" adds the `also_copy` line. `python-mutation-data.mjs` reads `mutants/**/*.meta` (`exit_code_by_key`) with the generated and the original source; `languages/python/ingest/mutmut.mjs` splits the generated file into function blocks by indentation (a closing bracket at the `def` indent continues a wrapped signature), diffs `x_f__mutmut_orig` against `x_f__mutmut_N` on tokens, and hands `Survived` and `NoCoverage` (exit 0; 5 and 33) to the shared `mutantFindings`, plus a `mutation-summary` metric per status over all parsed keys. Keys exist but none matches `x…__mutmut_N` is a thrown error naming the supported range (`SUPPORTED_MUTMUT`, the one place the range is written in code). Identity `symbol|original→mutated#n`, `n` counted per status and file among equal keys in mutant order (a same-named function in another module has its own count); the line comes from locating the original block in the real file. Exit 1 with "could not find any test case for any mutant" is accepted and turns the unchecked (`null`) results into 33. `writeMutmutConfig` (`project-tools/mutmut/mutmut-config.mjs`) always writes nitpicker's `[tool.mutmut]` into the snapshot (mutmut reads the pyproject first, so a `setup.cfg` section stops applying), keeping from the project's table only `also_copy`, the process-isolation keys and, for source roots of `.`, `source_paths`; `mutmutSettings` applies the project's whole table over nitpicker's only under `tools.mutmut.precedence` with `project` first. The `do_not_mutate` of a generated `[tool.mutmut]` is the test patterns plus each `exclude` glob and `<glob>/*` (mutmut matches with `fnmatch` against the project-relative path, where `*` also crosses `/`). Head's `mutants/` is removed after reading; base's stays so `python-mutation-reuse.mjs` can copy its `.meta` files (only those) into head when the name-status diff from the base commit to head lists nothing but added or modified non-test `.py` files under a source root, and only those of modules outside the changed files' reverse import closure (`import-scan.py`: a Python `ast` script run in the project's environment over head's source roots, edges to every module an `import`, `from … import` or relative import can name, files that do not parse have none; a failed scan reuses nothing).
- **Ruff selection.** `nitpicker-ruff.toml` lists the stable codes of the `RUF`, `G`, `N`, `PT`, `S` and `TRY` groups one by one. `ruffConfigFor` (`python-ruff-config.mjs`) runs `ruff rule --all --output-format json` in the environment, keeps the stable rules (`isStableRule`: not preview, not removed), and writes the toml without the selected codes the installed ruff does not know (a prefix like `E4` is kept when a known rule starts with it), so ruff 0.9 to 0.16 run one file; when the listing fails it uses the toml as it is. The lint step adds `--config 'lint.flake8-pytest-style.<option> = <value>'` flags from `pytestStyleFlags`, and the rules step calls `ruffConfigFor` too, so `--show-files` and the lint agree.
- **Ruff identity.** The SARIF goes through `prepareSarif` (`shared/ingest/sarif.mjs`) with the message text as the subject, so identity is `fp:nitpicker/subject=<message>`; ruff messages name the symbol, and repeats in one file get `#n`.
- **Type checker choice.** `detectTypeCheckers` scores each checker from the live checkout's hint files: a config (`[tool.mypy]`, `mypy.ini`, a `[mypy]` or `[mypy-...]` section, `[tool.pyright]` or `[ tool.pyright ]`, `pyrightconfig.json`) counts 2 and a declared dependency (a name anywhere on a line, so inline arrays count) 1; the higher score wins, and a tie or no hint at all probes `mypy --version` then `pyright --version` then `basedpyright --version` in the environment (`resolveTypeChecker`). basedpyright is a third entry: its config is `[tool.basedpyright]` (or `[ tool.basedpyright ]`), its dependency is the name `basedpyright` or the `basedpyright-pre-commit` hook. basedpyright also reads `[tool.pyright]` and `pyrightconfig.json`, so once it scores above 0 those no longer count for pyright and only a declared `pyright` dependency can still pick pyright. The probes run `mypy`, `pyright`, `basedpyright` in that order. The choice is read from the live root so both snapshots run the same checker, and it is part of the tool versions in the cache key.
- **mypy run.** `mypy --strict [--enable-error-code deprecated] --explicit-package-bases --show-error-codes --no-error-summary --no-pretty --hide-error-context --no-color-output --cache-dir <report dir>/mypy-cache <source roots>` with `MYPYPATH` set to the snapshot's import roots (mypy does not read `PYTHONPATH`); `--enable-error-code deprecated` is added when `mypy --version` reports 1.14 or later (an older mypy rejects the unknown code); the pyright config sets `reportDeprecated: error`. Exit 0 or 1 is a result, anything else `types-failed`. `--config-file` is a file generated in the report directory (`mypy-config.mjs`): the project's `[mypy]`, `[tool.mypy]` (pyproject) or `mypy.ini` section reduced to `plugins` (file plugins made absolute), `mypy_path`, `python_version`, `namespace_packages`, `custom_typeshed_dir` and per-module `ignore_missing_imports` and `follow_imports`, plus nitpicker's `exclude` as one regular expression; everything that skips or weakens checking is dropped, so no project setting can turn the gate off. `--python-executable` is the environment's `sys.executable`, because mypy otherwise introspects its own interpreter and misses the project's packages. Lines are matched as `path:line[:col]: error|warning: message  [code]`; notes and the summary are ignored. Identity is the message, `#n` per (file, rule).
- **pyright and basedpyright run.** basedpyright has pyright's CLI and `--outputjson` shape (`ingestPyright` with tool `basedpyright`) and is run the same way: `basedpyright --outputjson --project <report dir>/pyrightconfig.json`. Its modes are `off`, `basic`, `standard`, `strict`, `recommended` (its default) and `all`; the config forces `strict`, which has pyright's meaning, because `all` adds opinionated rules such as `reportAny`, `reportUnusedCallResult` and `reportImplicitOverride`. It reads `pyrightconfig.json`, `[tool.basedpyright]` and `[tool.pyright]`; it does not read a `basedpyrightconfig.json` (1.40), so nitpicker does not detect or extend that name either. A baseline (`.basedpyright/baseline.json`) is looked up next to the config and does not apply to files outside that directory, so none applies from the report directory. basedpyright 1.40 honors `# pyright: ignore` only (not `# basedpyright: ignore`), which `no-inline-suppression` already bans. A generated `pyrightconfig.json` in the report directory (`extends` the project's `pyrightconfig.json` or a `pyproject.toml` with `[tool.pyright]` (`[tool.basedpyright]` too for basedpyright), `typeCheckingMode: strict`, `enableTypeIgnoreComments: false`, `ignore: []`, `executionEnvironments: []` (a project's per-directory environments can switch rules off), `exclude` nitpicker's globs relative to the config (plus pyright's defaults) in place of the project's, `include` the source roots, `extraPaths` the import roots). `include` has to be relative to the config file (pyright ignores absolute entries with a warning); `extends` and `extraPaths` may be absolute. The JSON is read from the first `{` because the pip wrapper can print a notice first; only the first line of a message is the identity.
- **Project tool layers.** `languages/python/adapters/project-tools/` (`project-tool-layers.mjs`: `toolLayers(context, tool)` returns `{ optedIn, appliesProject, nitpickerFirst, configRoot }` from the shared `precedenceLayers` for `tools.pyright` (also basedpyright), `tools.mypy` and `tools.mutmut`; `ignored-notices.mjs` prints the one `Ignoring ...; opt in with ...` line per tool through `pythonStyle().summary`; `requireProjectConfig` throws the shared missing-config error). Without the opt-in only environment keys are read: `pyright/pyright-project-config.mjs` copies `venv`, `venvPath`, `pythonVersion`, `pythonPlatform`, `stubPath`, `typeshedPath`, `extraPaths` and the root, `extraPaths`, version and platform of each execution environment (following `extends`, JSONC parsed by `shared/jsonc/jsonc.mjs`, `[tool.pyright]` or `[tool.basedpyright]` TOML), and `mypy-layers.mjs` keeps per-module sections only for modules the project does not own (the entries of the import roots and of the `mypy_path` directories: directories, `.py` and `.pyi` files, `-stubs` packages). Under the opt-in with `project` first the project's keys overlay nitpicker's strict config; the project's `include`, `exclude` and `extraPaths` are merged with nitpicker's and its other keys replace them. The config is read from `policyRoot`, but `pyright-project-config.mjs` re-roots the source paths (`include`, `exclude`, `extraPaths`, `stubPath`, an environment's `root`) onto the snapshot's own `projectRoot` and leaves `venvPath` and `typeshedPath` in the head checkout; under the opt-in it searches the parent directories up to the first `.git`. A config that fails to parse comes back as `{ file, files, unreadable }` and `requireProjectConfig` reports it as unparsable; `files` (also the `extends` chain) feeds `pythonConfigFiles`. The mypy project `exclude` is left as written and nitpicker's globs become `--exclude` arguments. mypy then gets `strict = true` in the file and no `--strict` flag, because a flag overrides global keys but not per-module sections, and the file value lets project keys override it.
- **Python libraries.** `languages/python/rules/libraries/`: `project-libraries.mjs` `detectLibraries(projectRoot)` returns `{ database, logging, validator, validators }` from the declared dependencies (runtime before development; `DEFAULT_LIBRARIES` when the project shows none), using `library-tables.mjs` (`VALIDATORS` with the package names, the import roots the boundary guards and the call that parses, `LOGGERS`, `DATABASES` with the placeholder style of the SQL hint). `dependencyNames` and the detection read through `languages/python/libraries/python-dependencies.mjs`, the one declared-dependency reader (the dependency findings, the framework allowances and the pytest collection options use it too), with its parts in `dependencies/` (`requirement-names.mjs`, `requirement-files.mjs`, `setup-py.mjs`): `readPythonDependencies(projectRoot)` returns `{ runtime, development, dependencies, complete, declaresDev, manifest }`, where `runtime` and `development` are sorted normalized names (a package in both counts as runtime) and `dependencies` lists each declaration with its group and file, read from `pyproject.toml` PEP 621, optional dependencies, dependency groups, Poetry (its `main` group is runtime), uv, pdm and hatch, a `Pipfile`, `requirements*.txt` (without constraints files, following `-r` includes inside the project, reading the `.in` beside a compiled file or only its direct entries), `setup.cfg` and the literal lists of `setup.py`, decoding a BOM or UTF-16 (`readProjectText`); `requirementName`, `normalizeRequirementName` and `isDevelopmentGroup` are exported with it. The detection runs when the report is read (`readPythonFindings`) and when the rules step writes its options, where `boundaryRoots` (the import roots of every declared validation library) is how `pydantic-boundary` knows what to guard.
- **Rules script.** `nitpicker_rules.py` is stdlib-only and needs Python 3.10 or later (every Python still supported upstream; the file itself parses on older ones, so below 3.10 `main` writes one `rules-skipped` entry with the interpreter version, which `ingest/rules-report.mjs` turns into a `python-rules/rules-skipped` tool error, instead of a traceback); it takes a file list, a report path and an options file (`rule-options.json`), parses each file once with `ast`, finds comments with `tokenize`, and works in two phases. `index/project.py` first builds a `Project` over all the files (the names each defines, suffixes, module names and relative imports, one context per file, the test files, a memo, and `locate` for the definition a call refers to), so a rule can follow a call into another file; then every module of `checks/` (comments, declarations, shell, state), `security/` (`sql/`, tls, hashes, timeouts, loading), `discovery/` (test collection, helpers), `environment/`, `errors/` (`errors.py` and `handling.py` for `swallowed-exception` and `blind-suppress`;
